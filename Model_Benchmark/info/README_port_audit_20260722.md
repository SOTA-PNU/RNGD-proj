# 열린 포트 점검과 정리 (2026-07-22)

이 문서는 서버에 열려 있던 TCP/UDP 포트를 전부 조사해서 쓸모없는 것을 정리한 작업의 기록입니다. 무엇을 지웠고 무엇을 왜 남겼는지, 그리고 점검 중에 드러난 라우터 인증 문제를 담았습니다.

## 1. 한 줄 요약

7월 21일 백그라운드 작업이 남기고 간 **목(mock) 서버 7개와 유령 VS Code 프로세스 1개**를 정리해서 TCP 리스닝이 21개에서 13개로 줄었습니다. NPU 서빙과 편집기 세션은 전부 무사합니다. 대신 **라우터(:8400)가 인증 없이 외부에 열려 있는 상태**를 확인했는데, 이건 재시작이 필요해서 손대지 않고 남겨 뒀습니다.

## 2. 정리한 것

## 4. 라우터 인증이 꺼져 있습니다

점검 중 확인한 내용이라 함께 적어 둡니다. 실행 중인 라우터에 인증 키가 설정돼 있지 않아, **네트워크에서 키 없이 그대로 접근됩니다**.

확인한 사실입니다.

- 실행 중인 프로세스 환경에 `SDI_API_KEY`도 `FURIOSA_API_KEY`도 없습니다 (`/proc/2099006/environ` 검색 결과 0건).
- 인증 미들웨어는 키가 있을 때만 동작합니다 — `furiosa_router.py:515`가 `if API_KEY and ...` 조건입니다. 키가 없으면 검사 자체를 건너뜁니다.
- 바인딩 기본값이 `0.0.0.0`입니다 (`furiosa_router.py:739`).
- 방화벽이 없습니다. `ufw`는 inactive, iptables 정책은 전부 ACCEPT입니다.
- 루프백이 아닌 LAN 주소로 실제 확인했습니다. `curl http://10.125.19.138:8400/v1/models`가 인증 헤더 없이 HTTP 200과 모델 31개를 반환합니다.

이 서버가 사내망 안에만 있는 게 아니라는 점이 걸립니다. 점검 시점에 공인 IP `129.254.74.11`에서 들어온 SSH 세션이 붙어 있었습니다. 경계 장비가 8400도 넘겨주는지는 서버 안에서는 알 수 없습니다.

다만 이건 코드 결함이 아니라 **의도된 모드**입니다. `serve-router.sh:47`이 인증 OFF를 "승인된 사내망 전용"이라고 명시하고, `README.md:128`도 "이미 `0.0.0.0` 바인딩이라 Bearer 인증을 켜고 네트워크로 열면 됩니다"라고 안내합니다. 즉 설계는 "인증 켜고 개방"인데 지금은 개방만 되어 있습니다. 쟁점은 "사내망 전용"이라는 전제가 지금도 맞는지입니다.

무엇이 열려 있냐면, 조회 경로(`/v1/models`, `/router/status` 등) 말고 `POST /v1/chat/completions` 계열이 문제입니다. 이 경로가 `ROUTER.ensure(model)`을 호출하는데, 여기서 백엔드를 새로 띄우고 카드가 모자라면 `_evict_until()`로 **돌아가던 백엔드를 LRU로 쫓아냅니다**. 인증 없는 호출자가 추론을 공짜로 쓰는 데 그치지 않고 RNGD 4장에 원하는 모델을 올리거나 실행 중인 작업을 내릴 수 있다는 뜻입니다.

고치는 방법은 `README.md:132`에 있는 대로입니다.

```bash
SDI_API_KEY="<비밀키>" bash serve-router.sh start   # 인증 켜서 재시작
SDI_BIND=127.0.0.1 bash serve-router.sh start      # 또는 로컬 전용으로 닫기
```

이번 점검에서는 실행하지 않았습니다. 어느 쪽이든 재시작이 필요하고, 그러면 워밍업된 8410 백엔드가 내려가 콜드스타트를 물게 됩니다. 그 비용은 `furiosa_router.py:530` 주석에 "콜드스타트 900s ... 실측"으로 적혀 있습니다. 점검 시점에 같은 워크트리에서 다른 세션이 작업 중이기도 했습니다. 방화벽으로 막는 방법도 있지만 그건 README가 상정한 원격 클라이언트 접속을 끊습니다. 조용한 시간에 키를 정해서 재시작하는 게 맞습니다.

## 5. 손대지 않은 선택 항목

둘 다 우분투 기본 서비스이고 잔해가 아니라서, 끌지 말지는 판단이 필요합니다.

- **cupsd (631)** — 인쇄 데몬. `127.0.0.1`과 `[::1]`만 열려 있어 네트워크에서는 안 보입니다. 끄면 `sudo systemctl disable --now cups cups-browsed cups.socket cups.path`. 이 서버 작업에는 영향이 없지만 루프백 전용이라 얻는 것도 적습니다.
- **avahi-daemon (UDP 5353 등)** — mDNS 응답기. 정리 후 남은 것 중 **유일하게 모든 인터페이스에 열린 서비스**라 같은 대역에 호스트 이름을 계속 알립니다. 끄면 `sudo systemctl disable --now avahi-daemon avahi-daemon.socket`. GNOME 데스크톱의 네트워크 검색에 쓰이므로 `.local` 이름으로 이 서버를 찾는 게 없는지만 확인하면 됩니다. 참고로 5353 외의 포트 번호는 데몬이 시작할 때 임의로 정하므로 어딘가에 고정해 적어 두면 안 됩니다.

`/tmp`에 남은 스크래치 디렉터리(`vrf`, `srtest`, `vfy_timeout`, `ocaudit`, `av`)도 그대로 뒀습니다. 합쳐서 1.5MB고 검증 로그가 들어 있어 재부팅 때 알아서 사라집니다.

## 6. 다시 확인하는 방법

```bash
sudo ss -tlnp                      # TCP 리스닝과 소유 프로세스
sudo ss -ulnp                      # UDP
sudo readlink /proc/<pid>/cwd      # 작업 디렉터리 ((deleted)면 유령)
sudo tr '\0' ' ' < /proc/<pid>/cmdline
sudo ss -tnp state established '( sport = :<port> )'   # 실제로 쓰는 데가 있는지
```

프로세스 생존 확인에 `kill -0`을 쓸 때는 주의가 필요합니다. root 소유 프로세스에 일반 사용자로 보내면 EPERM이 나서 살아 있는데도 죽은 것처럼 보입니다. 이번에 sshd가 죽은 줄 알고 놀랐던 원인입니다. `ps -p <pid>`나 `systemctl is-active`로 확인하는 게 맞습니다.
