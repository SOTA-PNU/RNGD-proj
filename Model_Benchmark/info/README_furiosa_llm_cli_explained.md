# furiosa-llm CLI가 하는 일: build와 serve를 예시 모델로 쉽게 (개념편)

작성일 2026-06-15.

이 문서는 FuriosaAI의 NPU(인공지능 전용 칩)에서 언어 모델을 돌릴 때 쓰는 명령 도구인
**furiosa-llm**의 두 핵심 명령 `build`와 `serve`가 각각 무슨 일을 하는지를, 실제 모델 하나를
예로 들어 차근차근 설명합니다. 어려운 내부 구조까지 들어가되, 중학생도 흐름을 따라올 수
있도록 비유를 많이 썼습니다.

이 문서는 "표준 모델이 잘 되는 경우"를 다룹니다. Qwen3-Coder-Next처럼 표준 방식이 막히는
특별한 모델 이야기는 [README_qwen3_coder_next.md](README_qwen3_coder_next.md)에서 이어집니다.
모델 구조(어텐션·DeltaNet) 개념은 [README_attention_and_gated_deltanet.md](README_attention_and_gated_deltanet.md)를
먼저 읽으면 더 잘 이해됩니다.

---

## 1. NPU가 뭐고, 왜 "굽기(build)"가 필요한가

NPU는 인공지능 계산만 아주 빠르게 하도록 만든 전용 칩입니다. 우리가 쓰는 RNGD라는 NPU가
그런 칩입니다. 그런데 NPU는 똑똑한 만능 컴퓨터가 아니라, **미리 정해진 모양의 계산을 아주
빠르게 반복하는 기계**에 가깝습니다. 특히 행렬 곱셈(숫자 표끼리 곱하는 계산) 같은 걸 잘합니다.

언어 모델은 보통 파이썬과 PyTorch로 쓰여 있습니다. 이건 NPU가 바로 못 알아듣습니다. 그래서
모델을 NPU가 이해하고 빠르게 돌릴 수 있는 형태로 **번역하고 미리 짜 맞추는 과정**이 필요합니다.
이 과정이 바로 `furiosa-llm build`입니다. 요리에 비유하면, 생재료(파이썬 모델)를 NPU가 바로
데워 먹을 수 있게 미리 조리해서 도시락(아티팩트)으로 만들어 두는 일입니다.

그렇게 만든 도시락을 받아서, 실제로 사용자 질문에 답을 만들어 주는 서버로 띄우는 명령이
`furiosa-llm serve`입니다. 즉 **build는 미리 굽는 일, serve는 구운 걸 데워서 손님에게 내는
일**입니다.

## 2. 예시 모델: Qwen2.5-Coder-7B-Instruct

설명을 구체적으로 하려고, 이 프로젝트에서 실제로 빌드해 둔 모델 하나를 예로 듭니다.
**Qwen2.5-Coder-7B-Instruct**입니다. 코딩을 잘하도록 학습된 모델이고, 구조가 깔끔한
표준 트랜스포머라서 예시로 딱 좋습니다.

이 모델의 특징(설정값 그대로):
- 종류: `qwen2` (표준 트랜스포머, 특이한 선형 어텐션이나 MoE 없음)
- 크기: 약 7B(70억) 파라미터
- 층 수: 28개
- 어텐션: 쿼리 머리 28개, 키·밸류 머리 4개(GQA), 머리 하나의 크기 128
- MLP: SwiGLU, 중간 차원 18944(빽빽한 dense MLP, 전문가 섞기 없음)
- 단어 사전 크기(vocab): 152064
- 다룰 수 있는 길이(컨텍스트): 최대 32768 토큰

여기서 핵심은 **이 모델의 모든 층이 7절에서 말한 "뒤에 덧붙이기만 하는 KV 캐시"를 쓰는
보통의 softmax 어텐션**이라는 점입니다. 그래서 furiosa-llm의 표준 build/serve가 그대로 잘
동작합니다. (개념 문서의 7절 참고.)

## 3. build가 하는 일 (단계별로 쉽게)

`furiosa-llm build`는 대략 이런 순서로 모델을 NPU용 도시락(아티팩트)으로 바꿉니다. 명령 한
줄을 치면 안에서 이 단계들이 차례로 일어납니다.

명령 모양(개념):
```bash
furiosa-llm build <모델이름/경로> <결과 폴더> -tp 8
```
`-tp 8`은 "이 모델을 NPU 8조각(PE 8개)에 나눠서 돌리겠다"는 뜻입니다(아래 4단계에서 설명).

### 1) 모델과 설정 받기, 그리고 양자화

먼저 모델의 가중치(학습된 숫자들)와 설정 파일을 읽습니다. 그다음 보통 **양자화**를 합니다.
양자화는 숫자를 더 작은 자리수로 줄여서(예: 16비트를 8비트로) 용량과 계산을 가볍게 만드는
기술입니다. 사진을 약간 압축해도 거의 똑같아 보이는 것과 비슷합니다. Qwen2.5-Coder-7B 예시
아티팩트는 16비트로 두었지만, 더 큰 모델은 FP8(8비트)로 줄이기도 합니다.

### 2) trace: 모델을 "계산 순서도"로 펼치기

파이썬 모델 코드는 if문이나 반복문이 섞여 있어서 NPU가 통째로 못 받습니다. 그래서 모델을
한 번 가짜 입력으로 돌려 보면서, 실제로 일어나는 계산들을 **순서도(그래프)**로 쭉 펼쳐
기록합니다. 이걸 trace(추적)라고 합니다. 결과는 "이 숫자에 저 행렬을 곱하고, 그 결과에
softmax를 하고…" 같은 계산 블록들의 연결 그림입니다.

### 3) color와 partition: NPU 여러 조각에 나눠 칠하기

큰 모델은 NPU 한 조각에 다 안 들어갑니다. 그래서 계산 순서도를 여러 덩어리로 나눠서 NPU
여러 조각(PE)에 분배합니다. 이때 각 계산 블록에 "너는 몇 번 조각 담당"이라고 색을 칠하듯
표시하고(coloring), 같은 색끼리 묶어 조각을 만듭니다(partition). `-tp 8`이면 8조각으로
나눕니다. 이렇게 한 모델을 여러 조각이 나눠서 동시에 계산하는 것을 **텐서 병렬(tensor
parallel, tp)**이라고 합니다. 여러 사람이 큰 표를 세로로 나눠 동시에 계산하는 것과 같습니다.

### 4) compile: 각 조각을 NPU 바이너리로 번역

이제 각 조각의 계산 순서도를 NPU 컴파일러에게 넘겨, NPU가 바로 실행할 수 있는 기계어 묶음으로
번역합니다. 이 번역된 결과물 하나하나를 **EDF**라고 부릅니다(NPU가 실행하는 진짜 바이너리).
조각이 많으면 EDF도 여러 개 나옵니다.

### 5) save: 도시락으로 묶기 (아티팩트)

마지막으로, 위에서 만든 EDF들과 모델 설정, 토크나이저(글자를 토큰 번호로 바꾸는 도구),
양자화된 가중치를 한 폴더에 모아 **아티팩트(artifact)**로 저장합니다. 이게 완성된 도시락입니다.

실제로 Qwen2.5-Coder-7B를 빌드한 아티팩트 폴더 안에는 이런 파일들이 들어 있습니다:
```
artifact.json            (이 도시락의 목차·설명서: 모델 종류, 조각 수 등)
binary_bundle.zip        (NPU가 실행하는 EDF 바이너리들의 묶음. 이게 핵심)
config.json              (모델 설정)
tokenizer.json 등        (글자 <-> 토큰 변환기)
generation_config.json   (생성 기본값)
chat_template.jinja      (대화 형식 틀)
params-....safetensors/  (가중치 폴더. 이름이 .safetensors로 끝나도 디렉터리이고,
                          안에 model-0000N-of-0000M.safetensors 샤드 여러 개 + index가 들어 있음)
```
여기서 `binary_bundle.zip`이 가장 중요합니다. 이 안에 NPU에서 실제로 돌아가는 컴파일된
계산(EDF)이 들어 있어서, 이게 있어야 serve가 NPU로 빠르게 답을 만들 수 있습니다.

## 4. serve가 하는 일 (단계별로 쉽게)

`furiosa-llm serve`는 build가 만든 도시락(아티팩트)을 받아서, 사용자 질문에 답하는 서버를
띄웁니다. ChatGPT API와 똑같은 모양(OpenAI 호환)으로 요청을 받습니다.

명령 모양(개념):
```bash
furiosa-llm serve <아티팩트 폴더>
```

안에서 일어나는 일:

### 1) 도시락 펼치고 NPU에 올리기

아티팩트의 설명서(artifact.json)를 읽고, EDF들을 NPU 조각들에 배치합니다. 모델이 어떤
종류인지, 몇 조각으로 나뉘었는지를 확인합니다.

### 2) KV 캐시 자리 만들기

생성 중에 과거 단어들의 키·밸류를 저장할 KV 캐시 공간을 NPU 메모리에 미리 잡아 둡니다.
이 KV 캐시는 개념 문서 7절에서 말한 것처럼 **뒤에 덧붙이기만 하는** 방식으로 동작합니다.
furiosa의 서빙 런타임은 이 KV 캐시를 작은 블록 단위로 효율적으로 관리합니다.

### 3) 똑똑한 스케줄러로 여러 손님 동시에 받기

서버에는 여러 사용자가 동시에 질문을 보낼 수 있습니다. furiosa 런타임 안의 스케줄러가 이
요청들을 모아서, NPU가 쉬지 않고 일하도록 효율적으로 끼워 넣습니다. 이렇게 여러 요청을 한
배치에 섞어 계속 돌리는 방식을 **연속 배칭(continuous batching)**이라고 합니다. 식당에서
한 테이블 음식이 끝날 때까지 기다리지 않고, 준비된 요리부터 계속 내보내는 것과 비슷합니다.

### 4) 토큰을 한 개씩 만들어 흘려 보내기

요청이 오면 모델이 다음 토큰을 하나 만들고, 그걸 화면에 흘려 보내고(스트리밍), 그 토큰을
포함해 다시 다음 토큰을 만들고, 이걸 문장이 끝날 때까지 반복합니다. 결과는 OpenAI API
형식(`/v1/chat/completions` 같은 주소)으로 돌아옵니다.

**중요한 점:** 이 모든 무거운 일(KV 캐시 관리, 스케줄러, 토큰 생성 루프)은 furiosa가 만든
**컴파일된 런타임(폐쇄형 바이너리)** 안에서 돌아갑니다. 우리가 파이썬으로 그 내부를 직접
고칠 수는 없습니다. 이 점이 다음 문서에서 Qwen3-Coder-Next를 다룰 때 중요해집니다.

## 5. build와 serve의 관계 한눈에

```
[ build (미리 굽기) ]
  파이썬 모델 + 가중치
    → (양자화) → trace(순서도로 펼치기) → color/partition(조각으로 나눠 칠하기)
    → compile(조각마다 NPU 바이너리 EDF로) → save(아티팩트 도시락으로 묶기)
  결과물: artifact.json + binary_bundle.zip(EDF들) + 가중치 + 토크나이저

                         │  (도시락을 넘김)
                         ▼

[ serve (데워서 내기) ]
  아티팩트 도시락
    → NPU에 EDF 올리기 → KV 캐시 자리 잡기 → 스케줄러로 여러 요청 받기
    → 토큰 하나씩 생성·스트리밍
  결과물: OpenAI 호환 API 서버 (질문하면 답을 만들어 줌)
```

핵심만 다시: **build는 모델을 NPU가 먹을 수 있는 형태로 한 번 굽는 일**이고, **serve는 그
구운 걸 받아 실제로 사람에게 답을 만들어 주는 일**입니다.

## 6. 꼭 알아 둘 용어 몇 개

- **아티팩트(artifact)**: build가 만든 결과 폴더(도시락). 설정·EDF·가중치·토크나이저가 다 들어 있음.
- **EDF / binary_bundle.zip**: NPU가 실제로 실행하는 컴파일된 바이너리(EDF)와 그 묶음 파일.
- **양자화(quantization)**: 숫자 자리수를 줄여(예: 16비트 → FP8 8비트) 용량·속도를 아끼는 기술.
- **tp / pp / dp**: 모델을 NPU 여러 조각에 나누는 방식.
  - tp(텐서 병렬): 한 계산을 여러 조각이 나눠서 동시에. 예시 모델은 tp8.
  - pp(파이프라인 병렬): 층을 조각별로 나눠 맡김(1층~10층은 조각A, 11~20층은 조각B 식).
  - dp(데이터 병렬): 같은 모델을 여러 벌 복제해 서로 다른 요청을 동시에 처리.
- **KV 캐시**: 생성 중 과거 단어들의 키·밸류를 저장해 재사용하는 공간. 뒤에 덧붙이기만 함.
- **preset / bucket**: 모델마다 자주 쓰는 입력 길이 묶음(버킷)을 미리 정해 둔 설정. 빌드 시
  어떤 길이들을 준비할지 정하는 데 쓰입니다.

(더 깊은 내부 동작과 SDK 파일 위치까지 보고 싶으면 같은 폴더의 `ALL_about_build_serve.md`,
`BUILD_COMPIL.md`를 참고하세요. 이 문서는 개념 중심으로만 설명했습니다.)

## 7. 그런데 왜 어떤 모델은 이 표준 길이 막힐까

Qwen2.5-Coder-7B처럼 보통의 어텐션만 쓰는 모델은 위 build/serve가 그대로 잘 됩니다. 모든
층이 "뒤에 덧붙이기만 하는 KV 캐시"를 쓰기 때문입니다.

그런데 개념 문서 11절에서 본 것처럼, Gated DeltaNet 층은 KV 캐시가 아니라 **상태 행렬을 읽고
고쳐 다시 쓰는** 메모리를 씁니다. furiosa의 표준 서빙 런타임은 "뒤에 덧붙이기만 하는 KV 캐시"만
다룰 줄 알아서, 이 "읽고 고쳐 쓰기" 메모리를 담을 자리가 없습니다. 그래서 Qwen3-Coder-Next
같은 모델은 표준 build/serve로는 그대로 돌릴 수 없습니다.

이 막힘을 우리가 어떻게 우회해서 Qwen3-Coder-Next를 실제로 NPU에서 돌렸는지가 다음
문서의 주제입니다.
- 다음 문서: [README_qwen3_coder_next.md](README_qwen3_coder_next.md)
