## 0. 한 줄 요약

furiosa-opt는 퓨리오사가 공개한 **TCP Virtual ISA(vISA)** 입니다. RNGD NPU의 연산 엔진·메모리·스케줄을 **Rust로 직접 손으로 짜는 저수준 커널 프로그래밍 도구**예요. 지금까지 우리가 싸워온 닫힌 `furiosa-llm`(모델 컴파일러)보다 **한 단계 아래 계층**으로 내려가서, op 지원 목록·model_type 게이트·serve 게이트를 **통째로 건너뛰고** NPU에 커널을 올릴 수 있는 길입니다.

다만 중요한 사실 세 가지를 먼저 못박습니다.

1. **컴파일러 자체는 공개 안 됐습니다.** 공개된 건 *언어·타입시스템·시뮬레이터·예제·하드웨어 매뉴얼*이고, 실제 EDF 코드젠(`npu_opt` 플러그인)은 미리 빌드된 닫힌 바이너리(`cargo-furiosa-opt`)로만 배포됩니다. 소스 빌드는 막혀 있어요(`disabled-strategies=["compile"]`).
2. **여기서 만든 커널은 furiosa-llm의 `.edf` 아티팩트에 끼워 넣을 수 없습니다.** 둘 다 "EDF"라고 부르지만 **바이트 포맷이 완전히 다릅니다**(아래 §7에서 직접 증명). 같은 칩에서 돌긴 하지만, 우리가 쓰던 masquerade / serve 파이프라인과는 **별도의 실행 경로**예요.
3. **알파(experimental) 단계**입니다. 예제에 TODO가 남아 있고, 일부 경로는 아직 `todo!()`로 비어 있습니다.

## 1. furiosa-opt가 뭔지

- 칩 이름: **TCP (Tensor Contraction Processor)** = RNGD. 추론용 대규모 병렬 가속기.
- **vISA(Virtual ISA)** = TCP의 프로그래밍 인터페이스. PyTorch/XLA처럼 메모리 배치·스케줄을 숨기지도 않고, 바이트 단위 저수준 커널 API처럼 빡세지도 않은, **그 중간 높이**. "텐서 단위로 생각하되 메모리 할당과 텐서유닛 스케줄은 직접 관리"한다고 소개합니다. (`docs/src/introduction.md:6-10`)
- 대상 독자 두 부류: ① vISA를 직접 손으로 쓰는 프로그래머, ② vISA를 생성하는 컴파일러 개발자. 둘 다 Rust 기본 지식 가정. (`docs/src/introduction.md:9-11`)
- 라이선스: **Apache-2.0**, Copyright 2025-2026 FuriosaAI. (`LICENSE`, `NOTICE`)
- git 로그가 전부 `Project import generated by Copybara` → **내부 모노레포에서 일부만 추려서 일방향 미러링한 공개본**입니다. 즉 전체 소스가 아니라 큐레이션된 부분집합. (`git log`)

## 3. 하드웨어 모델 (vISA가 노출하는 것)

### 계층 (RNGD 기준, `docs/src/quick-start.md`)
| 레벨 | 개수 | 역할 |
|---|---|---|
| Chip | 시스템마다 다름 | 최상위, HBM 보유 |
| Cluster | 칩당 **2** | 256 슬라이스 묶음 |
| Slice | 클러스터당 **256** | 텐서유닛 1개 실행 |
| Lane | 슬라이스당 **8** | Contraction MAC 배열의 한 행 |

- `Cluster=2`, `Slice=256`은 **런타임 하드 단언**입니다(다른 값이면 panic). (`furiosa-opt-std/src/engine/fetch.rs:50-51`)
- 칩 단위로만 잡힙니다. 부분 칩/클러스터 사용은 아직 미지원. (`docs/src/mapping-tensors/spatial-temporal-dimensions.md:67-69`)

### 텐서유닛 파이프라인 (고정 순서)
`Fetch → Switch → Collect → Contraction → Vector → Cast → Transpose → Commit`
- 각 엔진이 한 줄씩 문서화돼 있고, 커널에서 메서드 체인으로 호출합니다.
- Contraction: `contract_outer / contract_packet / contract_time / contract_lane` (공간/시간/레인 축약).
- Vector 엔진: Exp/NegExp/Sqrt/Tanh/Sigmoid, fp 사칙·FMA·div, 고정소수점, clip, intra/inter-slice reduce 등 → 이걸로 **softmax·layernorm·활성함수**를 손으로 조립. (`furiosa-opt-std/src/engine/vector/op/semantics.rs:104-137`)

### 메모리 계층 (`docs/src/quick-start.md`)
| 종류 | 위치 | 용량(RNGD) | 역할 |
|---|---|---|---|
| HbmTensor | 패키지 위 | 48GB, 1.5TB/s | 가중치·활성 장기 저장 |
| DmTensor | 온칩 SRAM | 256MB(512KB/슬라이스) | 주 작업 메모리 |
| SpmTensor | 온칩 SRAM | TBD, 2TB/s | 임시·중간값 |
| TrfTensor | 온칩 SRAM | 8KB/lane | Contraction용 레지스터파일 |
| VrfTensor | 온칩 SRAM | 8KB/slice | Vector용 레지스터파일 |

- **SRAM 주소를 사람이 직접 배정**합니다(겹치면 안 됨). 컴파일러가 해저드는 체크해주지만 **자동 할당은 안 해줍니다**. (`docs/src/scheduler.md:24-28`)
- 실행 컨텍스트 둘이 동시에 돕니다: `ctx.main`(주 연산) / `ctx.sub`(보통 TRF/VRF 프리페치). 둘이 SRAM을 공유하므로 주소 충돌 주의. (`docs/src/quick-start.md`, `furiosa-opt-std/src/context.rs:19-83`)
- 같은 뱅크 64회 위반 같은 건 **클러스터 리셋(치명적)** 으로 이어짐. 스케줄러는 재배치를 안 해줌. (`docs/src/moving-tensors/memory-performance.md:86-121`)

## 4. 프로그래밍 모델 (실제 코드 모양)

핵심: **커널이 그냥 Rust 함수**고, 타입시스템(const 제네릭 + 타입스테이트 + 매핑 대수)이 메모리 계층·축 배치·파이프라인 순서를 전부 인코딩합니다. **잘못된 커널은 컴파일이 안 됩니다**(나쁜 아티팩트를 뱉는 게 아니라).

1. **축·매핑 선언**
   - `axes![A = 2048]` → 축마다 유닛 구조체 생성(이름·크기). 중복 이름은 컴파일 에러. (`furiosa-mapping-macro/src/lib.rs:54`)
   - `m![...]` 미니언어 연산자: `,`=Pair, `/`=Stride(분할), `%`=Modulo(내부 개수), `=`=Resize, `#`=Padding(하드웨어 단위 수로 패딩). (`furiosa-mapping-macro/src/parser/parser.lalrpop:45-69`)
   - 예: `DmTensor<bf16, m![1], m![1 # 2], m![A / 8 # 256], m![A % 8]>` = A 축을 칩1·클러스터2중1·256슬라이스 분산·슬라이스당 8개로 매핑. 나눠떨어짐 조건은 const 단언으로 검사(`Stride`는 `L::SIZE % SIZE == 0`).

2. **타입 텐서**: 메모리 계층마다 별도 구조체 — `HostTensor / HbmTensor / DmTensor / TrfTensor / VrfTensor`. 계층 이동(`to_dm`, `to_hbm`, `to_trf`, `to_vrf`)은 타입을 바꾸면서 DMA 정렬 단언(`assert_dma_layout`)을 같이 돌림. (`furiosa-opt-std/src/tensor/memory.rs`)

3. **파이프라인 = 타입스테이트**: `ctx.main.begin(view).fetch().collect().contract_*()...commit()`. 각 단계 전이는 `CanApply*` 마커가 성립할 때만 메서드가 존재 → `collect` 전에 `commit` 부르면 **타입 에러**. (`furiosa-opt-std/src/engine/mod.rs:19-173`)

4. **호스트/디바이스 한 소스**: `#[device(chip = 1)]` 함수. 매크로가 cfg로 갈라서, NPU가 아니면 원본 Rust 본문을 **CPU에서 그대로 실행**(시뮬레이션), NPU면 미리 컴파일된 EDF(`.bin`)를 로드해 실행. 호스트는 `launch(kernel, (&mut ctx, &in_hbm)).await`. (`furiosa-opt-macro/src/lib.rs:100-271`, `runtime/mod.rs:195`)

5. **백엔드 4종** (`cargo furiosa-opt --backend ...`, `runtime/mod.rs:21-40`):
   | 백엔드 | 기본 | 하는 일 | 필요한 것 |
   |---|---|---|---|
   | `typecheck` | | 본문을 빈(phantom) 텐서로 실행 → 모양/매핑만 검사 | NPU·SDK 불필요 |
   | `simulation` | **○** | 호스트에서 전체 수치 해석(실제 값) | NPU·SDK 불필요 |
   | `emulation` | | 버퍼 에뮬레이터(문서엔 없음, 일부 미구현) | NPU 불필요 |
   | `npu` | | 컴파일된 EDF를 실제 하드웨어에 디스패치 | **SDK + 물리 NPU 필요** |
   - 기본값 simulation은 드라이버가 아니라 `furiosa-opt-std/build.rs:5-9`가 주입 → 그냥 `cargo build`도 simulation으로 빌드됩니다.

GEMM 커널 한 토막 (`base-template/src/kernel/gemm_kernel.rs`):
```rust
pub type Slice = m![I / 32, J / 32];   // 출력 I,J를 256 슬라이스에 16x16 타일로 분산
let b_trf = ctx.sub.begin(b.view()).fetch().collect().to_trf(TrfAddress::Full);
let result = ctx.main.begin(a.view()).fetch().collect()
    .contract_outer(&b_trf).contract_packet().contract_time().contract_lane(LaneMode::Interleaved)
    .cast().commit(0);
result.to_hbm(&mut ctx.tdma, 2 << 28)
```

## 5. 예제로 "증명된" 능력 vs 아닌 것

증명된 것(테스트로 수치 검증):
- **MNIST 2층 MLP** — 진짜 safetensors 가중치 로드, 이미지 10장에 대해 `argmax==label` 단언 통과. **저장소에서 유일하게 완전 검증된 실제 NN**. (`furiosa-opt-examples/src/mnist/mod.rs:64-172`, `tests/mnist_tests.rs:33-57`)
- **matmul** 4096/16384(i8)/split-reduce/cluster-reduce(2-way)/chip-reduce(4-way) — TRF 분할·split-K 누적·손코딩 ReduceScatter. (단, 대부분 특정 백엔드에서만 통과, NPU 경로는 TODO)
- **Vector 엔진 ~40개 테스트** — intra/inter-slice reduce, fxp 포화연산, fp exp/div, ternary select, VRF stash 등 호스트 레퍼런스 대비 검증.
- **DMA scatter** — 비2의제곱(612) 캐시에 512 키 기록 검증. (gather는 미검증 — 일부 분할 조건에서 실패한다고 명시)

표현은 됐지만 끝까지 검증은 안 된 것:
- **Qwen2.5-0.5B 전체 디코더** — embedding/attention/decoder/head 4개 커널로 분해돼 있고, attention 안에 KV-cache scatter·Q·Kᵀ·수치안정 마스크드 GQA softmax·score·V 가 **진짜로 구현**돼 있음. 하지만 24층 e2e 테스트 `run_qwen`은 `#[ignore]`(DmaCommandScatter lowering 미구현), 가중치는 `uninit()`, **출력 정확도 단언 없음** → 표현 가능성 증명이지 정확성 증명은 아님. (`furiosa-opt-examples/src/transformer/`, `tests/transformer_tests.rs:266-278`)
- 최상위 `attention.rs`(Llama-3.1 MLPerf prefill 첫 블록)는 embedding gather + RMSNorm까지만 있고 **본문 끝이 `// TODO`**, 테스트도 ignore. (`furiosa-opt-examples/src/attention.rs:92`)
- **MoE**는 문서만(소스·테스트 없음). branchless TopK·cumsum·one_hot·histogram·gather/scatter를 프리미티브로 조립하는 법을 글로 설명. (`docs/src/kernel-examples/mixture-of-experts.md`)
- **Llama-3 70B**도 개념 설명 글만(코드 0줄).

## 6. 설치·실행 (이 머신에서 실제로 가능한 것)

NPU/SDK 없이도 되는 것(개발·검증):
```bash
rustup toolchain install nightly-2026-05-01      # 드라이버가 이 nightly에 ABI 고정
cargo install cargo-binstall && cargo binstall cargo-furiosa-opt   # 닫힌 컴파일러 바이너리
cargo install cargo-generate
cargo generate furiosa-ai/furiosa-opt base-template && cd base-template
cargo furiosa-opt run  --release --bin gemm                 # simulation: 호스트 수치 실행
cargo furiosa-opt --backend typecheck run --release --bin gemm   # 모양/매핑만 검사
cargo furiosa-opt test --release --bin gemm                 # 레퍼런스 대비 수치 검증
```
- OS 의존성: `sudo apt install libclang-dev gcc-aarch64-linux-gnu` (libclang은 빌드 시 bindgen이 무조건 돌아서 필요, aarch64 GNU 툴체인은 NPU `.bin` 생성용). (`README.md:28-33`, `furiosa-opt-std/build.rs:19-28`)
- 빌드 자체는 인터넷이 필요합니다 — `furiosa-mapping/build.rs`가 닫힌 `libfuriosa_mapping_impl.a`를 릴리스에서 받아 SHA256 검증 후 정적 링크(`FURIOSA_MAPPING_IMPL_LOCAL_PREBUILT`로 우회 가능).

실제 NPU에서(우리 4장 머신, SDK 설치돼 있음):
```bash
FURIOSA_OPT_NPUS=0,1 cargo furiosa-opt --backend npu test --test mnist_tests
```
- `FURIOSA_OPT_NPUS`는 런타임 환경변수(칩 ID 콤마 구분). 칩마다 **양쪽 half-cluster를 pe0-7로 통째 묶는 2×4-PE 융합만** 지원 — pe0-3/pe0-1 같은 좁은 분할은 "Invalid device ID"로 실패. (`furiosa-opt-std/src/runtime/npu/ffi.rs:49-83`)

> 주의: 공개 SDK에는 **호스트용 NPU 시뮬레이터가 없습니다**. 물리 NPU 없이는 simulation(수치)·typecheck(모양)만. (`docs/src/introduction.md:44`)

## 7. ⚑ 핵심: furiosa-llm 의 `.edf` 와 같은 포맷인가? → **아니오 (직접 검증)**

둘 다 "EDF"라는 이름을 쓰지만 **바이트 포맷이 서로 못 읽을 만큼 다릅니다.** 직접 까봤습니다.

**furiosa-llm `.edf`** (`~/.cache/furiosa/llm/compiled_graphs/*.edf`) — **CBOR로 인코딩된 고수준 텐서 그래프 IR**:
```
앞부분(hex): a1 63 'Edf' a6 65 'nodes' 8a a1 64 'Copy' ...
필드: nodes / srcs_and_dsts / axes / tag / size / stride / base
```
즉 `{ "Edf": { "nodes": [ {"Copy": {...}}, ... ] } }` 같은 **그래프 노드 구조**. PE 명령어가 아님.

**furiosa-opt 의 `.bin`** (vISA 내부 파이프라인 `MIR→VISA→LIR→EDF`의 최종 산출물; `Stage::Edf`는 코드젠 단계 이름이고 실제 파일은 `.bin`) — `furiosa_kernel_load(rt, edf, len)`에 들어가는 바이트는 **pert-ipc / RuntimeKernel 명령어 스트림**:
- 동봉된 `libdevice_runtime.so`(2.1MB ELF) 안 문자열: `device-runtime/src/spec.rs`, `RuntimeKernel`, `pert`, `librenegade.so`, `furiosa-hal2/src/...`, 그리고 `Invalid PE ID` / `Invalid DRAM addr` 같은 **저수준 NPU 드라이버 에러**. `.so` 안에 **"edf" 문자열은 아예 없음**(grep 결과 0건).
- 이 `.so`가 `librenegade.so`를 dlopen → `/dev/rngd` ioctl 로 칩 구동.

**교차 검증:** furiosa-llm `.edf`에는 pert-ipc 토큰(LoadInst/TuCommand/RuntimeKernel)이 없고, `libdevice_runtime.so`에는 furiosa-llm CBOR 토큰(nodes/srcs_and_dsts/Copy)이 없습니다. **두 포맷은 상호 파싱 불가.**

**그래서 결론:**
- ✅ vISA 커널은 **같은 물리 NPU**에서, **같은 저수준 드라이버 스택**(furiosa-hal2 + librenegade.so + /dev/rngd, 같은 pe0-7 융합)으로 돕니다. "같은 하드웨어를 탄다"는 맞습니다.
- ❌ 하지만 **포맷·로더가 다릅니다.** vISA의 `.bin`을 furiosa-llm `.edf` 아티팩트에 끼워 넣거나 serve 파이프라인에 주입할 수 **없습니다**. 우리가 쓰던 **masquerade(artifact.json model_type 위장)·serve 게이트 우회와는 무관한, 완전히 별개의 실행 경로**입니다.

## 8. 우리 작업과의 관련성 (가장 중요한 부분)

우리가 그동안 한 건: 닫힌 `furiosa-llm`을 통해 모델을 NPU에 올리기(빌드/serve 게이트, op 지원 DB, model_type 위장, DeltaNet 디플로이 등). vISA는 그 **아래 계층**을 직접 만지게 해줍니다.

**새로 열리는 것**
1. **op 지원 DB / model_type 게이트를 통째로 우회.** vISA에는 aten op 허용목록도, model_type 검사도 없습니다. 컴파일 경로는 그냥 커널 단위 `MIR→VISA→LIR→EDF`. (`furiosa-opt-std/src/diag.rs:75-122`)
   → 고수준 컴파일러가 거부하던 연산(gather/scatter 등)을 **엔진을 직접 두드려 표현** 가능. `dma_gather`·`dma_scatter`가 1급 프리미티브(임베딩 룩업·KV캐시 기록에 실제 사용). (`scatter_gather.rs`, `transformer/attention/kv_cache.rs:83,146`)
2. **DeltaNet류 recurrent 커널을 손으로 짤 여지.** 필요한 1차 재료가 다 있습니다: Contraction 엔진, Vector 엔진의 게이팅 비선형(Sigmoid/Exp/...), Tag-Unit 데이터 의존 분기(`engine/vector/branch.rs`), 그리고 **루프 캐리 상태를 TRF/VRF/DM의 고정 주소에 두고 호스트 루프로 돌리는 방식**. → 이는 우리 [[qwen3-next-blocker]] 의 "남은 벽 = 컴파일 아니라 serve의 순환상태 풀 없음" 과 정확히 맞물립니다. **단 추정입니다**: 정적 shape 강제 + "한 번에 커널 하나" 디스패치 모델이라, 재귀 전체를 정적 커널로 펴거나 호스트 오케스트레이션을 직접 짜야 함(성능 미지수).
3. **하드웨어 매뉴얼 그 자체가 자산.** Switch/Collect/Contraction/Vector 시맨틱, TRF/VRF 뱅킹, 스케줄러 해저드 모델이 글로 다 있음 → **왜 고수준 컴파일러가 특정 op를 거부/조건부 처리했는지** 이해하는 1차 사료. 우리 [[op-support-verified]] 의 "8-타일 제약" 같은 조건들의 근거를 여기서 확인 가능.
4. **하드웨어 없이 수치 검증.** simulation 백엔드가 실제 값으로 레퍼런스 대비 검증 → 커널 로직을 NPU 점유 없이 먼저 맞춰볼 수 있음.

**열리지 않는 것 / 함정**
- **furiosa-llm/serve 스택은 그대로 못 씀.** §7대로 포맷이 달라서, vISA 커널을 기존 `.edf`나 serve에 주입 불가. LLM 서빙에 필요한 디코드 루프·KV/상태 풀·샘플러·연속배치·토크나이저는 **하나도 없음** → 직접 호스트 하네스를 짜야 함.
- **컴파일러는 닫힘.** `MIR→VISA→LIR→EDF` 내부는 못 봅니다. 어떤 Rust 구문/op가 유효 EDF까지 살아남는지는 직접 돌려봐야 알 수 있음(`npu_opt` 소스 없음).
- **노동량·락인.** 모든 SRAM 주소 수동 배정, 모든 축 수동 매핑. nightly-2026-05-01 ABI 고정 + 닫힌 binstall 드라이버 + (NPU 경로는) SDK·물리 NPU 필수.
- **알파.** 동적 shape 없음(MoE는 최악 grid를 패딩으로 미리 계산). gather 일부 조건 실패, attention 예제 미완성 등.

## 9. 결론 — "이걸로 뭘 할 수 있나"

- **할 수 있다:** RNGD NPU용 커스텀 커널(GEMM·attention·softmax·RMSNorm·RoPE·KV캐시·MoE 라우팅·gather/scatter 등)을 **Rust로 직접 작성**하고, 컴파일타임 타입검사로 매핑 오류를 잡고, NPU 없이 simulation으로 수치 검증한 뒤, (닫힌 무료 컴파일러 + SDK + NPU로) 실제 칩에 올린다. **고수준 컴파일러의 op 제약·model_type/serve 게이트를 건너뛴다.** 하드웨어 매뉴얼은 즉시 활용 가능한 1차 자료.
- **하려면 각오할 것:** 컴파일러는 블랙박스, 노동집약, nightly 락인, 알파 품질, 그리고 **furiosa-llm 서빙 파이프라인과는 별개 경로**(EDF 포맷 다름 → masquerade 무관).
- **우리 로드맵상 의미:** DeltaNet/Qwen3-Next처럼 고수준 컴파일러가 막던 연산을 **저수준에서 손으로 뚫을 새 길**. 다만 "serve로 바로 배포"가 아니라 "별도 device-runtime 경로로 커널을 직접 구동 + 호스트 오케스트레이션 자작"이 현실적 그림.

## 9.5. ⭐ qwen3-next를 vISA로 구현 가능한가? (2026-06-25, **v0.3.0 재검증**)

질문: "furiosa-opt vISA로도 qwen3-next 구현 못하나?" → **컴퓨트는 됩니다(이론상). 하지만 vISA가 새로 풀어주는 건 없습니다.** 막힌 부분(정식 serve의 cross-step 상태)은 vISA로도 안 풀리고, v0.3.0도 관련 기능을 추가하지 않았습니다.

**v0.3.0(2026-06-23) 변화(CHANGES.md 실측)**: `simulation`/`typecheck` 백엔드 정식 추가, vISA API 일부 개정, `Tensor::reshape`→`RawTensor` 프리미티브화, cargo-furiosa-opt 다운로드 경로 수정. **recurrent/loop/serve/linear-attention 추가 0.** 컴파일러 여전히 닫힘 — 새 `furiosa-opt-lower` 크레이트도 "thin safe wrappers over the **prebuilt** `furiosa-opt-lower-impl` static library"(릴리스에서 .a 받아 SHA256 검증 후 정적 링크, `furiosa-opt-lower/src/lib.rs:1-6`·`build.rs:25-40`). 모델 예제도 여전히 Qwen2.5-0.5B 표준 어텐션뿐(Mamba/DeltaNet/state-space 0).

**1) DeltaNet 순환 루프 = vISA도 host-driven(실용상 on-device 루프 없음).** vISA 실행 모델은 "커널 + **host 프로그램(`src/*.rs`)이 `launch(kernel,...)`로 커널을 디스패치**"(`docs/src/introduction.md`) — 우리 `qcn/` host-loop과 **정확히 같은 아키텍처**, Rust로 더 저수준일 뿐. 공개 저장소(v0.3.0) 기준 **on-device 루프/제어흐름 프리미티브의 예제·문서가 없음**(loop/while/for/scan/iterate/carried-state grep 0건): `StreamSequencer`는 메모리 스트리밍(`sequencer.rs` "the outer loop levels"=DMA 타일링), `branch.rs`는 Vector Engine Tag-Unit **elementwise select**(반복 아님), 정적 shape 강제("TCP's static shape constraints"). 즉 순환은 host가 매 스텝 커널 launch → host-bound 병목 동일, autoregressive(가변길이)는 정적 shape라 못 펴고 펴려면 worst-case 패딩. **⚠️ 정정(2026-06-26 벤더 답변): "프리미티브가 아예 없다"는 단정은 부정확 — HW/vISA 레벨엔 if·loop 프리미티브가 실제로 존재(시퀀셜 루프 제어 가능)하나 공개 저장소에 노출·예제가 없었을 뿐. 단 우리가 실제로 필요한 "스텝 사이 순환상태를 칩에 고정 + host 왕복 제거"=Persistent Kernel은 아직 미구현(2026 목표). 따라서 host-bound 병목이 그대로라는 실전 결론은 유지. §9.6 참조.**

**2) 정식 serve = vISA로도 불가(§7·§8 그대로).** vISA엔 디코드 루프·KV풀·cross-step 상태풀·샘플러·OpenAI 서버가 0개(autoregressive/decode/generate/kv-cache 개념 docs 0건). 게다가 vISA의 `.bin`(pert-ipc)은 furiosa-llm `.edf`(CBOR)와 포맷이 달라 serve 주입 불가(§7). 결국 **host 하네스 자작 필수** — 그건 우리가 이미 Python으로 했고(`qcn/`) 정식 serve CLI에 shim까지 연결함([[qwen3-next-blocker]] 20·21차).

**3) 결론.** vISA는 qwen3-next의 **컴퓨트를 더 저수준으로 다시 짤 수 있는 길**일 뿐, **우리가 이미 가진 것(furiosa.torch TacticKernel로 compute-complete + host-loop serve + pp4) 이상을 주지 않음.** 정작 벤더벽(정식 런타임 연속배칭·스케줄러·cross-step 상태풀)은 vISA가 **들어가는 길이 아니라 완전 별개 경로**라 그대로 막힘(2026.3+ 벤더). 유일한 이론적 가치=저수준 제어로 순환상태를 온칩 고정주소에 두고 sub-op을 촘촘히 엮어 **decode host 왕복을 줄일 여지**(현 host-bound 40s/tok 완화). 단 ①루프는 여전히 host-driven ②저장소에 순환 예제 0(미검증) ③거대 재작성 대비 불확실 → **실용성 낮음.** **한 줄: "vISA로 qwen3-next 컴퓨트는 가능하나, 막힌 serve는 못 풀고 우리가 이미 한 host-loop의 더 힘든 재구현일 뿐."**

| **5** | **동적 shape** 지원 계획 — 우리가 버킷+패딩 빌드를 강제당한 이유 확인 | **"단기간 내 완전 임의 동적 shape 계획 없음. 단 가변 시퀀스 대응을 위한 1년 단위 중장기 로드맵에 동적 shape 플랜 포함"** | ✅ **확인.** 동적 shape 부재=우리 버킷(고정 max-model-len+worst-case 패딩) 강제의 공식 원인. "오긴 오지만"(1년 중장기) 가깝진 않음 → **버킷 전략 당분간 유지.** |

**🆕 Schedule Viewer(질문 4 후속, 실측).** 컴파일러 내부 스케줄을 공식 GUI로 보는 신규 도구.
- 보여주는 것: 컴파일된 TCP 스케줄의 **인터랙티브 실행 타임라인** — 병렬 연산(동시 실행 태스크)·리소스/컨텍스트 점유·파이프라인 의존성(블로킹)·텐서/연산자 단위 정보(vISA 텐서 이름·shape·수명·연결).
- 생성: `cargo furiosa-opt compiler build --device-function <fn> --dump-schedule <path.json>` → 커널 아티팩트 + 스케줄 JSON 생성.
- 실행: `cargo install furiosa-schedule-viewer` → `furiosa-schedule-viewer [--host 127.0.0.1] [--port 9254]`(기본 `127.0.0.1:9254`, 브라우저 자동 오픈). 노드 클릭=텐서/연산자 속성, 호버=의존성 하이라이트, 드래그=타임라인 줌, brush=메모리 영역 포커스.
- **우리에게의 의미:** [[callgraph-analysis]]에서 build의 택틱탐색·EDF 스케줄을 콜그래프로 힘들게 추론했는데, 이걸 **공식 도구로 직접 가시화**. 단 이건 **vISA(`.bin`) 경로의 스케줄 뷰어**이지 furiosa-llm build(`.edf`) 스케줄을 직접 보여주는지는 별개 확인 필요(같은 컴파일러 백엔드라 유사할 가능성은 있음).

**종합.** 우리가 막힌 두 핵심 축 — **온칩 순환상태(Persistent Kernel, Q2)** 와 **동적 shape(Q5)** — 둘 다 퓨리오사 로드맵상 **"올해~1년" 안에 들어와 있음.** ∴ 우리 host-loop·버킷 우회는 버릴 게 아니라 **공식 기능이 올 때까지의 "다리"**로 가치 명확, 기능 도착 시 우리 구조 위로 교체하면 됨. §9.5 결론("vISA가 새로 풀어주는 건 없다")은 유지하되, **단 한 군데 — "vISA에 루프 프리미티브 없음"은 "공개 저장소엔 예제 없지만 HW엔 있음 + 정작 필요한 Persistent Kernel은 2026 목표"로 정정.**
