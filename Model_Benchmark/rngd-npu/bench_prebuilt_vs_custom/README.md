라우터(:8400)에 등록된 채팅 모델 15종을 **같은 입력, 같은 출력 한도**로 재고 답변까지 저장한 결과.
2026-09-11~12 판: RNGD 4장, furiosa-llm 2026.3.0, 커널 7.0.0-30. 14종을 쟀고 1종은 못 떴다(아래 못 잰 것).
덱은 `모델별-성능정리-2026-09-11.pptx`(48장). 2026-08-29 판(max_tokens 1024)은 `results/`, `summary.json`,

## 조건

```
프롬프트  네 종류(사실 질문, 코드 작성, 계산 추론, 개념 설명)를 모든 모델에 같은 문장으로
샘플링    temperature 0 (greedy)
길이      max_tokens 16384. Qwen2.5-0.5B 만 컨텍스트 4096 이라 3840
기록      finish_reason(stop = 스스로 멈춤, length = 한도에 걸림), 사고 토큰, 조각마다 도착 시각
지연      스트리밍으로 첫 토큰까지(TTFT)와 답이 끝날 때까지를 따로
처리량    단일 요청의 디코드 속도, 같은 질문 4개 동시 요청의 합계 속도
적재      serve 로그의 Loading LLM 부터 기동 완료까지
```

- 사고 토큰은 서버가 세 준 `usage.completion_tokens_details.reasoning_tokens` 다.
- serve 는 `prompt + max_tokens` 가 컨텍스트를 넘으면 잘라 주지 않고 **HTTP 400 으로 거절**한다
  (`/home/jun/furiosa/lib/python3.12/site-packages/furiosa_llm/errors.py:50`,
  `/home/jun/furiosa/lib/python3.12/site-packages/furiosa_llm/server/serving_chat.py:233`).
  그래서 한도는 모델마다 `min(max_tokens, 컨텍스트 − 256)` 으로 보낸다(`bench.py` 의 `cap_for`).
- 답변 원문은 덱 2부와 `results_len/<모델>.json` 에 발췌 없이 있다.

## 읽는 법

1. **속도는 멈춤 뺀 값으로 비교한다.** 오늘은 스텝 사이 멈춤 탓에 벽시계 속도가 흔들렸다(아래 절).
   멈춤 뺀 속도는 08-29 와 같다: Solar 59 / 59, Qwen3 32B 55 / 55, A3B Thinking 72 / 71 tok/s.
2. **TTFT 는 모델을 안 가린다.** 0.04~0.77초다(gpt-oss 4.0초만 예외). 기다림은 답이 끝날 때까지에서 생긴다.
3. **사고하는 모델은 짧은 질문에도 길게 쓴다.** 같은 30B 인데 A3B Instruct 2507 은 70~1,172토큰으로 끝나고,
   A3B Thinking 2507 은 사고만 1,100~1,540토큰을 먼저 쓴다. K-EXAONE 은 사고만 700~6,557토큰이다.
   짧게 묻고 받을 일에는 사고 없는 모델이 낫다.
4. **동시 처리는 카드 한 장짜리 작은 모델이 앞선다.** 0.5B 273, Qwen3 4B 225, Qwen3 8B 216, Llama 3.1 8B 182 tok/s.
   넉 장짜리 중 가장 빠른 Qwen3-Coder 30B 가 136 이다.
5. **모델을 바꾸면 기다린다.** 넉 장짜리는 65~772초(gpt-oss 579, Solar 772), 한 장짜리는 4~19초다.
6. **gpt-oss 120B 는 단일 요청 스텝이 약 1초다.** 258토큰 답에 256초가 걸렸다(아래 절).

## 측정 주의: 스텝 사이 멈춤

넉 장짜리 모델에서 조각 사이가 0.1~1초씩 끊기는 일이 잦았다. 정상 간격은 08-29 와 같으므로 모델이 느려진 것이
아니라 **스텝 사이가 막힌다.** 몇 분 단위로 밀려왔다 빠지고, 같은 모델도 시간대에 따라 0회에서 2천 회까지 달랐다
(Qwen3-Coder 17:59 0회, Solar 17:1x 2,107회). 동시 요청이 가장 크게 다친다. serve 로그의 생성량도 같은 시간에
떨어졌으니 측정 쪽이 아니라 서버 쪽 멈춤이다.

| 가설 | 실험 | 결과 |
|---|---|---|
| 라우터의 `furiosa-smi` 5초 주기 호출 | 라우터 없이 직접 요청, smi 없음 / 5초 / 쉬지 않고 (`diag.py stall --direct --smi`) | smi 없어도 멈춤 5~102회, smi 연속이 오히려 2~3회. smi 구간과 겹친 비율 5~17% = 우연 수준 |
| max_tokens 가 크면 멈춘다 | 같은 프롬프트, 동시 요청을 1024 와 16384 로 번갈아 | 차이 없음. Qwen3-32B 는 08-29 와 같은 1024 로도 동시 4요청이 67초(08-29 22초) |
| CPU 경합, cgroup 할당량 | serve 스레드 570개의 실행 대기, `cpu.max` | 대기 0.4%, 할당량 없음 |
| 카드 한 장의 열화 | 한 장짜리 모델을 카드 0~3 에 차례로 | 멈춤 0. 다만 19:15 OOM 뒤에는 한 장짜리 Qwen3-4B 도 요청마다 36~82회 멈췄다 |
| 온도, 전력 | `furiosa-smi info` | 37~38°C, 66~71 W |
| 동시 요청이 줄 서서 처리됨 | 요청별 종료 시각, 버킷의 최대 배치 | A3B Instruct 2507, Qwen3-32B 는 넷이 같이 끝남. 최대 attention 에서도 배치 4 이상 허용 |
| NUMA 노드 메모리 부족 | 0.5초마다 커널 카운터(`diag_sampler.py`)와 멈춤 시각 대조(`diag_corr.py`) | 멈춤 구간에 직접 회수, 압축 대기 0. 모델 사이 상관(−0.77)은 시간대가 섞인 것이고 Solar 한 모델 안에서는 +0.22 / −0.16. 메모리 압박이 0 이던 gpt-oss 구간에도 동시 요청이 느렸다 |

08-29 이후 바뀐 것은 **09-01 재부팅 때 커널이 6.17.0-40 에서 7.0.0-30 으로 올라간 것**이다(`last -x reboot`).
6.17 커널 이미지는 지워졌다. 원인 확정에는 root 가 필요하다(커널 로그, off-CPU 추적, 설치된 7.0.0-31 부팅 비교).

★ gpt-oss 120B 는 멈춤이 아니라 **스텝 자체가 약 1초**다(간격 중앙값 0.90~0.98초). 08-29 에도 단일 요청이
  0.8~3.0 tok/s 로 느렸다. serve 로그의 스케줄러 설정은 다른 모델과 같다. 원인 미확인.

## 못 잰 것

`Qwen3-30B-A3B-FP8` 은 **배포된 FXB 번들 자체가 고장**이라 뜨지 못한다. 캐시는 정상이고(32G,
형제 모델 33G, 미완성 파일 없음) 다운로드 문제가 아니다. 가중치 30.2 GiB 를 다 읽은 뒤 죽는다:

```
pyo3_runtime.PanicException: assertion `left == right` failed:
  element size mismatch for weight "model.embed_tokens.weight":
  safetensor dtype F32 is 4 bytes but EDF element type Bfloat16 is 2 bytes
```

50회 재현했다(2026-09-11 에도 같은 패닉). 같은 계열의 `Qwen3-30B-A3B-Instruct-2507-FP8` 과 `Thinking-2507-FP8` 은 정상이다.

`K-EXAONE-236B-A23B-NVFP4A16` 은 2026-09-11 적재 중 **서버 메모리가 바닥나 OOM killer 에 serve 가 죽었다**
(19:14 노드 여유 0.5/0.1 GB, `/proc/vmstat` 의 `oom_kill` 1, 다른 프로세스는 무사). 가중치 136.6 GiB 가 당시 서버
메모리 125 GiB 보다 컸다. 09-12 에 스왑이 207 GB 로 늘어난 뒤 `diag_evict.py` 로 페이지 캐시를 비우고(노드 여유
56/56 GB) 다시 올리니 636초에 떴고, 적재 중 serve 는 RSS 107 GB 에 스왑 96 GB 를 썼다. 그래서 이 판에 들어 있다.
OOM 이 또 나더라도 남의 프로세스가 아니라 이 serve 가 먼저 정리되도록 `oom_score_adj` 를 500 으로 올려 두고 쟀다.
