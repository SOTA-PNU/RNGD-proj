# Fetch and Commit Engine

이 예제들은 fetch-commit 패턴이 전체 스트리밍 경로(input tensor -> fetch sequencer -> [Switch Engine](../computing-tensors/switch-engine.md) -> [Collect Engine](../computing-tensors/collect-engine.md) -> commit unit -> output tensor)에서 배치 변환, 쓰기 단위, 하드웨어 용량 처리를 어떻게 좌우하는지 보인다.

네 예제는 fetch-commit 스트리밍 경로의 서로 다른 측면(축 재배열, 쓰기 단위, 메모리 배치 선택, 하드웨어 용량을 넘는 텐서의 처리)을 다루며, 각각 축 순열, full-flit commit, 꼬리 패딩 최적화, 텐서 분할 패턴에 대응한다.


## 예제 1: 축 순열

이 예제는 fetch-commit 사이클 중에 축을 순열해 텐서를 재배치하는 방법을 보인다. Switch Engine 을 써서 추가 연산 없이 축을 재배열한다.

```rust,ignore
axes![A = 3, B = 5, C = 2];

// Input: shape [A, B, C]
let input: DmTensor<f8, m![1], m![1], m![1], m![A, B, C]> = ...;

// Output: shape [B, A, C] (permuted layout)
let output: DmTensor<f8, m![1], m![1], m![1], m![B, A, C # 6]> = ctx
    .main
    .begin(input.view())
    .fetch::<m![A, B], m![C # 6]>()           // Time=[A,B], Packet=[C] padded to 8 bytes
    .collect::<m![A, B], m![C # 30]>()        // Pad to 32-byte flit (forwarding switch implied)
    .commit();                                // Write with permuted sequencer config
```

#### 입력 텐서

입력은 SRAM 에 저장된 3차원 텐서로 차원은 `[A=3, B=5, C=2]` 이고 원소는 모두 30개다.
- **모양**: `A × B × C = 3 × 5 × 2`
- **데이터 타입**: `f8` (8비트 부동소수점)
- **메모리 배치**: `m![A, B, C]` - `A` 가 가장 느리게, `C` 가 가장 빠르게 변하며 메모리에 연속 저장된다
- **기준 주소**: `b = 0` (SRAM 주소 0 에서 시작)
- **물리 저장 형태**: 원소는 `[A0,B0,C0][A0,B0,C1][A0,B1,C0]...[A2,B4,C1]` 순으로 놓인다

원소를 인덱스로 표기하면 메모리 내용은 다음과 같다.
```text
Address 0-1:   (A=0,B=0,C=0-1)
Address 2-3:   (A=0,B=1,C=0-1)
Address 4-5:   (A=0,B=2,C=0-1)
...continuing with A=0, varying B...
Address 10-11: (A=1,B=0,C=0-1)
...and so on
```

#### 출력 텐서 (목표)

같은 논리 텐서를 축을 순열해 `[B, A, C]` 배치로 저장한다.
- **모양**: 여전히 `B × A × C = 5 × 3 × 2` (같은 30개 원소, 다른 순서)
- **데이터 타입**: `f8` (동일)
- **메모리 배치**: `m![B, A, C # 6]` - 이제 `B` 가 가장 느리게 변하고, 원소마다 6바이트 패딩이 붙는다
- **기준 주소**: `b = 1024` (SRAM 주소 1024 에 저장)
- **물리 저장 형태**: 원소는 `[B0,A0,C0-1][B0,A1,C0-1][B0,A2,C0-1][B1,A0,C0-1]...` 순으로 놓인다

이 재배열은 메모리에서 어떤 원소가 인접하는지를 바꾼다. 입력에서는 `A=0` 에 대한 모든 `B` 값이 연속이지만, 출력에서는 `B=0` 에 대한 모든 `A` 값이 연속이다.

#### 처리

순열을 만들기 위해 Fetch, Switch, Commit 세 단계가 차례로 실행된다.

1. **Fetch Sequencer**: SRAM 에서 입력 텐서를 읽어 packet 스트림을 만든다
   - 시간 차원: `Time = m![A, B]` - 15 사이클(3×5)을 순회한다
   - packet 차원: `Packet = m![C # 6]` - 각 packet 은 `C` 원소 2개와 6바이트 패딩을 담는다
   - fetch 크기: 사이클당 8바이트 (하드웨어 정렬 요구를 만족)
   - 참고: 하드웨어가 8바이트 packet 정렬을 요구하므로 `C=2` 바이트만 쓸 수 없고, 8바이트로 패딩한다
2. **Collect Engine**: packet 을 commit 단계용 표준 32바이트 flit 으로 정규화한다
   - 입력 packet(8바이트)에 패딩을 붙여 32바이트 flit 을 만든다
   - 시간 차원: `Time = m![A, B]` - 그대로 15 사이클이다
   - flit 차원: `Flit = m![C # 30]` - 데이터 2바이트 + 패딩 30바이트 = 32바이트 flit
   - collect engine 은 데이터를 재배열하지 않고 packet 크기만 패딩·정규화한다
3. **Commit Unit**: 새 축 순서 `[B, A, C]` 로 SRAM 에 데이터를 쓴다
   - 시간 `m![A, B]` 로 들어온 flit 을 받아 메모리 배치 `m![B, A, C # 6]` 에 쓴다
   - 순열은 write sequencer 설정이 만든다
   - commit 크기: 쓰기당 8바이트 (fetch 크기와 동일)
   - 들어온 32바이트 flit 을 8바이트 쓰기 단위로 잘라낸다

write sequencer 설정은 시간 순서로 들어오는 스트림 `m![A, B, C]` 를 순열된 메모리 배치 `m![B, A, C #6]` 로 어떻게 매핑할지 결정한다.
`[axis=count:stride, ...] @ base / commit_size` 표기의 뜻은 다음과 같다. 각 축마다 `count` 번 반복하며 한 단계마다 `stride` 바이트씩 전진하고, `@` 는 기준 주소를, `/` 는 commit 연산 하나가 쓰는 바이트 수를 정한다(전체 sequencer 모델은 [Sequencer](../moving-tensors/sequencer.md) 참고).

sequencer 는 `[A=3:8, B=5:24, C=8:1] @ 1024 / 8` 로 설정된다
- `A=3:8` 은 반복 사이에 8바이트 스트라이드를 두고 3번 반복한다는 뜻이다
- `B=5:24` 는 반복 사이에 24바이트 스트라이드를 두고 5번 반복한다는 뜻이다
- `C=8:1` 은 스트라이드 1로 8바이트(packet 크기)를 쓴다는 뜻이다
- **기준 주소**: 1024 (출력 텐서가 여기서 시작)
- **commit 크기**: 쓰기 연산당 8바이트

이 설정 덕분에 `[A, B]` 시간 순서로 도착한 데이터가 `[B, A]` 공간 순서에 해당하는 주소에 기록된다. 쓰기가 일어나는 방식은 다음과 같다.

| 사이클 `i` | 시간 축 | 기록 대상 메모리 주소 | 설명 |
|-----------|-----------|------------------------|-------------|
| 0 | A=0, B=0 | 1024-1032 (B=0, A=0) | 첫 원소: 기준 주소에 기록 |
| 1 | A=0, B=1 | 1048-1056 (B=1, A=0) | 24바이트 스트라이드만큼 전진(다음 B) |
| 2 | A=0, B=2 | 1072-1080 (B=2, A=0) | 다시 24바이트 스트라이드 |
| 3-4 | A=0, B=3-4 | B=3,4 로 이어짐 | A=0 행 완료 |
| 5 | A=1, B=0 | 1032-1040 (B=0, A=1) | B=0, A=1 로 점프(사이클 0 에서 +8) |
| 6 | A=1, B=1 | 1056-1064 (B=1, A=1) | 다음 B 로 +24 스트라이드 |
| 7-14 | 이어짐 | ... | A=1,2 행 전체 완료 |

쓰기 패턴이 어떻게 인터리브되는지 보라. `A=0,B=0` 을 쓰고 `A=0,B=1` 을 쓰지만, 이들은 출력 배치에서 각 `B` 에 대한 모든 `A` 값이 함께 놓이는 주소로 간다.

#### 출력

commit 이 끝나면 SRAM 주소 1024 이후에 순열된 배치의 텐서가 담긴다.
- **메모리 배치**: 6바이트 패딩이 붙은 `[B=5, A=3, C=2]`
- **물리 배열**: `B=0` 에 대한 모든 `A` 값이 연속하고, 그다음 `B=1` 에 대한 모든 `A` 값이 이어진다
- **주소 구조**:
  ```text
  1024-1032: (B=0, A=0, C=0-1) + 6 bytes padding
  1032-1040: (B=0, A=1, C=0-1) + 6 bytes padding
  1040-1048: (B=0, A=2, C=0-1) + 6 bytes padding
  1048-1056: (B=1, A=0, C=0-1) + 6 bytes padding
  ...and so on
  ```

순열이 완료되었다. `[A, B, C]` 순서였던 같은 30개 데이터 원소가 이제 `[B, A, C]` 순서로 놓인다. 이 연산은 15 사이클(A×B 조합 하나당 한 사이클)이 걸리고 실제 연산은 전혀 필요하지 않으며, 주소 패턴만 다른 메모리 읽기/쓰기뿐이다.

**핵심 제약:**
축 순열 연산을 지배하는 제약은 세 가지다.

- **8바이트 정렬**: `commit_in_size` 와 `commit_size` 는 항상 8바이트 단위이므로, commit 대상 텐서는 언제나 8바이트 정렬된 범위에 대응하고 자연스럽게 8바이트 꼬리 정렬이 생긴다(꼬리를 8바이트에 맞추기 위해 dummy 가 추가된다).
- **Sequencer 한도**: Fetch Engine 과 마찬가지로 sequencer 엔트리는 총 8개로 제한된다(한도 < 65,536).
- **비연속 쓰기**: write sequencer 가 commit 주소를 정하므로, commit 된 데이터가 flit 시간 순서로 연속일 필요가 없다. `AB -> BA` 같은 순열이 가능하다.

**이 예제가 유용한 이유:**
축 순열은 딥러닝에서 흔히 필요하다.
- **텐서 배치 변환**: 연산에 따라 `NCHW`(batch, channels, height, width) 와 `NHWC`(batch, height, width, channels) 형식을 서로 변환한다
- **행렬 전치**: 실제 연산 없이 전치된 행렬을 요구하는 연산용으로 데이터를 준비한다
- **메모리 접근 최적화**: 가장 자주 접근하는 차원을 가장 안쪽에 두도록 축을 재배열해 캐시 성능을 높인다
- **연산 간 호환성**: 후속 연산의 입력 요구에 맞게 텐서를 다시 포맷한다

TCP 구조는 이런 재배치를 데이터 이동 중에 수행하므로 연산 자원을 쓰지 않고 별도의 전치 커널도 필요 없다.

## 예제 2: Full-flit Commit

이 예제는 32바이트 flit 을 더 작은 조각으로 자르지 않고 통째로 메모리에 쓰는 최적화인 full-flit commit 을 보인다.
텐서 차원이 자연스럽게 32바이트 경계에 정렬되면 commit slicer 가 필요 없으므로 그 오버헤드가 사라지고 write sequencer 설정도 단순해진다.

```rust,ignore
axes![A = 3, B = 5, C = 2];

// Input: same shape [A, B, C]
let input: DmTensor<f8, m![1], m![1], m![1], m![A, B, C]> = ...;

// Output: merge B and C, pad to 32 bytes per A slice
let output: DmTensor<f8, m![1], m![1], m![1], m![A, [B, C] # 22]> = ctx
    .main
    .begin(input.view())
    .fetch::<m![A], m![[B, C] # 22]>()        // Time=[A], Packet=[B,C] padded to 32 bytes
    .collect::<m![A], m![[B, C] # 22]>()      // Already 32-byte flit, identity collect
    .commit();                                // Full-flit commit: 3 cycles vs 15 in Example 1
```

#### 입력 텐서

입력 텐서는 예제 1과 동일하지만, full-flit 쓰기가 가능한 다른 메모리 배치로 commit 한다.
- **모양**: 원소 30개를 담은 `[A=3, B=5, C=2]`
- **데이터 타입**: `f8` (8비트 부동소수점, 원소당 1바이트)
- **메모리 배치**: `m![A, B, C]` - 표준 행 우선 순서
- **기준 주소**: `b = 0`
- **원소 크기**: 1바이트 × 30 원소 = 데이터 30바이트

#### 출력 텐서 (목표)

예제 1처럼 축을 순열하는 대신, 마지막 두 차원을 합치고 패딩을 붙인다.
- **모양**: 논리적으로는 여전히 `[A=3, B=5, C=2]` 이지만 `[A=3, BC=10]` 으로 저장된다
- **데이터 타입**: `f8` (동일)
- **메모리 배치**: `m![A, [B, C] # 22]` - B 와 C 차원을 합치고 22바이트 패딩을 붙인다
- **기준 주소**: `b = 1024`
- **물리 배치**: `A` 반복마다 데이터 10바이트(B×C)와 패딩 22바이트, 합쳐서 32바이트를 저장한다
- `A` 슬라이스당 32바이트 크기는 하드웨어 flit 크기와 정확히 맞아떨어져 full-flit 쓰기가 가능하다

#### 처리

데이터 차원이 하드웨어 flit 크기에 정렬되면 예제 1보다 단순한 파이프라인이 된다.

1. **Fetch Sequencer**: 입력을 읽어 곧바로 32바이트 packet 으로 패딩한다
   - 시간 차원: `Time = m![A, B]` - 15 사이클(3×5)
   - packet 차원: `Packet = m![[B, C] # 22]` - B 와 C 를 합치고 22바이트 패딩을 붙여 32바이트를 채운다
   - fetch 크기: 사이클당 32바이트 (분할하지 않은 온전한 packet)
   - sequencer 가 fetch 중에 데이터 10바이트를 32바이트로 패딩한다
2. **Collect Engine**: 32바이트 packet 을 받아 32바이트 flit 으로 넘긴다
   - 시간 차원: `Time = m![A]` - B 와 C 가 packet 으로 합쳐졌으므로 3 사이클로 단순해진다
   - flit 차원: `Flit = m![[B, C] # 22]` - 추가 패딩이 필요 없는 온전한 32바이트 flit
   - 재포맷이 필요 없다. packet 크기 = flit 크기 = 32바이트
3. **Commit Unit**: 32바이트 flit 을 자르지 않고 그대로 메모리에 쓴다
   - 32바이트 flit 을 받아 온전한 32바이트 단위로 기록한다
   - **commit_in_size = 32 bytes**: slicer 동작이 필요 없다
   - **commit_size = 32 bytes**: 쓰기 연산 하나가 flit 하나를 통째로 처리한다
   - 시간: `A` 하나당 한 사이클로 3 사이클뿐이며, 예제 1의 15 사이클보다 훨씬 빠르다

write sequencer 설정은 단순하다. `[A=3:32, [B,C]=32:1] @ 1024 / 32`
- `A=3:32` 는 32바이트 스트라이드로 3번 반복한다는 뜻이다(A 하나당 온전한 flit 하나)
- `[B,C]=32:1` 은 스트라이드 1로 32바이트를 쓴다는 뜻이다(flit 내용을 연속으로 기록)
- 각 사이클이 온전한 flit 하나를 쓴다. 사이클 0 은 A=0 의 flit 을, 사이클 1 은 A=1 을, 사이클 2 는 A=2 를 쓴다

#### 출력

commit 이 끝나면 SRAM 주소 1024 이후에 32바이트 정렬 블록으로 채워진 텐서가 담긴다.
- **메모리 배치**: `A` 슬라이스마다 정확히 32바이트를 차지하는 `[A=3, BC=10+padding]`
- **물리 구조**:
  ```text
  1024-1056: (A=0, all 10 B×C elements) + 22 bytes padding = 32 bytes
  1056-1088: (A=1, all 10 B×C elements) + 22 bytes padding = 32 bytes
  1088-1120: (A=2, all 10 B×C elements) + 22 bytes padding = 32 bytes
  ```
- **성능**: 예제 1의 15 사이클 대비 쓰기 3 사이클뿐이다(5배 빠름)
- **단순함**: 슬라이싱 오버헤드가 없고 복잡한 스트라이드 패턴도 없다

**이 예제가 유용한 이유:**
full-flit commit 은 중요한 최적화 전략을 보여준다.
- **정렬 최적화**: 차원을 32바이트 경계에 맞게 패딩할 수 있으면 commit 이 훨씬 효율적이 된다
- **사이클 감소**: 큰 쓰기를 적게 하는 편이 작은 쓰기를 많이 하는 것보다 빨리 끝난다
- **하드웨어 효율**: 온전한 flit 을 쓰면 메모리 대역폭 활용이 최대가 된다
- 하드웨어 단위에 맞추려고 패딩을 더하는 편이 전체 성능을 높이는 경우가 있다

이 기법은 특히 다음 경우에 값어치가 있다.
- 얻는 이득에 비해 패딩 오버헤드가 미미한 작은 텐서
- 조밀하게 저장할 필요가 없는 중간 결과
- 후속 연산도 32바이트 정렬에서 이득을 보는 상황

write sequencer 설정은 모든 엔트리에 0이 아닌 스트라이드를 요구한다.
따라서 슬라이싱을 넘어서는 데이터 폐기는 할 수 없고(선택적 쓰기 불가), commit 중에는 브로드캐스트(재사용) 연산도 불가능하다.

## 예제 3: 꼬리 패딩과 fetch 크기

꼬리 패딩의 양은 fetch/commit 효율에 큰 영향을 준다.
이 예제는 `A=65` 인 텐서를 commit 하는데, 패딩 양의 선택이 쓸 수 있는 fetch 크기를 결정한다.
패딩이 하드웨어 fetch 크기 제약과 어떻게 얽히는지 이해하면 메모리 사용량(패딩 적게)과 성능(하드웨어 경계에 맞춘 패딩 많이) 사이에서 최적화할 수 있다.

```rust,ignore
axes![A = 65, B = 2];

let input: DmTensor<f8, m![1], m![1], m![1], m![B, A # 72]> = ...;

// Option 1: dummy=7, fetch_size=24 bytes, 6 cycles
let out_7: DmTensor<f8, m![1], m![1], m![1], m![B, A # 72]> = ctx.main
    .begin(input.view())
    .fetch::<m![B * (A # 72) / 24], m![A % 24]>()
    .collect::<m![B * (A # 72) / 24], m![A % 24 # 8]>()
    .commit();

// Option 2: dummy=31, fetch_size=32 bytes, 6 cycles (best performance)
let out_31: DmTensor<f8, m![1], m![1], m![1], m![B, A # 96]> = ctx.main
    .begin(input.view())
    .fetch::<m![B * (A # 96) / 32], m![A % 32]>()
    .collect::<m![B * (A # 96) / 32], m![A % 32]>()
    .commit();
```

매핑 표현식 `m![A # 72]` 에서 `# 72` 는 `A` 를 72 원소까지 패딩한다.
이 패드를 아래 하드웨어 설정에서는 `dummy` 라고 부른다.

#### 문제

모양이 `[A=65, B=2]` 인 텐서(데이터 130바이트)를 commit 한다. 하드웨어 fetch 크기는 8, 16, 24, 32바이트 중 하나여야 한다.
성능을 최대로 하려면 `A` 차원의 패딩 양을 얼마로 정해야 하는지 구한다.

#### 입력 텐서

- **모양**: `[A=65, B=2]` - 원소 130개(A 차원 65개, B 차원 2개)
- **데이터 타입**: `f8` (원소당 1바이트)
- **메모리 배치**: `m![B, A+7]` - A 뒤에 꼬리 패딩 7바이트를 두고 저장한다
- **기준 주소**: `b = 0`
- **전체 크기**: `2 × (65 + 7) = 144 bytes` (패딩 포함)

#### 출력 텐서 (가변 패딩)

목표 텐서는 패딩 양을 달리 가질 수 있고, 각각 서로 다른 fetch 크기를 가능하게 한다.
- **모양**: `[A=65, B=2]` (논리 데이터는 동일)
- **데이터 타입**: `f8`
- **기준 주소**: `b = 1024`
- **메모리 배치 선택지**:
  - `m![B, A # 7]`: 패딩 7바이트 → 24바이트 fetch 크기 가능
  - `m![B, A # 15]`: 패딩 15바이트 → 16바이트 fetch 크기 가능
  - `m![B, A # 23]`: 패딩 23바이트 → 8바이트 fetch 크기 가능(최악)
  - `m![B, A # 31]`: 패딩 31바이트 → 32바이트 fetch 크기 가능(최선)

최적 fetch 크기 단위는 꼬리 `dummy` 값에 따라 달라진다.
아래 절에서 각 경우를 보인다.

### `dummy = 7`
- fetch sequencer 출력
  - `Time = m![B * (A # 7) / 24]`
  - `Flit = m![A % 24]`
  - fetch_size = 24 bytes
- Switch Engine 출력 (= commit unit 입력)
  - `Time = m![B * (A # 7) / 24]`
  - `Flit = m![A % 24 # 8]`
- Commit Unit
  - commit_in_size = 24 bytes
  - 잘린 모양
    - `Time = m![B * (A # 7) / 24]`
    - `Flit = m![A % 24]`
  - write sequencer 설정
    - `m![B, A # 7]` -> `m![B * (A # 7) / 24 * A % 24]`
    - Sequencer 설정: `[B=2:72, (A # 7)/24=3:24, A=24:1] @ 1024 / 24`

### `dummy = 15`
- fetch sequencer 출력
  - `Time = m![B * (A # 15) / 16]`
  - `Flit = m![A % 16]`
  - fetch_size = 16 bytes
- Switch Engine 출력 (= commit unit 입력)
  - `Time = m![B * (A # 15) / 16]`
  - `Flit = m![A % 16]`
- Commit Unit
  - commit_in_size = 16 bytes
  - 잘린 모양
    - `Time = m![B * (A # 15) / 16]`
    - `Flit = m![A % 16]`
  - write sequencer 설정
    - `m![B, A # 15]` -> `m![B * (A # 15) / 16 * A % 16]`
    - Sequencer 설정: `[B=2:80, (A # 15)/16=5:16, A=16:1] @ 1024 / 16`

### `dummy = 23`
- fetch sequencer 출력
  - `Time = m![B * (A # 23) / 8]`
  - `Flit = m![A % 8]`
  - fetch_size = 8 bytes
- Switch Engine 출력 (= commit unit 입력)
  - `Time = m![B * (A # 23) / 8]`
  - `Flit = m![A % 8 # 24]`
- Commit Unit
  - commit_in_size = 8 bytes
  - 잘린 모양
    - `Time = m![B * (A # 23) / 8]`
    - `Flit = m![A % 8]`
  - write sequencer 설정
    - `m![B, A # 23]` -> `m![B * (A # 23) / 8 * A % 8]`
    - Sequencer 설정: `[B=2:88, (A # 23)/8=11:8, A=8:1] @ 1024 / 8`

### `dummy = 31`
- fetch sequencer 출력
  - `Time = m![B * (A # 31) / 32]`
  - `Flit = m![A % 32]`
  - fetch_size = 32 bytes
- Switch Engine 출력 (= commit unit 입력)
  - `Time = m![B * (A # 31) / 32]`
  - `Flit = m![A % 32]`
- Commit Unit
  - commit_in_size = 32 bytes
  - 잘린 모양
    - `Time = m![B * (A # 31) / 32]`
    - `Flit = m![A % 32]`
  - write sequencer 설정
    - `m![B, A # 31]` -> `m![B * (A # 31) / 32 * A % 32]`
    - Sequencer 설정: `[B=2:96, (A # 31)/32=3:32, A=32:1] @ 1024 / 32`

### 정리: 패딩 선택이 미치는 영향

다음 표는 출력 꼬리 패딩이 성능에 어떤 영향을 주는지 정리한 것이다.

| 패딩 (`dummy`) | `fetch_size` | fetch 사이클 | 메모리 오버헤드 | 효율 |
|-------------------|------------|--------------|-----------------|------------|
| 7 | 24 bytes | 6 사이클 | 14 bytes (9.7%) | 양호 |
| 15 | 16 bytes | 10 사이클 | 30 bytes (18.8%) | 보통 |
| 23 | 8 bytes | 22 사이클 | 46 bytes (26.1%) | 나쁨 |
| 31 | 32 bytes | 6 사이클 | 62 bytes (32.3%) | 최선 |

**핵심 정리:**

- **성능 차이가 매우 크다**: `dummy=23` 은 22 사이클(8바이트 fetch)이 필요한 반면 `dummy=31` 은 6 사이클(32바이트 fetch)이면 되며, 패딩 양은 비슷한데도 거의 4배 빠르다
- **최적 패딩은 하드웨어에 맞춘다**: `(data_size + padding)` 이 32바이트(가장 큰 fetch 크기)로 나누어떨어질 때 성능이 가장 좋다
- **트레이드오프**: 패딩을 8바이트 더 붙이면(23→31) 메모리 오버헤드가 26.1%에서 32.3%로 늘지만(6% 증가에 그친다) 성능은 3.7배 좋아진다(22 사이클→6 사이클)
- **메모리를 조금 더 낭비하더라도 가능한 가장 큰 fetch 크기(32바이트)를 쓸 수 있는 패딩 양을 택한다**

**이 예제가 유용한 이유:**
패딩을 안이하게 고르면 성능이 크게 떨어진다.
- 23바이트 같은 임의 값으로 패딩하면 8바이트짜리 작은 fetch 를 쓸 수밖에 없다
- fetch 크기 제약을 이해하면 패딩을 전략적으로 고를 수 있다
- 가능하면 32바이트의 다음 배수까지 패딩한다
- 더 나은 패딩의 메모리 비용은 대개 성능 이득에 비해 무시할 만하다

### `dummy=23` 이 32바이트 commit 을 쓸 수 없는 이유

write sequencer 설정은 절대 텐서 경계를 넘어서면 안 된다. 이 제약 때문에 `dummy=23` 인 경우에는 32바이트 commit 을 쓸 수 없다.

- fetch sequencer 출력
  - `Time = m![B * (A # 31) / 32]` : A + 23 은 32로 나누어떨어지지 않으므로, fetch_size=32 바이트로 두면 A+31 원소를 fetch 해야 한다.
  - `Flit = m![A % 32]`
  - fetch_size = 32 bytes
- Switch Engine 출력 (= commit unit 입력)
  - `Time = m![B * (A # 31) / 32]`
  - `Flit = m![A % 32]`
- Commit Unit
  - commit_in_size = 32 bytes (commit_in_size 가 32 미만이면 유효한 A 부분이 잘리므로 commit_in_size=32 바이트로 두어야 한다)
  - 잘린 모양
    - `Time = m![B * (A # 31) / 32]`
    - `Flit = m![A % 32]`
  - write sequencer 설정
    - `m![B, A # 23]` -> `m![B * (A # 31) / 32 * A % 32]`
    - Sequencer 설정: `[B=2:88, (A # 31)/32=3:32, A=32:1] @ 1024 / 32`

**핵심 정리:** read sequencer 설정은 안전하게 초과 fetch 를 할 수 있지만(입력 텐서 범위를 넘는 `dummy` 주소를 읽어도 괜찮다), write sequencer 설정은 절대 텐서 경계 너머로 쓰면 안 된다(다른 텐서가 차지한 공간에 데이터를 쓸 수 있기 때문이다).
이 비대칭성 때문에 `dummy=23` 은 32바이트 fetch 를 쓸 수 없다.


## 예제 4: 텐서 분할

TCP 는 Vector Register File(VRF) 용량을 넘는 텐서를 분할로 처리한다. 하드웨어 제약에 들어가는 작은 조각으로 자동으로 쪼개고, 각 조각을 독립적으로 처리한다.

```rust,ignore
axes![A = 2048, B = 32];

// Input: 64KB tensor, exceeds 8KB VRF limit
let input: DmTensor<f8, m![1], m![1], m![1], m![A, B]> = ...;

// Segmented into two executions (compiler handles this automatically)

// Execution #0: first half of A
let seg_0: DmTensor<f8, m![1], m![1], m![1], m![A % 1024, B]> = ctx.main
    .begin(input.view().slice(A, 0..1024))
    .fetch::<m![A % 1024], m![B]>()
    .collect::<m![A % 1024], m![B]>()
    .commit();

// Execution #1: second half of A
let seg_1: DmTensor<f8, m![1], m![1], m![1], m![A @ 1024, B]> = ctx.main
    .begin(input.view().slice(A, 1024..2048))
    .fetch::<m![A @ 1024], m![B]>()
    .collect::<m![A @ 1024], m![B]>()
    .commit();
```

#### 문제

Vector Engine 의 VRF 는 슬라이스당 8KB 용량뿐이다. 이보다 큰 저장 공간이 필요한 텐서는 한 번의 연산으로 fetch 해 처리할 수 없다. 분할은 텐서를 여러 실행에 나누어 담는다.

8KB 한도는 전체가 아니라 슬라이스당 값이다.
클러스터에는 슬라이스가 256개 있지만(전체 VRF 2MB), 각 슬라이스는 8KB 만 담는다.
슬라이스 간 텐서 분배는 텐서 매핑의 슬라이스 차원으로 제어한다.
슬라이스 차원에 매핑된 원소가 충분하지 않은 텐서, 또는 개별 슬라이스에 행/열 전체가 필요한 연산(리듀스 연산에서 흔하다)은 256개 슬라이스를 다 쓰기도 전에 슬라이스당 한도에 걸린다.
매핑이 `m![1, 1, 1, 2048, 32]` 인 [2048, 32] 텐서는(슬라이스 분배 없음) 64KB 전부를 슬라이스 0에 저장하려 하므로 8KB 한도를 넘는다.
슬라이스 분배 `m![1, 1, 256, 8, 32]` 를 써도 각 슬라이스는 256바이트만 저장하지만, 중간 결과나 연산 제약 때문에 슬라이스당 더 많은 저장 공간이 필요할 수 있다.
분할은 각 슬라이스의 VRF 사용량이 8KB 하드웨어 한도 안에 머물도록 보장한다.

#### 입력 텐서

VRF 용량을 넘는 큰 2차원 텐서다.
- **모양**: `[A=2048, B=32]` - 원소 65,536개
- **데이터 타입**: `f8` (원소당 1바이트)
- **전체 크기**: 2048 × 32 = 65,536바이트 = 64 KB
- **메모리 배치**: `m![A, B]` - 표준 행 우선
- **기준 주소**: `b = 0`
- **문제**: 64 KB 는 슬라이스당 8 KB 인 VRF 한도를 크게 넘는다

#### 출력 텐서

같은 텐서를 다른 SRAM 위치에 써야 한다.
- **모양**: `[A=2048, B=32]` (동일)
- **데이터 타입**: `f8`
- **메모리 배치**: `m![A, B]`
- **기준 주소**: `b = 256K` (다른 위치)

#### 해결 전략

`A` 차원을 두 세그먼트로 나눈다.
- **세그먼트 1**: `A % 1024` (앞 1,024 원소) = 1024 × 32 = 32 KB
- **세그먼트 2**: `A @ 1024` (뒤 1,024 원소) = 1024 × 32 = 32 KB

각 세그먼트도 여전히 슬라이스당 8 KB 보다 크므로, 더 쪼개거나 차원을 슬라이스에 분배해야 한다.
분할은 텐서를 하드웨어가 감당할 수 있는 조각으로 나누어 임의 크기의 텐서를 처리한다.

#### 처리

텐서를 두 번의 별도 실행으로 처리한다.

### 실행 #0
- fetch sequencer 출력
  - `Time = m![A % 1024]`
  - `Flit = m![B]`
  - fetch_size = 32 bytes
- Switch Engine 출력 (= commit unit 입력)
  - `Time = m![A % 1024]`
  - `Flit = m![B]`
- Commit Unit
  - commit_in_size = 32 bytes
  - 잘린 모양
    - `Time = m![A % 1024]`
    - `Flit = m![B]`
  - write sequencer 설정
    - `m![A, B]` -> `m![(A % 1024), B]`
    - Sequencer 설정: `[A%1024=1024:32, B=32:1] @ 256K / 32`
    - 매핑이 `m![A, B]` 인 출력 텐서 전체 중 앞 절반만 fetch 해 commit 한다.

### 실행 #1 (뒤 절반)

A 차원의 뒤 절반을 처리한다.
- **fetch sequencer 출력**:
  - `Time = m![A @ 1024]` - 시간 차원이 A 원소 1024-2047 을 담당한다
  - `Flit = m![B]` - B 차원 전체를 담은 32바이트 packet
  - fetch_size = 32 bytes
- **Switch Engine 출력**:
  - `Time = m![A @ 1024]` - A 의 뒤 절반에 대한 1,024 사이클
  - `Flit = m![B]` - 32바이트 flit
- **Commit Unit**:
  - commit_in_size = 32 bytes (full flit commit)
  - write sequencer 설정: `[A@1024=1024:32, B=32:1] @ (256K + 32 * 1024) / 32`
  - 기준 주소: `256K + 32KB` (첫 세그먼트를 건너뛰는 오프셋)
  - 주소 256K+32KB 부터 256K+64KB 까지 기록한다

#### 출력

두 실행이 모두 끝나면 출력 텐서가 재구성된다.
- **메모리 배치**: 주소 256K 부터 시작하는 SRAM 에 완전한 텐서 `[A=2048, B=32]` 가 담긴다
- **세그먼트 1**: 주소 256K 부터 256K+32KB 까지가 `A[0:1023, B[0:31]]` 을 담는다
- **세그먼트 2**: 주소 256K+32KB 부터 256K+64KB 까지가 `A[1024:2047, B[0:31]]` 을 담는다
- **결과**: 입력과 논리적으로 동일하며 저장 위치만 다르다

컴파일러가 분할 필요 여부를 자동으로 판단해 텐서를 여러 실행으로 쪼갠다. 프로그래머 관점에서는 단일 논리 연산이며 분할은 드러나지 않는다.

**이 예제가 유용한 이유:**
텐서 분할은 실제 딥러닝 작업 부하에 필수다.
- **큰 모델 지원**: 요즘 LLM 은 VRF 에 들어갈 수 없는 수십억 원소짜리 텐서를 가진다
- **자동 처리**: 컴파일러가 VRF 용량에 맞춰 분할을 자동으로 관리한다
- **잘 설계된 분할에는 성능 손해가 없다**: 세그먼트 경계가 메모리 접근 패턴에 맞으면 분할로 인한 오버헤드는 미미하다
- **확장성**: 이 메커니즘 덕분에 고정된 하드웨어에서 임의 크기의 텐서를 처리할 수 있다
- **메모리 계층 활용**: 분할은 계층적 메모리 시스템(VRF → SRAM → HBM)에 자연스럽게 대응된다
