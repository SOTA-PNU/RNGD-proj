# 메모리 성능

메모리 성능은 커널 처리량에 결정적이다.
Fetch, Commit, DMA Engine 은 각각 성능 결과에 직결되는 API 선택지(`Packet` 크기, 접근 순서 등)를 노출한다.
이 페이지는 그 선택지를 측정 처리량과 잇는 하드웨어 사양과 제약의 근거를 문서화한다.

각 메모리 종류는 칩당 최대 대역폭이 있다.

| 메모리 | 최대 대역폭 |
|--------|---------------|
| DM | 칩당 2 TB/s |
| SPM | 칩당 2 TB/s |
| HBM | 칩당 1.5 TB/s |

이 최대치에 도달하려면 특정한 접근 패턴이 필요하다.
다음 표는 어기면 처리량이 떨어지는 규칙을 나열하며, 아래 절들에서 각 메모리 종류와 요인을 자세히 설명한다.

| 메모리 | 문제 | 규칙 | 대가 |
|--------|-------|------|---------|
| DM | 뱅크 기아 | 같은 뱅크 연속 접근 64회 미만 | NoC 타임아웃 → 하드웨어 리셋 |
| DM | DMN 인터리빙 | 클러스터당 2개 DMN 을 번갈아 사용 | 대역폭 50% 손실 |
| DM | 슬라이스 인터리빙 | DMN 당 32개 슬라이스에 분산 | 커맨드 큐 경합 |
| HBM | 정렬 | 256바이트 정렬 접근 | 비정렬 읽기: 2× 대가, 비정렬 쓰기: 약 50× 대가(RMW) |
| HBM | 뱅크 충돌 | 같은 뱅크 안에서 행 전환을 피할 것 | 30–40× 성능 저하 |
| HBM | 채널 인터리빙 | 32개 채널에 분산 | 병렬성 감소 |


## Data Memory (DM)

Data Memory(DM)는 칩당 256MB 를 담으며, 클러스터, Data Memory Network(DMN), 슬라이스, 뱅크로 계층 구성된다.
다음 표는 그 구조를 요약한다.

| 단위 | 개수 |
|------|-------|
| 클러스터 | Chip 당 2 |
| Data Memory Network (DMN) | Cluster 당 8 |
| 슬라이스 | DMN 당 32 |
| 뱅크 | Slice 당 16 |
| 행 | Bank 당 4096 |
| 바이트 | Row 당 8 |

클러스터끼리는 Switch Engine 을 통해 데이터를 주고받을 수 있다.
자세한 내용은 [전용 절](../computing-tensors/switch-engine.md)을 보라.
아래 하위 절들은 이 구조가 대역폭과 뱅크 접근 제약을 어떻게 결정하는지 설명한다.

### 슬라이스 안의 뱅크 구조

각 슬라이스는 전용 주소 공간을 가진 512KB SRAM 을 제공한다.
메모리는 각각 데이터 폭 8바이트인 16개의 병렬 뱅크로 구성되어, 총 128 B/cycle 의 데이터 접근 속도를 낸다.
개별 뱅크 하나에 대한 접근은 직렬화되지만, 주소 공간이 연속된 128바이트를 16개 뱅크 전체에 (뱅크당 8바이트씩) 분산해 병렬 접근이 가능하다.
다음 비트 매핑이 이 분산을 정의한다.

| 비트 # | 구성 요소        |
|-------|------------------|
| `0–2`   | 바이트             |
| `3–6`   | 뱅크             |
| `7–18`  | 행              |

연속된 주소는 서로 다른 뱅크로 매핑되어, 순차 스캔 중에도 병렬 접근이 가능하다.

### DMN 과 슬라이스 인터리빙

각 DMN 은 128 B/cycle 의 대역폭만 제공한다(32개 슬라이스가 데이터 경로를 공유한다).
표준 전송 단위인 256바이트는 DMN 당 두 사이클이 필요하므로, 연속적인 처리량을 유지하려면 두 DMN 에 걸쳐 접근을 파이프라인화한다.

  | 사이클 | DMN #0  | DMN #1 |
  |-------|---------|--------|
  |   0   | 읽기 #0 (1/2) |    (유휴)   |
  |   1   | 읽기 #0 (2/2) | 읽기 #1 (1/2) |
  |   2   | 읽기 #2 (1/2) | 읽기 #1 (2/2) |
  |   3   | 읽기 #2 (2/2) | 읽기 #3 (1/2) |
  |  ...  |     ...      |     ...      |
  |  2n-1 | 읽기 #2n-2 (2/2)| 읽기 #2n-1 (1/2)|
  |  2n   |      (유휴)       | 읽기 #2n-1 (2/2)|

> [!NOTE]
> 이론적으로는 커맨드 큐가 인터리빙 없이도 어느 정도 버스트 접근을 허용하지만, DMA 스트림을 생성할 때는 항상 DMN 에 걸쳐 인터리빙하라. 그것이 가장 자연스러운 방식이다.

슬라이스는 DMA, Fetch, Commit Engine 이 공유하므로, 각 DMN 안의 32개 슬라이스에 요청을 분산하면 경합이 줄어든다.
Data Memory Router 가 각 DMN 안에서 그 슬라이스들을 링 토폴로지로 연결한다. slice0_in → slice31_out, slice32_in → slice63_out 이다.
각 Data Memory Slice 는 대기 중인 DMA 요청을 위한 2엔트리 커맨드 큐를 가진다.
요청을 M 개 슬라이스에 분산하면 우선순위 때문에 개별 슬라이스가 지연되더라도 슬라이스당 필요한 처리량이 1/M 로 줄어든다.
n 사이클마다 DMN 인터리빙을 하면 포화 상태인 256 B/cycle 을 달성한다.

### 뱅크 기아

뱅크 기아는 DMA Engine 이 더 높은 우선순위 엔진이 점유한 DM 뱅크를 기다리며 무기한 막힐 때 발생한다.
64회 접근 규칙이 이를 막는다.
이 규칙을 어기면 Network-on-Chip(NoC) 타임아웃과 클러스터 전체 리셋이 발생해 모든 연산 상태를 잃는다.

각 DM 뱅크는 공유 자원이다.
높은 우선순위 엔진이 그 뱅크에 계속 접근하면 낮은 우선순위 요청자가 무기한 막히는데, 이는 우선순위 역전의 한 형태다.
DM 컨트롤러는 요청 우선순위를 다음 순서로 매긴다.

- main 컨텍스트 Fetch Engine
- main 컨텍스트 Commit Engine
- sub 컨텍스트 Fetch Engine
- sub 컨텍스트 Commit Engine
- DMA Engine

정상 동작 중에는 연산 엔진이 데이터에 먼저 접근해야 하므로, DMA 는 모든 메모리 엔진 중 우선순위가 가장 낮다.
그러나 이는 높은 우선순위 엔진이 같은 뱅크에 계속 접근할 때 위험한 상황을 만든다. 높은 우선순위 엔진들이 그 뱅크를 독점하는 동안 DMA Engine 의 요청은 큐에 앉아 전진하지 못한다.
Tensor DMA 는 NoC 허브를 통해 DRAM 및 DMN 과 통신하는데, 각 포트(DMA, DRAM, DMN)는 4,096 사이클 안에 요청을 확인응답해야 한다.
응답 없이 4,096 사이클이 지나면 NoC 프로토콜은 그 트랜잭션을 죽은 것으로 선언하고 예외 상태로 들어간다. 데드락과 무기한 멈춘 트랜잭션을 검출하기 위한 안전 장치다.
타임아웃이 발동하면 하드웨어에는 우아한 복구 수단이 없다.
유일한 복구는 클러스터 도메인 전체 리셋이며, 모든 연산 상태를 잃고 완전한 재초기화가 필요하다.

64회 접근 규칙이 이 파국을 막는다. Fetch 와 Commit Engine 은 DMA 가 활성인 동안 같은 뱅크에 64회 이상 연속으로 접근해서는 안 된다.
왜 64인가?
제약은 `(TDMA_IO_BYTE / DMN_IO_BYTE) * Max_Consecutive_Access * DMN_SIZE < 4096` 이며(`TDMA_IO_BYTE = 256`, `DMN_IO_BYTE = 128`, `DMN_SIZE = 32`), 여기서 `Max_Consecutive_Access < 64` 가 나온다.
이는 최악의 경우에도 DMA 요청이 NoC 타임아웃 전에 완료되도록 보장한다.


예를 들어 DMA Engine 이 뱅크 0에 (다른 15개 뱅크와 함께) 요청을 내는데 main 컨텍스트의 Fetch Engine 이 뱅크 0을 계속 요청한다고 하자.
DMA 요청은 멈추고, 이것이 4,096 사이클을 넘으면 NoC 타임아웃이 하드웨어 리셋을 강제한다.

- **스케줄링 모델**: 스케줄러는 컨텍스트 점유 정보를 사용한다. 연산 A 가 어떤 컨텍스트(예: main 컨텍스트)를 점유하면, 그 컨텍스트를 쓰는 다음 연산 B 는 A 가 끝날 때까지 기다린다.
  어떤 연산이 어떤 컨텍스트를 점유하는지 이해하면 병렬 실행을 예측할 수 있다.
- **컴파일러 스케줄링 동작**: Tensor Unit 연산이 64회 접근 한도를 위반하게 될 때, 컴파일러는 그 연산이 DMA 를 점유하는 것처럼 스케줄링해 동시 DMA 연산을 막는다.
  이는 데이터 준비와 연산이 병렬로 일어나는 TCP 구조 고유의 main/sub/DMA 컨텍스트 병렬성을 희생하지만, 파국적인 하드웨어 리셋은 피한다.
  이를 강한 제약으로 다뤄라. 같은 뱅크를 64회 이상 연속 접근하는 패턴은 절대 쓰지 마라.
- **64회 접근 한도 세부사항**:
  - 이 한도는 누적이다. 같은 뱅크에 대한 모든 엔진의 접근 총합이 64 미만이어야 한다. 커맨드에 걸쳐 인터리빙된 접근조차 이 총합에 쌓이기 때문이다.
    예를 들어 main: 30, sub: 20, DMA: 1 은 합계 51(안전)이지만, main: 30, sub: 35, DMA: 1 은 합계 66(기아 유발)이다.
  - 컴파일러는 개별 커맨드 각각을 같은 뱅크 연속 접근 64회 미만으로 유지하지만, 여러 커맨드가 동시에 돌 때 총합이 64에 도달하는 것은 막지 못한다.
  - 실제로 sub 컨텍스트가 같은 뱅크에 연속으로 접근하는 일은 드물다(`StoTrf`, `StoVrf` 연산은 보통 순차 주소를 쓰고 타일링이 같은 뱅크 접근을 막는다).
  - 한도를 넘길 sub 컨텍스트 연산도 DMA 와 동시에 스케줄링되지 않는다.
- **main/sub 컨텍스트 경합**: main 컨텍스트가 sub 컨텍스트를 굶길 수 있으나, 이는 덜 심각하다.
  - DMA 기아와 달리 sub 컨텍스트 기아는 NoC 타임아웃이나 하드웨어 리셋을 일으키지 않고 처리 시간만 늘린다.
  - 충돌 확률이 더 낮다. DMA Engine 은 한 번에 16개 뱅크를 점유하지만 sub 의 fetch/commit 엔진은 뱅크 하나만 점유한다.
  - 같은 컨텍스트 안의 fetch 와 commit 엔진 사이에는 파이프라인 백프레셔 때문에 기아가 발생하지 않는다.
  - **성능 영향 예시**: main 컨텍스트의 exec 커맨드가 특정 뱅크에 계속 접근하는 동안 sub 컨텍스트의 stos 커맨드가 스케줄링되면 sub 컨텍스트 처리가 지연된다.
    최악의 경우: 총 시간 = main 컨텍스트 시간 + sub 컨텍스트 시간.
    이상적인 경우: main 과 sub 가 서로 다른 뱅크에 접근해 총 시간 = max(main 컨텍스트 시간, sub 컨텍스트 시간) 을 달성한다.

어떤 연산이 병렬로 도는지 보여주고 실제 컨텍스트 배정을 확인해 주는 스케줄링 시각화 도구는 [Schedule Viewer](../appendix/schedule-viewer.md) 를 보라.


## Scratchpad Memory (SPM)


DM 과 SPM 은 둘 다 온칩 SRAM 이다.
둘은 문서화된 지연이나 용량 차이가 아니라 *의도된 용도*(그리고 그에 따른 컴파일러 할당 정책)로 구분된다.

**DM (Data Memory)** 은 Tensor Unit 파이프라인을 흐르는 텐서 데이터의 주 작업 메모리다.
DMA Engine 이 HBM(또는 다른 계층)에서 DM 을 채우고, Fetch Engine 이 DM 에서 Tensor Unit 으로 데이터를 스트리밍하며, Commit Engine 이 파이프라인의 결과를 DM 으로 되쓴다.
DM 할당은 프로그램의 텐서 수명이 이끄는 범용 정책을 따른다.

**SPM (Scratchpad Memory)** 은 컴파일러가 관리하는 준비 계층이다.
컴파일러가 SPM 에 무엇을 둘지 명시적으로 고르며, 접근할 때마다 DM 에서 다시 가져오지 않아야 하는 작고 자주 재사용되는 값을 위해 예약한다.

- 스칼라 상수와 설정 데이터,
- 활성함수 룩업 테이블,
- 여러 번 읽히는 DMN 별 소규모 작업 집합.

SPM 은 그렇지 않았다면 Fetch 나 DMA Engine 을 통해 DM 을 반복해서 읽게 만들 DMN 별 상태에 가장 유용하다.

DM 과 SPM 은 둘 다 Tensor Unit 의 연산 엔진에 직접 데이터를 공급하는 슬라이스별 **레지스터 파일**과는 구별된다([Computing Tensors](../computing-tensors/index.md) 참고).

- **TRF (Tensor Register File)** 는 [`.to_trf()`](../computing-tensors/collect-engine.md#to-trf) 로 채워지는 슬라이스별 레지스터 파일이며, Contraction Engine 이 매 사이클 읽는다.
- **VRF (Vector Register File)** 는 [`.to_vrf()`](../computing-tensors/collect-engine.md#to-vrf) 로 채워지는 슬라이스별 레지스터 파일이며, Vector Engine 이 매 사이클 읽는다.

따라서 파이프라인의 데이터 흐름은 이렇다. DMA 가 HBM 에서 **DM** 을 채우고 → Fetch 가 DM 에서 Tensor Unit 으로 데이터를 스트리밍하고 → Collect 가 그 스트림을 **TRF / VRF** 에 쓰고 → Contraction / Vector 가 TRF / VRF 에서 직접 읽고 → Commit 이 결과를 DM 으로 되쓴다.
**SPM** 은 커널이 필요로 하지만 다시 가져오고 싶지는 않은, 작고 지역성 높은 데이터를 위한 컴파일러 제어 준비 영역으로 옆에 자리한다.

각 DMN 은 128 B/cycle 대역폭의 SPM 을 담고 있으며, DMN 마다 전용 SPM 이 있으므로 DMN 간 경합 문제는 없다.


## High-Bandwidth Memory (HBM)

HBM 은 칩당 48GB 를 담고 총 1.5 TB/s 대역폭을 내지만, 그 최대치에 도달하려면 256바이트 정렬 접근과 32개 채널 전체에 걸친 채널 인터리빙이 필요하다.
비정렬 쓰기와 뱅크 충돌은 처리량을 30–50× 떨어뜨릴 수 있다.
다음 표는 HBM 의 구조를 요약한다.

| 단위 | 개수 |
|------|-------|
| 스택 | Chip 당 2 |
| 채널 | Stack 당 16 |
| 슬라이스 | Channel 당 3 |
| 뱅크 그룹 | Slice 당 4 |
| 뱅크 | Bank Group 당 4 |
| 행 | Bank 당 16K |
| 바이트 | Row 당 2K |


### 최대 대역폭

DMA Engine 하나(256GB/s 용량)를 포화시키려면 여러 채널에 걸쳐 접근을 인터리빙해야 한다.
HBM 최대 대역폭은 스택과 채널의 병렬 동작을 통해 칩당 1.5TB/s 에 이른다.
채널 컨트롤러는 0.75GHz 에서 64B/cycle 을 전송하며,[^HBM] 이는 채널당 48GB/s(0.75GHz x 64B/cycle) 또는 칩당 1.5TB/s(48GB/s x 32 채널)를 낸다.
기본 전송 단위는 256바이트이며, 채널당 4 클럭 사이클이 필요하다.

[^HBM]: 채널 컨트롤러는 0.75GHz 주파수로 동작하지만 사이클당 8회 버스트를 수행하므로 실효 주파수는 0.75×8=6GHz 가 된다.

최대 대역폭은 접근 패턴에 민감하다.
비정렬, 뱅크 충돌, 자원 공유는 각각 처리량을 심하게 떨어뜨릴 수 있다.
각 채널 컨트롤러는 대가를 최소화하도록 접근을 인터리빙하는 64엔트리 커맨드 큐를 갖지만, 병적인 경우에는 여전히 심각한 성능 저하가 일어난다.
다음 절들은 성능 저하의 원인과 피하는 방법을 설명한다.


### 칩 안의 주소 공간

HBM 주소 공간은 병렬 순차 접근에 최적화된 비선형 비트 매핑을 사용한다.
이 설계는 병렬성을 최대화하고 오버헤드를 최소화한다.

| 비트 # | 주 구성 요소   | 추가 구성 요소 |
|-------|------------------|--------|
| 0–7   | 바이트             |        |
| 8     | 스택            |        |
| 9–12  | 채널 |        |
| 13    | 뱅크 그룹 | 채널 |
| 14–16 | 바이트 | 채널           |
| 17–18 | 뱅크 | 채널           |
| 19    | 뱅크 그룹 | 채널     |
| 20    | 슬라이스 | 채널           |
| 21–33 | 행 | 채널 (21–28)         |
| 34    | 슬라이스     | 행 |
| 35    | 행              | |

각 구성 요소의 비트 배정은 물리 메모리 구조에 대응한다.
예를 들어 바이트 구성 요소는 행당 2K(2^11) 바이트를 나타내기 위해 11비트(비트 0-7, 14-16)를 차지한다.
세 가지 예외가 있다.

- **슬라이스 표현**: 슬라이스는 셋뿐인데도 두 비트(20과 34)가 슬라이스를 나타낸다.
- **연속 주소 공간**: 비트 34는 행 구성 요소의 영향을 받아 비트 34와 35가 동시에 1이 되지 않도록 보장하며, 이로써 연속된 48GB 주소 공간이 보장된다.
- **채널 XOR 매핑**: 채널 구성 요소는 비트 9-12 와 13-28 의 XOR 과 같다(예: 채널의 첫 비트는 비트 9, 13, 21, 25 의 XOR 과 같다).

이 비트 순서는 순차 접근이 스택, 채널, 뱅크 그룹, 뱅크에 동시에 분산되도록 하여 여러 메모리 자원을 병렬로 바쁘게 유지한다.


### 비정렬 접근

비정렬 접근은 HBM 성능을 크게 떨어뜨린다.
256바이트 경계를 넘는 읽기는 두 번의 전송이 필요하고(2x 대가), 비정렬 쓰기는 Read-Modify-Write(RMW) 연산이 필요하다(대략 50x 대가).
256바이트 최소 접근 단위는 비트 0-7(하위 8비트)로 정의되므로, 이 경계를 넘는 데이터는 이런 대가를 치른다.

- **비정렬 읽기**: 256바이트 경계를 넘는 읽기 요청은 두 번의 NoC 전송이 필요해 사실상 대역폭이 절반이 된다.
- **비정렬 또는 부분 쓰기**: 비정렬 쓰기는 DMA 패킷이 내부적으로 256바이트 트랜잭션으로 쪼개지기 때문에 발생한다.
  패킷 크기가 256바이트 정렬이 아니면(예: 2,800바이트 패킷은 256바이트 요청 10개와 240바이트 요청 1개로 나뉜다), 마지막 "남은" 트랜잭션에 RMW 연산이 필요하다.
  RMW 는 256바이트 단위 전체를 읽고, 요청된 바이트를 갱신한 뒤, 단위 전체를 되쓴다.
  RMW 는 정렬된 쓰기에 비해 쓰기를 대략 50× 느리게 만들 수 있다.


### 뱅크 충돌

HBM 뱅크는 한 번에 열린 행 하나만 유지한다.
같은 뱅크 안에서 다른 행으로 전환하려면 현재 행을 닫고 새 행을 열어야 한다.
이는 40-50 ns(1.5 GHz 에서 60-75 사이클)의 지연을 더하며, 이미 열린 행에 접근하는 것보다 30-40x 느리다.
이 대가는 연속된 접근이 같은 뱅크 안의 서로 다른 행을 향할 때마다 발생한다.
모든 행은 닫힌 상태로 시작하므로, 어떤 행이든 첫 접근은 항상 행 열기 비용을 치른다.

채널 인터리빙은 뱅크 충돌을 완화한다.
32개 채널 전체에 접근을 인터리빙하면 부하가 분산되고 충돌이 줄어든다.
비트 8-12(그다음 하위 5비트)는 독립적인 스택과 채널을 나타낸다.
이들을 낮은 주소에 두면 인접한 접근끼리의 간섭이 방지되며, 이는 연속된 연산을 병렬화하는 데 필수적이다.
채널 구성 요소가 비트 9-28 에 걸쳐 있으므로, 비연속 연산은 자연스러운 채널 인터리빙의 이득을 보는 경우가 많다.
그러나 스택 구성 요소는 비트 8 에만 대응하므로, 완전한 스택 인터리빙을 얻으려면 프로그래머가 접근이 두 스택을 번갈아 향하도록 명시적으로 보장해야 한다.

컨트롤러는 커맨드 인터리빙으로 행 전환 지연을 감춘다.
각 채널 안에서 컨트롤러는 뱅크에 걸쳐 커맨드를 자동으로 인터리빙하여, 다른 뱅크가 행 전환을 수행하는 동안에도 쓸모 있는 전송이 가능하게 한다.
컨트롤러는 커맨드 큐를 사용해 뱅크 상태를 관리한다.
FR-FCFS(First Ready-First Come First Served) 스케줄링을 쓰며, 이미 열린 행을 향하는 커맨드를 우선한다.

이런 정교한 스케줄링에도 불구하고, 같은 뱅크 안에서 행을 계속 전환하는 접근 패턴은 여전히 성능을 크게 떨어뜨린다.
컴파일러와 프로그래머는 코드를 생성할 때 행 전환 비용을 추정해야 한다.


### Column-to-Column Delay

`tCCD`(Column-to-Column Delay)는 같은 채널에서 연속된 읽기 또는 쓰기 커맨드 사이의 최소 시간이며, 최대 커맨드 발행률을 결정한다.
대부분의 접근 패턴에서는 `tCCD` 가 병목이 되기 전에 뱅크 충돌이나 채널 인터리빙이 먼저 지배한다.
벤더 사양은 `DRAM` 스택 층과 공유 자원 접근에 대한 아날로그 제약에 근거해 `tCCD` 값을 정한다.

`tCCD` 값은 연속된 커맨드가 어떤 메모리 자원을 향하는지에 달렸다.

| 커맨드 관계 | `tCCD` (`1.5GHz` 기준 사이클) | 상대 성능 | 대가의 이유 |
|-----------|----------------------|------------|--------|
| 같은 슬라이스, 다른 뱅크 그룹 | `2` | `1` | 뱅크 그룹의 이상적인 인터리빙 |
| 다른 슬라이스 | `3` | `2/3` | 데이터 경로 전환 |
| 같은 슬라이스, 같은 뱅크 그룹 | `4` | `1/2` | 네 뱅크가 I/O 버퍼를 공유 |

최적의 경우는 같은 슬라이스 안에서 서로 다른 뱅크 그룹 사이를 인터리빙하는 것으로(`1.5GHz` 에서 `tCCD = 2` 사이클), `0.75GHz` 에서 매 사이클 새 `64B` 커맨드를 발행할 수 있어 연속 전송과 채널 전속을 달성한다.
`2` 보다 큰 `tCCD` 는 커맨드 발행률과 채널 활용률을 낮춘다.

뱅크 충돌에 비하면 `tCCD` 로 인한 성능 저하는 덜 심각하다. 최악의 패턴이 뱅크 충돌과 겹치거나(이 경우 `tCCD` 는 부차적 효과다) 채널 인터리빙에 가려지기 때문이다.

- 다른 슬라이스(`tCCD = 3`): 슬라이스 ID 는 비트 `20` 에 대응하고 비트 `21` 은 행에 대응한다.
  따라서 슬라이스에 걸쳐 인터리빙하면 뱅크 충돌도 동시에 일으키기 쉽다.
- 같은 슬라이스, 같은 뱅크 그룹(`tCCD = 4`): 이 패턴은 비트 `13`, `19`, `20`, `34` 를 제외한 비트 `8-35` 를 인터리빙한다.
  비트 `29-35` 는 뱅크 충돌과 관련된다.
  비트 `8-28` 은 채널 인터리빙과 관련된다.
