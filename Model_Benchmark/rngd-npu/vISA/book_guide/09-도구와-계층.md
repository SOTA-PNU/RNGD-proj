## 0. 계층 한눈에 보기

| 계층 | 표현 도구 | 배치 어휘 | 덤프/계측 | 산출물 |
|---|---|---|---|---|
| **인터칩** | TCL (`furiosa-tcc`, `furiosa.tcl` eDSL) | `layout={Chip, Cluster, Split}` | **없음** | 단일 `.edf` 바이너리 |
| **슬라이스 내부(vISA)** | Rust `furiosa-opt-std` + `cargo furiosa-opt` | `Slice / Lane / Packet / TRF / VRF / commit` | `--dump-{visa,ir,schedule,graph,summary}` | `pkg::mod::fn.{bin,edf,hash}` |

핵심 경계(실측): TCL 공개 API 의 배치 어휘는 `Chip/Cluster/Split` 이 전부다.
`Slice`·`Lane`·`Packet`·`TRF`·`VRF` 같은 슬라이스 내부 데이터패스 어휘는 **vISA(Rust)에만** 있다.
근거: `_GROUND_TRUTH.md:37-42`, `furiosa/tcl/_lang/_context.py:79-113`.

## 1. `cargo furiosa-opt` — 무엇인가

### ① 책이 뭐라 하나
`cargo` 를 감싸는 얇은 래퍼. `cargo` 를 쓸 자리에 `cargo furiosa-opt` 를 쓰면 인자가 그대로 통과되고,
래퍼가 백엔드를 고르고 필요한 커널을 빌드한다(`appendix__cargo-furiosa-opt.md:3-4`).

### ② 우리 코드/환경 대응
- 래퍼 실체: `~/.cargo/bin/cargo-furiosa-opt`, 드라이버: `~/.cargo/bin/furiosa-opt-driver`(실측 `ls`).
- `cargo-furiosa-opt --version` → `cargo-furiosa-opt 0.3.0` 을 출력하지만 **바이너리는 0.4 세대**다
  (md5 가 로컬 v0.4.0 타르볼과 동일, `_GROUND_TRUTH.md:4-6`). **버전 문자열로 세대를 판단하지 말 것.**

### ③ 쉬운 설명
`cargo build/test/run` 앞에 `cargo furiosa-opt` 를 붙이면, 평소 cargo 흐름은 그대로 두고
그 옆에서 "이 빌드가 필요로 하는 `#[device]` 커널"을 대신 컴파일해 주는 도구다.

### ④ 함정
- `--version` 은 0.3.0 이라 착각을 부른다. **가능 백엔드 목록으로 세대를 확인하라**(아래 1.1).

### 1.1 top-level 실측 `--help` (요지)
```text
Usage: cargo furiosa-opt [OPTIONS] <COMMAND>
Commands:  compile, help
Options:
  --backend <BACKEND>   # 서브커맨드 앞에 준다
      Possible values:
        - typecheck : 매핑/셰이프만 검증, 값 계산 안 함
        - emulation : Npu 물리 버퍼 저장소 위에서 호스트 CPU 로 커널 실행
        - npu       : 컴파일된 커널을 NPU 에서 실행
      [default: emulation]
ENVIRONMENT:
  FURIOSA_OPT_OUT_DIR   # 커널 출력 디렉터리 (default: <workspace target>/furiosa-opt/kernel)
```
출처: 실측 `cargo furiosa-opt --help`(이 서버, 2026-07 기준).

> **책과의 결정적 차이** — 이 표를 외워라:
>
> | 항목 | 책(`appendix__cargo-furiosa-opt.md`) | 우리 래퍼(실측) |
> |---|---|---|
> | 기본 백엔드 | `simulation`(35행) | **`emulation`** |
> | 가능 백엔드 | typecheck / simulation / emulation / npu (39-42행) | **typecheck / emulation / npu** (`simulation` 없음) |
>
> 즉 `--backend simulation` 은 **이 서버에서 거부**된다(`simulation` 은 0.2/0.3 시절 이름). `_GROUND_TRUTH.md:7-8` 참고.
> 커리큘럼 CHEATSHEET(v0.2.0)이 `simulation(기본)` 이라 적은 것(`CHEATSHEET.md:23`)도 현재 래퍼엔 안 통한다.

### 1.2 백엔드 4종의 쓰임 (NPU 필요 여부)
| 백엔드 | 하는 일 | NPU | 이 서버에서 |
|---|---|---|---|
| `typecheck` | 타입 레벨 매핑/셰이프 검증(값 루프는 팬텀 텐서로 단락) | ❌ | OK |
| `emulation` (기본) | NPU 디바이스 경로를 호스트에서 시뮬 | ❌ | OK |
| `npu` | 실제 카드로 디스패치, 자동 커널 컴파일 트리거 | ✅ | **실기 검증됨** — 격리 테스트 89개 실행 / 80 PASS |

출처: 실측 `--help`, `appendix__cargo-furiosa-opt.md:39-42`, 실기는 [13-NPU-실기-매트릭스](./13-NPU-실기-매트릭스.md).
`typecheck`/`emulation` 은 카드 없이 돌아가므로 이 문서의 계측 예시는 이 둘 + `compile`(카드 불필요) 을 쓴다.

> **`--backend npu` 의 진짜 제약은 카드 점유가 아니라 "빌드 단위"다 (실기 실행 결과)**
>
> `--backend npu` 는 패키지 안의 ***모든*** `#[device]` 함수를 빌드 시점에 EDF 로 낮춘다.
> 테스트가 그 함수를 부르든 말든 무관하고, **하나라도 못 낮추면 크레이트 전체가 죽는다.**
> ```text
> # 벤더 예제 크레이트를 그대로 --backend npu test (실측 로그 ex_logs/npu.log)
>    Compiling [207/207] vrf_add_segmented::vrf_add_segmented
>     Finished 207 compiled, 0 filtered out
> error: could not compile `furiosa-opt-examples` (lib) due to 63 previous errors
> # → 테스트 0개 실행
> ```
> - **커널 필터는 `compile` 에만 있다. `test`/`build` 엔 없다.**
>   `--test <bin> -- --exact <test>` 로 테스트를 1개로 좁혀도 커널은 패키지 전량이 컴파일된다
>   (게이팅 크레이트 실측: `--backend npu test` 는 테스트 선택과 무관하게
>   `Finished 143 compiled, 0 filtered out` — `ex_logs/gated_npu_run.log:565`).
> - 우회는 실패 커널만 `#[cfg(not(backend = "npu"))]` 로 게이팅하는 것. 레시피는
>   [12-예제-전수실행](./12-예제-전수실행.md), 실기 결과는 [13-NPU-실기-매트릭스](./13-NPU-실기-매트릭스.md).

### 1.3 통과(passthrough) 형태
```bash
# 백엔드는 반드시 서브커맨드 "앞"에 온다 (뒤 인자는 전부 cargo 로 통과)
cargo furiosa-opt --backend typecheck run --release --bin gemm
cargo furiosa-opt test --test mnist_tests            # 기본 emulation
```

**함정**: 우리 예제 `/home/jun/yik` 는 `default-run` 이 없어 `run` 시 `--bin <이름>` 을 안 주면
cargo 가 "could not determine which binary" 로 죽는다(`_GROUND_TRUTH.md:19`). 5개 bin: `constant_add / elementwise_mul / dot_product / gemv / gemm`.

## 2. `cargo furiosa-opt compile` — 직접 컴파일 + 덤프

### ① 책이 뭐라 하나
`#[device]` 함수를 cargo 통과 없이 직접 커널로 컴파일한다. 항상 NPU 커널을 만들므로 `--backend` 를 받지 않는다
(`appendix__cargo-furiosa-opt.md:63-67`). 단일 커널을 컴파일하며 스케줄을 덤프하는 것이 대표 용례다.

### ② 우리 코드/환경 대응
실측 `cargo furiosa-opt compile --help`:
```text
Usage: cargo furiosa-opt compile [OPTIONS] [FILTER]...
Arguments:
  [FILTER]...  #[device] 이름에 대한 부분일치 필터. 비우면 전부
Options:
  -p, --package <NAME>        컴파일할 패키지(비우면 모든 커널 패키지)
      --dump-visa <FILE>      중간 vISA 를 파일로 덤프
      --dump-ir <FILE>        중간 LIR 을 파일로 덤프
      --dump-schedule <FILE>  스케줄을 JSON 으로 덤프
      --dump-graph <FILE>     IR 그래프를 JSON 으로 덤프
      --dump-summary <DIR>    컴파일 요약을 디렉터리로 덤프
      --message-format <FMT>  진단 포맷(예: json)
```
출처: 실측 `cargo furiosa-opt compile --help`(이 서버).

> **책엔 덤프가 2개뿐**(`--dump-visa`, `--dump-schedule`; `appendix__cargo-furiosa-opt.md:97-107`)이지만
> **우리 래퍼엔 5개**다: `--dump-visa / --dump-ir / --dump-schedule / --dump-graph / --dump-summary`.
> `_GROUND_TRUTH.md:41-42` 와 일치. 책만 보고 "덤프는 vISA/스케줄뿐"이라 결론 내리지 말 것.

### ③ 쉬운 설명
`compile` 은 "카드에 올리기 전 컴파일러 내부 상태를 파일로 토해내는" 계측 도구다.
카드를 잡지 않고도(NPU 점유 없이) 커널 하나의 vISA·중간표현·**사이클 단위 스케줄**을 볼 수 있다.

### ④ 함정
- `--dump-*` 는 **단일 커널일 때만** 의미가 있다(책도 "Should only be used when compiling a single kernel"라 명시, `appendix__cargo-furiosa-opt.md:100,106`).
  필터로 커널을 하나로 좁혀라. 이름이 모호하면 풀 경로를 쓴다: 예 `kernel::gemm_kernel::gemm_kernel`(`appendix__schedule-viewer.md:40`).
- **`<FILTER>` 는 부분문자열 매칭이다 — 풀 경로를 줘도 "하나로 좁혀지지 않는다"** (실측 함정).
  이름이 다른 커널의 **접두사**면 그 커널까지 함께 컴파일되고, **에러도 그 커널 것이 섞여 나온다**:
```text
$ cargo furiosa-opt compile -p furiosa-opt-examples "switch_assertions::inter_transpose::invalid_time0"
   Compiling [3/3] switch_assertions::inter_transpose::invalid_time0_mismatch
error: furiosa-opt: switch_assertions::inter_transpose::invalid_time0_mismatch: visa: internal compiler error: ...
    Finished 3 compiled, 204 filtered out        ← 1개가 아니라 3개가 잡혔다
```
  `invalid_time0` 을 지정했는데 `invalid_time0_mismatch`·`invalid_time0_size` 까지 3개가 선택됐고,
  **지정한 `invalid_time0` 자체는 컴파일에 성공한다**(에러는 남의 것).
  - 접두사 충돌 후보: 소스에서 추출한 커널 200개 중 **8개**(이 값은 커널 목록으로 재확인함).
  - **커널별 컴파일을 스크립트로 돌릴 때 규칙**: "출력에 error 가 있으면 FAIL" 은 틀린다.
    에러 줄이 `error: furiosa-opt: <정확한 커널명>:` 로 **그 커널을 지목할 때만** FAIL 로 집계하라.
    실제로 이 규칙 없이 집계했다가 판정 1건이 오염됐다([13-NPU-실기-매트릭스](./13-NPU-실기-매트릭스.md) §7.4).
  - **덤프에도 같은 함정**: 필터가 2개 이상을 잡으면 덤프가 어느 커널 것인지 보장되지 않는다(책도 단일 커널 전제).
    → `Finished N compiled` 의 **N 이 1 인지 확인**하는 습관을 붙여라.
  - 위 출력의 `3 + 204 = 207` 은 **툴 자체의 커널 집계**(제네릭 단형화 포함)다. 소스 텍스트 추출 **200**,
    게이팅 후 실기 빌드 **143** 과 서로 다른 정당한 수다 — 맞추려 하지 말 것.
- **target 오염 주의**: 덤프든 실기든 `CARGO_TARGET_DIR` 를 작업용 별도 경로로 지정하고
  사용자 프로젝트 target 을 오염시키지 말 것(실기 매트릭스 130건 덤프 + 89건 실행에서 지킨 규칙:
  `CARGO_TARGET_DIR=target_sched` / `target_npu`). 커널 산출물 기본 위치는 `FURIOSA_OPT_OUT_DIR`(기본 `<target>/furiosa-opt/kernel`).
- `/home/jun/yik` 는 `furiosa-opt-std="0.3"` 핀 + 구식 `src/furiosa-opt.tag` 마커라, 현재 래퍼는
  `[package.metadata.furiosa-opt]` 를 요구해 **"no kernel packages found"** 로 커널 컴파일을 거부한다
  (`_GROUND_TRUTH.md:9-16`). 즉 `yik` 는 `compile`/`--backend npu` 가 지금 그대로는 안 되고, `typecheck`/`emulation` 만 된다.

### 2.1 덤프 옵션별 용도(실측 설명 기준)
| 옵션 | 무엇을 덤프 | 형식(실측 산출물) | 주 용도 |
|---|---|---|---|
| `--dump-visa <FILE>` | 중간 **vISA** | 텍스트 — **Rust `Debug` 포맷**(어셈블리 리스팅 아님, 2.4.1) | 컴파일러가 만든 슬라이스 내부 명령 확인 |
| `--dump-ir <FILE>` | 중간 **LIR** | 텍스트(LIR) | 로우레벨 IR(스케줄 직전) 확인 |
| `--dump-schedule <FILE>` | **스케줄** | JSON | Schedule Viewer 입력, 사이클/병렬성 분석 |
| `--dump-graph <FILE>` | **IR 그래프** | JSON (`tensors`/`operators`/`inputs`/`outputs`/`hidden_outputs`) | 텐서/오퍼레이터 연결 구조 |
| `--dump-summary <DIR>` | **컴파일 요약** | 디렉터리 — 파일 **20개**(2.4.2) | 리소스/사이클 요약 묶음 |

주의: `--dump-ir` 의 실측 도움말은 "intermediate **LIR**"라고 명시한다(단순 "IR"이 아님). 위 표의 "무엇을 덤프"는 실측 도움말 문구 그대로다.

**실적용 범위**: 5종 **전부** 산출물을 만들어 봤다. `--dump-schedule` 은 커널 130개(2.3),
나머지 4종은 `mnist::forward` 1개로 한 번에(2.4). 덤프 쪽에 남은 미확인은
`--dump-ir` 텍스트의 내부 문법과 `summary.json` 의 일부 스케줄러 키 의미뿐 — [12절](#12-미확인으로-남긴-것) 참고.

### 2.2 예시 — 실측 (yik 로는 여전히 컴파일 불가, 벤더 예제 크레이트로 실행)

출처: `appendix__cargo-furiosa-opt.md:76-78`, `appendix__schedule-viewer.md:34-41`, 실측 `sched_scan.sh`(11.1).

### 2.3 `--dump-schedule` 산출물 — 실측 스키마 (커널 130개)

**이 덤프는 AOT 컴파일러 산출물이라 NPU 를 점유하지 않는다.** 실기 테스트가 카드를 쓰는 동안에도
130개 커널 덤프를 **병행 실행**했다(실측). 즉 "사이클 단위 계측 = 카드 필요"는 사실이 아니다.

> **값의 성격을 섞지 말 것**: 아래 사이클 수는 **컴파일러의 스케줄 모델 예측**이다.
> 카드에서 측정한 실행 시간이 아니다. 실기 실행 결과(통과/실패/HAL 에러)는
> [13-NPU-실기-매트릭스](./13-NPU-실기-매트릭스.md).

JSON 최상위 키(실측): `title`, `total_memory`, `page_size`, `instructions`, `tensors`

| 경로 | 내용 (실측 `mnist::forward`) |
|---|---|
| `total_memory` / `page_size` | `268435456` / `16777216` |
| `instructions[].tpe` | 인스트럭션 종류(130개 전체 집합 11종): `DmaLoad`·`DmaStore`·`DmaDtod`·`DmaGather`·`DmaScatter`·`DmaStos`·`DmaOther`·`DmaInterChip`·`Core`·`Sub`·`Main` (`mnist::forward` 는 `DmaLoad/DmaStore/Core/Main/Sub` 5종) |
| `instructions[].contexts` | 실행 엔진: `DmaEngine`·`PeCore`·`MainContext`·`SubContext`·`VectorEngine`·`InterChipTransfer`, 그리고 `Noop` — 엔진이 아니라 **스팬 0(`begin==end`) 인스트럭션의 표식**이다(130개 전체 116건, 전부 `tpe:"Sub"`·전부 스팬 0. `mnist::forward` 에선 `reshape()` 4건). `tpe` 값이 아니니 혼동 금지 |
| `instructions[].lifetime.{begin,end}` | **사이클 단위 점유 구간** → 커널 스팬 = `max(end)` |
| `instructions[].description` | **소스 위치가 그대로 들어있다**: `--> furiosa-opt-examples/src/mnist/mod.rs:14:66` + `weight.to_dm(&mut ctx.tdma)` |
| `instructions[].util` | `total_util` / `base_util` / `efficiency` |
| `tensors[]` | `name, index, buffer_type(Sram/Trf/Vrf), lifetime, address, size, physical_pages, shape, fingerprint` |

→ **Schedule Viewer 없이도 이 JSON 만으로 엔진별 사이클 분해가 된다.** 뷰어는 이 서버 미설치(4절)지만
그것이 사이클 분석의 차단 사유는 아니다. 분해 스크립트는 11.1 의 `sched_analyze.py`.

기준점(분석기 검증용): `mnist::forward` = **17,953 cycle / 22 instruction**
(`DmaEngine` 12,365 = 68.9%, `MainContext` 7,682, `VectorEngine` 1,162, `SubContext` 790, `PeCore` 600).
→ [11-MNIST-실행결과](./11-MNIST-실행결과.md) 에 독립적으로 기록된 수치와 **정확히 일치**한다.

커널 130개 합산 결론(스케줄 모델): **총 사이클의 96.5%가 `DmaEngine`**(75,464,336 cycle / 인스트럭션 470개),
`PeCore` 는 인스트럭션이 1,557개로 최다인데 3.3%. 커널별로도 DMA 비중 **중앙값 82.8%**.
분포·해석·최적화 함의는 [13-NPU-실기-매트릭스](./13-NPU-실기-매트릭스.md) §4 참고(여기서 중복하지 않는다).

### 2.4 나머지 4종 덤프 산출물 — 실측 (`mnist::forward`)

한 번의 컴파일로 4종을 동시에 뽑았다. **NPU 미점유**(AOT 컴파일러 산출물).
```bash
cargo furiosa-opt compile -p furiosa-opt-examples "mnist::forward" \
    --dump-summary /tmp/dsum --dump-visa /tmp/dvisa.txt \
    --dump-graph /tmp/dgraph.json --dump-ir /tmp/dir.txt
#   Finished 1 compiled, 206 filtered out     ← N=1 확인(2절 ④ 규칙)
```

| 옵션 | 산출물 | 크기(`mnist::forward`) | 형식 |
|---|---|--:|---|
| `--dump-visa` | 텍스트 1파일 | 49,901 B | **Rust `Debug` 포맷** (2.4.1) |
| `--dump-graph` | JSON 1파일 | 37,987 B | 최상위 키 `tensors` / `operators` / `inputs` / `outputs` / `hidden_outputs` |
| `--dump-ir` | 텍스트 1파일 | 52,125 B | LIR 텍스트 (내부 문법은 미확인 — 12절) |
| `--dump-summary` | 디렉터리 | 파일 **20개** | 2.4.2 |

#### 2.4.1 `--dump-visa` 는 vISA 어셈블리 리스팅이 **아니다** (기대치 조정)

이름만 보면 명령 리스팅을 기대하지만, 실제 산출물은 컴파일러 내부 구조체를 Rust `Debug` 로 찍은 것이다:
```text
Program { functions: {"mnist::forward": Function { params: [Tensor(TensorDecl {
    var: TensorVar(0), shape: MappingShape { ...
```
- 한 줄이 극단적으로 길고 사람이 훑기에 부적합하다. `grep` 으로 심볼을 찾는 용도로 쓰고,
  "명령 순서를 눈으로 읽는" 작업은 `--dump-schedule`(2.3, 사이클·소스 위치 포함)로 하는 게 맞다.
- 안정된 텍스트 포맷이 아니라 `Debug` 출력이므로 **파서를 붙이지 말 것**(래퍼 버전에 따라 바뀔 수 있다).

#### 2.4.2 `--dump-summary` 디렉터리 구성 — 파일 20개 (실측)

```text
summary.log                          # 사람이 읽는 사이클 요약
summary.json                         # 같은 내용 + 스케줄러 내부 통계

json/lir_ir_viewer.json

```
- **`sfr/` 가 명령 단위 레지스터 설정까지 노출한다.** SFR = Special Function Register, 커널 명령마다 1파일:
```yaml
---
fetch_unit:
  mode_indirect_table:
    bytes:
      - 0
      - 0
```
- **`json/lir_ir_viewer.json` 과 `fir/lir.fir` 가 [OPTIMIZATION-SURFACE](./OPTIMIZATION-SURFACE.md) L2 #8 이
  말한 `*_ir_viewer.json` / `.fir` 덤프다** — 스케줄 휴리스틱 힌트를 뒤집고 diff 를 뜨는 창구가 여기다.
- `summary.log` 의 사이클 요약은 `--dump-schedule` 보다 항목이 세분돼 있다(`total_instruction_cycle`
  vs `total_execution_cycle`, `*_only`). **이것도 컴파일러 산출물이고 실기 실행 측정이 아니다.**
  수치와 해석은 [07-스케줄링](./07-스케줄링.md) 참고(여기서 중복하지 않는다).

```jsonc
// VSCode settings.json (책 예시, appendix__language-server.md:22-26)

```

### ③ 쉬운 설명

## 4. Schedule Viewer — 스케줄 시각화

### ① 책이 뭐라 하나
`--dump-schedule` 로 만든 스케줄 JSON 을 불러 **실행 타임라인**으로 보여주는 로컬 웹 UI.
어떤 연산이 병렬로 도는지, 각 연산이 어느 컨텍스트/리소스를 점유하는지, 무엇이 파이프라인을 막는지를 본다
(`appendix__schedule-viewer.md:2-5`).

### ② 우리 환경 대응
- 실측: 이 서버엔 `furiosa-schedule-viewer` 도 **설치 안 됨**(`~/.cargo/bin` 에 없음). 필요하면 `cargo install furiosa-schedule-viewer`.
- 실행:
```bash
furiosa-schedule-viewer                       # 기본 127.0.0.1:9254, 브라우저 자동 오픈
furiosa-schedule-viewer --host 127.0.0.1 --port 9254
```
출처: `appendix__schedule-viewer.md:12-27`.
- 입력 생성(카드 불필요): `cargo furiosa-opt compile <device-fn> --dump-schedule <json>`(`appendix__schedule-viewer.md:34-37`).

### ③ 쉬운 설명
파이프라인 뷰어다. 노드를 클릭하면 이름/수명(lifetime)/컨텍스트/연결 노드가 왼쪽에 뜨고,
오퍼레이터를 고르면 그 입출력 텐서가, 텐서를 고르면 연결된 오퍼레이터가 강조된다(`appendix__schedule-viewer.md:48-55`).
사이클 범위 드래그로 확대, **Enable Brush** 로 사이클+메모리주소 범위를 함께 좁혀 특정 구간을 파고든다(`appendix__schedule-viewer.md:57-64`).

### ④ 함정
- 뷰어의 텐서/오퍼레이터는 **실제 하드웨어 명령 기준**이라, vISA 소스에 적은 텐서/오퍼레이터와 **다를 수 있다**.
  가능하면 vISA 텐서 이름·셰이프와 오퍼레이터 설명을 함께 보여주긴 한다(`appendix__schedule-viewer.md:53-55`).
  → 즉 뷰어에 보이는 명령 수가 소스 라인 수와 1:1 이 아니다. 컴파일러가 펼친/합친 결과임을 감안하라.

## 5. TCL vs vISA 계층 경계 (핵심)

이 서버에서 "vISA 로만 되는 것"이 무엇인지 묻는 질문의 답이 여기 있다.

### 5.1 TCL 은 어디서 멈추나 (실측)
`furiosa.tcl` 의 배치 어휘는 `tcl.context(layout={Chip, Cluster, Split})` 가 전부다.
파이썬 `Layout` 은 Rust `InterChipContext` 를 그대로 미러링한다:
```python
# furiosa/tcl/_lang/_context.py:83-89 (docstring 인용)
#   Mirrors the Rust ``InterChipContext`` struct::
#       pub struct InterChipContext {
#           pub chip: AxisTagSize,
#           pub cluster: Option<AxisTagSize>,
#           pub split: Vec<AxisTagSize>,
#       }
```
- 필드는 `chip / cluster / split` 뿐(`_context.py:102-104`).
- TCL 의 연산 순서 모델은 `fetch → dpe → ve → commit` 4단계(`furiosa/tcl/_builder_history.py:42,93`).
- 실측 grep: TCL 공개 API 에 `Slice / Lane / Packet / TRF / VRF` 를 **배치 프리미티브로 노출하는 심볼은 0건**.
  (`commit` 은 있으나 이는 op 경계 이름이지 슬라이스 내부 데이터패스 배치가 아님.) 근거: `_GROUND_TRUTH.md:37-40`.

즉 **TCL 은 칩/클러스터/스플릿(=클러스터 경계)까지만** 텐서를 배치하고,
**슬라이스 내부(Lane ≤ 8, Packet ≤ 64 B, TRF/VRF 레지스터파일, commit-trim)는 노출하지 않는다.**

### 5.2 vISA 만 노출하는 것
Rust `furiosa-opt-std` 는 슬라이스 내부까지 내려간다. 예(우리 예제):
```rust
// /home/jun/yik/src/kernel/gemm_kernel.rs:4-9
pub type Chip    = m![1];
pub type Cluster = m![1 # 2];
pub type Slice   = m![I / 32, J / 32];   // ← 슬라이스 격자 (TCL 엔 없는 어휘)
pub type Lane    = m![J % 8];            // ← 레인 (TCL 엔 없는 어휘)
```
`Slice`·`Lane`·`Packet`·`TRF`·`VRF`·`commit`(트림) 은 vISA(Rust) 계층에서만 표현된다.
크레이트 소스에도 슬라이스 내부 엔진이 다 있다: `engine/contraction/{lane,packet,time}.rs`, `engine/vector/*`, `engine/commit.rs`
(`~/.cargo/registry/.../furiosa-opt-std-0.4.0/src/engine/`).

> **주의(문서 오류 인용 금지)**: `gemm_kernel.rs:8` 주석 "Each slice handles a 16 × 16 output tile" 은 **틀렸다**.
> `Slice = m![I/32, J/32]` = 16×16 **격자 = 256 슬라이스**이고, 각 슬라이스가 담당하는 타일은 `m![I%32, J%32] = 32×32` 다.
> 검산: 256 × (32×32=1024) = 262,144 = I·J(512·512). (`_GROUND_TRUTH.md:32-34`.) 이 주석을 그대로 옮기지 말 것.

### 5.3 계측(덤프) 대비: `furiosa-tcc` vs `cargo furiosa-opt compile`
| | `furiosa-tcc` (TCL) | `cargo furiosa-opt compile` (vISA) |
|---|---|---|
| 역할(실측 도움말) | "Compile TC-DSL to EDF" | "Compile `#[device]` functions to kernels" |
| 입력 | TC 소스 파일 / `--stdin` | Rust `#[device]` 함수 |
| 타깃 지정 | `--target-npu`(예 `renegade-8pe`, `renegade-8pe-4chip`) | 패키지 메타데이터/필터 |
| 출력 | `--output` 단일 EDF 바이너리 | `pkg::mod::fn.{bin,edf,hash}` |
| 캐시 | `--cache-root` | 커널별 캐시(`FURIOSA_OPT_OUT_DIR`) |
| **덤프/프로파일** | **전무** (`--dump-*` 옵션 없음) | **5종** `--dump-{visa,ir,schedule,graph,summary}` |
| 사이클 단위 스케줄 | ❌ | ✅ (`--dump-schedule` → 뷰어 또는 JSON 직접 파싱; **커널 130개 실적용 확인**, 2.3) |
| 카드 필요 | 컴파일 자체엔 불필요(EDF 생성) | 덤프도 카드 불필요 — **실기 테스트가 NPU 를 쓰는 중에도 병행 실행됨(실측)** |

출처: 실측 `furiosa-tcc --help`(옵션이 `--version/--target-npu/--output/--cache-root/--stdin` 뿐), 실측 `compile --help`, `_GROUND_TRUTH.md:41-42`.

**결론**: 컴파일러 내부(사이클 스케줄·중간 IR·vISA)를 **들여다보는 계측은 vISA 쪽에만** 있다.
TCL 로 인터칩 배치를 잡되 슬라이스 내부 타이밍을 분석하려면 그 커널을 vISA 로 내려 `cargo furiosa-opt compile --dump-*` 로 봐야 한다.

## 6. EdfModule — vISA/TCL EDF 를 서빙에 얹기 (부분 미확인)

### ① 무엇이 있나 (실측)
`furiosa.torch.custom_ops.edf.EdfModule`(`.../furiosa/torch/custom_ops/edf.py:131`)은
컴파일된 EDF(`ir.Edf`)를 감싸는 `torch.nn.Module` 이다. `furiosa.torch` 최상위에서 `EdfModule` 로 export 됨
(`furiosa/torch/__init__.py:44,54`).
- 생성: `EdfModule(ir.Edf)` — 바이너리/weight/스택 크기/IO 블록 등을 준비(`edf.py:131-241`).
- 로딩: `.to(device)` 로 weight/바이너리를 RNGD 디바이스에 올림(`edf.py:260-298`).
- 실행: `torch.ops.furiosa.edf(...)` 커스텀 op 을 호출(`edf.py:362-391`).
- 상위 래퍼 `CompileModule.from_exported(...)` 은 torch export → `compiler.compile(...)` → `EdfModule` 로 연결(`edf.py:464-481`).

### ② 쉬운 설명
서빙(torch) 쪽에서 "이미 컴파일된 EDF 바이너리"를 하나의 `nn.Module` 처럼 불러 `forward()` 로 돌리는 진입점이다.
weight/바이너리를 카드에 올리는 로딩·실행을 이 모듈이 관리한다.

### ④ 미확인 (중요)
- 이 서버에서 관측된 `EdfModule` 의 EDF 는 **torch export → `compiler.compile`** 경로로 만들어진다(`edf.py:479`).
  반면 `cargo furiosa-opt`(vISA)의 `*.edf` 나 `furiosa-tcc`(TCL)의 `--output` EDF 를 **그대로** `EdfModule` 에 얹는
  공식 경로는 이 소스만으로는 **확인되지 않았다**. `ir.Edf` 로 로드하는 API 존재/호환성은 미확인.
- 따라서 "vISA/TCL 로 뽑은 EDF 를 EdfModule 로 서빙" 은 **가능성일 뿐, 이 문서에선 미확인**으로 남긴다.
  카드 로딩(`.to(rngd)`, `_execute_edf`)은 **카드가 열려 있는 지금도** 시도하지 않았다
  (실기 검증은 vISA 테스트 경로로만 했다 — [13-NPU-실기-매트릭스](./13-NPU-실기-매트릭스.md)). 여전히 미확인.

## 10. 함정 모음 (그대로 옮기면 틀리는 것)

1. **`--version` 은 0.3.0 인데 세대는 0.4** — 세대는 가능 백엔드 목록으로 판단(`_GROUND_TRUTH.md:4-8`).
2. **`--backend simulation` 안 됨** — 이 래퍼는 `typecheck/emulation/npu` 만. 기본은 `emulation`(책의 `simulation` 은 무시).
3. **덤프는 2개가 아니라 5개** — 책엔 vISA/스케줄만, 실측엔 `+ir/graph/summary`.
4. **`--dump-ir` 은 LIR** — 실측 도움말 문구가 "intermediate LIR". "IR" 로 뭉뚱그리지 말 것.
5. **`yik` 로는 `compile`/`npu` 불가** — 구식 `.tag` 마커 + `0.3` 핀 → "no kernel packages found". `typecheck/emulation` 만 됨(`_GROUND_TRUTH.md:9-19`).
6. **`gemm_kernel.rs:8` 의 "16×16 output tile" 주석은 오류** — 16×16 은 슬라이스 격자(256개), 각 타일은 32×32(`_GROUND_TRUTH.md:32-34`).
7. **`furiosa-tcc` 엔 덤프/프로파일 옵션이 없다** — 계측하려면 vISA 로 내려 `cargo furiosa-opt compile --dump-*`.
8. **뷰어의 텐서/op 은 하드웨어 명령 기준** — vISA 소스와 1:1 아님(`appendix__schedule-viewer.md:53-55`).
9. **프록시/뷰어는 이 서버에 미설치** — 각각 GitHub 릴리스 다운로드 / `cargo install furiosa-schedule-viewer` 필요.
10. **덤프 시 target 오염 금지** — `CARGO_TARGET_DIR` 를 별도 경로로. 사용자 프로젝트 target 을 건드리지 말 것.
11. **`compile <FILTER>` 는 부분문자열 매칭** — 이름이 접두사인 다른 커널까지 컴파일되고 **그 커널의 에러를 물려받는다**.
    커널 200개 중 8개가 충돌 후보, 실제 오염된 판정 1건. 대책: `Finished N compiled` 의 N 확인 +
    에러를 `error: furiosa-opt: <정확한 커널명>:` 로 귀속(2절 ④).
12. **`--backend npu` 는 패키지의 모든 `#[device]` 를 낮춘다** — 테스트 1개만 돌려도 커널은 전량 컴파일.
    하나라도 실패하면 크레이트 전체 빌드 실패(실측: 207 컴파일 / 63 에러 / 테스트 0개 실행). 커널 필터는 `compile` 에만 있다(1.2).
13. **`compile` 성공 ≠ 실기 실행 성공** — 컴파일과 에뮬레이션을 모두 통과한 커널이 실기에서는 커널 **로드** 단계
    (`furiosa_kernel_load`)에 `range end index ... out of range` 로 프로세스째 abort 한 사례가 3건 있다.
    계측 도구가 보증하는 범위는 컴파일러까지다([13-NPU-실기-매트릭스](./13-NPU-실기-매트릭스.md) §2.1).
14. **`--dump-visa` 를 어셈블리 리스팅으로 기대하지 말 것** — 실측 산출물은 Rust `Debug` 출력
    (`Program { functions: {"mnist::forward": Function { params: [...`, 49,901 B). 명령을 순서대로 읽으려면
    `--dump-schedule` 을 쓴다(2.4.1).
15. **`--dump-summary` 의 사이클 값도 컴파일러 산출물이다** — `summary.log` 는 실기 실행 측정이 아니다.
    `--dump-schedule` 과 같은 성격의 스케줄 모델 값이다(2.4.2, [07-스케줄링](./07-스케줄링.md)).

## 12. 미확인으로 남긴 것

1. **EdfModule ↔ cargo/tcc EDF 직결 여부**: `EdfModule` 은 torch export→`compiler.compile` 경로의 `ir.Edf` 를 감싼다.
   `cargo furiosa-opt` 의 `*.edf` 나 `furiosa-tcc --output` EDF 를 그대로 `EdfModule` 로 로드하는 공식 API 는 소스로 확인 못 함
   (카드는 열려 있으나 실기 검증을 vISA 테스트 경로로만 했고 이 경로는 시도하지 않았다 — 6절 ④).
2. **`FURIOSA_OPT_NPUS` 환경변수**: 커리큘럼(v0.2.0)엔 있으나 현재 래퍼 `--help` ENV 에 미노출. 현재 래퍼에서의 존재/의미 미확인.
3. **`--dump-ir` LIR 텍스트의 내부 문법**: 산출물 자체는 실측했다(52,125 B, LIR 텍스트 — 2.4).
   그 텍스트의 문법·필드 구조는 읽어보지 않았으므로 미확인.
   (**해소됨 → 본문으로 이동**: `--dump-summary` 산출물 구조(파일 20개, 2.4.2),
   `--dump-visa` 형식(Rust `Debug`, 2.4.1), `--dump-graph` 최상위 스키마(2.4),
   `--dump-schedule` JSON 스키마(2.3).)
4. **`--dump-summary` 의 `summary.json` 스케줄러 키 의미**: `beam_size` / `total_states_visited` /
   `operator_schedule_heuristic` 키가 **존재하지만 `mnist::forward` 에서는 전부 `None`** 이고
   `schedule_method` 는 빈 문자열이다. **키가 있다는 사실만 실측**이며, 다른 커널·설정에서 값이 채워지는지는 미확인.
5. **Schedule Viewer / 언어서버 프록시 실동작**: 두 바이너리 모두 이 서버 미설치라 화면 동작은 책 설명(`appendix__*.md`)에만 의존, 실측 아님.
   단, **뷰어 미설치는 사이클 분석의 차단 사유가 아니다** — `--dump-schedule` JSON 을 직접 파싱해 커널 130개를
   엔진별로 분해했다(2.3, 11.1 `sched_analyze.py`).
6. **`furiosa-tcc` 의 EDF 와 vISA `.edf` 의 바이너리 호환성**: 동일 확장자지만 상호 교체 가능 여부 미확인.
