## 0. 이 장이 푸는 근본 문제 — 두 개의 용량 벽

RNGD(TCP)에는 두 벽이 있어 큰 텐서를 한 번에 못 민다. 이 장의 모든 기법이 이 벽을 우회한다.

| 메모리 | 용량 | 벽에 걸리면 |
|---|---|---|
| DM (on-chip SRAM) | 전체 256 MB, **slice당 512 KB** | 타일링 / DMA 왕복 |
| VRF (Vector Engine 피연산자) | **slice당 8 KB** (bf16 ≈ 4096개) | split-reduce / segmentation |
| TRF (Contraction Engine 입력) | **lane당 8 KB, slice당 8 lane** = full 64 KB/slice | rhs 타일을 잘게 쪼갬 |

출처: `_GROUND_TRUTH.md:51-52`(DM 256MB·512KB/slice, TRF 8KB/lane×8lane, VRF 8KB/slice), `docs/kernel-examples__tiling.md:7`(VRF 8KB/slice).

> **초심자용**: "VRF 8 KB는 slice당이지 전체가 아니다"가 이 장 최대 함정이다. 클러스터에 slice 256개라 총 2 MB지만, slice 하나는 8 KB뿐. `m![1,1,1,2048,32]`처럼 slice 차원에 아무것도 안 뿌리면 64 KB가 전부 slice 0에 몰려 터진다. 출처: `docs/kernel-examples__fetch-commit-engine.md:429-435`.

## 1. 병렬성·reduce 계층 표 (책이 이 장을 여는 지도)

### ① 책이 뭐라 하는가
`kernel-examples__index.md:8-15`의 표: 각 매핑 차원이 **공간(Spatial)** 인가 **시간(Temporal)** 인가, 그리고 **누가 그 축을 reduce하는가**를 정리한다.

| 차원 | 종류 | reduce 하드웨어 | 책 근거 |
|---|---|---|---|
| `Chip` | 공간 | DMA + Vector Engine | `index.md:10` |
| `Cluster` | 공간 | DMA + Vector Engine | `index.md:11` |
| `Slice` | 공간 | Vector Engine (Inter-Slice Reducer = GAT 글로벌 가산기 트리) | `index.md:12` |
| `Lane` | 공간 | Contraction Engine | `index.md:13` |
| `Time` | **시간** | Contraction Engine (Time Reducer 누산기) | `index.md:14` |
| `Packet` | 공간 | Contraction Engine (Packet Reducer 트리) | `index.md:15` |

### ② 우리 코드의 어디
yik의 세 커널이 이 표를 그대로 쓴다. `reduce축(K/J/A)`을 어느 차원에 두느냐가 곧 설계다.

```rust
// /home/jun/yik/src/kernel/dot_product_kernel.rs:5-9  — A(reduce축) 전부를 Packet/Time에
axes![A = 2048];
pub type Slice = m![1 # 256];  // 1 active slice; m![A/8 # 256]이면 256 slice에 분산
pub type Time  = m![1];        // 시간 반복 없음
pub type Lane  = m![1];
```
```rust
// /home/jun/yik/src/kernel/gemv_kernel.rs:5-10  — I(출력)는 Slice에 보존, J(reduce)는 Time+Packet
axes![I = 256, J = 2048];
pub type Slice  = m![I];        // 출력 I를 256 slice에 분산 (I=256이라 slice당 1행)
pub type Time   = m![J / 32];   // reduce축 J를 시간으로 64회
pub type Packet = m![J % 32];   // reduce축 J를 패킷 32개로 공간
```

### ③ 쉬운 설명
reduce축(합산할 축, 행렬곱의 K)을 **Packet/Time/Slice에 두면 칩 안에서 싸게** 끝난다. **Chip/Cluster에 두면 칩 사이 DMA 통신**이 필요해 비싸다. 그래서 책은 "가능하면 reduce축은 Slice/Element에 두라"고 못 박는다(`docs/kernel-examples__chip-cluster-reduce.md:314`).

### ④ 함정
- "공간 분할"과 "시간 분할"을 헷갈리지 말 것. `Time`만 시간(loop)이고 나머지(Chip/Cluster/Slice/Lane/Packet)는 다 공간(동시)이다. `index.md:8-15`.

## 2. Tiling — 큰 텐서를 on-chip에 맞게 쪼개기

### ① 책이 뭐라 하는가
"타일링은 VRF/DM에 안 들어가는 큰 텐서를 작은 타일로 쪼개는 것"(`tiling.md:6-7`). 쓰는 상황 3가지(`tiling.md:12-18`): (1) 한 차원이 한 패스에 안 들어감, (2) 불러온 데이터 재사용으로 대역폭 절약, (3) 공간 차원은 다 썼는데 시간(loop)으로 더 나눠야 함.
**타일 크기가 모든 걸 결정한다**(`tiling.md:23`): VRF(8KB)/DM에 맞고, 32바이트 flit 정렬을 지키고, 이중 버퍼링 여유를 남겨야. 실행 4단계(`tiling.md:24`): (1) 바깥 차원 타일 루프 → (2) HBM→DM fetch → (3) 계산 → (4) 부분결과 누적 후 write-back.
> 주의: `tiling.md`는 문서 자체가 **WIP**다(`tiling.md:3-5` `[!WARNING] WIP`). 개념만 있고 코드는 다른 예제(split-reduce, matmul)에서 봐야 한다.

### ② 우리 코드의 어디
**(a) 컴파일타임 타일 분할 `tile`** — 확인된 예제 `tile.rs`:
```rust
// furiosa-opt-examples/src/tile.rs (main, curl 확인)
for b in 0..32 {
    let input_slice  = input.tile::<m![B], 1, m![A, 1 # 32]>(b);       // [A,B]에서 b열 슬라이스
    let output_slice = output.view_mut().tile::<m![B], 1, m![1 #{!} 32, A]>(b);
    input_slice.to_hbm_view(&mut ctx.tdma, output_slice);             // transpose [A,B]->[B,A]
}
```
`tile.rs`의 docstring이 중요한 함정을 명시한다: **SRAM(DM) 뷰를 타일링한 루프는 `visa→lir`에서 unroll되어 계산된 오프셋 `b = g*GROUP + j`가 상수로 folding되지만, HBM 뷰를 타일링한 루프는 unroll되지 않아** 오프셋이 반드시 bare 스칼라 변수여야 한다(`tile.rs`의 `tile_computed_offset` / `tile_view_in_nested_loop` docstring). → 계산된 타일 오프셋(예: Q헤드 select `qh = kv_head*GQA_GROUP + g`)은 SRAM 뷰를 타일링해야 folding된다.

**(b) yik gemm의 두 겹 타일링 의도** — yik gemm은 단일 패스(I=J=512, K=64라 DM에 다 들어감)라 실제 loop는 없지만, Slice 매핑이 "출력 타일링"을 표현한다:
```rust
// /home/jun/yik/src/kernel/gemm_kernel.rs:3-9
axes![I = 512, J = 512, K = 64];
pub type Slice = m![I / 32, J / 32]; // ← 주석 "Each slice handles a 16 × 16 output tile" 은 틀렸다(아래 ④)
```

**(c) 자동 segmentation** — VRF 8KB를 넘는 텐서는 컴파일러가 자동으로 여러 execution으로 쪼갠다. `[A=2048,B=32]` f8 = 64KB > 8KB라 A를 1024씩 두 segment로(`fetch-commit-engine.md:398-461`):
```text
seg_0: begin(input.slice(A, 0..1024)) ... commit(256K)
seg_1: begin(input.slice(A, 1024..2048)) ... commit(256K + 32K)   # fetch-commit-engine.md:411-423
```

### ③ 쉬운 설명
타일링엔 두 종류의 의도가 섞인다. **출력 타일링**(결과를 바로 HBM에 쓸 수 있으니 결과축부터 자름)과 **reduce 타일링**(reduce축이 작은 TRF에 안 들어가 잘라서 누적). 후자의 "잘라서 누적"이 곧 다음 절 split-reduce다.

### ④ 함정 (GROUND TRUTH가 정정한 주석 오류 + 2026-07-24 실기 실측)

## 3. Split Reduce — reduce축을 여러 물리 텐서로 쪼갤 때

### ① 책이 뭐라 하는가
reduce하려는 논리 축이 **하나의 연속된 하드웨어 차원에 매핑되지 못할 때**(`split-reduce.md:4`) 쓴다. 세 경우(`split-reduce.md:10-14`): 축이 VRF 8KB에 안 들어감 / 이미 여러 텐서에 나뉨(레이어·expert·시간 조각) / 같은 칩이지만 할당이 따로라 DMA보다 interleaved fetch가 쌈.
핵심 기법 **interleaved fetch**: 여러 텐서를 시간축으로 번갈아 읽어 `I` 인터리브 차원을 만들고, Vector Engine이 그 `I`축을 binary op(add/max/min)로 합친다(`split-reduce.md:27-45`). 책 의사코드:
```rust,ignore
// docs/kernel-examples__split-reduce.md:36-42 (책 pseudocode)
let interleaved = ctx.main.begin_interleaved().fetch(&tensor_0, &tensor_1); // I:2 생성
let reduced     = interleaved.reduce_add(axis: I);                          // VE가 I축 합산
```
2개만 합칠 땐 인터리브 차원 없이 `sum_0.binary_add(sum_1)`(`split-reduce.md:313-320`). 비용은 fetch가 지배 → N-way 분할 = N배 대역폭 → **분할 수 최소화**가 제1원칙(`split-reduce.md:324-343`).

### ② 우리 코드의 어디 — 책 의사코드 vs 실제 저수준 API
책의 `reduce_add(axis:I)`는 실제 std 0.4 API에서 훨씬 저수준이다. **직접 확인**한 `matmul_split_reduce.rs`(main): `[1024,2048]×[2048]→[1024]`에서 B(reduce축)를 512씩 4타일로 자르고 VE 이진 덧셈으로 누적:
```rust
// furiosa-opt-examples/src/matmul/matmul_split_reduce.rs:24-35 (curl 확인)
ctx.main
    .begin_interleaved::<I, _, _, _, _, _>(rhs.view(), lhs.view()) // I=2 (rhs→Group0, lhs→Group1)
    .fetch::<m![A / 8 % 8, I], m![A % 8]>()
    .fetch_cast::<i32>()
    .collect::<m![A / 8 % 8, I], m![A % 8]>()
    .vector_init()
    .vector_intra_slice_unzip::<I, m![A / 8 % 8, 1 # 2], m![A / 8 % 8]>() // I=2를 두 그룹으로
    .vector_clip_zip(ClipBinaryOpI32::AddFxp)                            // Group0 + Group1
    .vector_final()
    .commit_trim::<m![A % 8]>()
    .commit_view(out)
```
누적은 running accumulator가 아니라 **result0/result1/temp 3버퍼 핑퐁**으로 한다(`matmul_split_reduce.rs:74-135`): j=0은 result0 직접, 이후 temp에 부분곱을 내고 `add_split_contractions_i32`로 이전 누적과 더해 result0↔result1을 번갈아 채운다. j=3에서 `narrow_split_contractions_i8`로 i8 narrow.

**yik 대응**: yik dot_product/gemv는 reduce축이 한 텐서에 다 들어가서 split이 필요 없다. 대신 contraction 체인 자체가 "einsum = elementwise multiply + reduce"임을 보여준다:
```rust
// /home/jun/yik/src/kernel/gemv_kernel.rs:38-41 — J를 Time+Packet으로 reduce
.contract_outer::<Time, Packet, _, _>(&vector_trf)  // ← 0.3: 제네릭 4개 (_, _)
.contract_packet::<m![1]>()   // Packet Reducer 트리
.contract_time::<m![1]>()     // Time Reducer 누산
.contract_lane::<m![1], m![1 # 8]>(LaneMode::Interleaved)
```

### ③ 쉬운 설명 — "stash/zip" 메커니즘
`begin_interleaved`가 두 텐서를 I=2 시간 인터리브 스트림으로 만들고, `vector_intra_slice_unzip`가 Group0/Group1로 갈라, `vector_clip_zip(Add)`가 둘을 더해 **결과를 Group1 자리에** 놓는다(그래서 코드 주석 "result is implicitly filtered to Group 1 only"). 이게 in-place 누산 대신 더블버퍼가 필요한 이유다 — 새 부분곱과 이전 누적이 동시에 존재해야 zip으로 더할 수 있으니까.

### ④ 함정

## 4. Chip / Cluster Reduce — 손으로 짠 ReduceScatter / AllReduce

### ① 책이 뭐라 하는가
**먼저: 클러스터 안에서 끝낼 수 있으면 끝내라.** 칩/클러스터 경계를 넘기 전에 Contraction Engine + Inter-Slice Reducer만으로 `m![A]`(A=65,536)를 스칼라까지 접는 데 약 **296 cycle**(`chip-cluster-reduce.md:13-34`): Packet `A%32` 트리 깊이5=5, Time `A/32%8` 누산=8, Slice `A/256` Inter-Slice Reducer=256.

reduce축이 `Chip`/`Cluster`에 걸치면 칩 간 합산이 필요하다. 두 연산:
- **ReduceScatter**(`chip-cluster-reduce.md:38-185`): reduce하며 결과를 각 칩에 한 조각씩 분배(메모리 절약). 4칩 예: 대각 슬라이스 T0=Slice(0,1,2,3), T1=Slice(3,0,1,2)+ChipShuffle(1,2,3,0), T2=Slice(2,3,0,1)+ChipShuffle(2,3,0,1), T3=Slice(1,2,3,0)+ChipShuffle(3,0,1,2) → VE add로 A축 소거 → AllGather.
- **AllReduce**(`chip-cluster-reduce.md:188-312`): 모든 칩이 동일한 전체 결과(gradient 평균 등). 대각이 아니라 균일 ChipShuffle 회전 n-1번(4칩=3, 8칩=7, 16칩=15).

구현 3종(`chip-cluster-reduce.md:316-339`): Asymmetric Slice(`ParallelCopy`+`stos`) / Shuffle(`DmaCommand`·`PCIeDmaCommand`, 칩 간이라 주 비용 수백~수천 cycle) / Tensor Addition(interleaved fetch + VE add).

### ② 우리 코드의 어디 (직접 확인)
**2클러스터 ReduceScatter** — `matmul_cluster_reduce.rs`:
```rust

let sliced1  = ctx.sub.parallel_copy_cluster_slice::<2, ...>(tensor.view(), &[1, 0]); // 반대 대각
let shuffled1 = sliced1.view().dm_cluster_shuffle::<2>(&mut ctx.tdma, &[1, 0]);        // 클러스터 0↔1
ctx.main.begin_interleaved::<I, ...>(sliced0.view(), shuffled1.view())                // T0+T1
    .fetch...().vector_init()
    .vector_intra_slice_unzip::<I, ...>()
    .vector_clip_zip(ClipBinaryOpI32::AddFxp)...;
```
인덱스 배열 `&[0,1]`/`&[1,0]`이 책의 Slice(0,1)/Slice(1,0)에 1:1 대응. `dm_cluster_shuffle`의 `&[1,0]`이 ChipShuffle 회전.

**4칩 ReduceScatter** — `matmul_chip_reduce.rs`(직접 확인)는 같은 패턴을 4개로: `parallel_copy_chip_slice`로 T0=`&[0,1,2,3]`, T1=`&[3,0,1,2]`+`dm_chip_shuffle::<4>(&[1,2,3,0])`, T2=`&[2,3,0,1]`+`&[2,3,0,1]`, T3=`&[1,2,3,0]`+`&[3,0,1,2]` 만들고, 2단계 이진 덧셈으로 sum01=T0+T1, sum012=+T2, reduced=+T3(`matmul_chip_reduce.rs:82-171`). 책 §ReduceScatter의 대각+회전 그대로. `reduce_over_chip`의 출력형이 `[C/2%4]` 칩 차원으로 reshape되어 "결과를 B로 흩뿌림"을 표현한다.

### ③ 쉬운 설명

### ④ 함정
- **ChipShuffle 패턴은 데이터 이동일 뿐 텐서 모양을 안 바꿔서, 잘못된 순열을 넣어도 `cargo furiosa-opt check`(타입검사)는 통과한다.** '컴파일 OK ≠ 수치 정확' — 대각/회전 순열은 손으로 검증해야 한다. 출처: `chip-cluster-reduce.md:96-135`. **[실기] 여기에 한 단이 더 붙는다: 컴파일 OK ≠ 실기 실행 OK.** 위 블록의 `chip_shuffle`처럼 컴파일·에뮬레이션 다 통과하고 실기 커널 로드에서 abort하는 경우가 있다.
- reduce축을 Chip/Cluster에 두면 DMA 셔플(수백~수천 cycle)이 끼어 매우 비싸다. 가능하면 Slice/Element에 두어 GAT/VE로 칩 안에서 끝내라(`chip-cluster-reduce.md:314`).

## 5. Fetch / Commit Engine — 계산 없이 레이아웃 바꾸기

### ① 책이 뭐라 하는가
전체 스트리밍 경로: `input → fetch sequencer → Switch Engine → Collect Engine → commit unit → output`(`fetch-commit-engine.md:3`). 네 예제가 각 측면을 보여준다.
1. **Axis Permutation**(`:8-131`): `[A,B,C]→[B,A,C]`를 Switch Engine으로. fetch는 시간순 `[A,B]`로 읽어도 write sequencer가 주소를 `[B,A]` 순서로 만든다. 시퀀서 표기 `[axis=count:stride,...] @ base / commit_size`(`:78`). **계산 자원 0**으로 transpose/NCHW↔NHWC.
2. **Full-flit Commit**(`:133-219`): 차원이 32바이트(flit) 경계에 맞으면 slicer 없이 통째 쓰기. Example 1이 15 cycle→3 cycle(5배).
3. **Tail Padding**(`:224-365`): `[A=65,B=2]`에서 tail 패딩(`dummy`) 양이 fetch_size를 결정. fetch_size는 8/16/24/32바이트만 가능:

   | dummy | fetch_size | cycle | 오버헤드 | 평가 |
   |---|---|---|---|---|
   | 7 | 24B | 6 | 9.7% | Good |
   | 15 | 16B | 10 | 18.8% | Moderate |
   | 23 | 8B | 22 | 26.1% | Poor |
   | 31 | 32B | 6 | 32.3% | Best |
   출처 `fetch-commit-engine.md:353-358`. **데이터+패딩이 32로 나눠떨어지게 패딩하라.**
4. **Tensor Segmentation**(`:398-525`): 2절 (c)에서 설명. VRF 8KB 초과 자동 분할.

### ② 우리 코드의 어디
yik gemm의 fetch→collect 체인이 이 경로의 축약판이다:
```rust
// /home/jun/yik/src/kernel/gemm_kernel.rs:25-30 — B를 TRF에 올리며 32바이트 flit로 정규화
let b_trf = ctx.sub.begin(b.view())
    .fetch::<m![J % 8, J / 8 % 4], m![K]>()
    .collect::<m![J % 8, J / 8 % 4, K / 16], m![K % 16]>()  // ← Collect가 K를 16씩 32바이트 flit로
    .to_trf(TrfAddress::Full);
```
`collect::<..., m![K % 16]>()`가 곧 책의 "Collect Engine이 packet을 32바이트 flit로 정규화"다(bf16 16개 = 32바이트). tile.rs의 `tile_window_commit`(직접 확인)은 `commit_view` + `view_mut().tile()`로 32-wide 창을 64-wide DM의 위쪽 절반에 쓰는 실전 commit 패턴을 보여준다.

> **[실기 실측 — 가장 조용한 함정] 바로 이 `tile_window_commit`이 실기에서 엉뚱한 위치에 쓴다.** 커널은 실기 컴파일 OK, 에뮬레이션도 통과인데 실기 실행(`tile_tests::test_tile_window_commit_host`)은 `tests/tile_tests.rs:51`에서 값 불일치로 FAIL. 목적지 전체를 덤프해보면 **데이터는 순서대로 온전하고 쓰인 위치만 틀렸다**: `result[0..8]`=0(정상), **`result[8..40]`에 `input[0..32]`(=0,1,2,…,31)**, `result[32..64]`는 앞 8칸만 24..31.
> 산술: 의도 오프셋 32 elements × 4 B(f32) = 128 B인데 실제 착지는 8 elements = **32 B**(32 B ÷ 4 B = 8) → **32가 "요소 수"가 아니라 "바이트 수"로 적용된 정황**(산술 정황이며 런타임 소스로 확인한 것은 아니다).
> → **commit 창 오프셋을 쓰는 코드는 실기에서 목적지 전체를 덤프해 검증할 것.** 크래시도 HAL 에러도 없이 틀린다. 같은 유형의 조용한 오배치가 브로드캐스트 DMA에도 있다 → [13-NPU-실기-매트릭스](./13-NPU-실기-매트릭스.md).

### ③ 쉬운 설명
Fetch/Switch/Commit은 "계산 없이 주소 패턴만으로" transpose·병합·패딩을 한다. 압축 저장보다 32바이트에 맞춰 패딩하는 게 더 빠를 때가 있다(교훈: Example 2).

### ④ 함정 (비대칭성)
- **read sequencer는 텐서 밖을 overfetch해도 안전(읽기만)하지만, write sequencer는 절대 텐서 경계를 넘어 쓰면 안 된다**(남의 영역 침범). 그래서 `dummy=23`은 88이 32 배수가 아니라 32바이트 commit이 불가능하다. 출처: `fetch-commit-engine.md:374-395`.
- write sequencer는 stride 0 금지 → commit 시 broadcast(재사용)나 선택적 버리기 불가(`fetch-commit-engine.md:221`).

## 6. Transformer — Llama 3 70B prefill/decode 전 과정

### ① 책이 뭐라 하는가
디코더-only 모델을 **prefill(입력 전체 병렬)**과 **decode(한 토큰씩, KV 캐시 재사용)** 두 단계로. 파라미터(`transformer.md:19-31`): V=128256, D=8192, F=28672, L=80, h_q=64, h_kv=8, **G=8(=h_q/h_kv)**, d_k=128, RoPE용 d_k=d_k_prime(64)·f(2).

**Prefill 흐름**(`transformer.md:34-372`): Embedding(gather, TensorDMA) → [레이어 L회: Input RMSNorm(VE) → GQA{QKV proj(einsum, D reduce) → RoPE(2×2 회전행렬 gather+einsum) → KV Cache 저장(DM→HBM) → Scores=Q@Kᵀ/√d_k(d_k reduce, G는 K에서 broadcast) → Causal Mask(VE **branch log**) → Softmax(VE) → Weighted Sum=score@V → O proj → Residual} → FFN{Post-Attn RMSNorm → SwiGLU: gate/up einsum, SiLU(gate)·up, down einsum → Residual}] → Final RMSNorm → LM Head(prefill은 마지막 토큰만 slice) → Sampling(**Host에서**, TCP 아님).

**einsum의 reduce 분해**(`transformer.md:98-105`) — 이게 1~7장 전체를 잇는 고리:
```text
matmul = einsum = broadcast → elementwise multiply(Contraction) → reduce-add:
  packet reduce  → Packet Reducer
  time reduce    → Time Reducer
  slice reduce   → global adder tree(GAT)
  split reduce   → interleaved fetch + VE binary op   (← 3절)
  cluster/chip   → DMA + interleaved fetch + VE       (← 4절)
```

**Decode 차이**(`transformer.md:375-694`): s_in=1(단일 토큰) / KV 캐시 **Update**(concat: slice간 RoutingEngine·parallel copy, HBM은 DMA) / autoregressive라 **causal mask 불필요**. Attention 모양: prefill `[B,h_q,s_in,s_in]` vs decode `[B,h_q,1,s]`. **prefill=compute-bound, decode=memory-bound**(`transformer.md:680-694`).

### ② 우리 코드의 어디 — furiosa-opt-examples 트랜스포머(Qwen 2.5 0.5B)
책은 개념(Llama 3 70B), **코드는 repo에 Qwen 2.5 0.5B 디코더 전체가 손코딩**돼 있다. 직접 확인한 헤더:
```rust
// furiosa-opt-examples/src/transformer/mod.rs:1 (curl 확인)
//! Qwen 2.5 0.5B composable transformer kernels (4PE, W16A16KV16, bf16).
//   embedding | embedding..transformer_0:qkv_projection
//   attention | transformer_N:attention (prefill, S=1024)
//   decoder   | transformer_N:output_projection..transformer_N+1:qkv
//   head      | transformer_-1:output_projection..output (+ LM head)
```
```rust
// furiosa-opt-examples/src/transformer/attention/mod.rs:38-70 (curl 확인)
//! Pipeline: KV Cache Scatter → Q*K^T Matmul → Softmax → Score*V Matmul
//   scale = head_dim**-0.5 = 0.125 (applied in attn_weight)
//   GQA: 14 Q-heads / 2 KV-heads = 7 groups (G=7, softmax per group)
```
**핵심 발상**: 단계 경계를 "레이어 경계"가 아니라 "재사용 가능한 파이프라인 경계"에 둔다. `decoder` 커널 하나가 레이어 N 뒷부분(o_proj→MLP)을 끝내고 곧바로 레이어 N+1 앞부분(QKV→RoPE)을 시작 → 잔차+정규화 결과를 HBM에 내렸다 올리는 왕복 없이 이어감.

**KV 캐시 scatter**(직접 확인)가 임베딩 gather의 거울상임을 보여준다 — 인덱스를 바이트 오프셋으로 변환 후 DMA:
```rust
// furiosa-opt-examples/src/transformer/attention/kv_cache.rs (curl 확인)
// row index → byte offset (row stride = K * sizeof(bf16) = 128*2 = 256):
.vector_fxp(FxpBinaryOp::MulInt, 256)   // 그다음 dma_scatter로 캐시에 씀
```

### ③ 쉬운 설명 — "값에 의존하는 제어흐름은 전부 정적화"
TCP는 256 slice에 동일 명령을 동시에 실행하므로 런타임 값에 따라 분기하면 안 된다. 그래서:
- **Causal mask** = if-else가 아니라 `attention_mask`를 VE **branch log**에 써서 거대음수(`-3.4e38`) 주입 → exp 후 0(`transformer.md:184-197`).
- **RoPE** = 삼각함수가 아니라 미리 계산한 2×2 회전행렬 table을 gather한 뒤 einsum 하나(`transformer.md:107-139`).
- **Softmax** = max-subtract → exp → sum → div의 VE 시퀀스, GQA는 그룹마다 독립.

### ④ 함정 (2026-07-24 실기·커널 전수 컴파일로 갱신)
- **[실기 실측] 트랜스포머 4단계가 전부 실기 컴파일 불가 — 그것도 컴파일러 내부 오류(ICE)다.** 커널 단위 전수 컴파일:

## 7. Mixture of Experts — branchless TopK + blockwise 희소 계산

### ① 책이 뭐라 하는가
토큰마다 E개 expert 중 K개만 처리(`mixture-of-experts.md:4`). 파라미터: E(보통 128), K(llama4=1, gpt-oss=4, qwen3=8)(`:48-50`). 논리 4단계(`:53-129`): Gating(`scores=einsum(x,W_router)`) → Top-K(+softmax=routing_weights) → Sparse Expert(선택된 것만 up/down) → Combine(K개 가중합).

TCP 두 난제와 해법(`:138-158`):
- **난제1 제어흐름**: Top-K 분기문이 SIMT에서 치명 → **branchless TopK**(행렬연산+비트조작).
- **난제2 동적 shape**: 토큰별 라우팅은 불규칙·동적 → **expert 중심 + blockwise**(고정 크기 블록).

**Branchless TopK**(`:160-244`): (1) **Bit Packing** `Packed=(Score<<16)|Index`로 정렬 시 ID 유지. **Comparison Trick** `Packed>=0이면 그대로, 아니면 ^0x7fff0000`으로 float 음수 대소 뒤집힘을 정수비교로 해결. (2) **Parallel Ranking** `T×E×E` 전쌍 비교 `Compare[t,i,j]=1 if val[j]>val[i]` → `Rank[t,i]=sum_j Compare`(나보다 높은 expert 수=내 순위). (3) **Filter&Unpack** `Mask=(Rank<K)`로 FilterCompaction → `Scores=Packed>>16`, `Indices=Packed&0xffff` → softmax.

**Blockwise**(`:246-378`): expert별 토큰 수 `L_e`가 동적(최악 L_e~T) → 고정 블록 B로 관리, `Grid Size G = sum_e ceil(Count_e/B)`, 최악 `(T*K-E)/B + E`. cumsum 기반 주소 계산(One-Hot → Histogram → Num_Blocks → Global_Offset=cumsum-Num_Blocks → Local_Offset → Expert_IDs=filter_compaction → `Scatter_Idx=Global_Offset*B+Local_Offset`) → Dispatch(scatter) → Weight Gather + Sparse MLP → Combine(역 gather + routing_weights + K reduce). **Cumsum**도 VE **branch logger**로 정적화(`:379-401`).

### ② 우리 코드의 어디
**repo에 MoE 예제 커널은 없다**(`paths.txt` 확인: matmul/transformer/mnist/scatter_gather는 있으나 moe 소스 없음). 하지만 구성 요소는 전부 다른 예제에 있다:
- `one_hot`/`histogram`/`cumsum`/`filter` = Vector Engine 연산(`furiosa-opt-std/src/engine/vector/`).
- `scatter`/`gather` = `scatter_gather.rs`의 `dma_scatter`/`dma_gather`(KV 캐시와 같은 API).
- `einsum` = 3·6절의 contraction 체인.

→ MoE는 이 문서 다른 절 도구들의 조합이라, "MoE 전용 마법"은 없다. 값 의존 제어(Top-K/cumsum)를 정적 행렬연산·branch log로 바꾸는 게 전부다.

### ③ 쉬운 설명
"토큰이 expert를 고른다"(token-centric)를 "expert가 토큰을 모은다"(expert-centric)로 뒤집고, 가변 길이를 고정 블록으로 패킹해 컴파일러가 정적 shape로 다룰 수 있게 만든다.

### ④ 함정
- 책의 MoE 코드 블록은 전부 `rust,ignore`(의사코드)다. 실제 std API로는 3절처럼 훨씬 저수준(vector_intra_slice_unzip/clip_zip)으로 풀어야 한다 — repo에 완성 예제가 없으니 이 부분은 **미확인 청사진**으로 취급.

## 8. 왜 이 예제들이 사용자 DeltaNet(qwen3-next-proj)의 청사진인가

사용자는 `/home/jun/RNGD-proj/Model_Benchmark/qwen3-next-proj`에서 **Qwen3-Coder-Next의 Gated DeltaNet**(선형/recurrent attention) 레이어를 NPU에 올리는 작업 중이다. 확인된 구조(`qcn/deltanet_layer.py:3-40`):
- linear key heads 16, value heads 32 (n_rep=2), head_k_dim=head_v_dim=128, hidden=2048.
- **per-head 독립 recurrence**: 32개 헤드에 `dn_chunk_full` 청크 커널을 **loop**하며 헤드별 상태 `S[h]` 모양 `[K,V]`를 threading.
- host에 남는 건 둘뿐: softplus(DSL op 없음), S_prev-독립 per-chunk precompute(tri-inverse T-matrix). 나머지 matmul/elementwise/reduce는 전부 NPU.

이 구조가 이 장 예제들과 1:1로 겹친다:

| DeltaNet 요소 | 대응하는 이 장의 예제·패턴 |
|---|---|
| 시퀀스를 chunk로 쪼개 순차 처리 + 상태 threading | **2절 Tiling**의 "시간 분할 + (4)누적", **6절 decode**의 chunk별 상태 흐름 |
| per-head 상태 `S[h]=[K,V]`를 청크마다 갱신 | **6절 KV Cache Update**(kv_cache.rs scatter/갱신) — recurrent state = "매 청크 갱신되는 KV 캐시" |
| 32 헤드 loop (독립 recurrence) | **6절 softmax의 GQA 그룹 loop**(GROUP_SRAM_ADDRS 7개 = 그룹당 독립 그래프), 계산된 헤드 오프셋은 **2절 tile.rs**의 SRAM-tiled unroll 규칙 |
| `delta = (v - kv) * beta` 체인 (SubF→MulF) | **3·5절 VE 체인**. 사용자 자신의 `tk_kernels/dn_delta.yaml:1-13`이 정확히 이 두 chained op(op0 SubF→op1 MulF, 중간 tensor id 3 DFG chaining)로 구현됨 |
| q@k, (k@v)→state, state@q 등 작은 matmul | **3절 contract 체인**(einsum = multiply + Packet/Time/Lane/Slice reduce) |
| softplus·tri-inverse가 host에 남음 | **6·7절 "값 의존 제어는 branch log/host로"** 원칙의 실제 사례 (softplus는 DSL op 부재로 host) |

→ **결론**: DeltaNet 커널은 "긴 시퀀스를 청크로 타일링(2절) + 청크마다 상태를 recurrent KV처럼 갱신(6절) + 헤드별로 loop(6절 GQA) + 작은 einsum들(3절) + 값 의존 연산은 host/branch로 빼기(6·7절)"의 조합이다. 이 장을 읽는 것은 DeltaNet 커널을 손으로 짜는 문법·용량·reduce 배치 감각을 그대로 얻는 것이다.

> **[실기 실측 2026-07-24] 이 청사진에 붙는 제약 3개** — 위 대응표는 개념적으로 유효하지만, 참고할 예제들의 실기 상태는 다음과 같다.
> 1. **청크·헤드 loop을 호스트 `for`/`if`로 쓰면 실기 컴파일이 죽는다** (`Branch conversion is not yet implemented`, 2절 ④ `matmul_16384` 실측). 32헤드 loop은 매핑 차원이나 **SRAM 뷰 타일링**으로 표현해야 하고, 계산된 헤드 오프셋(`qh = kv_head*GQA_GROUP + g`)은 SRAM-tiled 루프 위에서만 상수로 folding된다(`tile_computed_offset` 실패로 확증).
> 2. **베낄 원본인 트랜스포머 4단계가 전부 ICE**(6절 ④)이고 에뮬레이션에도 통과 기록이 0개다. "Qwen 파이프라인 구조를 그대로 따라간다"는 전제는 실기에서 성립하지 않는다 — 설계 참고로만 쓰고 검증은 처음부터 직접 해야 한다.
> 3. **작은 einsum의 reduce를 Chip/Cluster에 두면 실기로 못 간다**(4절 실측: chip/cluster reduce 전멸). reduce축은 Slice/Time/Packet 안에서 끝내라 — 책의 권고가 실기에선 권고가 아니라 필수 조건이다.

> 단, `_GROUND_TRUTH.md`와 커리큘럼 10 §10.5의 냉정한 결론: **vISA `.bin` ≠ furiosa-llm `.edf`**. vISA는 커널을 손으로 짜 NPU 연산력에 직접 접근하는 길이지, furiosa-llm serve 게이트를 우회하는 길은 아니다. DeltaNet을 vISA로 짜도 serve 경로에 그대로 꽂히지는 않는다(이 사실은 프로젝트 분석 근거이며 이 문서에서 재검증하지 않음 — 미확인).

## 10. 한 장으로 묶는 핵심 직관

1. **용량 벽**(DM 512KB/slice, VRF 8KB/slice, TRF 64KB/slice)이 모든 걸 강제한다.
2. **한 번에 안 들어가니 쪼갠다**: 타일링(손) / segmentation(컴파일러 자동).
3. **쪼갠 reduce를 다시 합친다**: 칩 안이면 split-reduce(interleaved fetch + VE add), 칩/클러스터 밖이면 chip/cluster reduce(+ParallelCopy slice + DMA shuffle).
4. **레이아웃은 fetch-commit 경로에서 계산 없이** 바꾸되 32바이트 정렬을 노린다.
5. **값에 의존하는 제어흐름(causal mask·Top-K·cumsum·softplus)은 전부 정적 행렬연산·branch log·host로** 바꾼다 — TCP에서 큰 모델을 돌리는 비결.
6. Transformer·MoE·DeltaNet은 위 도구들의 조합일 뿐이다.
7. **[실기 실측] 4번의 "32바이트 정렬"은 취향이 아니라 실기 통과 조건이다.** 소스에서 뽑은 커널 200개 중 **137 OK / 63 FAIL**이고, 실패 사유가 반복해서 정렬이다 — `not aligned by 8`(DMA 시퀀서), `tail_size % min_align`, `incorrect buffer size`(부분 충전 레인 그룹의 꼬리 패딩 누락). AOT 스케줄 모델 덤프(커널 130개, **실기 실행이 아니라 컴파일러 사이클 모델**)에서도 총 사이클의 **96.5%가 DmaEngine**(75,464,336 cycle / 인스트럭션 470개)이고 PeCore는 인스트럭션이 1,557개로 최다인데 **3.3%**뿐, 커널별 DMA 비중 중앙값 **82.8%**다. → 정렬을 못 맞추면 컴파일에서 막히고, 맞춰도 비용은 DMA가 낸다. 상세: [13-NPU-실기-매트릭스](./13-NPU-실기-매트릭스.md).
8. **[실기 실측] `compile` 성공 ≠ 실기 실행 성공 ≠ 값 정확.** 세 단이 따로다. 컴파일·에뮬레이션 다 통과하고 실기에서 커널 로드 abort(4절), 또는 **에러 하나 없이 목적지를 틀리게 쓰는 조용한 오배치**(5절 ②)가 실제로 있었다. **실기 검증에는 값 비교와 목적지 덤프를 항상 붙일 것.**
