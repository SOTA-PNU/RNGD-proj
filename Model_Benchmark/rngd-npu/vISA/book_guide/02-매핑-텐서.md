## 0. 큰 그림 — 왜 매핑부터인가

책 첫 두 줄이 전부다: *"Tensors have no intrinsic order of elements. A mapping assigns each tensor index to a buffer position, defining that order."* (`mapping-tensors__index.md:3-4`).

- **텐서** = 축 좌표 → 값의 수학적 대응. 메모리 모양은 없음.
- **매핑** = "텐서 인덱스 ↔ 버퍼 위치" 사전. 이게 성능을 결정한다(하드웨어는 연속 블록으로 읽으므로 멀리 떨어진 원소는 전송 증가, `index.md:10`).
- 한 번 할당하면 레이아웃은 복사·전치 없이 못 바꾼다(`index.md:12`). 그래서 할당 시점 선택이 이후 모든 연산을 제약한다.
- vISA는 stride/offset 숫자를 사람이 만지는 대신 **논리 축으로 선언만** 하고, 컴파일러가 물리 배치·정렬·스케줄을 유도한다(`index.md:82-95`).

major/minor 직관 하나만 챙기면 된다: **매핑식에서 왼쪽이 major(가장 바깥, 가장 느리게 변함), 오른쪽이 minor(가장 안쪽, 연속 저장)**(`index.md:88`). `H`×`W` 예의 세 레이아웃:

| 레이아웃 | 매핑식 | 의미 | 출처 |
|---|---|---|---|
| H-major | `m![H, W]` | W 스캔 연속, H 스캔 캐시라인당 1원소 | `index.md:88-90` |
| W-major | `m![W, H]` | 반대 | `index.md:88-90` |
| 2×2 타일 | `m![H / 2, W / 2, H % 2, W % 2]` | 앞 둘=타일 인덱스, 뒤 둘=타일 내부 위치 | `index.md:91` |

바깥 차원은 하드웨어 시간 루프(`Time`), 안쪽 차원은 병렬 레인 폭(`Packet`)이 된다(`index.md:76-79`) — 이 두 이름이 §3의 시간/공간 차원으로 이어진다.

## 1. `m![]` 미니언어 — 연산자별 정확한 의미

`m![...]`이 만드는 건 전부 Rust 타입이고, 모두 `M` 트레잇을 구현한다(`dsl.rs:23-31`):

```rust
// furiosa-mapping-types-0.4.0/src/dsl.rs:23-31
pub trait M: Debug + Clone {
    const SIZE: usize;                 // 버퍼 칸 수(원소 개수)
    fn to_value() -> Mapping;          // 런타임 값 표현
    fn map(i: usize) -> Option<Index>; // 버퍼 위치 i -> 텐서 인덱스(범위 밖이면 None)
}
```

매핑의 의미는 딱 두 가지, `SIZE`와 `map`이다. 그래서 **두 매핑이 "동등(equivalent)"** = `SIZE`가 같고 모든 `i`에서 `map(i)`가 같음(`mapping-expressions.md:472-478`).

아래 표는 각 연산자를 0.4.0 실제 구현과 함께 정리한 것이다. **모든 `SIZE`/`map` 식은 `dsl.rs`에서 직접 확인**했다.

| 연산자 | 예 | 펼침 타입 | `SIZE` | `map(i)` | 출처(dsl.rs) |
|---|---|---|---|---|---|
| Symbol | `m![I]` | `Symbol<I>` | `I::SIZE` | `i![I: i]` | `66-83` |
| `,` Pair | `m![I, J]` | `Pair<m![I], m![J]>` | `L::SIZE * R::SIZE` | `L::map(i / R::SIZE) + R::map(i % R::SIZE)` | `220-244` |
| `/` Stride | `m![J / 64]` | `Stride<m![J], 64>` | `L::SIZE / 64` | `L::map(i * 64)` | `104-127` |
| `%` Modulo | `m![J % 64]` | `Modulo<m![J], 64>` | `64` | `L::map(i % L::SIZE)` | `133-156` |
| `=` Resize | `m![J = 2]` | `Resize<m![J], 2>` | `2` | `i<2 ? L::map(i) : None` | `162-183` |
| `#` Padding | `m![J # 640]` | `Padding<m![J], 640, Top>` | `640` | `L::map(i)` (늘어난 칸은 `None`) | `193-214` |
| `1` Identity | `m![1]` | (Identity) | `1` | `map(0)=i![]`, 그 외 `None` | — (책 `mapping-expressions.md:126-148`) |

핵심 포인트 몇 가지:

**Pair(`,`)** — floor 나눗셈/나머지로 분해한다. `l.add(r)`로 두 부분 인덱스를 **합친다**(`dsl.rs:238-243`). 왼쪽이 major:

```rust
// dsl.rs:238-243
fn map(i: usize) -> Option<Index> {
    let mut l = L::map(i / R::SIZE)?;  // 몫 = 바깥(major)
    let r = R::map(i % R::SIZE)?;      // 나머지 = 안쪽(minor)
    l.add(r);
    Some(l)
}
```

**Stride(`/N`)** vs **Modulo(`%N`)** — 한 축을 "바깥 블록 인덱스"와 "블록 내부 위치"로 쪼갠다. 둘 다 `assert!(L::SIZE % N == 0)`을 **const 평가**로 강제한다:

```rust
// dsl.rs:112-115 (Stride)  ── N으로 못 나누면 컴파일 실패
const SIZE: usize = {
    assert!(L::SIZE % SIZE == 0, "Stride size must divide the original size");
    L::SIZE / SIZE
};
// dsl.rs:141-144 (Modulo)
const SIZE: usize = {
    assert!(L::SIZE % SIZE == 0, "Modulo size must divide the original size");
    SIZE
};
```

- `m![J / 64]` (J=512) → 크기 8(=512/64), `map(i)=J.map(i*64)` = 블록 인덱스(0,64,128,…의 대표).
- `m![J % 64]` → 크기 64, `map(i)=J.map(i%512)` = 블록 내부 0..64.
- `m![J / 64, J % 64] ≡ m![J]` (stride-modulo 분해 항등식, `mapping-expressions.md:483`).

**Resize(`=`) vs Modulo(`%`) 혼동 주의**(`mapping-expressions.md:315-317`): Resize는 **버퍼를 잘라 SIZE를 줄이고**, Modulo는 **원래 버퍼 크기를 유지하며 같은 크기 블록으로 partition**한다. 정반대다.

**Padding(`#`)** — 버퍼를 SIZE로 **키우지만** `map`은 원래 inner 그대로라(`dsl.rs:211-213`) 늘어난 칸은 어떤 인덱스에도 대응하지 않아 `None`을 돌려준다. 3종류가 타입에 새겨진다(`mapping-expressions.md:182-197`): `#`/`#{*}`=Top(임의값, 기본), `#{0}`=Zero(0 보장), `#{!}`=Bottom(접근 금지). 파서에서 `Top`이 기본(`parser.lalrpop:51-54`).

## 2. 연산자 우선순위·중첩 — `C % 32 / 2`의 연산 순서

작업에서 지목한 중첩 예를 문법으로 정확히 풀자. **소스로 직접 확인**한 문법(`parser.lalrpop`):

```
// furiosa-mapping-macro-0.4.0/src/parser/parser.lalrpop
Mapping0 (41-45):  <Mapping1> "Comma" <Mapping0>   → Pair   (우측 재귀 = 우결합, 가장 느슨)
Mapping1 (47-73):  <Mapping1> "Slash"   <Num>      → Stride  (좌측 재귀 = 좌결합)
                   <Mapping1> "Percent" <Num>      → Modulo  (좌결합, Stride와 같은 레벨)
                   <Mapping1> "Eq"      <Num>      → Resize
                   <Mapping1> "Hash"    <Num>      → Padding
Mapping2 (76-81):  Symbol / 1 / { escape } / ( ) / [ ]   (가장 강함)
```

정리하면:

1. **`,`(Pair)가 가장 느슨하고 우결합**. `m![A,B,C,D] = Pair<A, Pair<B, Pair<C, D>>>`(`mapping-expressions.md:96`).
2. **`/ % = #`는 모두 같은 우선순위, 좌결합**(전부 `<left:Mapping1> …` 좌측 재귀).
3. 심볼/`1`/escape/괄호가 가장 강함.

그래서 **`C % 32 / 2` = `(C % 32) / 2`** — 왼쪽에서 오른쪽으로:

```
m![C % 32 / 2]
  = Stride< Modulo< Symbol<C>, 32 >, 2 >
      ^ 나중(/2)        ^ 먼저(%32)
```

- 먼저 `C % 32` → `Modulo`, `SIZE = 32`.
- 다음 `… / 2` → `Stride`, `SIZE = 32 / 2 = 16`.

C=512(예: 우리 `I` 축)로 실측 계산: `m![I % 32 / 2]`는 `Modulo<Symbol<I>,32>`(크기 32, `map(x)=i![I:x]`) 위에 `Stride<...,2>`(크기 16, `map(i)=inner.map(i*2)`). 결과: 크기 16, 값 0,2,4,…,30 — **32블록 안의 짝수 위치**.

책의 거울 예 `m![B / 32 % 2] = (B/32) % 2`(`mapping-expressions.md:329` 안의 `B / 32 % 2`)도 같은 규칙: `/32` 먼저(Stride, B/32=16), `%2` 나중(Modulo, 2). 좌결합이라는 것이 두 예에서 일관되게 확인된다.

> **함정**: `m![A, B / 64]`는 `Pair<m![A], Stride<m![B],64>>`이지 `Stride<Pair<...>,64>`가 **아니다**. `,`가 항상 가장 바깥이다. 디바이스 텐서 타입을 읽을 때 이걸 기억하면 헷갈리지 않는다.

## 3. 공간 차원(Chip/Cluster/Slice/Lane) vs 시간 차원(Time/Packet)

`HostTensor<D, E>`는 매핑 하나로 끝이지만, 디바이스 텐서는 레이아웃을 **여러 전용 차원으로 쪼갠다**(`spatial-temporal-dimensions.md:1-8`). 각 계층이 텐서 타입의 별도 `M` 타입 파라미터가 된다.

### 3-1. 텐서 타입 파라미터 순서 (작업 지정 항목)

```rust
// spatial-temporal-dimensions.md:22-41, 114-126
struct HbmTensor<D, Chip,                      Element>;              // HBM: Chip만
struct DmTensor <D, Chip, Cluster, Slice,      Element>;             // SRAM(DM)
struct TrfTensor<D, Chip, Cluster, Slice, Lane, Element>;            // SRAM(TRF): Lane 추가
struct VrfTensor<D, Chip, Cluster, Slice,      Element>;             // SRAM(VRF)
struct TuTensor <'l, const P: Position, D, Chip, Cluster, Slice, Time, Packet>; // 파이프라인 스트림
```

| 타입 | 파라미터 순서 | 특이점 |
|---|---|---|
| `HbmTensor` | `<D, Chip, Element>` | **Cluster/Slice 없음** — HBM은 칩 단위 분산까지만 |
| `DmTensor` | `<D, Chip, Cluster, Slice, Element>` | 온칩 SRAM |
| `TrfTensor` | `<D, Chip, Cluster, Slice, Lane, Element>` | `Lane`이 슬라이스 안 8레인에 분산 |
| `VrfTensor` | `<D, Chip, Cluster, Slice, Element>` | Lane 없음 |
| `TuTensor` | `<'l, P, D, Chip, Cluster, Slice, Time, Packet>` | `Time`+`Packet`(스트림), `P`=파이프라인 단계 |

> **주의**: `Element`(마지막 매핑)와 공간 차원들은 **서로 겹치지 않는 축을 담당**한다. "담는다(hold)"의 정의상 각 원소는 *모든 차원 매핑이 만든 부분 인덱스의 합* 위치의 값을 저장한다(`tensor-semantics.md:9, 17-22`). §4에서 우리 커널로 이 합을 직접 검산한다.

### 3-2. 공간 차원 크기 제약 (하드웨어 개수와 정확히 일치)

| 유닛 | 개수 | 제약 | 패딩 예 | 출처 |
|---|---|---|---|---|
| `Chip` | 시스템마다 | `Chip::SIZE == NUM_CHIPS` | `m![1 # NUM_CHIPS]` | `spatial-temporal-dimensions.md:59` |
| `Cluster` | 칩당 2 | `Cluster::SIZE == 2` | `m![1 # 2]` | 동:60 |
| `Slice` | 클러스터당 256 | `Slice::SIZE == 256` | `m![X / N # 256]` | 동:61 |
| `Lane` | 슬라이스당 8 | `Lane::SIZE <= 8` | — | 동:76 |

- 커널이 하드웨어보다 적게 쓰면 `#`로 패딩해 채운다. `m![1 # 2]` = 활성 1 + 패딩 1(`동:64-66`).
- 현재 런타임은 칩 단위(`#[device(chip = N)]`)라 **칩·클러스터 부분 사용은 아직 미지원**(`동:67-69`).
- **실측 보강**: 다중 칩/클러스터를 실제로 쓰는 벤더 예제는 **실기에서 하나도 동작하지 않는다.** 기전은 두 가지다. ① `--backend npu` 컴파일부터 실패: `matmul::matmul_chip_reduce`(`strides([8,128,4,...]) is not aligned by 8`), `matmul::matmul_cluster_reduce`(`tail_size % min_align (1) != 0`), `cluster_chip_shuffle_slice::{cluster_shuffle,chip_slice,cluster_slice}`, `memory_op::hbm_chip_shuffle`. ② **컴파일은 통과**하는데 실기에서 죽음: `cluster_chip_shuffle_slice::chip_shuffle`은 컴파일 OK이고 `shuffle_slice_tests::test_chip_shuffle`이 **실기 커널 로드에서 abort**(요구 56,576 vs 실제 37,888) — `compile` 성공이 실기 실행을 보장하지 않는 실례다. 즉 이 서버의 RNGD 4장을 vISA로 함께 쓰는 경로는 아직 열려 있지 않다 — [13-NPU-실기-매트릭스](./13-NPU-실기-매트릭스.md).
- Element 용량 한계(`동:71-77`): `DmTensor` ≤ 512KB/slice, `TrfTensor` ≤ 8KB/lane, `VrfTensor` ≤ 8KB/slice. 시작 주소가 `size_of::<D>()` 배수가 아니면 read-modify-write로 **약 50× 느려짐**(`동:79`).

### 3-3. 시간 차원: `Time`과 `Packet`

파이프라인을 흐르는 `TuTensor`는 Chip/Cluster/Slice에 더해 `Time`·`Packet`을 갖는다(`spatial-temporal-dimensions.md:81-143`).

- **`Time`**: 전달 반복(iteration)을 순서대로 세는 순차 루프 카운터. 하드웨어 상한 없음, 데이터 양에 따라 커짐(`동:86`).
- **`Packet`**: 한 번의 시간 반복마다 각 슬라이스가 받는 원소 수(추가 공간 차원, `동:87`).

책 worked example(`동:128-143`), shape `{N=4, C=64, H=32, W=32}`를 Fetch 출력으로 스트리밍:

```rust
// spatial-temporal-dimensions.md:133-137
Slice  = m![C / 2];    // 64채널을 32슬라이스에 분산  (C/2 = 32)
Time   = m![N, H, W];  // 4*32*32 = 4096 번 반복
Packet = m![C % 2];    // 매 반복 슬라이스당 2채널
```

32슬라이스 병렬 × 슬라이스당 2채널 = 한 반복에 64채널 처리. "`C`를 `/2`(바깥)는 슬라이스 공간에, `%2`(안쪽)는 패킷에" — 이게 §4 커널의 `J`를 슬라이스/레인/엘리먼트로 쪼개는 사고방식과 동일하다.

## 4. 우리 `gemm_kernel.rs` 완전 해부 (256 슬라이스 · 32×32 타일 검산)

파일: `/home/jun/yik/src/kernel/gemm_kernel.rs`. 축 선언과 계층 매핑:

```rust
// gemm_kernel.rs:3-9
axes![I = 512, J = 512, K = 64];

pub type Chip    = m![1];              // 3-2 제약: NUM_CHIPS=1 (#[device(chip=1)])
pub type Cluster = m![1 # 2];          // 활성 1 + 패딩 1 → Cluster::SIZE == 2
pub type Slice   = m![I / 32, J / 32]; // ← 아래 검산
pub type Lane    = m![J % 8];          // Lane::SIZE == 8 (<= 8)
```

### 4-1. `Slice = m![I / 32, J / 32]` → 256 슬라이스 (검산)

- `I / 32`: `Stride<Symbol<I>, 32>`, `SIZE = I::SIZE / 32 = 512 / 32 = 16` (I-블록 인덱스, 블록당 32).
- `J / 32`: 마찬가지로 `SIZE = 16` (J-블록 인덱스).
- `Slice = Pair<m![I/32], m![J/32]>`, **`SIZE = 16 × 16 = 256`** ✓ (3-2의 `Slice::SIZE == 256` 충족).

즉 슬라이스는 **(I-블록, J-블록)의 16×16 격자 = 256개**. 각 슬라이스는 하나의 (I-블록, J-블록) 쌍에 대응한다.

### 4-2. 각 슬라이스가 맡는 타일 = `m![I % 32, J % 32]` = **32×32** (검산)

`result`의 Element 매핑이 슬라이스가 실제로 담는 데이터다:

```rust
// gemm_kernel.rs:35 (result 타입)
DmTensor<bf16, Chip, Cluster, Slice, m![I % 32, J % 32]>
//                                   ^^^^^^^^^^^^^^^^^^ Element = 슬라이스 1개가 담는 타일
```

- `I % 32`: `Modulo`, `SIZE = 32`. `J % 32`: `SIZE = 32`.
- Element `SIZE = 32 × 32 = 1024`.
- **전체 검산**: 256 슬라이스 × 1024(32×32) = **262,144 = I·J = 512×512** ✓.

축별로도 맞는다:
- I: `I/32`(슬라이스, 16) × `I%32`(엘리먼트, 32) = 512 ✓
- J: `J/32`(슬라이스, 16) × `J%32`(엘리먼트, 32) = 512 ✓

### 4-3. 주석 오류 정정 (`_GROUND_TRUTH.md:31-35`)

`gemm_kernel.rs:8`의 주석 **"Each slice handles a 16 × 16 output tile" 은 틀렸다.**

| 항목 | 매핑식 | 실제 크기 | 커널 주석이 말한 것 |
|---|---|---|---|
| 슬라이스 **격자** | `m![I / 32, J / 32]` | 16 × 16 = **256 슬라이스** | (여기의 16×16을 타일로 오해) |
| 슬라이스당 **타일** | `m![I % 32, J % 32]` | **32 × 32** = 1024 | ✗ "16×16"이라 잘못 적음 |

반례로 확인: 만약 타일이 16×16이라면 256 × 256 = 65,536 ≠ 262,144. 즉 "16×16 타일" 가정은 I·J와 안 맞는다. **"16×16"은 슬라이스 격자 치수이지 타일 크기가 아니다.**

또한 `gemm_kernel.rs:23`의 *"Switch Engine distributes B across 256 slices"* 주석도 오해 소지가 있다: 실제로 `switch()`는 **호출되지 않으며**, 슬라이스 분배는 `to_dm`의 `Slice` 타입 파라미터가 수행한다(`_GROUND_TRUTH.md:35`). `gemm_kernel.rs:24`의 "(16 × 16) output tile"도 같은 오류로 32×32가 맞다.

### 4-4. `Lane = m![J % 8]`과 `J`의 3단 분해

`b_trf`의 타입에서 `J`가 슬라이스/레인/엘리먼트로 어떻게 나뉘는지 보자:

```rust
// gemm_kernel.rs:25 (b_trf 타입)
TrfTensor<bf16, Chip, Cluster, Slice, Lane, m![J / 8 % 4, K]>
//                            Slice=m![I/32,J/32]  Lane=m![J%8]  Element=m![J/8%4, K]
```

`J`(=512)에 기여하는 세 차원의 부분 인덱스(=`map`이 만드는 `i![J: …]`)와 크기:

| 차원 | 매핑 | 크기 | 부분 인덱스(값) | J의 비트 |
|---|---|---|---|---|
| Slice(J쪽) | `J / 32` | 16 | `J.map(i*32)` → `i![J: 32·j₃]` | [8:5] |
| Element(J쪽) | `J / 8 % 4` | 4 | `i![J: 8·j₂]` | [4:3] |
| Lane | `J % 8` | 8 | `i![J: j₀]` | [2:0] |

- 크기 곱: 16 × 4 × 8 = **512 = J** ✓ (빠짐·겹침 없이 J를 완전 분할).
- 부분 인덱스 합: `J = 32·j₃ + 8·j₂ + j₀`. 어떤 J든 `j₃=J/32`, `j₂=(J/8)%4`, `j₀=J%8`로 유일 분해 → "hold" 정의(부분 인덱스의 합, `tensor-semantics.md:17-22`)를 그대로 만족.

`J / 8 % 4`의 연산 순서(§2 규칙): `(J/8) % 4` = `Modulo<Stride<Symbol<J>,8>,4>`. `/8` 먼저(J/8=64), `%4` 나중(크기 4). 슬라이스의 32열(=`J%32`)을 다시 **4그룹(엘리먼트) × 8레인(Lane)** 으로 쪼갠 것: 4×8=32 ✓.

### 4-5. HBM → DM → TRF, 그리고 매핑이 바뀌어도 값은 같다

```rust
// gemm_kernel.rs:12-19 (요지)
a: &HbmTensor<bf16, Chip, m![I, K]>          // 입력: Chip + Element=m![I,K]
let a: DmTensor<bf16, Chip, Cluster, Slice, m![I % 32, K]> = a.to_dm(&mut ctx.tdma, 0);
let b: DmTensor<bf16, Chip, Cluster, Slice, m![J % 32, K]> = b.to_dm(&mut ctx.tdma, 1 << 12);
```

`HbmTensor<bf16, m![1], m![I, K]>` → `DmTensor<…, Slice=m![I/32,J/32], m![I%32, K]>`. 매핑은 칩/클러스터/슬라이스/엘리먼트로 다르게 펼쳐지지만, **담는 텐서(수학적 값)는 동일**하다 — `.to_dm()`은 *mathematical tensor move* `f(T)=T`(`tensor-semantics.md:46-64`).

> **주의**: 0.4.0 API는 `to_dm(&mut ctx.tdma)`처럼 **명시적 주소 인자를 제거**했다(`_GROUND_TRUTH.md:23`). 그런데 yik의 이 커널은 `a.to_dm(&mut ctx.tdma, 0)`, `b.to_dm(&mut ctx.tdma, 1 << 12)`처럼 **0.3 시그니처(주소 인자 포함)**로 작성돼 있다. 즉 yik는 `furiosa-opt-std = "0.3"` 핀 그대로다. 현재 0.4 래퍼로 이 커널을 그대로 컴파일/실행하려면 API 포팅이 필요하다(`_GROUND_TRUTH.md:14-16, 21-25`). 매핑 자체(축→계층 분배)의 논리는 세대와 무관하게 위 검산대로 유효하다.

## 5. `mapping-expressions` 예제를 우리 축(I/J/K)으로 재서술

책 예제는 `A=8, B=512, C=13, D=61`을 쓴다. 우리 축(`I=512, J=512, K=64`)으로 바꿔 `map()` 값까지 손으로 검산한다. **모든 규칙은 `dsl.rs` 구현과 일치**한다.

### 5-1. Pair (`mapping-expressions.md:91-120` → I/K)

```rust
type E = m![I, K];   // I=512, K=64
// SIZE = 512 * 64 = 32768,  I-major / K-minor
// map(0)   = i![I:0, K:0]
// map(63)  = i![I:0, K:63]
// map(64)  = i![I:1, K:0]     (64 = 64*1 + 0)
// map(130) = i![I:2, K:2]     (130 = 64*2 + 2)
// map(32768) = None
```

R::SIZE=K::SIZE=64로 나눈 몫이 I, 나머지가 K. 책의 `map(519)=i![A:1,B:7]` 논리와 동형.

### 5-2. Stride/Modulo가 원래 축과 동등 (`md:254-296` → J)

```rust
type E = m![J / 64, J % 64];   // J=512 → 8블록 × 64
// map(130) = i![J/64:2, J%64:2]   (130 = 64*2 + 2)
// 모든 i에서 E::map(i) == m![J]::map(i)  →  m![J]과 동등 (md:483)
```

우리 커널에 실제로 등장하는 K 분해: `m![K / 16, K % 16]` (K=64 → 4 × 16 = 64). `collect::<m![J%8, J/8%4, K/16], m![K%16]>()`(`gemm_kernel.rs:29,39`)에서 `K`를 `K/16`(4)와 `K%16`(16)으로 쪼개는 게 바로 이것이다.

### 5-3. Padding vs Resize (`md:150-222` → 우리 상황)

```rust
// Padding: Cluster = m![1 # 2]  (gemm_kernel.rs:6)
//   = Padding<Identity, 2>, SIZE=2
//   map(0) = Some(i![])   // 활성 클러스터
//   map(1) = None         // 패딩 슬롯 (임의값 가능, 유효 데이터 아님)

// Resize: 논리 뷰 축소 (버퍼 확장하는 Padding과 반대)
type R = m![K = 16];   // K=64를 앞 16개로 자름, SIZE=16
//   map(15) = i![K:15],  map(16) = None
```

책의 `m![C, D # 64]`(D=61→64 정렬)와 `m![C, D = 2]`(잘라 줄임) 대비를, 우리 커널에 실재하는 `m![1 # 2]`와 `= N` 형태로 옮긴 것.

### 5-4. 중첩 stride/modulo — 비트 재배열 (`md:319-357`)

책의 `m![B / 64, B % 32, B / 32 % 2]`는 버퍼 비트 묶음과 텐서 인덱스 비트 묶음이 달라지는 예다(뱅크 인터리빙·캐시 효율에 대응). 우리 커널의 `J` 3단 분해(§4-4)가 정확히 같은 종류의 재배열이다: 버퍼 상 `[Slice j₃][Element j₂][Lane j₀]` 순서가 `J`의 비트 `[8:5][4:3][2:0]`로 재조립된다.

## 7. 함정 모음 (그대로 옮기지 말 것 포함)

1. **커널 주석 "16×16 output tile"은 틀렸다.** 슬라이스 격자 16×16(=256 슬라이스), 타일은 32×32. 검산: 256×1024=262,144=I·J (`_GROUND_TRUTH.md:31-34`, 본문 §4-2/4-3).
2. **`switch()`는 호출되지 않는다.** 슬라이스 분배는 `to_dm`의 `Slice` 타입 파라미터가 한다(`_GROUND_TRUTH.md:35`).
3. **`,`가 가장 느슨.** `m![A, B/64]`=`Pair<A, Stride<B,64>>`. `/%=#`는 같은 레벨 좌결합 → `C % 32 / 2 = (C%32)/2`(§2, `parser.lalrpop:41-81`).
4. **`/`·`%`의 나눗수는 축 크기를 정확히 나눠야 한다.** 아니면 런타임이 아니라 **컴파일 시 const assert**가 터진다("Stride/Modulo size must divide the original size", `dsl.rs:113,142`). 예: J=512에서 `m![J/7]`은 컴파일 실패.
5. **bare 정수는 `1`(Identity)만 허용.** `m![64]` 같은 건 컴파일 오류 — 크기가 필요하면 `axes!`로 이름을 붙여라(`parser.lalrpop:76-81`).
6. **Padding 슬롯을 유효 데이터로 착각 금지.** `#`로 늘어난 칸은 `map()`이 `None`(Top 종류는 임의값, `dsl.rs:211-213`, `mapping-expressions.md:182-197`).
7. **Chip/Cluster/Slice 크기는 하드웨어 개수와 정확히 일치.** `Cluster::SIZE==2`, `Slice::SIZE==256`. 적게 쓰면 `#` 패딩. 현재 런타임은 칩 단위라 부분 사용 미지원(`spatial-temporal-dimensions.md:56-69`).
8. **DM 시작 주소 정렬.** `size_of::<D>()` 배수 아니면 read-modify-write로 ~50× 느려짐(`동:79`).
9. **타입체크 통과 ≠ NPU로 낮춰짐(실측).** 벤더 예제 크레이트를 `--backend typecheck`로 빌드하면 커널 낮추기 오류 **0건**인데, 같은 크레이트를 `--backend npu`로 빌드하면 **소스에서 추출한 커널 200개 중 63개가 실패**(137 OK, 68.5%)하고 그 63개 때문에 **크레이트 전체 빌드가 죽어 테스트가 0개 실행된다**. 실패 문구 상당수가 매핑 모양이다(다만 전부는 아니다 — 63개 중 **13개는 `internal compiler error`**, 2개는 제네릭 미단형화로 분류된다. ICE는 사용자가 매핑을 고쳐서 못 피한다):
   ```
   mir: Collect time mismatch. Expected: A / 4 % 4, got: A / 4
   mir: commit_trim packet mismatch. Expected A % 4 # 8 or a trimming of it, got A % 8
   lir: T7
          caused by: incorrect buffer size at T7: DramShape { inner: []|[A_1=8:8] }: buffer.size() (256) != num_chips * intra_chip_size (228)
   ```
   마지막 것은 벤더가 **`valid_*`로 이름 붙인** `contract_outer_assertions::lane_size::valid_size_{1,2,4}`가 실기 컴파일에서 죽는 사례다(256 vs 228/232/240). 출력 매핑은 셋이 서로 다르다 — `valid_size_1`은 `m![A, 1 # 8]`(A=8 → 64칸 × i32 = 256 B), 나머지 둘은 `m![A, R / 4 # 8]`·`m![A, R / 2 # 8]`(`contract_outer_assertions.rs:60,91`)로 역시 256 B다. 그런데 **부분 충전 레인 그룹의 꼬리 패딩이 DRAM 크기 계산에서 누락**된다 — §1의 Padding(`#`)이 타입 수준에서는 완벽히 성립하는데도 백엔드가 그 크기를 다르게 센다. → **매핑이 타입체크를 통과하고 이름이 `valid_*`라도 실기 가능성의 근거가 못 된다.** 전수 매트릭스·분류: [12-예제-전수실행](./12-예제-전수실행.md), [13-NPU-실기-매트릭스](./13-NPU-실기-매트릭스.md).
10. **세대 함정.** yik는 0.3 핀 + `src/furiosa-opt.tag`. 현재 0.4 래퍼는 커널 패키징을 `[package.metadata.furiosa-opt]`로 요구하므로 이 커널의 `--backend npu`/`compile`은 "no kernel packages found"로 거부(`_GROUND_TRUTH.md:9-16`). `to_dm(…, addr)`의 주소 인자도 0.3 시그니처(`동:23`).

## 8. NPU 없이 매핑 확인하기

매핑의 `SIZE`/`map`은 **순수 CPU 코드**라 카드·래퍼 없이 `cargo test`로 검증된다(커리큘럼 실험 02.1~02.3과 동형). 예:

```rust
// 임의의 base 프로젝트 test 모듈에 추가 (NPU 불필요, plain `cargo test`)
#[cfg(test)]
mod m_play {
    use furiosa_opt_std::prelude::*;
    axes![I = 512, J = 512, K = 64];

    #[test] fn slice_is_256() {
        assert_eq!(<m![I / 32, J / 32]>::SIZE, 256);       // §4-1 검산
    }
    #[test] fn tile_is_32x32() {
        assert_eq!(<m![I % 32, J % 32]>::SIZE, 1024);      // §4-2 검산 (32*32)
    }
    #[test] fn stride_mod_equiv_j() {
        type E = m![J / 64, J % 64];
        for i in 0..512 { assert_eq!(E::map(i), <m![J]>::map(i)); } // §5-2
    }
    #[test] fn order_of_ops() {
        // C % 32 / 2 = (C%32)/2 → 크기 32/2 = 16, 짝수 위치
        assert_eq!(<m![I % 32 / 2]>::SIZE, 16);            // §2
        assert_eq!(<m![I % 32 / 2]>::map(1), Some(i![I: 2]));
    }
}
```

- **주의(경로 오염 금지)**: 만약 `cargo furiosa-opt compile --dump-schedule/--dump-visa` 등으로 사이클 스케줄을 보려면(NPU 불필요) 반드시 `CARGO_TARGET_DIR=/home/jun/.claude/jobs/46bc5c7e/tmp/…`를 지정해 사용자 프로젝트 `target/` 오염을 피한다. 단 yik는 0.3 핀이라 `compile`이 커널 패키징 단계에서 거부될 수 있다(§7-10). 계측 옵션 존재는 `_GROUND_TRUTH.md:41-42` 참고.
- 잘못된 나눗수(`m![J / 7]`)로 컴파일 실패를 직접 유도하면(§7-4) "잘못된 레이아웃은 애초에 빌드되지 않는다"는 타입 수준 불변식을 눈으로 확인할 수 있다. **역은 성립하지 않는다** — `SIZE`/`map` 단위테스트와 typecheck를 다 통과한 매핑도 `--backend npu`에서 낮추기에 실패할 수 있다(§7-9).
