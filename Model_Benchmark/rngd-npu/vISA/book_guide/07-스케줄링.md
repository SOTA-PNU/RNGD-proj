## 1. 책이 뭐라 하는가 — 스케줄러는 두 가지만 본다

책 첫 문단(`docs/scheduling.md:4`):

> The scheduler translates vISA programs into execution schedules from programmer input: the execution context selected for each operation, the written order of operations, and explicit memory address assignments. The scheduler reduces execution cycles while preserving the exact same results as sequential execution.

정리하면 스케줄러가 소비하는 입력은 세 가지이지만 본질은 두 축이다.

1. **연산에 붙인 컨텍스트** (`ctx.main` / `ctx.sub` / `ctx.tdma` / `ctx.pdma` 중 무엇으로 시작했나)
2. **코드에 쓰여진 순서 + 명시한 주소** (재배치는 하되 순차 실행과 같은 결과를 보장하는 범위 안에서만)

**초심자용 쉬운 설명** — GPU/CPU 컴파일러는 레지스터도 알아서 배정하고 연산도 자유롭게 재배치한다. vISA는 다르다. 메모리 자동 할당기가 없어서 "이 텐서는 DM 어디"를 (0.3에서는) 사람이 박고, 스케줄러는 그 주소를 근거로 의존성을 계산한다. 대신 결과는 항상 순차 실행과 동일하게 나오도록 보장된다(`scheduling.md:5`). 즉 **동시성은 스케줄러가 자동으로 짜 주지만, 그 판단 재료(컨텍스트 배치 + 주소)는 사람이 준다.**

## 2. 실행 컨텍스트 — 책은 3개, 코드는 4개

### 책 (docs/scheduling.md:79)
하드웨어가 노출하는 실행 컨텍스트는 개념상 셋이다(`docs/computing-tensors__index.md:71`).

- **Main** (`ctx.main`) — Tensor Unit 파이프라인 전체를 구동, 주 연산. (`scheduling.md:83`, `computing-tensors__index.md:73`)
- **Sub** (`ctx.sub`) — 같은 파이프라인의 **부분집합**. Contraction 엔진과 일부 기능이 빠진다. 보통 main이 계산하는 동안 다음 피연산자를 TRF/VRF로 미리 당겨오는(prefetch) 용도. (`scheduling.md:84`, `computing-tensors__index.md:74`, `:78`)
- **DMA** (`ctx.tdma`) — Tensor Unit 바깥의 DMA 엔진만 굴려 HBM↔DM, HBM↔SPM, DM↔SPM 이동. (`scheduling.md:85`, `computing-tensors__index.md:75`)

### 우리 코드 (furiosa-opt-std 0.4.0)
`Context` 구조체는 **필드가 4개**다. "DMA 컨텍스트"가 텐서 DMA와 PCIe DMA로 갈리기 때문이다.

```rust
// ~/.cargo/registry/.../furiosa-opt-std-0.4.0/src/context.rs:69
pub struct Context {
    pub main: TuContext<{ Tu::Main }>,     // context.rs:71  메인 텐서 유닛
    pub sub:  TuContext<{ Tu::Sub }>,      // context.rs:73  서브 텐서 유닛
    pub tdma: DmaContext<{ Dma::Tensor }>, // context.rs:75  텐서 DMA (칩 내 HBM<->DM)
    pub pdma: DmaContext<{ Dma::Pcie }>,   // context.rs:77  PCIe DMA (호스트<->HBM)
}
```

`enum Tu { Main, Sub }` (`context.rs:23`), `enum Dma { Tensor, Pcie }` (`context.rs:32`). `Context::acquire()` 는 `Mutex`로 감싼 전역 싱글톤을 돌려준다(`context.rs:85`) — 디바이스 컨텍스트는 프로세스에 하나뿐이다.

**초심자용 쉬운 설명 (WHY 필드로 나눴나)** — 한 함수 안에서 `ctx.tdma`로 DMA를 돌리고 `ctx.sub.begin(...)`으로 프리페치를 시작하고 `ctx.main.begin(...)`으로 본 계산을 동시에 적을 수 있는 건 Rust의 **필드별 분리 빌림(disjoint borrow)** 덕분이다. 서로 다른 필드라 각각 `&mut`로 독립적으로 빌린다. **소스에서 서로 다른 컨텍스트를 동시에 빌리는 모양**이 곧 **하드웨어에서 그 컨텍스트들이 동시에 도는 것**과 대응된다.

| 컨텍스트 | 필드 | tpe(스케줄 JSON) | 구동 자원 | 커널에서 하는 일 |
|---|---|---|---|---|
| Main | `ctx.main` | `Main` | MainContext (+VectorEngine 등) | 축약/벡터 등 주 연산 |
| Sub | `ctx.sub` | `Sub` | SubContext | TRF/VRF 프리페치 (Contraction 불가) |
| Tensor DMA | `ctx.tdma` | `DmaLoad`/`DmaStore` | DmaEngine | 칩 내 HBM↔DM |
| PCIe DMA | `ctx.pdma` | `DmaLoad`/`DmaStore` | DmaEngine | 호스트↔HBM (`launch` 전후) |

> **주의** — 책은 "3개"라고 세지만 이는 개념 분류이고, 실제 API 자원은 4갈래다. 커리큘럼 08도 같은 지적을 한다(`08_scheduler.md:45`).

## 3. 동시성 규칙 — 같은 컨텍스트는 줄 서고, 다른 컨텍스트는 같이 간다

책(`scheduling.md:89`):

> Operations in the same context run sequentially, but operations in different contexts can run in parallel.

직렬화(순서 강제)가 생기는 원인은 딱 두 가지다.

1. **자원 충돌(resource conflict)** — 두 연산이 같은 컨텍스트/스케줄링 단위를 써야 하면 뒤엣것이 기다린다. 예: main과 sub가 둘 다 Vector 엔진을 필요로 하면 하나가 대기(`scheduling.md:97`).
2. **메모리 의존성(memory dependency)** — 같은 주소에서 해저드가 생기면 순서를 지킨다(`scheduling.md:94`).

**함정** — "다른 컨텍스트면 무조건 병렬"이 아니다. 같은 주소에서 RAW/WAR/WAW가 걸리면 다른 컨텍스트라도 대기가 들어간다. 반대로 같은 컨텍스트는 주소가 안 겹쳐도 자원 충돌로 직렬화된다.

## 4. 해저드 3종 — RAW / WAR / WAW (Memory Allocation)

Tensor Unit은 HBM에 있는 텐서를 직접 계산하지 못한다. 반드시 메모리 계층을 명시적으로 타고 올라와야 하고(`scheduling.md:122`), **모든 텐서 이동에 목표 계층과 정확한 주소를 지정**해야 한다(`scheduling.md:125`). 스케줄러는 그 주소로 텐서 수명을 추적해 세 해저드를 판정한다(`scheduling.md:128`–`:130`).

| 해저드 | 책 정의 | 뜻 | 스케줄러 처리 |
|---|---|---|---|
| **RAW** (read-after-write) | consumer must wait until the producer has written | 쓴 값을 봐야 하는 읽기 | 읽기 앞에 암묵적 대기 삽입 |
| **WAR** (write-after-read) | write must not overwrite while an earlier reader still needs the old value | 아직 읽는 값을 덮어쓰기 금지 | 쓰기를 읽기 뒤로 미룸 |
| **WAW** (write-after-write) | overlapping writes must follow original program order | 같은 주소 쓰기 순서 보존 | 프로그램 순서 유지 |

**초심자용 쉬운 설명** — 배리어(`wait()`)를 손으로 넣을 필요가 없다. "main이 sub를 기다린다"는 건 마법이 아니라 **둘이 같은 주소에서 RAW가 생겼을 때** 스케줄러가 main 앞에 대기를 넣어 주는 것뿐이다. 주소가 안 겹치고 해저드가 없으면 둘은 그냥 겹쳐 돈다. 이 판정의 입력이 바로 "우리가 명시한 주소"라서, 자동 동기화는 되지만 **주소는 여전히 사람이 준다**(0.3) 는 결론이 나온다.

## 5. 우리 커널의 sub/main 분업 (핵심)

책의 MNIST 예제(`scheduling.md:26`)는 FC 두 층 MLP다. 구조는 우리 예제와 같다: **sub가 한 피연산자를 레지스터파일로 적재하고, main이 그것을 읽어 축약한다.** sub는 Contraction을 못 하므로(부분집합) "적재 담당", main이 "계산 담당"이라는 자연스러운 분업이다.

### 5.1 yik 예제 (0.3세대) — sub→TRF, main→contract

`/home/jun/yik/src/kernel/gemm_kernel.rs:18`–`:49` (요지):

```rust
// yik/src/kernel/gemm_kernel.rs:18  (0.3 API: to_dm 에 주소 인자를 직접 준다)
let a = a.to_dm(&mut ctx.tdma, 0);        // A -> DM 주소 0
let b = b.to_dm(&mut ctx.tdma, 1 << 12);  // B -> DM 주소 4096 (겹침 회피)

// yik/src/kernel/gemm_kernel.rs:25  sub: B 를 TRF 로 적재 (Contraction 안 함)
let b_trf = ctx.sub.begin(b.view())
    .fetch::<...>().collect::<...>()
    .to_trf(TrfAddress::Full);

// yik/src/kernel/gemm_kernel.rs:35  main: A 를 흘려 contract, b_trf 를 읽음(RAW)
let result = ctx.main.begin(a.view())
    .fetch::<...>().collect::<...>()
    .contract_outer::<..., _, _>(&b_trf)   // <-- b_trf 를 여기서 읽음 => RAW
    .contract_packet::<m![1]>()...
    .commit(0);
result.to_hbm(&mut ctx.tdma, 2 << 28)
```

같은 분업이 `gemv_kernel.rs:23`(vector→TRF, main이 matrix 축약), `dot_product_kernel.rs:22`(rhs→TRF, main이 lhs 축약)에도 그대로 있다. `elementwise_mul_kernel.rs:21`은 축약이 없어 sub가 **VRF**(TRF 아님)에 rhs를 적재하고 main이 `vector_fxp`로 곱한다 — Contraction이 아니라 Vector 엔진 경로.

> **함정 (GROUND_TRUTH:33)** — `yik/src/kernel/gemm_kernel.rs:8` 주석 "Each slice handles a 16 × 16 output tile" 은 **틀렸다**. `Slice = m![I/32, J/32]` 는 16×16 **격자(=256 슬라이스)** 이고, 각 슬라이스가 담당하는 타일은 `m![I%32, J%32] = 32×32` 다. 검산: 256 × 1024 = 262,144 = I·J (512×512). 아래 0.4 트윈은 이 주석이 고쳐져 있다.

> **함정 (GROUND_TRUTH:35)** — 같은 커널 주석의 "Switch Engine distributes..." 는 오해 소지. 실제로 `switch()` 는 호출되지 않고, 분배는 `to_dm` 의 Slice 타입 파라미터가 한다.

### 5.2 0.4세대 트윈 — visa_dn `dn_state_bf16`

yik는 `furiosa-opt-std = "0.3"` 를 핀하고 `src/furiosa-opt.tag` 마커를 쓴다. 현재 0.4 래퍼는 `[package.metadata.furiosa-opt]` 를 요구하므로 **yik는 그대로는 `compile`/`--backend npu` 가 안 된다** (GROUND_TRUTH:14, "no kernel packages found"). 그래서 사이클 실측은 같은 데이터플로를 0.4 API로 옮긴 스크래치 프로젝트 `.../tmp/visa_dn` 으로 뽑았다.

`.../tmp/visa_dn/src/kernel/dn_state_kernel.rs:23`–`:52` — DeltaNet 상태 갱신 `S[k,v] = Σ_c Kt[k,c]·Dt[v,c]` (외적 누산, GEMM과 동형):

```rust

    .collect::<m![V % 8, V / 8 % 4, C / 16], m![C % 16]>()
```

`dn_state_kernel.rs:14` 주석은 올바르다: "16 x 16 grid of slices; each slice owns a 32 x 32 tile" — yik의 오류를 교정한 판본이다.

## 6. 실측 스케줄 — `--dump-schedule` (NPU 없이 사이클을 준다)

### 6.1 핵심 사실 (GROUND_TRUTH:41–42)
- `furiosa-tcc` 에는 덤프/프로파일 옵션이 **전무**하다.
- `cargo furiosa-opt compile` 은 `--dump-schedule / --dump-ir / --dump-visa / --dump-graph / --dump-summary` 를 제공하며, **카드를 잡지 않고** 사이클 단위 스케줄을 낸다. `compile` 은 커널만 직접 컴파일할 뿐 `--backend npu` 평가가 아니다(래퍼 `--help` 실측: `compile` = "Compile #[device] functions to kernels directly, without a cargo build").
- 덤프는 AOT 컴파일러 산출물이라 NPU를 점유하지 않는다 → **실기 테스트가 카드를 쓰고 있는 동안에도 동시 실행 가능**하다. 이 세션에서 커널 130개 스케줄을 이 경로로 뽑았다(§6.7).

> **이 절의 사이클은 컴파일러 스케줄 모델의 "예측"이다.** 실기(NPU)에서 실제로 돈 결과가 아니다. 실기 실행 결과는 [13-NPU-실기-매트릭스](./13-NPU-실기-매트릭스.md)(테스트 89개 중 80 PASS)에 있고, **스케줄이 나온다 ≠ 실기에서 돈다**(§10의 함정).

### 6.2 이 세션에서 실제로 돌린 명령
```bash

cd /home/jun/.claude/jobs/46bc5c7e/tmp/visa_dn
cargo furiosa-opt compile dn_state_bf16 \
  --dump-schedule .../visa_book_guide/dn_state_bf16.sched.json
# 출력: Compiling [1/1] kernel::dn_state_kernel::dn_state_bf16
#       Finished 1 compiled, 1 filtered out
#       (exit 0, NPU 미점유)
```
- 위치 인자 `dn_state_bf16` 은 `#[device]` 이름 부분일치 필터다(`appendix__schedule-viewer.md`). `dn_state_f32` 는 "1 filtered out" 으로 제외됐다.

### 6.3 실측 스케줄 표 — `dn_state_bf16` (bf16 변형)

JSON `instructions[]` 의 `tpe` · `contexts` · `lifetime.begin/end` 를 그대로 옮김. 단위는 스케줄러 사이클.

| index | tpe | contexts | begin → end | 지속 | 소스 |
|---|---|---|---|---|---|
| 1 | `DmaLoad` | DmaEngine | 2003 → 5121 | 3118 | `dt.to_dm` (`:29`) |
| 7 | `Sub` | SubContext | 5121 → 5896 | 775 | `ctx.sub…to_trf` (`:31`) |
| 9 | `DmaLoad` | DmaEngine | 5321 → 8341 | 3020 | `kt.to_dm` (`:28`) |
| 14 | `Main` | MainContext**+VectorEngine** | 8341 → 9118 | 777 | `ctx.main…commit` (`:38`) |
| 17 | `DmaStore` | DmaEngine | 9118 → 81849 | **72731** | `state.to_hbm` (`:52`) |
| 21 | `Core` | PeCore | 81849 → 81849 | 0 | `state.to_hbm` (`:52`) |
| `ExplicitSync(5)` | `Core` | PeCore | 81849 → 82449 | 600 | (동기화 배리어) |

**총 스케줄 길이 ≈ 82,449 사이클.** (이 커널에서는 `tpe` 가 `DmaLoad / DmaStore / Sub / Main / Core` 5종으로만 나온다. 130개 전수에는 `DmaDtod`·`DmaGather` 등 다른 DMA tpe도 있다 — §6.7.)

### 6.4 이 표에서 읽어야 할 4가지

**(a) 같은 컨텍스트 = 직렬 (자원 충돌).** 두 `DmaLoad`(idx 1, 9)는 모두 `DmaEngine` 자원이다. dt 로드가 5121에 끝나야 kt 로드가 5321에 시작한다(+200 사이클 갭). 서로 데이터 의존이 없는데도 **엔진이 하나라 줄을 선다** — 책 `scheduling.md:97` 의 "same scheduling resource" 규칙 그대로다.

**(b) 다른 컨텍스트 = 병렬.** `Sub`(idx 7, SubContext, 5121–5896)와 kt `DmaLoad`(idx 9, DmaEngine, 5321–8341)는 **5321–5896 구간에서 겹쳐 돈다.** 컨텍스트가 다르니 병렬(`scheduling.md:89`). 소스엔 어떤 동기화도 없다.

**(c) RAW 게이팅이 시작 시각을 정한다.**
- `Sub`(idx 7)는 dt DM 텐서(idx 1의 출력)를 읽는다 → dt 로드가 끝나는 **5121에 정확히 시작**(RAW).
- `Main`(idx 14)은 입력이 둘: kt DM(idx 9, 8341 종료)과 dt_trf(idx 7, 5896 종료). **더 늦은 producer(8341)에 맞춰 시작**한다. 즉 dt_trf 프리페치는 5896에 이미 끝났지만 kt 로드가 끝나길 ~2445 사이클 기다린다 → **sub 프리페치가 kt DMA 뒤로 완전히 숨었다.** 이게 "sub로 미리 당겨 두면 main 대기시간이 준다"의 실측 증거다(책 NOTE `scheduling.md:108`–`:114` 의 overlap 논리와 동일).
- `DmaStore`(idx 17)는 state(idx 14, 9118 종료)를 읽어 9118에 시작(RAW).

**(d) 진짜 병목은 계산이 아니라 저장이다.** `DmaStore`(state→HBM) 하나가 72,731 사이클로 전체의 **약 88%**다. 실제 연산 구간(2003–9118)은 ~7,115 사이클(8.6%)에 불과. 스케줄을 실측하면 "우리가 최적화할 곳은 축약이 아니라 결과 write-back"이라는 걸 눈으로 본다.

### 6.5 f32 변형과의 대조 — `tpe`/`contexts` 가 달라진다

같은 데이터플로의 `dn_state_f32`(`:62`, `.cast()` 없이 f32 누산을 그대로 commit) 스케줄(`.../tmp/audit_out/f32_sched.json`)과 비교:

| 항목 | bf16 (`dn_state_bf16`) | f32 (`dn_state_f32`) |
|---|---|---|
| `Main`(idx 14) contexts | `MainContext` **+ VectorEngine** | `MainContext` 만 |
| 원인 | `.cast::<bf16,…>()`(`:48`)가 캐스팅 경로를 씀 | cast 없음 → Vector 엔진 미개입 |
| `state` 텐서 size (JSON) | 1,048,576 | 2,097,152 (2×, f32=4B) |
| 총 길이 | ≈ 82,449 | ≈ 82,328 |

**교훈** — 커널에 `.cast()` 한 줄을 넣고 빼는 것만으로 `contexts` 목록에 `VectorEngine` 이 들락거린다. 스케줄 JSON은 "어느 엔진이 실제로 개입하는가"를 인스트럭션 단위로 드러낸다.

> **주의 (미확인)** — JSON의 `util.total_util/base_util/efficiency` 는 **커널 130개 전부, 모든 인스트럭션에서 `0.0`** 이다(이 덤프의 항구적 성질이지 이 커널만의 문제가 아니다). 따라서 begin/end **순서·의존성**은 신뢰하되, `DmaStore` 72,731 사이클의 절대값이 어떤 비용모델에서 나왔는지(그리고 f32/bf16 store 지속이 동일한 이유)는 이 덤프만으로는 단정하지 않는다. 절대 사이클은 상대 비교용으로만 사용.
> 단, "**store/DMA가 사이클을 지배한다**"는 결론 자체는 130개 커널로 확대 재현됐다(§6.7, 커널별 DMA 비중 중앙값 82.8%).

|---|--:|
| 90% 이상 | **54 / 130** |
| 50% 이상 | **107 / 130 (82%)** |
| 50% 미만 | 23 / 130 |

**사이클 스팬 분포** (커널 130개):

**분석기 검증 기준점 — `mnist::forward`**: **17,953 사이클 / 인스트럭션 22개.** 엔진 분해 DmaEngine **12,365**(스팬 대비 **68.9%**), MainContext 7,682, VectorEngine 1,162, SubContext 790, PeCore 600. DRAM io 419,968 B, edf 68,106 B. 이 값은 [11-MNIST-실행결과](./11-MNIST-실행결과.md)에 독립적으로 기록된 수치와 **정확히 일치**한다 → 위 130개 집계를 낸 분석기가 옳다는 근거. **여기에 `summary.log` 의 `total_execution_cycle` 이 세 번째 독립 확인으로 붙는다(§6.8c) — 17,953 / main 7,682 / sub 790 / io 12,365 가 자릿수까지 같다.** 또한 이 엔진 분해 합(22,599)이 스팬(17,953)을 넘는 이유가 §6.8(a)의 `hidden` 이다.

> **같은 자리가 두 번 발목을 잡는다** — 사이클을 지배하는 그 DMA 경로가 실기 컴파일 실패에서도 반복해 등장하는 원인 중 하나다: `strides([8,128,4,...]) is not aligned by 8`(DMA 시퀀서 8 B 정렬 요구), `tail_size % min_align != 0` 등으로 커널 여럿이 실기로 낮춰지지 않는다. 실패 커널 목록·분류는 [12-예제-전수실행](./12-예제-전수실행.md).

### 6.8 `--dump-summary` 가 `--dump-schedule` 보다 정밀하다 — `hidden` 과 `*_only`

`--dump-schedule` 은 인스트럭션별 begin/end만 준다. 총 사이클은 `max(lifetime.end)` 로 우리가 계산해야 하고, 엔진별 점유를 더하면 스팬을 넘는다(§6.7). **`--dump-summary` 는 그 분해를 컴파일러가 직접 적어 준다.**

```bash
cargo furiosa-opt compile -p furiosa-opt-examples "mnist::forward" --dump-summary /tmp/dsum
# Finished 1 compiled, 206 filtered out   (exit 0, NPU 미점유)
```

`/tmp/dsum/summary.log` 실측 발췌 — **자릿수 그대로**:

```
- total_instruction_cycle  : 23337 (main + sub + io)
- total_execution_cycle    : 17953 (main + sub + io - hidden)
- estimated_execution_cycle: 17953 (skip-aware)
- main                     : 42.790% (7682)
- sub                      :  4.400% (790)
- io                       : 68.874% (12365)
- sync                     :  0.000% (0)
- spill_io                 :  0.000% (0)
- main_only                : 12.226% (2195)
- sub_only                 :  4.400% (790)
- io_only                  : 38.311% (6878)
- sync_only                :  0.000% (0)
- spill_io_only            :  0.000% (0)
- dram_usage_io            : 419968B
- peak_memory_usage_bytes: 440803328
```

> 이 수치도 `--dump-schedule` 과 같은 **컴파일러 산출물**이다. 실기(NPU) 실행 측정이 아니다.

**(a) `hidden` 이 "엔진 점유 합 > 100%" 의 정체다.** `io 68.874% + main 42.790% + sub 4.400% = 116.064%` 로 100%를 넘는데, 이건 오류가 아니라 **엔진이 겹쳐 돌기 때문**이다. 로그가 그 차이를 이름으로 붙여 준다: 인스트럭션 사이클 합 **23,337** − 실행 사이클 **17,953** = **5,384 사이클이 hidden**(다른 엔진 뒤로 숨은 구간)이다. (`total_instruction_cycle` 이 `(main+sub+io)` 표기와 달리 `7,682+790+12,365 = 20,837` 과 2,500 어긋나는 점은 §11에 미확인으로 남겼다.) §6.7의 "비중은 엔진별 사이클 합 대비다(엔진끼리 겹쳐 도니 이 합은 스팬 합보다 크다)" 라는 단서와 §6.4(b)의 "다른 컨텍스트 = 병렬" 이 여기서 하나의 수치로 만난다.

**(b) `*_only` 가 겹치지 않은 순수 점유 — 정직한 병목 수치다.** mnist에서 `io` 총 점유는 68.874%(12,365)지만, **다른 엔진에 가려지지 않은 순수 io는 `io_only` 38.311%(6,878)** 다. `main_only` 12.226%(2,195) / `sub_only` 4.400%(790) / `sync_only` 0 / `spill_io_only` 0. `*_only` 합은 54.938%(9,863)로 100%를 넘지 않는다(정의상 배타적).

> **"DMA가 지배한다"를 말할 때 어느 쪽 숫자인지 밝혀야 한다.** 68.874%는 *총 점유*, 38.311%는 *가려지지 않은 부분*이다. 이 문서 §6.7이 mnist에 대해 쓴 "DmaEngine 12,365(스팬 대비 68.9%)"는 앞쪽(총 점유)이다. 지연을 줄일 여지를 논할 때 쓸 값은 뒤쪽(`io_only`)이다.

**(c) 17,953 의 세 번째 독립 확인.** 서로 다른 세 경로가 자릿수까지 일치한다.

| 출처 | 총 사이클 | main | sub | io |
|---|--:|--:|--:|--:|
| `--dump-schedule` → 분석기 `max(lifetime.end)` (§6.7) | 17,953 | 7,682 | 790 | 12,365 |
| [11-MNIST-실행결과](./11-MNIST-실행결과.md) 의 독립 기록 | 17,953 | 7,682 | 790 | 12,365 |
| `summary.log` `total_execution_cycle` | **17,953** | **7,682** | **790** | **12,365** |

`dram_usage_io 419,968 B` 도 §6.7의 기존 기록과 같다.

**(d) 백분율의 분모는 `total_execution_cycle` 이다** (검산: `7682/17953 = 42.790%`, `12365/17953 = 68.874%`, `6878/17953 = 38.311%`, `2195/17953 = 12.226%`, `790/17953 = 4.400%` — 0이 아닌 6줄 `main`·`sub`·`io`·`main_only`·`sub_only`·`io_only` 전부 소수 3자리까지 재현). 즉 100%가 곧 17,953 사이클이다.

**(e) 두 덤프의 분해 축이 다르다.** `summary.log` 는 **컨텍스트 축**(main/sub/io/sync/spill_io), `--dump-schedule` 은 **엔진 축**(DmaEngine/MainContext/VectorEngine/SubContext/PeCore)이다. 겹치는 셋은 정확히 일치하지만(main=MainContext, sub=SubContext, io=DmaEngine), §6.7이 mnist에서 본 `VectorEngine 1,162` · `PeCore 600` 에 대응하는 줄은 `summary.log` 에 **없다**. 두 표를 나란히 놓을 때 이 축 차이를 무시하면 안 된다. ([11-MNIST-실행결과](./11-MNIST-실행결과.md) §4는 `VectorEngine 1,162` 가 Main 인스트럭션 4개의 동시 점유라 `main 7,682` 안에 이미 포함된다고 본다 — 인스트럭션별 근거는 [10-MNIST-실전해부](./10-MNIST-실전해부.md) §7.)

## 7. 이중 버퍼링(Double-Buffering) — 기다림을 지우는 패턴

### 책 (docs/scheduling.md:136)
sub가 채운 바로 그 회차에 main이 같은 절반을 읽으면 RAW로 main이 기다린다(§6.4c). 이 대기를 없애려면 **TRF를 두 절반으로 쪼개, sub는 "다음" 배치를 한 절반에 채우고 동시에 main은 "지금" 배치를 다른 절반에서 읽는다.** 회차마다 절반을 교대한다.

```rust
// docs/scheduling.md:146  (책 예제, 0.4 메서드 이름 to_trf_at 사용)
let mut trf = ctx.sub.begin(weights[0].view())
    .fetch::<...>().collect::<...>()
    .to_trf_at(TrfAddress::FirstHalf);          // 루프 전 첫 절반 프라이밍
for i in 0..N {
    let other_half = if i % 2 == 0 { TrfAddress::SecondHalf } else { TrfAddress::FirstHalf };
    let next_trf = (i + 1 < N).then(|| ctx.sub.begin(weights[i+1].view())
        .fetch::<...>().collect::<...>().to_trf_at(other_half));   // 반대 절반에 다음 배치
    ctx.main.begin(input[i].view()).contract_outer::<...>(&trf)...; // 현재 절반 읽기
    if let Some(t) = next_trf { trf = t; }
}
```

**WHY 겹쳐 도나** (`scheduling.md:173`): sub의 쓰기와 main의 읽기가 **서로 다른 TRF 절반(=다른 주소)** 이라 WAR가 없고, 동시에 **다른 컨텍스트**라 자원 충돌도 없다. 위험도 충돌도 없으니 스케줄러가 자동으로 완전히 겹친다. 같은 절반을 쓰면 WAR로 다시 직렬화된다.

### 우리 코드의 대응 (0.4.0 API)
- `to_trf()` — 인자 없이 **`TrfAddress::Full` 기본** (`collect.rs:80`).
- `to_trf_at(address: TrfAddress)` — 절반 명시, 이중 버퍼링용 (`collect.rs:87`).
- `enum TrfAddress { FirstHalf, SecondHalf, Full }` (`tensor/memory.rs:108`).
- VRF는 하드웨어가 절반을 강제하지 않는다(`scheduling.md:142`). `to_vrf()` (`collect.rs:103`) / `to_vrf_at(address: u64)` (`collect.rs:109`)로 8KB 안에서 겹치지 않는 영역을 사람이 직접 잡는다.

### 하드웨어 근거 (docs/computing-tensors__register-files.md:97)
> The TRF enables double-buffering by splitting each bank into two halves: the TRF Sequencer loads from one half while a store fills the other, and the two can be flipped between iterations.

- `Full` = 뱅크 128행 전부, `FirstHalf` = 0–63행, `SecondHalf` = 64–127행 (`register-files.md:98`).
- 절반 모드는 슬라이스당 **40 KB로 용량 제한** (`register-files.md:99`).
- 두 절반은 같은 뱅크를 공유해 같은 사이클에 같은 뱅크를 치면 읽기가 우선(파이프라인이 이번 사이클에 데이터가 필요하니), store는 대기(`register-files.md:103`–`:104`).

> **참고** — 위 실측 커널(`dn_state`)은 단일 배치라 `to_trf()`(Full)만 쓴다. 이중 버퍼링은 위 루프처럼 `to_trf_at`로 절반을 교대해야 관측된다. 우리 5개 yik 예제에는 이중 버퍼링 루프가 없다(모두 1-shot).

## 8. 세대 차이 — 0.3(yik) vs 0.4(visa_dn) 주소 API

GROUND_TRUTH:23 — 0.4는 to_dm/to_hbm/to_trf/commit 의 **명시적 주소 인자를 제거**했다. 실측 시그니처:

| 동작 | 0.3세대 (yik) | 0.4세대 (visa_dn / 크레이트) | 0.4 소스 |
|---|---|---|---|
| HBM→DM | `to_dm(&mut ctx.tdma, 0)` | `to_dm(&mut ctx.tdma)` | `memory.rs:450` |
| HBM→DM (주소 명시) | — | `to_dm_at(&mut ctx.tdma, addr)` | `memory.rs:466` |
| Collect→TRF | `to_trf(TrfAddress::Full)` | `to_trf()` / `to_trf_at(addr)` | `collect.rs:80` / `:87` |
| Collect→VRF | `to_vrf(0)` | `to_vrf()` / `to_vrf_at(addr)` | `collect.rs:103` / `:109` |
| 결과→DM | `commit(0)` | `commit()` | `commit.rs:25` |
| DM→HBM | `to_hbm(&mut ctx.tdma, 2<<28)` | `to_hbm(&mut ctx.tdma)` | `memory.rs:388` |

- `type Address = u64` (DM/VRF 주소), TRF만 `enum TrfAddress` (`memory.rs:23`, `:108`) — 이 타입 구분은 두 세대 공통.
- **결론** — 0.3은 "주소를 항상 손으로", 0.4는 "기본은 자동, 필요하면 `_at`". 그래도 스케줄러의 해저드 판정은 여전히 주소 기반이다(자동 배치는 컴파일러가, 명시가 필요하면 `_at`).

## 10. 함정 / 주의 모음

- **`compile --dump-schedule` 은 NPU를 안 잡는다.** 카드 없이 사이클을 뽑는 유일한 공식 경로. `furiosa-tcc` 엔 이런 옵션이 없다(GROUND_TRUTH:41–42). 단 `CARGO_TARGET_DIR` 를 tmp 하위로 격리해 target 오염을 피하라.
- **yik는 현재 래퍼로 compile 불가.** `furiosa-opt-std="0.3"` + `src/furiosa-opt.tag` 조합은 "no kernel packages found"로 거부된다. 0.4 래퍼는 `[package.metadata.furiosa-opt]` 를 요구한다(GROUND_TRUTH:9–10, 14). 사이클 실측은 0.4 프로젝트(visa_dn)로만 가능.
- **"다른 컨텍스트=항상 병렬"은 틀림.** 같은 주소 RAW/WAR/WAW면 대기가 들어간다. 실측에서 Main은 dt_trf가 준비돼도 kt 로드를 기다렸다(§6.4c).
- **"같은 컨텍스트=항상 직렬".** 데이터 의존이 없어도 자원(엔진)이 하나면 줄 선다. 두 DmaLoad가 그 예(§6.4a).
- **sub에 Contraction을 넣지 말 것.** sub는 main의 부분집합이라 Contraction 엔진을 못 굴린다(`computing-tensors__index.md:78`). 축약은 main, sub는 TRF/VRF 프리페치.
- **주소 자동 할당기는 없다(개념).** 0.4가 기본 주소를 자동으로 잡아 주지만, 겹치지 않게 배치하는 책임과 `_at` 로 명시할 권한은 여전히 프로그래머에게 있다. 두 텐서가 겹치면 실제 SRAM 손상 + 스케줄러 오판이 동시에 난다.
- **이중 버퍼링은 절반 교대가 핵심.** sub/main이 같은 TRF 절반을 쓰면 WAR로 오버랩이 깨진다(`scheduling.md:173`). 매 회차 FirstHalf/SecondHalf를 번갈아야 한다.
- **JSON의 util은 커널 130개 전부에서 0.0.** 절대 사이클(특히 store 72,731)의 비용모델 근거는 미확인. 순서/의존성 관측용으로 쓰고 절대값은 상대 비교로만.
- **엔진 점유 합이 100%를 넘는 건 오류가 아니다.** 엔진이 겹쳐 돌기 때문이고, 그 겹친 양이 `summary.log` 의 `hidden` 이다(mnist: 23,337 − 17,953 = **5,384**). 총 사이클로 쓸 값은 `total_execution_cycle`(17,953)이지 `total_instruction_cycle`(23,337)이 아니다(§6.8a).
- **"io 68.874%" 와 "io_only 38.311%" 를 섞지 말 것.** 앞은 총 점유, 뒤는 다른 엔진에 가려지지 않은 순수 점유다. 병목을 말할 때 어느 쪽인지 밝혀야 한다(§6.8b).
- **사이클 총량이 필요하면 `--dump-schedule` 대신 `--dump-summary` 를 쓰라.** `--dump-schedule` 은 총 사이클 필드가 없어 `max(lifetime.end)` 를 직접 계산해야 하지만, `summary.log` 는 총량·컨텍스트별 점유·`hidden`·`*_only` 를 컴파일러가 적어 준다. 둘 다 NPU를 잡지 않고 둘 다 **컴파일러 산출물**이다.
- **프롤로그 ~2000은 DMA 기동 지연이다(런타임 초기화가 아니다).** 130개 실측: 첫 인스트럭션이 `DmaLoad`면 2003, `DmaDtod`면 2000, `Sub`면 **0**에서 시작(§6.7). 프롤로그가 스팬의 절반을 넘는 커널이 130개 중 **16개**다(스팬 3,050~3,762 커널에서 2,003이 53~66%). 짧은 커널끼리 비교할 때는 프롤로그를 뺀 값으로 보라. 스팬 최소(16)인 커널은 `Sub` 로 시작해 프롤로그가 아예 없다.
- **명령 수로 비용을 추정하지 말 것.** 인스트럭션 **12개**인 `at_primitives::vrf::multi_vrf_at` 가 10,845,036 사이클인데, 인스트럭션 **258개**인 `tile::tile_simple` 은 6,840,200 사이클로 오히려 싸다. 비용은 명령 수가 아니라 DMA 쪽에 붙는다(§6.7).
- **스케줄이 나온다 ≠ 실기에서 돈다.** `compile`(스케줄 덤프)이 성공해도 실기에서는 커널 로더가 죽는 사례가 있다 — `reshape` 2건·`shuffle_slice` 1건은 `furiosa_kernel_load` 에서 범위초과로 **프로세스 abort** 한다. `reshape` 는 "range end index 50560 out of range for slice of length 33792"(50,560 / 33,792 = 1.496), `shuffle_slice` 는 56,576 / 37,888(1.493) — 세 건 모두 요구 크기가 실제의 약 1.5배다. 컴파일·에뮬레이션 모두 통과한다. 상세는 [13-NPU-실기-매트릭스](./13-NPU-실기-매트릭스.md).

## 11. 미확인으로 남긴 것

- `DmaStore` 72,731 사이클의 **비용모델 근거**, 그리고 f32(2×바이트)와 bf16의 store 지속이 동일하게 나오는 이유. JSON `util` 이 커널 130개 전부에서 0.0이라 덤프만으로 단정 불가. (현상 자체 — DMA가 사이클을 지배한다 — 는 130개로 재현 완료 §6.7. 남은 미확인은 **절대값의 근거**에 한정된다.)
- 프롤로그 **~2000 사이클의 물리적 정체**. "DMA 기동 지연"까지는 130개 실측으로 좁혔지만(§6.7: DmaLoad 2003 / DmaDtod 2000 / 비-DMA 0), 그 2000이 무엇을 채우는 시간인지는 책·래퍼 문서에 근거가 없다. (구 항목 "런타임 초기화 추정"은 폐기 — 비-DMA로 시작하는 커널 21개가 0에서 출발하므로 성립하지 않는다.)
- 0.4 `emulation` 백엔드가 커리큘럼 08의 "주소 무검사" 실험(08.2/08.3)을 **현재 세대에서 어떻게 재현**하는지. (emulation 자체는 이번 세션에 **104 passed / 0 failed** 로 정상 동작 확인 — §9. 미확인은 "주소를 검사하지 않는지"를 확인하는 실험 절차뿐이다. 이 문서는 스케줄 관측(compile 경로)에 한정했다.)
- 스케줄 JSON `history` 필드의 의미 — 130개 커널의 모든 인스트럭션에서 빈 객체 `{}` 라 해석 불가. (`physical_pages` 는 해결: `Sram` 텐서의 페이지 인덱스, §6.2.)
- `summary.json` 의 `operator_schedule_heuristic` · `beam_size` · `total_states_visited` 는 **키가 존재하지만 `mnist::forward` 에서 전부 `None`**, `schedule_method` 는 빈 문자열이다. 다른 커널·설정에서 채워지는지, 각 키가 무엇을 뜻하는지 미확인. **키가 있다는 사실만 실측**이다(§6.8).
