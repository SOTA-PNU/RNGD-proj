## 0. 이 문서의 위치와 전제

Tensor Unit 파이프라인 순서(책 `commit-adapter.md:139`, `transpose-engine.md:44` 종합):

```
Fetch → [Switch] → Collect → [Contraction] → [Vector] → [Cast] → [Transpose] → Commit Adapter(Trim→…) → Commit
```

- **Vector/Cast/Transpose 는 모두 선택적**. Contraction 을 건너뛴 elementwise 커널은 `Collect → Vector → Commit` 만 탄다(예: `~/yik/src/kernel/constant_add_kernel.rs`).
- **함정(세대 불일치)**: `~/yik` 는 `furiosa-opt-std = "0.3"` 을 핀한다(`Cargo.toml:40 부근`). 이 문서의 파일:줄 인용은 **우리 서버에 설치된 0.4.0 크레이트 소스**를 authoritative 로 삼는다(`_GROUND_TRUTH.md` 지시). 다행히 Vector/Cast/Commit 메서드 체인 모양은 0.3↔0.4 가 거의 같아 `~/yik` 코드가 그대로 대응 예로 쓸 수 있다. 다만 `--backend npu` 는 0.3 핀+`furiosa-opt.tag` 때문에 현재 래퍼에서 막힌다(`_GROUND_TRUTH.md:13-16`). 이 문서의 **코드 인용 자체**는 NPU 를 쓰지 않는다.
- **갱신(2026-07-24 실기 실측)**: `~/yik` 은 여전히 `--backend npu` 불가지만, **벤더 예제 크레이트 `furiosa-opt-examples` 를 게이팅해 실기(RNGD NPU)에서 테스트 89개를 실행했다.** 그래서 이 문서의 4개 엔진 중 Vector/Cast/Transpose 는 이제 **실기 실행 결과**가 있다(§10 요약, 각 절에 "실기 실측" 표시). 게이팅 레시피는 [12-예제-전수실행](./12-예제-전수실행.md) §7·§10, 매트릭스 원본은 [13-NPU-실기-매트릭스](./13-NPU-실기-매트릭스.md). 실기 실행 결과와 컴파일러 **스케줄 모델 예측**(`--dump-schedule`)은 이 문서에서 항상 구분해 적는다.

## 1. Vector Engine 전체 구조 (`vector-engine/index.md`)

### ① 책 요약
Vector Engine 은 elementwise 연산과 리덕션을 한다(GELU/SiLU 활성화, softmax/layernorm, 이항 연산, intra/inter-slice 리덕션). **32비트 타입 `i32`/`f32` 만** 받는다(`index.md:6`).

### ② 우리 코드 대응
```rust
// furiosa-opt-std-0.4.0/src/engine/vector/tensor/mod.rs:110,115
impl<'l, const T: Tu, P: CanApplyVectorInit, D: VeScalar, ...>
    TuTensor<'l, T, P, D, ...>
{
    pub fn vector_init(self) -> VectorInitTensor<'l, T, D, ...> { ... }
}
```
```rust
// furiosa-opt-std-0.4.0/src/engine/vector/scalar.rs:24,37,41
pub trait VeScalar: MaterializableScalar + Any { const KIND: VeScalarKind; }
impl VeScalar for i32 { const KIND = VeScalarKind::I32; }
impl VeScalar for f32 { const KIND = VeScalarKind::F32; }
```
`vector_init` 의 제네릭 바운드가 `D: VeScalar` 이고, `VeScalar` 는 `i32`/`f32` **딱 두 개에만** 구현된다. 즉 "i32/f32 only" 는 문서 문장이 아니라 **타입 시스템으로 강제된 하드웨어 제약**이다(`_GROUND_TRUTH.md:50` 과 일치). bf16 텐서로 `vector_init()` 을 부르면 컴파일이 거부한다.

### ③ 초심자용 설명
- DPE(Contraction) 는 bf16·f8 곱을 **f32 로**, i4·i8 곱을 **i32 로** 넓혀 누산해 내보낸다(`index.md:7`). 그래서 VE 입구에는 이미 32비트만 온다.
- DPE 를 건너뛰고 원본 저정밀을 VE 로 바로 넣고 싶으면, Fetch Engine 의 type-cast 어댑터가 미리 32비트로 넓혀야 한다(`index.md:8`). VE 자체는 넓히기를 안 해준다.

### ④ 체인 골격
`vector_init()` 으로 진입, `vector_final()` 로 탈출. 그 사이에 두 하위 블록이 있다:
- **Intra-Slice Chain** — 각 슬라이스 내부에서 elementwise/이항/슬라이스내 리덕션 (`vector_intra_slice_tag()` 로 진입).
- **Inter-Slice Reducer** — 클러스터의 **256 슬라이스**를 가로질러 리덕션 (`vector_inter_slice_reduce()` 로 진입).

두 블록이 다 도는 경우 순서는 **`IntraFirst`**(체인→리듀서) 또는 **`InterFirst`**(리듀서→체인). 4가지 경로(`tensor/mod.rs:27-30`):

| 경로 | 흐름 |
|---|---|
| intra only | `vector_init → intra_slice_tag → …stages… → vector_final` |
| intra→inter | `… → intra stages → vector_inter_slice_reduce → vector_final` |
| inter only | `vector_init → vector_inter_slice_reduce → vector_final` |
| inter→intra | `vector_init → vector_inter_slice_reduce → intra_slice_tag → …stages… → vector_final` |

**우리 커널의 최소 VE 사용** (`~/yik/src/kernel/constant_add_kernel.rs:22-28`):
```rust
.vector_init()
.vector_intra_slice_tag(TagMode::Zero)   // 태그 스테이지로 체인 진입
.vector_fxp(FxpBinaryOp::AddFxp, 1)      // 모든 원소에 상수 1 더하기
.vector_final()
```

## 2. Intra-Slice Chain (`intra-slice-chain.md`)

### ① 책 요약
슬라이스별 독립 elementwise/이항/슬라이스내 리덕션. 활성화·정규화 같은 후처리를 담당. 고정된 순서의 12 스테이지를 부분 선택해 체인한다(`intra-slice-chain.md:57`).

### ② 12 스테이지 표 (`intra-slice-chain.md:62-75`)

| # | Stage | Method | Way | Operand |
|---|---|---|---|---|
| 1 | Entry | `vector_intra_slice_tag()` | 8 | – |
| 2 | Logic | `vector_logic()` | 8 | yes |
| 3 | Fxp | `vector_fxp()` | 8 | yes |
| 4 | FxpToFp | `vector_fxp_to_fp()` | 8 | – |
| 5 | Narrow | `vector_narrow_split()` / `vector_narrow_trim()` | 8→4 | – |
| 6 | Float | `vector_fp_unary/binary/ternary()` | 4 | yes |
| 7 | IntraSliceReduce | `vector_intra_slice_reduce()` | 4 | – |
| 8 | FpDiv | `vector_fp_div()` | 4 | yes |
| 9 | Widen | `vector_widen_concat()` / `vector_widen_pad()` | 4→8 | – |
| 10 | FpToFxp | `vector_fp_to_fxp()` | 8 | – |
| 11 | Clip | `vector_clip()` | 8 | yes |
| 12 | Filter | `vector_filter()` | 8 | – |

메서드 시그니처는 크레이트에 실재한다: `vector_fxp` (`tensor/vector_tensor.rs:1202`), `vector_fxp_to_fp` (`:1259`), `vector_narrow_trim` (`:1344`), `vector_fp_unary` (`:1381`), `vector_intra_slice_reduce` (`:1525`), `vector_widen_pad` (`:1752`), `vector_clip` (`:1826`), `vector_stash` (`:456`), `vector_final` (`:511`).

### ③ 초심자용 핵심 3개념

**(가) Way8 vs Way4 (왜 narrow/widen 이 필요한가)**
- Logic/Fxp/Clip 클러스터는 8-way(사이클당 8원소), Float 클러스터는 4-way(`intra-slice-chain.md:77-79`). Float ALU 가 반쪽 처리량이라 나머지와 균형을 맞추려 4-way 로 돈다.
- 그래서 float 연산을 쓰려면 **반드시** 앞에서 `Narrow`(8→4), 뒤에서 `Widen`(4→8) 으로 감싼다. `vector_final()` 과 `vector_inter_slice_reduce()` 둘 다 8-way 를 요구하므로, 4-way 상태로 끝낼 수 없다(`intra-slice-chain.md:85`).

책 f32 파이프라인 예 (`intra-slice-chain.md:534-539`):
```rust
.vector_intra_slice_tag(TagMode::Zero)
.vector_narrow_trim::<m![A % 2 # 4]>()   // Way8 → Way4
.vector_fp_unary(FpUnaryOp::Sigmoid)
.vector_widen_pad::<m![A % 2 # 8]>()      // Way4 → Way8
.vector_final()
```
- `narrow_trim`/`widen_pad`: 뒤쪽 4원소가 패딩일 때 잘라내고/다시 패딩으로 채움.
- `narrow_split`/`widen_concat`: 양쪽 4원소 다 실데이터일 때 두 4-way flit 으로 쪼갰다가 다시 합침.

**(나) ALU 풀 — "invocation 당 각 ALU 1회"**
각 스테이지는 ALU 풀을 공유하고, **한 Tensor Unit invocation 에서 같은 ALU 를 두 번 못 쓴다**(`intra-slice-chain.md:182`). ALU 매핑은 크레이트 소스가 근거:

| 클러스터 | ALU (RngdAlu, `vector/alu.rs:11`) | 대표 Op (`vector/op/mod.rs`) |
|---|---|---|
| Fxp | `FxpAdd` | `AddFxp/AddFxpSat/SubFxp/SubFxpSat` (`op/mod.rs:154`) |
| Fxp | `FxpMul` | `MulFxp/MulInt` (`op/mod.rs:156`) |
| Float | `FpFpu` | `Sqrt/Tanh/Sigmoid/Erf/Log/Sin/Cos/DivF` (`op/mod.rs:211,237`) |
| Float | `FpExp` | `Exp/NegExp` (`op/mod.rs:210`) |
| Float | `FpMul0/FpMul1/FpFma` | `MulF(alu)` (`op/mod.rs:225,235`) |
| Clip | `ClipMax/ClipMin/ClipAdd` | `Max/Min/AbsMax/AbsMin/AddFxp` (`op/mod.rs:402`) |
| Reduce | `ReduceAccTree` | intra-slice reduce (`op/mod.rs:283,302`) |

- 함정 예 (`intra-slice-chain.md:184`): `tanh(sqrt(x))` 은 한 invocation 에 못 담는다 — 둘 다 `FpFpu` 를 쓰기 때문. 반면 `exp(sqrt(x))` 는 OK (`FpExp` + `FpFpu`, `intra-slice-chain.md:363-368`).
- 함정 예 (`intra-slice-chain.md:260-268`): `AddFxp` 뒤에 `SubFxp` → 둘 다 `FxpAdd` 라 **런타임 panic** `"FxpAdd is already in use"`. `MulInt`(=`FxpMul`) 는 다른 ALU 라 체인에 껴도 되지만, **껴 넣어도 `AddFxp`↔`SubFxp` 충돌은 해소되지 않는다** — 아래 실기 실측.
- **실기 실측 (npu) — 이 충돌은 실기에서 컴파일 타임에 잡힌다.** 벤더 예제 `ve_elementwise_fxp_chain` 이 정확히 `AddFxp → MulInt → SubFxp` 다(`furiosa-opt-examples/src/vector_engine/normal.rs:41-43`). 에뮬레이션에서는 런타임 panic(테스트가 `catch_unwind` 로 그 panic 을 **기대한다** — `tests/vector_engine/normal.rs:73-89`, `catch_unwind` 는 `:74`, panic 을 요구하는 단언 `assert!(result.is_err())` 는 `:88`. 즉 의도적 음성 표본이다), `--backend npu` 에서는 낮추기가 거부된다:
  ```
  error: furiosa-opt: vector_engine::normal::ve_elementwise_fxp_chain: visa: while lowering TensorUnit
         caused by: 6 is not available for op Binary(SubFxp)
  ```
  `--backend npu` 는 패키지의 **모든** `#[device]` 함수를 빌드 시점에 낮추므로, 이런 음성 표본 하나가 크레이트 전체 빌드를 죽인다 → `#[cfg(not(backend = "npu"))]` 게이팅 필요([12-예제-전수실행](./12-예제-전수실행.md) §7·§10).

**(다) Operand 소스 3종 + arg mode** (`intra-slice-chain.md:88-121`)

| 소스 | 예 | 설명 |
|---|---|---|
| 상수 | `100`, `2.5f32` | 스칼라 브로드캐스트 |
| VRF 텐서 | `VeRhs::vrf(&t)` 또는 `&vrf` | VE 진입 전 `.to_vrf()` 로 미리 적재. **여러 번 읽기 가능** |
| Stash | `Stash` | `vector_stash()` 로 찍은 이전 스냅샷. **1회만** 읽힘 |

우리 커널의 VRF operand 실사용 (`~/yik/src/kernel/elementwise_mul_kernel.rs:37`):
```rust
.vector_fxp(FxpBinaryOp::MulInt, &rhs_vrf)   // 슬라이스별 rhs 8원소와 곱
```
여기서 `rhs_vrf` 는 sub 컨텍스트가 `.to_vrf(0)` 로 미리 채운 것(`elementwise_mul_kernel.rs:26`) — main 과 sub 가 병렬로 돈다.

**실기 실측 (npu) — "VRF 는 여러 번 읽힌다"는 확인됐고, f32 read-twice 예제는 컴파일이 안 된다**
- `ve_elementwise_multi_vrf` 는 같은 `vrf1` 을 `vector_fxp(AddFxp, &vrf1)` 와 `vector_clip(AddFxp, &vrf1)` 에서 **두 번 읽는다**(`src/vector_engine/normal.rs:595-597`) → **실기 통과**. 다중 읽기는 하드웨어에서 검증됐다.
- 그런데 f32 판 `ve_vrf_read_twice_ok_f32`(같은 `z_vrf` 를 `Mul0`·`Mul1` 로 2회, 기대값 z³)는 **실기 컴파일 실패** — 이름이 `_ok_` 인데도(이름으로 판단하면 틀린다). 막히는 곳은 이중 읽기가 아니라 sub 컨텍스트의 `.to_vrf()` shape 검증이다: `visa: while lowering StoVrf … kernel-declared fn_output_shape does not match vrf_shape` — fn_output InSlice `[[[A_1=2]+6]=8]` vs vrf `[A_1=2]`(`src/vector_engine/normal.rs:164`). **에뮬레이션은 통과한다** → 에뮬레이션 통과가 실기 컴파일을 보장하지 않는다.
- 상류가 `#[ignore] // Failing on cpu` 로 막아둔 `test_ve_elementwise_vrf` 는 **낡은 주석이다** — 강제 실행하면 에뮬레이션·실기 모두 통과(실기 0.14s).

- **Stash** (`intra-slice-chain.md:108-114`): residual/skip-connection(`max(f(x), x)`) 용. `vector_stash()` 로 `x` 를 저장했다가 나중 이항 op 에서 `Stash` operand 로 읽음. 슬롯은 단일 사용(두 번 stash = 컴파일 에러), 읽기도 1회. Narrow/Widen 을 건너서도 살아있다(`intra-slice-chain.md:113`). **함정**: Pair 모드에서 불가, `IntraFirst` 로 inter-slice 리듀서에 넘어가면 stash 는 사라짐(`intra-slice-chain.md:114`).
- **실기 실측 (npu) — 최악의 함정: `ve_stash_fp_fp` 는 하드웨어를 hang 시킨다.**
  - **정지하는 조합**: stash 를 **narrow 이후(Way4/fp) 구간**에서 찍고 widen 뒤 `vector_clip(ClipBinaryOpF32::Max, Stash)` 로 읽기(`src/vector_engine/normal.rs:464-469`). **에뮬레이션은 통과**하는데 실기에서는 **단독 실행에서도** 60초 타임아웃 후 죽는다:
    ```
    test vector_engine::normal::test_ve_stash_fp_fp has been running for over 60 seconds
    furiosa_kernel_run: HAL error on ClusterId(npu0pe0-3): Unknown error -110 (os error -110)
    panicked at furiosa-opt-std/src/backend/npu/kernel.rs:118: kernel execution failed
    ```
    `-110` = 리눅스 `ETIMEDOUT`. NPU 카드 자체는 손상되지 않고(직후 `alive / 0.00 GiB`) 프로세스 종료로 회복된다.
  - **전염된다**: 이 커널이 한 번 걸리면 **같은 프로세스의 이후 모든 커널 실행이 `-110` 으로 실패**한다. 평범한 `cargo test` 로 vector_engine 을 돌리면 통과가 **10개**로 떨어지고(실패 25) 멀쩡한 커널 22개가 "실패"로 집계된다. `--test-threads=1` 직렬화도 소용없다(동시성이 아니라 프로세스 상태 오염). → **테스트마다 새 프로세스 + `timeout` 필수**([13-NPU-실기-매트릭스](./13-NPU-실기-매트릭스.md)).
  - **다른 stash 조합은 전부 실기 통과**: `ve_elementwise_stash_f32`(stash 를 narrow **전**, Way8 에서 찍고 같은 f32 clip 으로 읽음, `:118-133`), `ve_stash_fp_fxp`(fp stash → `fp_to_fxp` → i32 clip, `:480`), `ve_stash_fxp_fp`(`:428`), `ve_stash_fxp_fxp`(`:404`), `ve_elementwise_ternary_stash`. 즉 실기에서 죽는 것은 **"Way4 구간에서 찍은 stash 를 f32 clip 으로 읽는"** 이 한 조합뿐이다 — 책이 "stash 는 Narrow/Widen 을 건너서도 살아있다"고 한 바로 그 경로다. 원인은 미확인(문서 끝 "미확인 / 한계" 참조).
- **arg mode** (`intra-slice-chain.md:127-132`): `BinaryArgMode::Mode10` 은 stream/operand 슬롯을 뒤집어 `operand - stream` 계산. 예 `vector_fxp_with_mode(SubFxp, Mode10, 7)` → `7 - x`.

### ④ Tag 스테이지 (`intra-slice-chain.md:186-207`)
Entry 인 Tag 는 각 32비트 원소에 4비트 태그(0-15)를 붙인다. **비트3(MSB)=GroupId** (Filter/Pair 모드가 두 그룹으로 가름), 비트0..2=비교 결과 플래그.
- `TagMode::Zero`: 전부 0 (대부분 커널의 기본, 조건부 연산 없음).
- `TagMode::Comparison([...])`: 원소별 4개 비교로 비트 채움.
- `TagMode::AxisToggle{axis}`: GroupId = axis_index % 2 — Pair 모드의 내부 구현.

### ④ Pair 모드 요약 (`intra-slice-chain.md:146-178`)
2-way 그룹 축을 가진 텐서를 `vector_intra_slice_unzip()` 로 두 병렬 스트림(group0/group1)으로 쪼개, 서로 관계 연산(pairwise add, 비대칭 스케일) 후 `_zip` op 로 다시 합침. 우리가 본 예 (`vector-engine/index.md:184-190`):
```rust
.vector_intra_slice_unzip::<I, m![1 # 2], m![1]>()   // I 축으로 group0/group1 분리
.vector_clip_zip(ClipBinaryOpI32::AddFxp)             // group0 + group1
```
**함정**: Pair 모드 전체에서 `stash()`/`filter()` 불가, `_zip` 전(paired phase)에는 inter-slice 리듀서 전이 불가. 소스 구현은 `tensor/vector_tensor_pair.rs` (54KB, 별도 파일).

**실기 실측 (npu)**: Pair 모드 테스트(`vector_engine::zip::*`) **12개 중 11개 PASS**. 유일한 실패 `test_ve_group_pair_ternary_selective` 는 **버그가 아니라 1 ULP 반올림 차이**다 — 512개 중 **489개(95.5%)가 비트 단위 동일**, 불일치 23개, **최대 ULP 1**, 최대 상대오차 **1.742e-07**. 가장 나쁜 원소조차 `npu=4.0194473` vs `host=4.019448`(f32 마지막 한 자리). 테스트가 `tests/common.rs:21` 의 `assert_f32_vec_eq` 로 **비트 일치**를 요구해서 실패로 잡힌 것이다. → 실기 f32 결과를 검증할 때 비트 일치를 기준으로 쓰지 말 것(ULP 허용).

## 3. Intra-Slice Reduce (`intra-slice-reduce.md`)

### ① 책 요약
`IntraSliceReduce` 스테이지는 각 슬라이스 **내부의** `Time`/`Packet` 에 있는 축을 접는다(`Chip`/`Cluster`/`Slice` 는 통과). 슬라이스를 가로지르는 리덕션은 Inter-Slice Reducer 담당(`intra-slice-reduce.md:3-4`).

### ② 파라미터 & 코드
`vector_intra_slice_reduce::<Reduce, OutTime, OutPacket>(op)` (`tensor/vector_tensor.rs:1525`).
- `Reduce`(=REDUCE_LABEL): 접을 축. `Time`/`Packet` 에서 이 축을 가진 모든 factor 제거, 출력 shape 에 없어야 함.
- `op`: `IntraSliceReduceOpI32{AddSat,Max,Min}` / `IntraSliceReduceOpF32{Add,Max,Min}` (`op/mod.rs:271,290`). 전용 accumulator-tree ALU(`ReduceAccTree`) 사용 — 사용자가 ALU 못 고름.

### ③ 3가지 배치 (`intra-slice-reduce.md`)
| 배치 | 하드웨어 동작 |
|---|---|
| R in `Time` | 시간축 누산 (temporal accumulator, slot ≤ 8) |
| R in `Packet` | flit 내 4-way 트리 리듀스 `op(op(a,b),op(c,d))` |
| R in 둘 다 | Packet 은 트리, Time 은 누산 |

`f32` 전체합 예 (책 `vector-engine/index.md:148-159`):
```rust
.vector_narrow_trim::<m![R % 4]>()                       // Way8→Way4
.vector_intra_slice_reduce::<R, m![1], m![1 # 4]>(IntraSliceReduceOpI32::AddSat)  // Time·Packet 부분 합
.vector_widen_pad::<m![1 # 8]>()                          // Way4→Way8
.vector_inter_slice_reduce::<m![1 # 256], m![1]>(InterSliceReduceOpI32::AddSat)   // Slice 부분 합
```

### ④ 함정 — 누산 슬롯 8개 한계 & 패딩 제외
- `InnerTime::SIZE > 8` 이면 API 거부(`intra-slice-reduce.md:155-175`, 예: 12슬롯 요청 시 reject).
- 리듀스 축을 하드웨어 크기에 맞춰 패딩하면 패딩칸의 쓰레기값을 **반드시** 제외해야 한다. 두 전략(`intra-slice-reduce.md:190-210`):
  1. **VCG**(§4) — 컴파일러가 자동 설정, flit 마다 valid_size 태깅. 선호됨.
  2. **Identity 패딩** — Fetch 마스킹이 패딩칸에 리듀스 항등원(Add→0, Max→`-inf`/`i32::MIN`, Min→`+inf`/`i32::MAX`)을 미리 채움. 단 `exp(x)+…` 같이 비가역 변환이 앞서면 `exp(p)=0` 인 `p` 가 없어 적용 불가.

### ⑤ 실기 실측 (npu) — 하드웨어 리듀스 순서는 호스트 순차 기준과 다르다

- **`IntraSliceReduceOpI32::AddSat`(=`saturating_add`)는 결합법칙이 성립하지 않는다.** `(MAX+1)+(-1) = MAX-1` 인데 `MAX+(1+(-1)) = MAX`. 더하는 순서가 다르면 결과가 **정당하게** 달라진다.
- 실측: `ve_intra_slice_reduce_split_time_packet`(`R16=16`, `AddSat`, `src/vector_engine/reduce.rs:217`) 실기 실행에서 512개 중 **387개(75%) 불일치**, 최대 오차 **2.7e9**, `2147483647`(=`i32::MAX`)까지 나왔다. 입력이 `rand()` i32 라 거의 모든 레인이 포화하고, 결과가 전적으로 순서에 좌우된다.
- **결정적 실험**: 같은 커널에 포화가 불가능한 작은 값(−50..50)을 넣으니 **실기에서 통과(0.12s)**. → 데이터 오염이 아니라 **하드웨어 병렬 리듀스 순서**가 호스트 순차 기준과 다른 것. **커널은 옳다.**
- **교훈**: 비결합 연산(`AddSat`, 부동소수 덧셈)을 검증할 때는 **순서 독립적인 입력**으로 한 번 더 확인할 것. 안 하면 "실기에서 i32 리듀스가 깨진다"는 틀린 결론을 낸다.
- **`R` 을 Slice+Time 로 쪼갠 배치는 실기 컴파일 자체가 안 된다**: `ve_intra_slice_reduce_split_slice_time`(`S=15 → S # 16`, Slice `/4` · Time `%4`, `src/vector_engine/reduce.rs:172-192`) → `visa: while lowering TensorUnit / caused by: cannot reduce pack alias`. 테스트가 없어 에뮬레이션 실행 검증도 없는 커널이다.
- 나머지 리듀스는 실기 통과: `intra_slice_reduce_{add_f32,add_fxp_sat,max_f32,max_i32,min_f32,min_i32}`, `inter_slice_reduce_{add_f32,add_sat_i32,max_i32}`, `vru_then_vau_i32` 전부 PASS([13-NPU-실기-매트릭스](./13-NPU-실기-매트릭스.md)).

## 4. Valid Count Generator (VCG) (`vcg.md`)

### ① 책 요약
리듀스 축 `R` 을 `Slice`/`Time`/`Packet` 에 sub-expression 으로 배치하면, 컴파일러가 VCG 를 설정해 각 8원소 flit 에 `valid_size`(실데이터 개수)를 태깅한다. 패딩 자동 제외. (`vcg.md:1-11`)

### ② 구조 (`vcg.md:33-52`, 의사코드는 책이 Rust `ignore` 블록으로만 제시 — 크레이트에 공개 심볼 없음)
```
valid_size(s, t) = 모든 time_filter 가 valid → packet_clipper.valid_size(t)
                                       else → 0
```
- **Time Filter** ×3: 슬라이스 s·타임스텝 t 별로 유효 여부. `SliceMajor`/`TimeMajor` 모드로 R 을 Slice·Time 에 나눠 배치 가능. 슬라이스 비교 3케이스(below=전부유효 / boundary=`idx<time_thres` / above=전부무효)로 판정.
- **Packet Clipper** ×1: flit 당 `clamp(axis_size - idx, 0, packet_span)` — 슬라이스 무관, t 에만 의존.

### ③ 초심자용
`R # PADDED_SIZE / n % m` 꼴 factor 를 각 하드웨어 차원에 하나씩 배정한다. 예(`vcg.md:20-26`) `R=43 → R # 48` 을 Slice(`/8`)·Time(`/2%4`)·Packet(`%2`) 3분할. "Putting It All Together"(`vcg.md:488-616`) 는 `[H,C,W]=[5,5,19]` 을 packet clipper 1 + time filter 2 로 추적하는 히트맵을 준다.

### ④ 표현 불가 패턴 (`vcg.md:619-846`) — 반드시 피할 것
| 패턴 | 이유 |
|---|---|
| Slice 내 sub-expr 역순(minor 가 major 바깥) | per-slice R 범위가 비단조 → 단일 slice_thres 불가 |
| Slice 가 두 Time 사이에 낀 interleave | 슬라이스마다 유효 스텝 수가 달라짐 |
| TimeMajor 과다 패딩 (`PADDED − R::SIZE > slice_span`) | 도달 불가 R 인덱스 발생 → Emulation panic `"out x residue must factor the operand"` |
| Packet 에 major R(`/8`) 또는 다른 축 공유 | contiguous-prefix 속성 깨짐 |
| Slice+Packet 분할 (`R::SIZE % packet_span ≠ 0`) | `valid_size(t)` 가 슬라이스별로 못 달라짐 |

제약(`vcg.md:850-857`): packet clipper 1개, time filter 3개, 한 invocation 에 최대 4축 추적. → downstream narrow 시 valid_size 분할 규칙은 `vcg.md:869-878`.

**실기 실측 주의**: 이 표는 **VCG 표현 가능성**만 말한다. 표의 금지 패턴과 별개로 **실기 낮추기가 거부하는 배치**가 있다 — 리듀스 축을 Slice·Time 에 나눈 `ve_intra_slice_reduce_split_slice_time` 이 `cannot reduce pack alias` 로 막힌다(§3⑤). 배치를 정했으면 `--backend npu` 로 한 번 컴파일해 봐야 안다.

## 5. Inter-Slice Reducer (`inter-slice-reducer.md`)

### ① 책 요약
클러스터의 **256 슬라이스**를 가로질러 리덕션. `Chip`/`Cluster`/`Packet` 보존, `Slice`/`Time` 를 `OutSlice`/`OutTime` 로 재작성. 출력은 입력 모드와 무관하게 항상 **Way8** (`inter-slice-reducer.md:3-6`).

### ② 코드
i32/f32 별도 API (`tensor/vector_tensor.rs:553`, `:596`):
```rust
// vector_tensor.rs:553
pub fn vector_inter_slice_reduce<OutSlice: M, OutTime: M>(
    self, op: InterSliceReduceOpI32,
) -> VectorInterSliceReduceTensor<'l, T, i32, Chip, Cluster, OutSlice, OutTime, Packet, {VeOrder::IntraFirst}>
```
연산 집합 (`op/mod.rs:313,327`): I32 = `Add/AddSat/Max/Min`, F32 = `Add/Max/Min/**Mul**`. (F32 에만 `Mul`, I32 에는 `AddSat` 이 따로 있음에 주의.)

### ③ OutSlice 채우기 3방식 (`inter-slice-reducer.md:44-51`)
리듀스로 비워진 Slice 슬롯을 (1) dummy `1 # n`, (2) 새 차원 broadcast, (3) Time→OutSlice **promotion** 중 하나로 채운다. 셋은 자유롭게 섞임. Promotion 은 순서를 보존하지 않는다.

| 예 | einsum | 채우기 |
|---|---|---|
| `inter_slice_add` (`:72`) | `AR → A` | dummy `1 # 4` |
| `broadcast_into_x` (`:106`) | `PRW → PWX` | 새 차원 X broadcast |
| `axis_promotion` (`:140`) | `PRSUVW → PSUVW` | Time 의 V 를 OutSlice 로 승격 |

### ④ 함정 & 성능
- 규칙1: 리듀스 부분은 **Slice 의 안쪽(innermost) factor** 여야 하고, stride 1 로 연속이어야 함(`inter-slice-reducer.md:48`).
- 지연은 `O(r)` (r = 리덕션 그룹의 슬라이스 수, 링 1회 순회). 보통 상류 작업이 이 꼬리를 가려 병목 아님. 큰 r·작은 텐서에서만 드러남(`inter-slice-reducer.md:164-170`).

## 6. Cast Engine (`cast-engine.md`) — "정밀도를 고르는 자리"

### ① 책 요약
`f32`/`i32` 파이프라인 결과를 저정밀(bf16 등)으로 **좁혀서(narrowing)** Commit 전에 저장비용을 줄인다. flit(32B) 당 1개, 절대 병목 아님(`cast-engine.md:3,76`).

### ② 코드
```rust
// furiosa-opt-std-0.4.0/src/engine/cast.rs:63
pub fn cast<OutD: Scalar, OutPacket: M>(self) -> CastTensor<...>
where D: Cast<OutD> { verify_cast::<D, OutD, Packet, OutPacket>(); ... }
```
`CollectTensor`/`ContractTensor`/`VectorFinalTensor` 가 모두 `.cast()` 노출(`cast-engine.md:8`). 입력은 `VeScalar`(i32/f32) 만(`cast.rs:57` impl 바운드). `OutD`=목표 타입, `OutPacket`=출력 레이아웃을 **kernel writer 가 고른다**. 나머지는 컴파일러 유도.

우리 커널 실사용 (`~/yik/src/kernel/gemm_kernel.rs:44`, `dot_product_kernel.rs:40`):
```rust
.cast::<bf16, m![J % 8 # 16]>()   // f32 누산기 출력을 bf16 으로 좁힘
```

**실기 실측 (npu) — f32→bf16 은 값까지 검증됐다.** 벤더 예제 MNIST 가 같은 패턴을 4곳에서 쓴다(`furiosa-opt-examples/src/mnist/mod.rs:31,86,114,174` — `.cast::<bf16, m![1 # 16]>()` → `commit_trim` → `commit`). `mnist_tests::test_mnist` 는 **실기에서 통과하며 이미지 10장 전부 정답**이다 → Cast Engine 의 f32→bf16 narrowing 은 하드웨어에서 end-to-end 정확도까지 확인됐다([11-MNIST-실행결과](./11-MNIST-실행결과.md), [13-NPU-실기-매트릭스](./13-NPU-실기-매트릭스.md)).

### ③ 지원 변환표
책 표(`cast-engine.md:68-72`)와 **우리 크레이트 `Cast` impl 실측**을 대조:

| 입력 D | 책이 말하는 OutD | 0.4.0 크레이트 `impl Cast<OutD> for D` 실재? |
|---|---|---|
| `i32` | `i4`, `i8`, `i16` | ✅ i4(`cast.rs:134`), i8(`:80`), i16(`:148`) |
| `f32` | `f8e5m2`, `f8e4m3`, `f16`, `bf16` | ✅ f8e5m2(`:121`), f8e4m3(`:108`), bf16(`:94`) / ❌ **`f16` 없음** |

**중요한 정정(실측)**: 책 표는 `f32 → f16` 을 지원으로 적지만, **0.4.0 std 크레이트에는 `f16` 타입도 `impl Cast<f16> for f32` 도 없다**(`cast.rs` 전체 grep: bf16/f8e4m3/f8e5m2 만). 따라서 이 세대에서 `.cast::<f16, _>()` 는 컴파일되지 않는다. `i16` 은 반대로 impl 이 실재한다. 책과 코드가 어긋나는 지점이니 f16 은 쓰지 말 것.

### ④ "정밀도를 고르는 자리" — vISA vs TCL 정정
- 사용자 ACCV 문서 맥락에서 **Cast 의 `OutD` 선택 = 출력 정밀도를 고르는 자리**가 맞다. vISA 에서는 `.cast::<OutD, OutPacket>()` 의 타입 파라미터가 그 자리다(`cast.rs:63`).
- **그러나 이 세션의 정정**: "정밀도 선택이 vISA 전용"이 아니다. **TCL 도 출력 dtype 을 고를 수 있다**. 벤더 TCL 예제가 근거:
  - `~/furiosa/lib/python3.12/site-packages/furiosa/tcl/examples/contract.py:30` → `return commit.typecast(t, tcl.bf16)`
  - `.../examples/quantized_einsum.py:102` → `commit.typecast(output, tcl.bf16)`
  - `.../tcl/_lang/_instruction.py:99` → `typecast_to: Optional[ElementType]`
  즉 dtype 선택은 TCL 의 commit 경로(`commit.typecast`)에도 노출된다. TCL 이 vISA 에 못 미치는 것은 **배치 어휘**(Slice/Lane/Packet/commit-trim 은 vISA 전용, `_GROUND_TRUTH.md:37-42`)이지 **출력 dtype 선택이 아니다**. 두 계층 모두 출력 정밀도를 고를 수 있다.

| 4-bit | 16 | 16 | 16, 32 |
| 8-bit | 8 | 8 | 8, 16, 32 |
| 16-bit | 8 | 4 | 8, 16, 32 |
| 32-bit | 8 | 2 | 8, 16, 32 |

5 스테이지(`transpose-engine.md:76-110`): **Unpack**(패딩 버림) → **Gather**(packets_per_col 개 flit 을 in_cols 행으로) → **Transpose**(`[in_rows×in_cols]→[in_cols×in_rows]`) → **Trim**(패딩 행 버림, `out_rows ≤ in_cols`) → **Align**(각 행을 32B flit 로 패딩).

### ④ 함정 & 성능
- **버퍼링 모드가 지연을 지배**(`transpose-engine.md:328-343`): `in_cols ≤ 16` → double buffering(입출력 겹침, 빠름), `> 16` → single buffering(직렬화, 느림). 같은 데이터라도 in_cols 를 16 이하로 유지하면 사이클이 준다(예: Large Column 128 vs 유사 케이스).
- 32비트(f32/i32) 는 max in_rows 가 2 로 뚝 떨어진다 — 넓은 원소일수록 한 번에 전치 가능한 행이 적다.
- 우리 `~/yik` 커널들은 transpose 를 안 쓴다(전부 `cast → commit_trim → commit`). 대응 코드는 크레이트 테스트 `transpose.rs:126-234` 참고.

### ⑤ 실기 실측 (npu) — Transpose Engine 은 MNIST 로 검증됐다
- 벤더 예제 MNIST 가 `.transpose()` 를 **4곳에서 실사용**한다: `furiosa-opt-examples/src/mnist/mod.rs:46`(`m![H % 8] → m![1 # 16]`, bf16 bias 전치), `:60`, `:128`, `:149`. `mnist_tests::test_mnist` 실기 통과(10장 전부 정답) → **16비트 원소 전치 경로는 하드웨어에서 값까지 맞는다.**
- **주의(혼동 금지)**: 실기 매트릭스의 `transpose 1/1`(`transpose_tests::test_transpose_simple`)은 **Transpose Engine 이 아니다** — `src/transpose.rs:16,19` 는 `to_hbm()` 을 두 번 부르는 **TDMA relayout** 으로 `[A,B,C]→[C,A,B]` 를 만든다. 엔진 경로 검증으로 세지 말 것.
- `.transpose()` 를 쓰는 나머지 커널 `matmul::matmul_16384`(`src/matmul/matmul_16384.rs:53`)은 실기 컴파일 실패인데, 막힌 지점은 전치가 아니라 분기다: `visa: Branch conversion is not yet implemented`([13-NPU-실기-매트릭스](./13-NPU-실기-매트릭스.md)).

## 8. Commit Adapter (`commit-adapter.md`)

### ① 책 요약
Commit Engine 이 DM 에 쓰기 **전** elementwise 변환. `.commit_xxx(...)` 체인은 항상 `.commit(...)` 으로 끝난다. **Trimming 이 필수 첫 스테이지** — `.commit()` 은 `.commit_trim(...)` 뒤에만 도달 가능(`commit-adapter.md:6`).

### ② 파이프라인 (`commit-adapter.md:8-17`)
| 연산 | Main | Sub | 메서드 (`commit_adapter.rs`) |
|---|---|---|---|
| Trimming | ✅ | ✅ | `commit_trim::<OutPacket>()` (`:156`) |
| Type Casting(+선택 ReLU) | ✅ | ❌ | `commit_cast::<OutD>(Activation)` (`:186`) |
| Valid Count Packing | ❌ | ✅ | `commit_valid_count_pack(count)` (`:220`) |
| Generate Mode | ❌ | ✅ | 독립 API (TuTensor 체인 아님) |

- Main: `Trim → [Cast(+ReLU)] → commit`
- Sub: `Trim → [ValidCountPack] → commit`

### ③ commit_trim 이 dtype 무관하게 필수인 이유 (`commit-adapter.md:19-31`)
스트림 flit 은 **항상 32B** 지만 유효원소가 그보다 적을 수 있고, 뒤는 패딩. 그대로 쓰면 DM 의 유효영역 밖 바이트를 패딩으로 덮어쓴다. Trimming 은 앞쪽 `valid_size` 원소만 쓴다(`D[valid_size]` ∈ {8,16,24,32}B, 32=no-trim). **패딩이 없어 valid_size 가 이미 32B 여도 trim 은 no-op 로 체인을 anchor** 하려고 여전히 호출해야 한다. 그래서 dtype·패딩 유무와 무관하게 모든 commit 은 trim 을 먼저 탄다.

```rust
// furiosa-opt-std-0.4.0/src/engine/commit_adapter.rs:156
pub fn commit_trim<OutPacket: M>(self) -> CommitTrimTensor<...> {
    verify_commit_trim::<D, Packet, OutPacket>(); ...
}
```
`D: MaterializableScalar` 바운드(`commit_adapter.rs:136-147`)라 i5/i9 는 commit 불가.

우리 커널 실사용 (`~/yik/src/kernel/constant_add_kernel.rs:29-30`):
```rust
.vector_final()
.commit_trim::<m![A % 8]>()          // OutPacket 로 패딩 제거
.commit::<m![A % 8]>(1 << 12);       // DM 주소로 실제 write
```
`gemv_kernel.rs:43` 처럼 `.commit_trim::<m![1 # 4]>()` 로 8→4 리사이즈도 한다.

### ④ commit_cast 의 존재 이유 & 현재 상태 (함정)
- **왜 별도 cast 가 commit 경로에 또 있나**(`commit-adapter.md:84-92`): Cast Engine 은 Vector Engine **위에** 얹혀 변환 중 VE 를 점유한다. main 컨텍스트가 Cast Engine 으로 f32→bf16 하면 VE 가 바빠 sub 컨텍스트가 병렬로 못 돈다. 그래서 main-contraction ∥ sub-VE 를 동시에 돌릴 때만 변환을 Commit Adapter 로 우회시켜 VE 를 비운다. Sub 컨텍스트 자체는 type casting 미지원.
- **ReLU 는 독립 스테이지가 없다**(`commit_adapter.rs:31-41`): `Activation::Relu` 는 narrowing cast(`f32→bf16`)에 **fuse** 될 때만 존재. `Activation::None` 은 평범한 cast.
- **함정(미구현)**: 0.4.0 크레이트에서 `verify_commit_cast` 는 `todo!("commit_cast is not yet implemented")` (`commit_adapter.rs:239`), `verify_commit_valid_count_pack` 도 `todo!` (`:243`), `commit_valid_count_pack` 의 `_valid_count` 는 아직 버려짐(`:217-218` TODO). 즉 이 세대에서 **commit_cast / valid_count_pack 는 아직 실동작 아님** — 실쓰는 정밀도 변환은 Cast Engine(`.cast()`, §6) 으로 하라. `commit_trim` 만 실검증된다(`verify_commit_trim` → `config_commit_trim`, `:232`).
- **실측 보강**: 벤더 예제 크레이트(`#[device]` 커널 207개)에서도 `commit_cast`/`commit_valid_count_pack` **사용 0건**(`grep -rn "commit_cast\|commit_valid_count_pack" src` = 0). 벤더조차 안 쓴다. 반면 `commit_trim` 은 commit 경로를 타는 실기 통과 커널이 전부 탄다(MNIST 포함) → 이 세대의 유일한 실동작 commit 스테이지. 단 commit 을 아예 안 쓰는 TDMA/DMA 전용 통과 커널도 있다(`src/transpose.rs`·`src/scatter_gather.rs`·`src/param.rs` 는 `commit_trim`·`.commit(` grep 0건).

### Generate Mode (`commit-adapter.md:134-139`)
sub 전용 ITOS(immediate-to-SRAM): 상수 `u32` 하나를 sub 파생 DM 주소에 직접 씀. Fetch/Vector 등 전 파이프라인 우회.

## 함정 요약 (한눈에)
1. VE 는 **i32/f32 만** — bf16 을 넣으려면 Fetch/Contraction 이 먼저 32비트로 넓혀야 함(`scalar.rs:24`).
2. 같은 ALU 두 번 = panic. `tanh(sqrt)` 불가, `AddFxp`+`SubFxp` 불가(`intra-slice-chain.md:184,260`).
3. float 연산은 **narrow→…→widen** 으로 감싸야 하고 8-way 로 끝내야 함(`intra-slice-chain.md:85`).
4. intra reduce 누산 슬롯 8개 한계, 패딩 제외는 VCG 또는 identity 패딩(`intra-slice-reduce.md:155,190`).
5. VCG 표현 불가 배치(역순 Slice, interleave, 과다패딩, 복잡 Packet, Slice+Packet)를 피할 것(`vcg.md:619`).
6. Cast: **`f16` 은 0.4.0 크레이트에 없다**(책 표와 불일치). f32→{bf16,f8e4m3,f8e5m2}, i32→{i4,i8,i16} 만 실재(`cast.rs`).
7. Commit: `commit_trim` 은 dtype 무관 필수(anchor). `commit_cast`/`valid_count_pack` 는 이 세대 아직 `todo!`(`commit_adapter.rs:239,243`).
8. 출력 정밀도 선택은 vISA(`.cast`)뿐 아니라 **TCL(`commit.typecast`)도** 가능(이 세션 정정).
9. **실기 hang**: Way4 구간에서 찍은 stash 를 f32 clip 으로 읽는 조합(`ve_stash_fp_fp`)은 실기에서 정지 → HAL `-110`(ETIMEDOUT). **같은 프로세스의 이후 커널까지 전부 오염**되니 테스트마다 새 프로세스 + `timeout` 필수(§2③).
10. `MulInt` 를 껴 넣어도 `AddFxp`↔`SubFxp` 충돌은 안 풀린다. 실기에서는 **컴파일 에러**(`6 is not available for op Binary(SubFxp)`)로 나오고, 게이팅 없으면 크레이트 전체 빌드가 죽는다(§2③).
11. **`AddSat` 리듀스는 순서 의존**(비결합). 실기 값이 호스트 순차 기준과 달라도 커널이 맞을 수 있다 — 순서 독립 입력으로 재검증(§3⑤). f32 검증도 비트 일치 대신 ULP 허용(§2④).
12. **에뮬레이션 통과 ≠ 실기 통과**: `ve_vrf_read_twice_ok_f32` 는 에뮬레이션 통과인데 실기 컴파일 실패, `ve_stash_fp_fp` 는 에뮬레이션 통과인데 실기 hang(§2③). 별개로 `ve_elementwise_fxp_chain` 은 에뮬레이션에서 panic 을 기대하는 의도적 음성 표본이고 `ve_intra_slice_reduce_split_slice_time` 은 테스트가 없어 에뮬레이션 검증 자체가 없다 — 둘 다 실기 컴파일 실패(§2③·§3⑤).

## 미확인 / 한계

**이번 세션(2026-07-24 실기)에 해소된 항목**: "transpose 의 실사용 미확인" → 벤더 예제 MNIST 가 `.transpose()` 를 4곳에서 쓰고 실기에서 통과(§7⑤). `~/yik` 이 transpose 미사용인 것은 그대로다.

- **f16 캐스트**: 책 `cast-engine.md:71` 은 `f32→f16` 을 지원으로 명시하나, 설치된 0.4.0 std 크레이트에는 f16 타입·impl 부재로 확인 불가. 하드웨어(`config_cast` FFI) 레벨에서 지원할 수도 있으나 이 크레이트 API 로는 호출 불가 — **미확인**.
- **사용자 ACCV 문서 원문**: "Cast=정밀도 고르는 자리" 문맥은 태스크 지시로만 받았고 ACCV 문서 자체는 읽지 않음. vISA/TCL 양쪽 dtype 선택 가능은 크레이트/TCL 예제로 **검증됨**.
- **commit_cast 의 실제 정밀도 변환 정확도**(RNE 등): `commit_cast` 가 `todo!` 라 emulation 실행 결과로는 미확인. Cast Engine 경로의 f32→bf16 RNE 는 `cast.rs:373-385` 테스트로 확인됨(추가로 실기 MNIST 로 end-to-end 확인, §6).
- **`ve_stash_fp_fp` hang 의 원인**: 커널 소스는 정상 모양이고 에뮬레이션도 통과. 컴파일러 산출물(EDF) 문제인지 런타임/HAL 문제인지 **미확인**. `-110` 이후 같은 프로세스가 계속 오염되는 기전(어떤 상태가 남는지)도 미확인 — 회피책(프로세스 격리)만 검증됨.
- **`6 is not available for op Binary(SubFxp)` 의 "6"**: `FxpAdd` 재사용으로 읽히지만 ALU 인덱스 매핑을 크레이트 소스로 확인하지는 않았다 — **미확인**.
- **`ve_vrf_read_twice_ok_f32` / `ve_intra_slice_reduce_split_slice_time` 을 어떻게 고치면 실기로 올라가는지**: shape 패딩(InSlice 8 vs 2)·pack alias 를 손보면 될 것으로 보이나 **수정·재컴파일 미시도**.
