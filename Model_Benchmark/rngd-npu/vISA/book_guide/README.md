## ⚠️ 먼저 읽을 것 — 이 서버의 버전 현실

공식 문서·우리 커리큘럼과 **설치본이 어긋난다**. 헷갈리면 [`_GROUND_TRUTH.md`](./_GROUND_TRUTH.md) 를 보라.

| 항목 | 문서/커리큘럼이 말하는 것 | **우리 서버 실측** |
|---|---|---|
| 래퍼 세대 | `--version` → 0.3.0 | **0.4 세대** (바이너리 md5가 v0.4.0 타르볼과 동일) |
| 기본 백엔드 | 커리큘럼(v0.2.0): `simulation` | **`emulation`** (`typecheck`/`emulation`/`npu`, `simulation` 없음) |
| 커널 마커 | `src/furiosa-opt.tag` | **`[package.metadata.furiosa-opt]`** 요구 |
| `/home/jun/yik` npu | — | **현재 래퍼로 `--backend npu` 불가** (0.3 핀+tag). typecheck/emulation은 OK |
| **`--backend npu` 범위** | 책은 언급 없음 | **패키지의 *모든* `#[device]` 함수를 빌드 시점에 컴파일.** 하나라도 못 낮추면 크레이트 전체가 죽는다 → 벤더 예제는 그대로 돌리면 **에러 63개로 빌드 실패** |
| **실기 실행 가능성** | — | **가능하다.** npu0~npu3 유휴 확인 후 게이팅으로 **테스트 89개 실행, 80개 통과** ([13번](./13-NPU-실기-매트릭스.md)) |

> ### ★ 실기로 뭘 하려면 반드시 알아야 하는 것 두 가지
> 1. **`--backend npu` 는 패키지의 모든 커널을 낮춘다.** 테스트가 부르지 않는 커널도 포함이다.
>    우회법은 실패 커널에만 `#[cfg(not(backend = "npu"))]` 를 붙이는 **게이팅**(상류가 이미 쓰는 관용구).
> 2. **테스트마다 새 프로세스로 돌려라.** hang 커널 하나가 HAL `-110` 으로 뒤 커널을 전부 오염시킨다 —
>    격리하면 통과 수가 **10 → 33** 으로 3배 달라진다.
>
> 그리고 성능을 손대려면: 사이클의 **96.5% 가 DMA**, 연산(PeCore)은 3.3% 다
> (`compile --dump-schedule` 로 커널 130개의 스케줄을 떠서 합산한 값 —
> **컴파일러 스케줄 모델 예측이고 실측 벽시계가 아니다**).
> 슬라이스 내부 최적화의 상한이 3.3% 라는 뜻이다([13번 §4](./13-NPU-실기-매트릭스.md)).

## 읽는 법
- **처음 배우면**: 00 → 01 → 02 순서. 02(매핑)가 제일 중요하고 어렵다.
- **엔진 이해**: 03(이동) → 04(분배) → 05(축약) → 06(벡터).
- **직접 최적화**: `OPTIMIZATION-SURFACE.md` 먼저, 그다음 관련 엔진 문서.
- **"vISA로만 되는 것"**: 09(계층 경계) + 04(TCL이 못 내려가는 슬라이스 내부).
- **실기(NPU)에서 돌려보려면**: **13번이 먼저다.** 무엇이 실제로 도는지, 실기 결함 4유형
  (로더 abort · 조용한 데이터 오배치 · hang · 오탐[커널은 옳은데 테스트 기준이 과함 — 1 ULP·리듀스 순서]),
  그리고 내 코드를 실기에 올리는 절차가 있다.
  12번은 그 배경(왜 크레이트를 그대로 못 쓰나 + 게이팅 레시피).
- **성능을 손대려면**: `OPTIMIZATION-SURFACE.md` 의 계측 절과 13번 §4를 같이 보라.
  사이클의 96.5% 가 DMA 라서(스케줄 모델 예측) **어디를 최적화할지가 바뀐다.**
- **_GROUND_TRUTH.md 는 앵커다.** 1~51행은 다른 문서가 행 번호로 참조하므로 보존되고,
  실기 실측(N1~N12)은 그 아래에 추가돼 있다.
