## 0. 파이프라인 한눈에

패킷 스트림은 타입상태(typestate)로 단계가 강제된다. 어떤 텐서가 어떤 엔진에 들어갈 수 있는지는
`mod.rs` 의 `CanApplyXxx` 마커 트레이트 그래프가 **컴파일 타임에** 못박는다.

```text
BeginTensor
  └─ fetch ────────────────► FetchTensor
                               ├─ fetch_mask / fetch_table_lookup / fetch_cast / fetch_zero_point_sub  (Fetch Adapter, 전부 선택)
                               ├─ switch ──────► SwitchTensor
                               └─ collect ─────► CollectTensor   (adapter·switch 건너뜀 가능)
SwitchTensor
  └─ collect ──────────────► CollectTensor
CollectTensor
  ├─ to_trf ───► TrfTensor          (→ Contraction Engine)
  ├─ to_vrf ───► VrfTensor          (→ Vector Engine)
  └─ contract_outer / cast / transpose / commit_* ...
```
출처: `engine/mod.rs:19-118` (파이프라인 그래프 주석), 간선 정의 `engine/mod.rs:214-284`.

**초심자용**: "Fetch = DM 에서 스트림 뽑기", "Switch = 슬라이스끼리 값 주고받기", "Collect = 패킷을 32바이트로 정규화",
"to_trf/to_vrf = 정규화된 데이터를 연산 엔진 전용 레지스터파일에 적재". 네 단계 중 **Adapter 와 Switch 는 건너뛸 수 있고**,
Collect 는 사실상 필수(하류 엔진이 32바이트 flit 만 먹기 때문).

**함정 — 단계 순서는 하드웨어 파이프라인 순서**: 메서드 체인 순서가 곧 하드웨어 단계 순서다.
`fetch_mask` 다음 `fetch_cast` 는 되지만 그 반대는 타입상태가 막는다(`mod.rs:216-235`).

## 1. Fetch Adapter — 스트림 원소 변환 4단계

### 책이 뭐라 하는가
Fetch Engine 이 뱉은 패킷 스트림에 **원소 단위 변환**을 얹는 단계. Switch 로 넘어가기 *전*에 적용된다.
네 스테이지 전부 선택이며, 하드웨어 파이프라인 순서(mask → table lookup → cast → zero-point sub)로 호출한다.
(`docs/computing-tensors__fetch-adapter.md:3-15`)

| 스테이지 | 메서드 | 하는 일 | main/sub |
|---|---|---|---|
| Masking | `fetch_mask::<OutTime,OutPacket>()` | 시퀀서 우측 패딩 슬롯을 0 으로 (`# n` → `#{0} n`) | main 전용 |
| Table Lookup | `fetch_table_lookup::<OutD>()` | HW 룩업테이블로 값 치환(Sigmoid/GeLU/MXFP4 등) | main 전용 |
| Type Casting | `fetch_cast::<OutD>()` | 원소 타입 변환(`i8→i32`, `bf16→f32`, `f32→bf16` 등). 지연 1~2 사이클 | main+sub |
| Zero-Point Sub | `fetch_zero_point_sub::<OutD>(zp)` | 양자화 zero point 빼고 확장(`i4→i5`, `i8→i9`) | main 전용 |

책: main-context adapter 는 네 스테이지 전부, sub-context adapter 는 `fetch_cast` 만 지원(`fetch-adapter.md:15`).

### 우리 코드의 어디에 대응하는가
- 스테이지 impl: `engine/fetch_adapter.rs:156-305` (`fetch_mask` / `fetch_table_lookup` / `fetch_cast` / `fetch_zero_point_sub`).
- 진입 게이팅: `engine/mod.rs:216-236` (어느 타입상태가 어느 스테이지로 갈 수 있나).
- **우리 gemm/gemv/dot_product 커널은 Adapter 스테이지를 하나도 쓰지 않는다** — `fetch()` 직후 바로 `collect()`.
  (예: `gemm_kernel.rs:28-29`, `dot_product_kernel.rs:26`, `gemv_kernel.rs:27-28`)

### 초심자용 쉬운 설명
`fetch()` 는 "DM 에서 스트림을 뜬다"까지만 한다. 그 스트림에 마스킹·룩업·형변환을 걸고 싶으면 그 위에 메서드를 *체인* 한다.
안 걸면? `FetchTensor` 그대로 Switch 나 Collect 로 흘려보내면 된다(`fetch-adapter.md:8`).

## 2. Switch Engine — 슬라이스 간 데이터 분배

### 책이 뭐라 하는가
다른 엔진은 전부 자기 슬라이스의 DM 파티션에서 per-slice 로 돌지만, **Switch Engine 만 256-슬라이스 링 네트워크로
슬라이스 경계를 넘어** 데이터를 옮긴다: 한 슬라이스 값을 그룹에 broadcast, 슬라이스끼리 swap, 어느 슬라이스가 어느 값을
갖는지 permute. `FetchTensor::switch()` 가 `SwitchTensor` 를 낳고, `Slice`·`Time` 매핑만 바뀐다
(`Chip`/`Cluster`/`Packet`·데이터 값은 보존). (`docs/computing-tensors__switch-engine.md:1-9`)

`SwitchConfig` 변형(`switch-engine.md:33-40`):

| Config | 용도 | `ring_size` |
|---|---|---|
| `Forwarding` | 슬라이스 교환 없이 그대로 통과 | `1` (변형 없음 — `switch()` 생략) |
| `Broadcast01` | 안쪽 `slice1`·`slice0` 둘 다 sub-ring 전체에 broadcast | `slice1 × slice0` |
| `Broadcast1` | `slice1` 만 broadcast, `slice0` 은 `Slice` 유지 | `slice1 × slice0` |
| `Transpose` | `Slice` 안에서 `slice1`↔`slice0` swap | `slice1 × slice0` |
| `InterTranspose` | `Slice` 의 `slice1` ↔ `Time` 의 `time1` swap | `slice1 × slice0` |
| `TransposedBroadcast1` | `slice0` 을 `Time` 으로 broadcast + `slice1` 을 최내측 `Slice` 로 (= Transpose 후 Broadcast1) | `slice1 × slice0` |
| `CustomBroadcast{ring_size}` | 위로 표현 못하는 임의 permute/부분추출 — 컴파일러가 snoop bitmap 합성 | 사용자가 직접(2의 거듭제곱) |

### 우리 코드의 어디에 대응하는가
- `switch()` impl: `engine/switch.rs:65-73`. 시그니처 `switch::<OutSlice, OutTime>(config: SwitchConfig)`.
- `SwitchConfig` 정의는 엔진 크레이트가 아니라 lowering 크레이트에서 re-export: `switch.rs:35`
  (`pub use furiosa_opt_lower::SwitchConfig;`). 변형 목록·검증은 `config_switch`(lowering) 안에 있음.
- CustomBroadcast 검증 테스트(permute/broadcast/slicing 패턴 예시)가 `switch.rs:90-317` 에 대량으로 들어있어
  실제로 어떤 매핑 변환이 허용되는지 표본으로 읽을 수 있다.

### 초심자용 쉬운 설명
256개 슬라이스를 하나의 물리 링(라우터 1개/슬라이스)으로 엮고, `256/ring_size` 개의 **sub-ring** 으로 쪼갠다.
각 라우터는 snoop bitmap(256엔트리) 을 보고 들어온 패킷마다 output/forward-right/forward-left 를 정한다
(`switch-engine.md:351-394`). "broadcast" 는 여러 출력 슬라이스가 같은 bitmap 엔트리를 갖는 모양,
"Slice→Time" 은 한 출력 슬라이스가 여러 소스를 시간축으로 모으는 모양(`switch-engine.md:396-399`).

성능: `cycles ≈ ring_size × Time::SIZE × flits_per_packet` (`switch-engine.md:419`).
`flits_per_packet = sizeof(D) × Packet::SIZE / 32`. sub-ring 은 병렬이라 per-ring 사이클 = 칩 전체 지연.

### 함정 / 주의
- **우리 gemm_kernel 은 `switch()` 를 호출하지 않는다.** `gemm_kernel.rs:22-23` 주석 "Switch Engine distributes
  B across 256 slices" 는 **오해를 부르는 서술**이다(GROUND_TRUTH `_GROUND_TRUTH.md:35`). 실제 체인은
  `.begin().fetch().collect().to_trf()` 로 **switch 가 없다**. 슬라이스 분배는 `switch` 가 아니라
  **`to_dm(...)` 호출 시 `Slice` 타입 파라미터**(`gemm_kernel.rs:8` 의 `pub type Slice = m![I/32, J/32]`)가 한다.
- **슬라이스 간 교환이 필요 없으면 `switch()` 를 생략하고 `FetchTensor` 에서 바로 `.collect()`** — 이게 `Forwarding`.
  `SwitchConfig` 에는 `Forwarding` 변형 자체가 없다(`switch-engine.md:42-47`). 우리 커널이 정확히 이 경로.
- broadcast 축(`X`/`Y`)은 **새 축**이어야 하고(입력 Slice/Time 에 없어야 함), 패딩 금지, 출력 Slice 에 정확히 1회
  등장. CustomBroadcast 의 7개 제약(순서 보존, 최내측 Time 위치, 드롭값은 패딩만, ring_size 2의 거듭제곱 등)은
  `switch-engine.md:601-658`.
- Switch 는 패킷을 **건드리지 않는다**(패딩·reshape 없음). 반드시 뒤에 `collect` 로 flit 정규화(`switch.rs:1-6`,
  `switch.rs:62-64` 주석). 진입 시 `assert_packet_aligned_by_access_width`(`switch.rs:43`).

### 실기 실측 — Switch 는 실기에서 견고하다 (실제 NPU 실행)

- `switch_assertions` 바이너리 **18/18 통과**(테스트마다 별도 프로세스). 그중 **실제로 `switch()` 를 호출하는 것은 10건**:
  `Broadcast01` 3건, `Broadcast1` 2건, `Transpose` 3건, `InterTranspose` 2건.
  나머지 8건(packet 패딩 5 · slice 1 · alignment 2)의 커널에는 `.switch()` 호출이 없어 **Switch 실행 근거로는 못 쓴다**

  260행(broadcast1 모듈)이고 alignment(9–70행)·packet(73–219행)·slice(220–243행) 에는 하나도 없다 —
  이름이 `packet_padding_added_in_switch` 인 커널조차 `.switch()` 를 안 쓴다.
  → **`Broadcast01`/`Broadcast1`/`Transpose`/`InterTranspose` 4개 Config 는 실기에서 실제로 돈다.**
  전체 매트릭스는 [13-NPU-실기-매트릭스](./13-NPU-실기-매트릭스.md), 게이팅 절차는
  [12-예제-전수실행](./12-예제-전수실행.md).
- **위 표의 나머지 두 Config 는 실기 실행 미검증**(Config 별 사용처를 전수 grep 한 결과):
  - `CustomBroadcast` — `switch_engine::custom_broadcast`(ring_size 4)는 **컴파일 OK 인데 호출하는 테스트가 없다**.
    나머지 사용처 `matmul::matmul_16384`(`Branch conversion is not yet implemented`)·
    `transformer::embedding::forward`(컴파일러 ICE)는 Switch 와 무관한 이유로 컴파일 실패.
  - `TransposedBroadcast1` — 사용처가 `matmul::matmul_split_reduce2::matmul_with_split_reduce2` 하나뿐이고
    그 커널이 ICE 로 죽는다.
- **⚠ i4(서브바이트) + 패킷 패딩은 실기로 못 간다**: `switch_assertions::alignment::aligned_fetch_packet_i4`

  `incorrect buffer size at T4: DramShape { inner: []|[A_1=8:64, B_1=32:1] }: buffer.size() (256) != num_chips * intra_chip_size (240)`.
  `m![A, B # 64]`(8×64 i4 = 256 B)인데 백엔드가 240 B 로 센다. **형제 커널 `..._i8`·`..._bf16` 은 컴파일 OK +
  실기 통과** → 매핑을 그대로 두고 타입만 i4 로 바꾸면 막힌다.
  (참고: 이 커널은 `switch()` 를 안 쓴다. 체인은 fetch → `fetch_cast::<i4>` → collect → commit_trim → commit.)
- **`*_assertions` 의 `invalid_*` / `*_mismatch` 커널은 일부러 잘못 만든 표본**이다. 컴파일 실패가 정상인 경우가 많지만
  **전부는 아니다**(이 이름 42개 중 **FAIL 25 / OK 17** — 예: `switch_assertions::inter_transpose::invalid_time0` 은
  컴파일 성공한다. 프론트엔드 타입상태·verify 단계에서 걸리도록 만든 표본이라 백엔드 낮추기까지는 통과한다).
  그리고 **어떤 테스트도 호출하지 않는다**(`grep -rn "invalid_\|_mismatch" tests/` = 0건). 컴파일 FAIL 목록을 읽을 때
  이들을 공백으로 세지 말 것. 역으로 **`valid_*` 라는 이름이 통과를 보장하지도 않는다**(§4 의
  `contract_outer_assertions::lane_size::valid_size_{1,2,4}` 가 반례).

## 3. Collect Engine — 패킷을 32바이트 flit 으로 정규화

### 책이 뭐라 하는가
하류 엔진(Contraction/Vector/Cast/Transpose/Commit)은 **정확히 32바이트 flit** 만 소비한다. Collect 는 임의 크기 패킷을
2단계로 정규화한다(`docs/computing-tensors__collect-engine.md:3-8`):
1. **Pad**: 다음 32바이트 경계까지 패딩(이미 32B 정렬이면 생략).
2. **Split**: flit 경계에서 쪼갬 — 안쪽 32B 는 `Packet2`, 바깥 flit 개수는 `Time2` 로 흡수(이미 32B 면 생략).

### 우리 코드의 어디에 대응하는가
- `collect()` impl: `engine/collect.rs:66-71`. 시그니처 `collect::<Time2, Packet2>()`.
- 결과 `CollectTensor` 생성자가 **패킷이 정확히 1 flit 인지 강제**: `collect.rs:39-43`
  `assert_packet_one_flit::<D, Packet>()`. (Fetch 는 이 검사를 미룸 — `fetch.rs:37-43`: 캐스트로 나중에 정렬될 수 있어서.)
- `FetchTensor` 와 `SwitchTensor` 둘 다 `.collect()` 노출(`collect-engine.md:14-19`). Fetch 진입점이 Switch 를 우회.

### 4가지 경우 (책 예제, `collect-engine.md:21-187`)

| 경우 | 입력 패킷 | 처리 | 출력 |
|---|---|---|---|
| Single-Flit | `i8 × 32` = 32B | 그대로 통과 | `Packet2 = m![B # 32]` |
| Sub-Flit | `i8 × 16` = 16B | 32B 로 패딩 | `Packet2 = m![B # 32]` |
| Multi-Flit | `bf16 × 32` = 64B = 2 flit | 안쪽 16개=32B→`Packet2`, 바깥 2 flit→`Time` | `Time=m![A,B/16], Packet=m![B%16]` |
| Multi-Flit+Pad | `i8 × 51` = 51B | 64B 로 패딩 후 2 flit 분할 | `Time=m![A,B#64/32], Packet=m![B#64%32]` |

### 초심자용 쉬운 설명
"패킷이 32바이트보다 작으면 0 으로 채우고, 크면 32바이트씩 잘라 그 개수를 Time 축으로 밀어넣는다." flit=32B 가
파이프라인의 화폐 단위. bf16 는 16개=32B 가 1 flit, i8 는 32개=32B 가 1 flit.

### to_trf / to_vrf 진입 (Collect 의 종착)
정규화 후 `CollectTensor` 는 하류 엔진으로 흐르거나 레지스터파일에 적재된다(`collect-engine.md:189-246`).
- `to_trf::<Row/Lane, Element>()` / `to_trf_at::<...>(TrfAddress)` — 코드 `collect.rs:74-95`.
- `to_vrf::<Element>()` / `to_vrf_at::<Element>(Address)` — 코드 `collect.rs:97-113`. **`to_vrf` 는 `VeScalar`(=`i32`/`f32`) 전용**
  (`collect.rs:98` 트레이트 바운드 `D: VeScalar`; `collect-engine.md:228`). 실기에서 실제로 되는/안 되는 형태는 **§4 VRF 실기 실측** 참조.

## 4. Register Files — TRF / VRF

### 책이 뭐라 하는가
Contraction/Vector 엔진은 스트림 입력 외에 **슬라이스당 1개씩의 레지스터파일**에서도 입력을 받는다: TRF 는 Contraction 을,
VRF 는 Vector 를 먹인다. 소비 엔진이 돌기 전에 채워져 있어야 한다(`docs/computing-tensors__register-files.md:1-6`).

**TRF 인터페이스** (`register-files.md:7-34`): `TrfTensor<D, Chip, Cluster, Slice, Lane, Element>`.
`Chip/Cluster/Slice` 는 소스에서 통과, `Lane` = 공간 병렬(활성 1/2/4/8 레인), `Element` = 레인당 레이아웃.
`.to_trf::<Lane, Element>()` 가 스트리밍 `Time`/`Packet` 을 `Lane`/`Element` 로 reshape:
```text
Lane    = Time / FlitsPerLane          # Time 의 바깥쪽이 Lane 이 됨
Element = [Time % FlitsPerLane, Packet] # 나머지 Time × Packet 이 레인당 Element
```
`FlitsPerLane` 는 컴파일러가 `Lane`·`Time` 에서 도출 → 각 레인은 연속 `FlitsPerLane` 개 flit 으로 채워진다.
matmul 에서 관례적으로 `Lane`=출력 채널, `Element`=수축(contraction)축 (`register-files.md:37`).

### 우리 코드의 어디에 대응하는가
- `to_trf` / `to_trf_at`: `engine/collect.rs:79-93`. `verify_to_trf`(`collect.rs:130-154`)가 lowering `config_to_trf`
  로 레인/용량/Element 규칙 검사, 초과 시 "exceeds register file capacity".
  **실측: `--backend npu` 빌드에서는 lowering 쪽 동일 검사가 먼저 걸려**
  `error: furiosa-opt: ...: mir: TRF data ... exceeds register file capacity (65536 bytes)` 로 보고된다(원문은 아래 용량 절).
  메시지 끝에 ` for <address>` 가 없는 것이 출처의 서명이다 = `furiosa_opt_lower` 의 `ToTrfError::ExceedsCapacity`
  Display(`furiosa-opt-lower-0.4.0/src/verify/engine/collect.rs:39`) 출력. `verify_to_trf` 쪽 `panic!` 은 크레이트에
  그대로 남아 있고(`collect.rs:150`, 메시지에 ` for Full` 이 붙는다) 이 표본을 실행하는 테스트가 없어
  **런타임 패닉 경로는 미검증**이다.
- `to_vrf` / `to_vrf_at`: `engine/collect.rs:97-113`.
- 우리 커널 TRF 적재 사례: `gemm_kernel.rs:25-30`(B 행렬), `gemv_kernel.rs:23-29`(vector),
  `dot_product_kernel.rs:22-27`(rhs). 셋 다 `sub` 컨텍스트에서 `.begin().fetch().collect().to_trf(...)`.

### TRF 아키텍처 (`register-files.md:76-116`)
- **banked SRAM: 8 lanes × 2 banks × 128 rows × 320 bits = 80 KB/slice**(원시 용량, 320-bit 행). 활성 레인 1/2/4/8.
- 320-bit(=40바이트) 행에 타입별로 몇 개 들어가나(`register-files.md:80-90`):
  `i4→i5`=64/행, `i4→i9`=32/행, `i8`/`f8`=32/행(40B/행), `bf16`=16/행(32B/행). `i4` 만 store 시 승격(zero-point sub 여지).
  단 **i4 커널은 0.4 백엔드에서 실기 컴파일이 안 된다**(§1 마지막 항목) → 이 행의 i4 항목은 책 서술 기준이고 실기 미검증.
- 활성 레인 < 8 이면 레인당 행 수가 늘어남(4활성→256행/뱅크, 1활성→1024)(`register-files.md:93`).
- **⚠ 실측 — 활성 레인은 지금 8 밖에 실기로 못 간다.** `contract_outer_assertions::lane_size::valid_size_{1,2,4}`
  (Lane = `m![1]` / `m![R/4]` / `m![R/2]`, `R=8`) 셋 다 실기 컴파일 실패:
  `incorrect buffer size at T7: ... buffer.size() (256) != num_chips * intra_chip_size (228 / 232 / 240)`
  — 부분 충전 레인 그룹의 꼬리 패딩을 DRAM 크기 계산이 누락한다. `valid_size_8`(Lane=`m![R]`)만 컴파일되고
  **실기 실행도 통과**(`lane_size::test_valid_size_8` PASS). 즉 책의 "활성 1/2/4" 는 하드웨어 사실이지만
  **0.4 백엔드가 아직 낮추지 못한다** → 레인 부분 활성에 의존하는 커널은 실기 계획에서 빼라.
  (커널 이름이 `valid_*` 인데도 실패한다 — §2 마지막 항목.)
- **Double buffering**: 각 뱅크를 반으로 — 한쪽에서 로드하는 동안 다른 쪽에 store. `TrfAddress` 3모드:
  `Full`(128행), `FirstHalf`(0–63), `SecondHalf`(64–127). Half 모드는 슬라이스당 40 KB 로 상한(`register-files.md:96-101`)
  — 사용가능 기준으로는 **32 KB**이고 컴파일러가 그 값을 강제한다(바로 아래 절).
- 읽기 캐시(2.5 KB) + 뱅크 교대로 store 경합 완화. narrow read(≤32B) 는 뱅크 교대 유지, wide read(64B) 는 두 뱅크
  매 사이클 점유(`register-files.md:106-116`).
- **DM 직접 적재 short command(StoTRF)**: 완전 연속 접근이면 Fetch→Switch→Collect→to_trf 전체를 우회
  (`register-files.md:64-66`). VRF 도 StoVRF 있음(`register-files.md:167-170`).

### ✅ 용량 숫자 화해 — 컴파일러가 강제하는 값으로 확정됨 (추정 아님)
- GROUND_TRUTH(`_GROUND_TRUTH.md:51`): **TRF 8 KB/lane(8 lane/slice), VRF 8 KB/slice**.
- 책(`register-files.md:77`): **80 KB/slice**(= 10 KB/lane, 320-bit 행 기준), Half 모드 상한 40 KB/slice.
- **실측 근거(이 세션 전수 컴파일 로그)** — 백엔드의 `mir` 검증이 상한을 숫자로 뱉는다:
  ```text
  contract_outer_assertions::trf_size::invalid_to_trf_full:
    mir: TRF data (524288 bytes = 8 lanes x 65536 bytes) exceeds register file capacity (65536 bytes)
  contract_outer_assertions::trf_size::invalid_to_trf_half:
    mir: TRF data (65536 bytes = 8 lanes x 8192 bytes) exceeds register file capacity (32768 bytes)
  ```
  → **Full 상한 = 65,536 B = 64 KB/slice = 8 KB/lane**, **FirstHalf/SecondHalf 상한 = 32,768 B = 32 KB/slice = 4 KB/lane**.
  (Half 쪽 사례는 `8 lanes × 8192 B` = 정확히 Full 상한인 데이터가 거부된 것 — Half 는 딱 절반이다.)
- 결론: 이전 판의 "내 계산(추정)" 이 맞았고 이제 **컴파일러가 그 값을 강제한다**는 근거가 붙었다.
  320-bit 행 = 물리 40바이트지만 packed 실사용은 **32바이트(1 flit)/행** → 32B × 2 banks × 128 rows =
  **8,192 B = 8 KB/lane**. GROUND_TRUTH 의 "8 KB/lane" 은 **사용가능 flit 데이터**, 책의 "80 KB/slice" 는
  **320-bit 행 슬랙 포함 원시 SRAM**. 두 척도를 잇는 비율이 32/40 이다: 80 KB × 32/40 = **64 KB**,
  40 KB × 32/40 = **32 KB** — 컴파일러 숫자와 정확히 맞는다.
- 위 두 커널은 **의도적 negative 표본**(§2 마지막 항목)이라 실패가 정상이다. 짝이 되는 양성 커널
  `trf_size::valid_to_trf_full`·`valid_to_trf_half` 는 컴파일 OK 이고 **실기 NPU 실행도 둘 다 통과** →
  `TrfAddress::Full` 과 `FirstHalf`(double buffering) 는 실기에서 동작한다. `at_primitives::trf::to_trf_at`
  (`test_to_trf_at`) 도 실기 통과.

### VRF (`register-files.md:119-175`)
- `VrfTensor<D, Chip, Cluster, Slice, Element>`. `.to_vrf::<Element>()` 는 `Element = [Time, Packet]` 로 평탄화.
- **VRF 용량 8 KB/slice** 는 GROUND_TRUTH(`_GROUND_TRUTH.md:51`)에서만 확인. 책의 "### Architecture"(`register-files.md:173-175`)
  절은 **본문이 비어 있어** VRF 물리 구조는 이 문서 소스로는 **미확인**.

## 5. 우리 gemm_kernel 체인 단계별

`gemm_kernel.rs` 는 두 컨텍스트로 나뉜다: `sub` 가 B 를 TRF 에 적재, `main` 이 A 를 스트리밍해 수축.

### 5-1. 격자·타일 정정 (GROUND_TRUTH `_GROUND_TRUTH.md:32-34`)
```rust
// gemm_kernel.rs:3,8-9
axes![I = 512, J = 512, K = 64];
pub type Slice = m![I / 32, J / 32]; // 주석 "16 × 16 output tile" 은 틀림
pub type Lane  = m![J % 8];
```
- `Slice = m![I/32, J/32] = 16×16 = **256 슬라이스 격자**`. 각 슬라이스가 담당하는 **타일**은 `m![I%32, J%32] = 32×32`.
- 검산: 256 슬라이스 × 1024(32×32) = 262,144 = I·J. (256×256 ≠ I·J → 원 주석 "16×16 tile" 오류.)

### 5-2. sub 컨텍스트: B → TRF (`gemm_kernel.rs:25-30`)
```rust
let b_trf: TrfTensor<bf16, Chip, Cluster, Slice, Lane, m![J / 8 % 4, K]> = ctx
    .sub
    .begin(b.view())                                            // b: DmTensor m![J % 32, K]  (line 19)
    .fetch::<m![J % 8, J / 8 % 4], m![K]>()                     // Time=(J%8,J/8%4), Packet=K(64 bf16=128B)
    .collect::<m![J % 8, J / 8 % 4, K / 16], m![K % 16]>()      // 128B=4 flit → 바깥 4개를 Time 으로
    .to_trf(TrfAddress::Full);                                  // Lane=J%8(8레인), Element=(J/8%4,K)
```
단계 해설:
1. **fetch**: 슬라이스 안 타일 `m![J%32, K]` 을 스트림으로. `Packet = m![K]` = 64 bf16 = 128바이트.
2. **collect**: 128B 는 4 flit(각 16 bf16=32B). 안쪽 16개→`Packet2 = m![K%16]`, 바깥 4개(`K/16`)→Time 으로 흡수.
   결과 Time flit 수 = `J%8 × J/8%4 × K/16` = 8×4×4 = **128 flit**.
3. **to_trf**: `Lane = m![J%8]`(8) 이 Time 바깥쪽을 차지 → `FlitsPerLane = 128/8 = 16`.
   `Element = [나머지 Time, Packet] = m![J/8%4, K]` = 4×64 = 256 (= 16 flit × 16 elem/flit ✓).
   즉 **레인 = 출력 채널(J의 8개), Element = (J의 4-그룹 × 수축축 K)** — 책의 matmul 관례와 일치(`register-files.md:37`).

### 5-3. main 컨텍스트: A 스트리밍 (`gemm_kernel.rs:35-46`, fetch/collect 부분만)
```rust
.begin(a.view())                                               // a: DmTensor m![I % 32, K]  (line 18)
.fetch::<m![I % 32, J / 8 % 4], m![K]>()                       // A 를 J/8%4 열그룹으로 재사용(broadcast-read)
.collect::<m![I % 32, J / 8 % 4, K / 16], m![K % 16]>()        // 동일한 4-flit 분할
.contract_outer::<m![I % 32, J / 8 % 4, K / 32], m![K % 32], _, _>(&b_trf)  // ← 여기부터 05 문서(Contraction)
```
- fetch/collect 는 sub 와 대칭. `contract_outer` 이후(수축·레인·커밋)는 **문서 05(연산 엔진 II)** 소관이라 여기선 다루지 않음.
- **switch 없음**: 위 체인 어디에도 `.switch()` 가 없다 → Forwarding(생략) 경로. 슬라이스 분배는 `to_dm` 의 `Slice` 파라미터가 이미 수행.

### 5-4. 다른 커널 대조
- `dot_product_kernel.rs:26` `collect::<m![{Time}, A/16], m![A%16]>()` — A=2048 bf16=4096B=128 flit 을 Time 으로.
- `gemv_kernel.rs:27-28` `collect::<m![J/16], m![J%16]>()` — 동일 패턴. 셋 다 switch 미사용.

## 6. 여기가 TCL 로는 못 내려가는 영역 — vISA 고유 제어축

**실측(grep, 이 세션에서 실행)**: `furiosa.tcl` 패키지 전체에서 `trf|vrf|lane|snoop|switch_engine|to_trf|to_vrf` = **0 건**.
TCL 의 배치 어휘는 `tcl.context(layout=...)` 의 **`Chip` / `Cluster` / `Split`** 이 전부이며,
`_operation.py:257` 의 `slice` 는 텐서 축 슬라이싱 연산일 뿐 하드웨어 Slice 개념이 아니다.
(근거: `_GROUND_TRUTH.md:37-40`, 그리고 grep 결과 `furiosa/tcl/__init__.py:75-77` = Chip/Cluster/Split.)

| 제어축 | TCL 공개 API | vISA |
|---|---|---|
| Chip / Cluster / Split(=Slice 분할) | 있음 (`layout={Chip, Cluster, Split}`) | 있음 |
| **Slice(격자) / Lane(≤8) / Packet(≤64B)** | **없음** | 있음 (`m![...]` 매핑 타입) |
| **TRF / VRF 적재(to_trf/to_vrf)** | **없음** | 있음 |
| **SwitchConfig / snoop bitmap** | **없음** | 있음 |
| commit-trim 등 커밋 어댑터 | **없음** | 있음 |

**요점**: TCL 은 **클러스터 경계에서 멈춘다.** 슬라이스 *내부* 데이터패스 — 어떤 레인이 어떤 출력 채널을 잡고,
패킷을 어떤 flit 으로 쪼개 TRF/VRF 어디에 넣고, 슬라이스끼리 어떻게 broadcast/transpose 할지 — 는 **vISA 만 노출**한다.
이 문서(04)가 다루는 fetch adapter·switch·collect·register file 전부가 그 "TCL 아래" 영역이다.

## 7. 버전 함정 — 0.3 커널 vs 0.4 크레이트/책

우리 서버 크레이트·책은 **0.4 세대**(`_GROUND_TRUTH.md:3-11`)지만, `/home/jun/yik` 는 `furiosa-opt-std = "0.3"` 을 핀한다
(`yik/Cargo.toml`). 이 문서 범위에서 실제로 갈리는 시그니처:

| 항목 | 0.3 (우리 커널 gemm_kernel.rs) | 0.4 (크레이트/책) | 근거 |
|---|---|---|---|
| `to_trf` 영역 인자 | `.to_trf(TrfAddress::Full)` — 값 인자 (`gemm_kernel.rs:30`) | `.to_trf()` = Full, `.to_trf_at(TrfAddress)` = 영역 (`collect.rs:79-93`) | `_GROUND_TRUTH.md:23` |
| `contract_outer` 제네릭 수 | 4개 `::<Time,Packet,_,_>` (`gemm_kernel.rs:40`) | 5개 `::<Time,Packet,_,_,_>` | `_GROUND_TRUTH.md:22` |
| 첫 타입 파라미터 이름 | — | `to_trf` 첫 param 을 코드·`register-files.md` 는 **`Lane`**, `collect-engine.md:196` 은 **`Row`** 로 부름(=같은 것) | `collect.rs:80` |

- 따라서 gemm_kernel 을 0.4 크레이트로 그대로 컴파일하면 `to_trf(TrfAddress::Full)` 시그니처가 안 맞는다.

- **`--version` 문자열로 세대 판단 금지**: 래퍼 `--version` 은 "0.3.0" 을 찍지만 바이너리는 로컬 0.4.0 과 md5 동일
  (`_GROUND_TRUTH.md:4-6`).

> **해소됨(이 세션)**: ~~TRF 8 KB/lane vs 책 80 KB/slice 화해가 추정~~ → 백엔드 `mir` 검증이 상한을
