## 0. 큰 그림 — 3계층, 3엔진

### ① 책이 뭐라 하는가
메모리 계층은 3개(HBM, DM, SPM)이고, 이들 사이를 **전용 이동 엔진 3개**가 옮긴다 (`index.md:3-9`).

| 엔진 | 경로 | 방향 |
|------|------|------|
| **Fetch** | DM → Tensor Unit | 읽어서 패킷 스트림으로 |
| **Commit** | Tensor Unit → DM | 스트림을 DM 에 씀 |
| **DMA** | DM / SPM / HBM **임의 쌍** | 계층 간 대량 이동 |

> TRF·VRF(슬라이스별 레지스터 파일)는 이 3엔진이 **안 건드린다**. Collect 엔진(`.to_trf()/.to_vrf()`)이 채우며 Computing Tensors 장 소관 (`index.md:9`, `memory-performance.md:158-164`).

파이프라인 데이터 흐름 (`memory-performance.md:163`):
```
DMA:  HBM → DM  →  Fetch: DM → TU  →  Collect: → TRF/VRF  →  Contraction/Vector 읽기  →  Commit: → DM  →  DMA: DM → HBM
```

### ② 계층별 용량·대역폭 (실측 인용)
`_GROUND_TRUTH.md:44-51` 및 `memory-performance.md:7-13`, `dma-engine.md:249-256`:

| 계층 | 용량 | 대역폭 | 비고 |
|------|------|--------|------|
| **HBM** | 48 GB/chip | **1.5 TB/s per chip** (32ch × 48 GB/s) | `memory-performance.md:171,190` |
| **DM** (SRAM) | 256 MB/chip, 512 KB/slice | 2 TB/s per chip / **256 B/cyc per cluster** (DMN 인터리빙 시) | `memory-performance.md:13,30,48` |
| **SPM** (SRAM) | — | 2 TB/s per chip / **128 B/cyc per cluster** | 컴파일러 관리 스테이징, 아직 API 미노출 `dma-engine.md:253` |
| **PCIe** | — | **30 B/cyc** | 온칩 DMA(256 B/cyc)보다 ~10배 느림 `dma-engine.md:648` |

**DMA 엔진 1기 = 256 B/cyc = 256 GB/s** (`dma-engine.md:256`, `_GROUND_TRUTH.md:46`). chip당 **8기**(`dma-engine.md:75`) → 합계 2048 B/cyc = 2 TB/s 로 DM 피크와 맞물린다.

### ③ 클럭 도메인 (헷갈리지 말 것 — `_GROUND_TRUTH.md:44-45`)
- **HBM 채널 컨트롤러 0.75 GHz** — 사이클당 8버스트 → **실효 6 GHz**. 채널당 64 B/cyc × 0.75 GHz = 48 GB/s (`memory-performance.md:190-193`).
- **DRAM 타이밍 표(tCCD 등)는 1.5 GHz 기준** (`memory-performance.md:276-282`).
- **DMA/코어 예제(cycle 추정)는 1 GHz 기준** (`dma-engine.md:330,368`).
- 그래서 같은 "cycle" 이라도 어느 표에서 왔는지에 따라 실제 시간이 다르다. 한 도메인의 사이클을 다른 도메인에 그대로 곱하지 말 것.

### ④ 함정
- "TU(Tensor Unit)로 옮긴다"는 표현은 부정확. 이동 엔진이 닿는 최하위 계층은 **DM** 이고, TU 내부의 TRF/VRF 는 Collect 가 채운다. 문서 제목의 "HBM↔DM↔TU" 는 실제로는 **HBM↔DM↔(스트림)↔TRF/VRF** 다.
- SPM 은 DM 과 물리적으로 같은 온칩 SRAM 이고, **용도/할당 정책만 다르다**(지연·용량 차이는 문서화되지 않음, `memory-performance.md:142-143`). 현재 사용자 대상 타입 아님.

## 1. Sequencer — 모든 이동의 공통 심장

### ① 책이 뭐라 하는가
Sequencer 는 **메모리 버퍼를 패킷 스트림으로 읽고, 스트림을 다시 버퍼로 쓴다** (`sequencer.md:3`). Fetch/Commit 은 시퀀서 1개로 DM 을 주소지정하고, DMA 는 **읽기 시퀀서 + 쓰기 시퀀서를 체인**해 중간 버퍼 없이 DM/SPM/HBM 사이를 옮긴다 (`sequencer.md:4-5`).

### ② 우리 코드의 어디
교육용 의사타입 `MemTensor`(버퍼) / `StreamTensor`(비행 중 텐서)로 패턴만 격리해 설명한다 — 실제 엔진은 `DmTensor/HbmTensor/TuTensor` 등을 쓰지만 전부 같은 `MemTensor → StreamTensor` 모양으로 환원된다 (`sequencer.md:9-10`).

```rust
// furiosa-opt-std-0.4.0/src/tensor/pseudo.rs:23-53
pub struct MemTensor<D: Scalar, Buf: M> { inner: Tensor<D, Buf> }
pub struct StreamTensor<'l, D: Scalar, Time: M, Packet: M> { /* Pair<Time, Packet> */ }
// read: MemTensor -> StreamTensor,  write: 역방향(브로드캐스트 거부)
pub fn read<'l, Time: M, Packet: M>(&'l self) -> StreamTensor<'l, D, Time, Packet> { ... }
pub fn write<'l, Time: M, Packet: M>(&mut self, stream: StreamTensor<'l, D, Time, Packet>) { ... }
```
- `Time` = 시간 매핑(반복), `Packet` = 공간 매핑(한 패킷 내용) (`sequencer.md:20`).
- `read` 는 브로드캐스트 허용(Fetch/DMA-read), `write` 는 각 버퍼 슬롯이 정확히 1개 소스를 가져야 함 → 브로드캐스트 쓰기는 **패닉** (`pseudo.rs:41-52`, `sequencer.md:109-115`).

### ③ 초심자용 쉬운 설명
버퍼는 "메모리에 놓인 표", 스트림은 "그 표를 특정 순서로 훑어 컨베이어에 흘리는 것". `read` 는 어느 축을 바깥 루프/안쪽 루프로 돌지(`Time`)와 한 번에 몇 개씩 집을지(`Packet`)를 고르는 일. 컴파일러는 이 선택을 **중첩 루프 Config** 로 낮춘다 (`sequencer.md:155-172`):

```
[ size_0 : stride_0, size_1 : stride_1, ... ] : packet_size    // subscript 0 = 최외곽 루프
```
각 entry 는 `size`(반복 횟수)·`stride`(반복 사이 건너뛸 원소 수)로 한 축의 순회를 인코딩.

핵심 성능 지표 `max_access_size = gcd(Packet::SIZE, contiguous_run)` — 한 번의 하드웨어 접근이 옮기는 원소 수. 클수록 패킷당 접근 횟수가 준다 (`sequencer.md:179-208`). 대부분 패킷이 DM 에서 연속이라 `max_access_size == Packet::SIZE` 지만, 비연속이면 더 작아진다.

### ④ 함정 / 제약 (`sequencer.md:568-606`)
- **entry 최대 8개**. 초과 시 컴파일러가 연속 쌍을 병합(`s1 == n2*s2` 일 때 `(n1*n2 : s2)`)한다. 병합 실패하면 컴파일 에러 → 매핑을 다시 짜거나 시퀀서 호출을 쪼갤 것.
- **iteration 한계**: entry 당 `size <= 65,536`.
- **packet size**: 1·2·4·8·16·32 바이트만.
- **양쪽 분해 호환성**: `Buf` 가 축을 `A%5,A/5` 로, 스트림이 `A%3,A/3` 로 쪼개면 `gcd(5,3)=1` 이라 공통 세분이 없어 **거부**된다(원소 총수가 같아도) (`sequencer.md:582-606`).
- 브로드캐스트는 stride `: 0` 으로 같은 주소를 반복 접근(시간·공간 복제). 쓰기 쪽 브로드캐스트는 불가.
- **읽기 브로드캐스트가 타입체크·에뮬레이션을 통과해도 실기에서 동작한다는 보장은 없다.** HBM→HBM 브로드캐스트 DMA 는 **실기에서 목적지에 아무것도 안 쓴다**(에러 없음) — §4 ④ 참조.

## 2. Fetch Engine — DM → TU 스트림

### ① 책이 뭐라 하는가
Fetch Engine 은 DM 텐서를 읽어 TU 용 패킷 스트림(`FetchTensor`)을 만든다. **슬라이스마다 시퀀서가 독립 실행**되어 각자 자기 DM 파티션을 읽는다 (`fetch-engine.md:1-4,42-44`). `Chip/Cluster/Slice` 차원은 그대로 보존(각 슬라이스가 제 파티션을 읽으므로) (`fetch-engine.md:17-19`).

### ② 우리 코드의 어디
`.begin(...).fetch::<OutTime, OutPacket>()` 형태. 우리 커널:

```rust
// visa_dn/src/kernel/dn_state_kernel.rs:40-42  (0.4 API)
ctx.main
   .begin(kt.view())
   .fetch::<m![K % 32, V / 8 % 4], m![C]>()   // OutTime, OutPacket
   .collect::<m![K % 32, V / 8 % 4, C / 16], m![C % 16]>()
```
```rust
// yik/src/kernel/dot_product_kernel.rs:33  (0.3 API, 동일 개념)
.fetch::<Time, m![A]>()      // Time = m![1], Packet = m![A]
```
크레이트 시그니처는 `engine/fetch.rs` 의 `fetch_impl` 앵커(문서가 include 하는 실제 코드, `fetch-engine.md:13-15`). `input.fetch::<m![A], m![B]>()` 는 512 time-step × 32-원소 i8 패킷을 낸다 (`fetch-engine.md:35-39`).

### ③ 초심자용 쉬운 설명
`.fetch::<OutTime, OutPacket>()` 에서 **OutTime = 스트림 시간 스텝 수**, **OutPacket = 패킷당 원소 배치**. 예컨대 `dot_product` 는 `Packet = m![A]`(A=2048 원소를 한 흐름으로), `dn_state` 는 `Packet = m![C]`(C=64, 수축 대상 축을 한 패킷으로) 흘린다.

패킷이 DM 에서 항상 연속인 건 아니고 하드웨어는 한 번에 **최대 32 B** 만 읽는다. 그래서 큰 패킷은 여러 번 읽어야 한다(**Multi-Read**). `cycles = Time::SIZE * (Packet::SIZE / read_size)` (`fetch-engine.md:51-59`). 같은 텐서라도 `OutPacket` 을 크게(2의 거듭제곱으로) 패딩하면 `read_size` 가 커져 사이클이 준다 — 30 B 텐서를 15 → 3 → 1 사이클로 줄이는 예 (`fetch-engine.md:166-206`).

### ④ 함정
- **출력 대역폭**: 하류 Collect 가 패킷을 **32 B flit** 으로 정규화 → 32 B 배수가 아니면 낭비. 20 B 패킷 = 37.5% 낭비, 40 B 패킷도 37.5% 낭비 (`fetch-engine.md:161-163`).
- **뱅크 기아 유발**: 같은 뱅크를 **64회 이상 연속** 접근하면 우선순위 낮은 Commit/DMA 를 굶겨 NoC 타임아웃 → 클러스터 리셋 (`fetch-engine.md:158`). 5장에서 상술.
- Interleaving: `begin_interleaved()` 로 매핑 동일한 두 텐서를 한 fetch 로 교대 스트림(예: `in1 + in2`). 최대 2개 (`fetch-engine.md:116-146`).
- **서브바이트(i4) 패킷은 실기 컴파일에서 막힌다** (2026-07-24 실측): `switch_assertions::alignment::aligned_fetch_packet_i4` 가 `incorrect buffer size ... buffer.size() (256) != num_chips * intra_chip_size (240)` 로 `--backend npu` 컴파일 실패 (`compile_all.log:377`). i4 는 DRAM 크기 계산이 4비트 폭을 반영하지 못한다. 에뮬레이션·타입체크에서는 안 드러난다.

## 3. Commit Engine — TU 스트림 → DM

### ① 책이 뭐라 하는가
Commit 은 Fetch 의 역. TU 파이프라인 끝 스트림 패킷을 DM 에 쓴다. 역시 슬라이스마다 독립 시퀀서, `Chip/Cluster/Slice` 보존 (`commit-engine.md:1-4,17`). 출력 `Element` 매핑이 `Time+Packet` 을 대체하며, **커밋 중 transpose** 도 가능(`Time` 축 재배열) (`commit-engine.md:18-19`).

### ② 우리 코드의 어디
```rust
// visa_dn/src/kernel/dn_state_kernel.rs:48-50  (bf16 변형)
.cast::<bf16, m![V % 8 # 16]>()   // f32 누산기 → bf16 (Cast 엔진)
.commit_trim::<m![V % 8]>()       // 패킷을 커밋 폭으로 트림
.commit();                         // DM 에 씀 (0.4: 주소 인자 없음)
```
```rust
// dn_state_kernel.rs:87-88  (f32 변형 — cast 없이 f32 그대로 커밋)
.commit_trim::<m![V % 8]>()
.commit();
```
0.3 대조: `yik/src/kernel/constant_add_kernel.rs:29-30` 은 `.commit_trim::<m![A%8]>().commit::<m![A%8]>(1 << 12)` 처럼 **주소·타입 인자**를 넘긴다. 크레이트 실제 시그니처는 `engine/commit.rs` 의 `commit_impl` 앵커(`commit-engine.md:13-15`).

### ③ 초심자용 쉬운 설명
`commit_trim` 은 연산 중 32 B flit 폭으로 부풀었던 패킷을 **실제 유효 폭(valid_size)** 으로 깎는 단계. `dn_state` bf16 변형은 f32 8원소(32 B)를 bf16 으로 캐스트하면 16원소(32 B)로 패딩되므로 `# 16` 으로 받았다가 `commit_trim::<m![V%8]>()` 로 8원소로 트림. f32 변형은 캐스트가 없어 처음부터 8원소(`# 8`)라 트림만 한다 (`dn_state_kernel.rs:47-49,58-60,86-87`).

`write_size = gcd(valid_size, access_size)`, `cycles = Time::SIZE * (valid_size/write_size)`. **main-context 는 `valid_size == write_size`** 라 패킷당 1사이클(나눗셈 항상 정수) (`commit-engine.md:56-62`).

### ④ 함정 (`commit-engine.md:49-53,116-130`)
- **주소 정렬**: 모든 시퀀서 stride 는 **8 B 배수**. 쓰기 단위 `D[valid_size]` 는 8/16/24/32 B 여야 함.
- **정렬 쓰기 불변식**: DM 쓰기 포트는 8 B 뱅크 폭 단위 → 부분 뱅크 쓰기 없음. 커밋은 항상 8 B 정렬이라 안전.
- **Slice Bitmap**: 256비트 마스크(클러스터 = 256슬라이스, 슬라이스당 1비트)로 어느 슬라이스가 커밋받을지 게이팅.
- Fetch 와 마찬가지로 같은 뱅크 64+ 연속 접근 금지(뱅크 기아).
- **`commit_trim` 패킷 불일치는 실기 컴파일 에러** (2026-07-24 실측): `matmul::matmul_split_reduce::matmul_with_split_reduce` 는 `mir: commit_trim packet mismatch. Expected A % 4 # 8 or a trimming of it, got A % 8` 로 `--backend npu` 컴파일 실패(`ex_logs/compile_all.log:317`). 트림 폭은 컴파일러가 기대하는 **패딩 형태(`# 8`)까지** 맞아야 한다.
- **[실기 결함] `commit_view` 의 타일 윈도 오프셋이 엉뚱한 위치에 착지한다** (2026-07-24 실기 실행, 에러 없음):
  `tile::tile_window_commit`(`src/tile.rs:74-88`, `commit_view(result.view_mut().tile::<m![D], 32, m![D = 32 #{!} 64]>(32))`)는
  `input[0..32]` 를 `result[32..64]` 에 넣으려는 커널인데, 실기에서는 `result[8..40]` 에 들어간다.
  **데이터는 순서대로 온전하고 쓰인 위치만 틀렸다.** 산술: 의도 오프셋 32 elements × 4 B = 128 B 인데 실제 착지는 8 elements = **32 B**
  → 32 가 "요소 수"가 아니라 "바이트 수"로 적용된 정황(런타임 소스로 확인한 것은 아님). 에뮬레이션은 통과.
  → 커밋 목적지 오프셋을 쓰는 커널은 **목적지 전체를 덤프해 위치를 검증**할 것. 상세: [13-NPU-실기-매트릭스](./13-NPU-실기-매트릭스.md) §2.

## 4. DMA Engine — DM / SPM / HBM 임의 쌍

### ① 책이 뭐라 하는가
DMA 는 **TU 파이프라인을 거치지 않고** 계층 간 텐서를 옮긴다. 읽기 시퀀서 + 쓰기 시퀀서 한 쌍이 lockstep 으로 돈다(공유 루프 카운트, 다른 stride/base). 레이아웃이 달라도 **수학적으로 같은 텐서** (`dma-engine.md:1-10,88-91`). chip당 **8기**, DMN 쌍마다 1기 (`dma-engine.md:75`).

### ② 우리 코드의 어디 — `to_dm` / `to_hbm` 이 타는 엔진
호출 표면은 **소스 텐서의 메서드 + `DmaContext` 인자** (`dma-engine.md:16-20`):
- `ctx.tdma` = **Tensor DMA** — 온칩(HBM↔HBM, HBM↔DM, DM↔DM).
- `ctx.pdma` = **PCIe DMA** — host↔HBM 전용, 별도 물리 엔진, async (`dma-engine.md:618-624`).

크레이트 실제 시그니처 (**0.4 는 주소 인자 없음** — `_GROUND_TRUTH.md:23`):
```rust
// furiosa-opt-std-0.4.0/src/tensor/memory.rs:449-462  (HbmTensor::to_dm)
pub fn to_dm<Cluster: M, Slice: M, Element2: M>(
    &self, _dma: &mut DmaContext<{ Dma::Tensor }>,     // ← 주소 인자 없음
) -> DmTensor<D, Chip, Cluster, Slice, Element2, B> { ... }

// memory.rs:842-843  (DmTensor::to_hbm)
pub fn to_hbm<Element2: M>(&self, _dma: &mut DmaContext<{ Dma::Tensor }>)
    -> HbmTensor<D, Chip, Element2, B> { ... }
```

우리 0.4 커널의 이동은 **전부 Tensor DMA(`ctx.tdma`)** 를 탄다:
```rust
// visa_dn/src/kernel/dn_state_kernel.rs:28-29,52   (0.4: 주소 인자 없음)
let kt: DmTensor<...> = kt.to_dm(&mut ctx.tdma);   // HBM → DM  (DmaLoad)
let dt: DmTensor<...> = dt.to_dm(&mut ctx.tdma);   // HBM → DM  (DmaLoad)
...
state.to_hbm(&mut ctx.tdma)                         // DM → HBM  (DmaStore)
```
반면 사용자 `yik` 프로젝트는 **0.3 API** 라 주소 인자를 넘긴다 — 현재 0.4 래퍼로는 안 맞는다:
```rust
// yik/src/kernel/gemm_kernel.rs:18-19,49   (0.3: 주소 인자 있음)
let a = a.to_dm(&mut ctx.tdma, 0);          // ← 0.4 엔 없는 두 번째 인자
let b = b.to_dm(&mut ctx.tdma, 1 << 12);
result.to_hbm(&mut ctx.tdma, 2 << 28)
```
> `_GROUND_TRUTH.md:14-16,23` — `yik` 는 `furiosa-opt-std = "0.3"` 핀 + `src/furiosa-opt.tag` 마커라 현재 래퍼에선 "no kernel packages found". 0.4 주소 없는 API 로 포팅해야 npu/실행 가능. (본 문서 실측은 이미 0.4 로 포팅된 `visa_dn`/`aud2_proj` 로 수행.)

### ③ 초심자용 쉬운 설명 — DmaSequencer 와 TDMA vs PDMA
DMA 는 읽기/쓰기 시퀀서를 **paired stride** 로 압축 표현한다 (`dma-engine.md:98-119`):
```rust
struct DmaEntry { axis: AxisName, size: usize, source_stride: isize, dest_stride: isize }
struct DmaSequencer { entries: Vec<DmaEntry>, stride0: u16 /*1..=4096, 패킷바이트*/, source_base, dest_base }
```
같은 `size`, 다른 stride → 레이아웃 변환(transpose 등)을 그대로 인코딩. `[A,B,C]→[C,A,B]` 전치는 HBM↔HBM 두 번의 `to_hbm` 으로 (`dma-engine.md:28-49`).

| 구분 | 컨텍스트 | 담당 | 대역폭 |
|------|----------|------|--------|
| **TDMA** (Tensor DMA) | `ctx.tdma` | 온칩 HBM↔HBM/HBM↔DM/DM↔DM | 엔진당 256 B/cyc, HBM 피크 1.5 TB/s 공유 |
| **PDMA** (PCIe DMA) | `ctx.pdma` | host↔HBM 만 | **30 B/cyc** (온칩의 ~1/10) |

`HostTensor.to_hbm()`/`HbmTensor.to_host()` 만 pdma, 나머지 온칩 이동은 tdma. host↔device 트래픽은 최소화하고 한 번 올려 재사용하라 (`dma-engine.md:645-649`).

### ④ 함정 / 고급 (`dma-engine.md:220-239,522-616`)
- **정렬**: HBM 읽기/쓰기 1 B, DM 읽기 1 B 지만 **DM 쓰기 8 B**. HBM↔DM 은 읽기·쓰기·패킷 모두 **8 B 정렬** 추가 요구. 어긋난 DM 쓰기 → Read-Modify-Write 로 3배 + 뱅크 블로킹.
- **정렬은 성능 문제가 아니라 컴파일 차단 요인이다** (2026-07-24 실측, `--backend npu` 컴파일 로그 원문):
  정렬 요구를 못 맞추면 **하드 에러**로 컴파일이 끊긴다. 끊기는 단계는 두 곳: DMA 시퀀서의 stride / tail 8 B 정렬은 `visa: while lowering Dma`, 부분 충전 그룹의 꼬리 패딩 누락은 `lir:` 단계(DRAM 버퍼 크기 계산). 즉 §5 에서 사이클을 다 먹는 그 자리가 컴파일도 막는다.
  - `matmul::matmul_chip_reduce` — `lhs.to_dm::<Cluster, m![A / 4], m![A % 4 # 8]>` (`src/matmul/matmul_chip_reduce.rs:19`) → `strides([8, 128, 4, 0, ...]) is not aligned by 8`
  - `vrf_add::vrf_add` — `lhs.to_dm::<Cluster, m![A / 8 # 256], m![B, A % 8]>` (`src/vrf_add.rs:19`) → `tail_size % min_align (4) != 0`
  - `matmul::matmul_cluster_reduce` — `to_dm` → `tail_size % min_align (1) != 0`
  - `contract_outer_assertions::lane_size::valid_size_{1,2,4}` (**`lir:` 단계**) — 부분 충전 레인 그룹의 꼬리 패딩을 DRAM 크기 계산이 누락 → `incorrect buffer size ... buffer.size() (256) != num_chips * intra_chip_size (228/232/240)`
  → **대표 VRF 예제(`vrf_add`)조차 실기에 못 올라간다.** 이름이 `valid_*` 인 커널도 실패하니 이름으로 판단하지 말 것.
  → 정렬 계열 에러는 실패 커널 목록 전반에서 반복 등장한다. 매핑을 짤 때 `Element` 분해를 **8 B 배수 + 명시 패딩(`# N`)** 으로 먼저 맞춰라. 전체 목록: [12-예제-전수실행](./12-예제-전수실행.md) §9, [13-NPU-실기-매트릭스](./13-NPU-실기-매트릭스.md) §7.
- **패킷 최대 4,096 B** (AXI 256 beat × 16 B). 하드웨어가 다시 256 B 단위로 쪼갬 → n B 패킷 = `ceil(n/256)` AXI 요청 (`dma-engine.md:239,283`).
- **불균등 분할**: 축이 DMN 수로 안 나뉘면 **heterogeneous aggregate** 로 떨어져 경계 DMN 이 명령을 쪼개고 각각 startup latency(~500 cyc) 를 문다. 균등 분할되게 shape 를 잡아라 (`dma-engine.md:204-218,490-520`).
- **Shuffle/Scatter/Gather**: `dm_cluster_shuffle`, `dma_scatter`(DM→HBM 인덱스 쓰기), `dma_gather_scaled/unscaled`(HBM→DM 인덱스 읽기, 페이지드 어텐션 블록테이블 등). scaled 는 인덱스가 **바이트 오프셋**, unscaled 는 **원시 행 위치** (`dma-engine.md:549-616`).
- **[실기 결함] 브로드캐스트 HBM→HBM DMA 는 목적지에 아무것도 쓰지 않는다** (2026-07-24 실기 실행, 크래시·에러 없음):
  ```rust
  // tests/broadcast.rs:12 — i32 0..512 를 [A=512, B=4] 로 펼치는 브로드캐스트 DMA
  let hbm2 = hbm1.to_hbm::<{ Dma::Tensor }, m![A, B]>(&mut ctx.tdma);
  ```
  기대 `[0,0,0,0,1,1,1,1,...]`, 실기 결과는 **2048/2048 전부 불일치**(최대 절대오차 2.139e+09, **0인 원소가 하나도 없음** — 기대값엔 4개).
  앞 4개가 `-1097810306, 1048624774, -1089814802, 1046945792` 인데 **2회 실행에서 앞 세 값이 완전히 동일** → 난수 쓰레기가 아니라 결정적으로 특정 영역을 읽는다.

  - 즉 목적지는 **미기록 상태로 남고**, HBM 은 0 초기화되지 않으므로 읽으면 이전 커널의 데이터가 그대로 나온다.
  - **에뮬레이션에서는 통과한다.** 값 검증을 안 붙이면 조용히 틀린 결과를 쓴다 → 실기 DMA 는 항상 값 검증과 함께 돌릴 것. 상세: [13-NPU-실기-매트릭스](./13-NPU-실기-매트릭스.md) §2.

## 5. Memory Performance — 왜 DMA 가 시간을 다 먹나

### ① 책이 뭐라 하는가
각 계층 피크 대역폭에 도달하려면 **특정 접근 패턴**이 필요하고, 위반하면 급격히 느려진다 (`memory-performance.md:15-26`):

| 메모리 | 이슈 | 규칙 | 벌칙 |
|--------|------|------|------|
| DM | 뱅크 기아 | 같은 뱅크 64회 미만 연속 | NoC 타임아웃 → 하드 리셋 |
| DM | DMN 인터리빙 | 클러스터당 2 DMN 교대 | 대역폭 50% 손실 |
| HBM | 정렬 | 256 B 정렬 접근 | 읽기 2×, 쓰기 ~50×(RMW) |
| HBM | 뱅크 충돌 | 같은 뱅크 내 row 전환 회피 | 30–40× |
| HBM | 채널 인터리빙 | 32채널 분산 | 병렬성 저하 |

- **DM 기하**: 클러스터 2/chip, DMN 8/cluster, 슬라이스 32/DMN, 뱅크 16/slice, row 4096/bank, 8 B/row. 128 연속 바이트가 16뱅크에 흩뿌려져 128 B/cyc 병렬 (`memory-performance.md:30-59`).
- **뱅크 기아 64-규칙**: `(TDMA_IO/DMN_IO)*Max_Consec*DMN_SIZE < 4096` = `(256/128)*x*32 < 4096` → `x < 64`. DMA 는 **최하위 우선순위**(main-fetch > main-commit > sub-fetch > sub-commit > DMA)라, 상위 엔진이 한 뱅크를 물고 있으면 DMA 요청이 4,096 cyc 안에 못 끝나 NoC 타임아웃 → **클러스터 리셋으로 연산 상태 전부 소실** (`memory-performance.md:86-121`).
- **HBM**: 채널 컨트롤러 0.75 GHz × 64 B = 48 GB/s, ×32ch = 1.5 TB/s. 기본 전송 단위 256 B = 채널당 4 cyc. **stack 비트(주소 8번)** 를 안 토글하면 32채널 중 16채널만 써 대역폭 반토막; row 충돌은 ~40 cyc/접근 (`memory-performance.md:186-257`).

### ② 우리 코드 — 스케줄 덤프(컴파일러 모델)
`dn_state` 커널(DeltaNet 상태 업데이트 `S[k,v]=Σ_c Kt[k,c]·Dt[v,c]`, `dn_state_kernel.rs:3-10`)을 `cargo furiosa-opt compile --dump-schedule`(NPU 불필요, `_GROUND_TRUTH.md:41-42`)로 뽑은 결과 — 파일 `/home/jun/.claude/jobs/46bc5c7e/tmp/2nd/d/bf16.sched.json` (7 인스트럭션, span 80,446 cyc):

| 인스트럭션 | 컨텍스트 | 소스 | begin→end | dur | span 대비 |
|------------|----------|------|-----------|-----|-----------|
| **DmaLoad** | DmaEngine | `dt.to_dm` (dn_state:29) | 2003→5121 | 3,118 | 3.9% |
| Sub | SubContext | `.fetch...to_trf` (dn_state:31) | 5121→5896 | 775 | 1.0% |
| **DmaLoad** | DmaEngine | `kt.to_dm` (dn_state:28) | 5321→8341 | 3,020 | 3.8% |
| Main | MainContext,Ve | contract 파이프라인 (dn_state:38) | 8341→9118 | 777 | 1.0% |

합산의 착시가 아니다 — 커널 하나하나가 그렇다:

### ③ 초심자용 쉬운 설명 — 왜 저장(DmaStore)이 지배하나
- 옮기는 데이터는 **512×512 bf16 결과 = 512 KB**. DMA 엔진 1기 256 B/cyc 이상적으로는 `524288/256 ≈ 2,048 cyc` 면 끝난다. 스케줄 모델값은 **72,731 cyc → 약 35.5배 느림**.
- 이 35× 는 책의 **HBM 뱅크 충돌 30–40×** / **정렬 안 된 쓰기 ~50× RMW** 범위(`memory-performance.md:23,172,234,248`)에 정확히 들어온다.
- 구조적 이유(개념): 결과 `state` 는 DM 에서 **슬라이스별 32×32 타일**(`Slice = m![K/32, V/32]`, `dn_state_kernel.rs:15`)로 흩어져 있는데, HBM 출력은 연속 `m![K, V]` 다. 한 K 행의 연속 V 는 16개(`V/32`) 슬라이스에 걸쳐 있어, row-major HBM 로 모으는 건 **레이아웃 변환 저장**(책 DMA Example 1 의 전치와 동류). 이때 256 B 미정렬·row 전환·채널 편중이 쉽게 발생한다.
- 교훈: **연산이 싸도(C=64 수축) 결과를 HBM 에 어떻게 눕히느냐가 커널 시간을 정한다.** 최적화 1순위는 컴퓨트가 아니라 **저장 레이아웃/정렬/채널·DMN 인터리빙**.

### ④ 함정 / 미확인
- 위 "35× 의 정확한 근본 원인(뱅크 충돌 vs 미정렬 RMW vs stack 비트 미토글)"은 **덤프만으로는 미확인**. 스케줄 덤프는 인스트럭션 컨텍스트·사이클만 주고, 채널 분포·요청별 벌칙은 안 준다. `util` 필드는 전 커널·전 인스트럭션이 `0.0` 으로 **덤프판 미채움 확정**(§5 ②-2)이라 활용 불가. 근거는 정황(35× 가 책의 30–50× 대역에 부합)일 뿐, 단정하지 말 것.
- 프롬프트가 참고로 준 "DmaStore ≈ 88%" 는 근사치. **스케줄 덤프의 정확값은 90.4%(bf16)/90.5%(f32)** 이며, 근거 파일은 `2nd/d/bf16.sched.json`·`audit_out/*_sched.json`.
- DM↔DM 같은 클러스터 전송은 읽기/쓰기가 **직렬화**(같은 뱅크 경쟁)되지만 HBM↔DM 은 파이프라인된다 (`dma-engine.md:259-261`). 위 커널의 store 는 DM→HBM 이라 이론상 파이프라인 대상 — 그럼에도 오래 걸린 건 HBM 쓰기 측 병목을 시사(정황).
