## 1. vISA 란 무엇인가 — 3계층 스택에서의 위치

### ① 책이 뭐라 하는가
TCP(Tensor Contraction Processor)는 추론용 대규모 병렬 가속기다. PyTorch/XLA는 메모리 레이아웃·스케줄을 숨기고, 저수준 커널 API는 바이트 단위 추론을 강요한다. vISA는 그 **중간**에서 "텐서로 추론하면서 메모리 할당과 텐서 유닛 스케줄을 직접 관리"하게 해준다. (`introduction.md:3-8`)

### ② TCP/RNGD 스택에서의 위치 — 3계층
| 계층 | 무엇 | 노출 어휘 | 근거 |
|------|------|-----------|------|
| PyTorch/XLA (상위) | 그래프·연산자, 레이아웃 자동 | 텐서 연산만 | `introduction.md:4` |
| **TCL** (`furiosa.tcl`) | 칩/클러스터/스플릿 배치 | `tcl.context(layout={Chip, Cluster, Split})` **가 전부** | `_GROUND_TRUTH.md:38` |
| **vISA** (`furiosa-opt`) | 슬라이스 내부 데이터패스까지 | Slice/Lane/Packet/TRF/VRF/commit-trim | `_GROUND_TRUTH.md:39-40` |

### ③ 초심자용 쉬운 설명
- **TCL은 "칩·클러스터를 어떻게 나눌지"까지만** 말한다. 클러스터 경계에서 멈춘다.
- **슬라이스 내부**(Lane ≤ 8개, Packet ≤ 64 B, 레지스터 파일 TRF/VRF)를 다루려면 **vISA만**이 그 손잡이를 준다.
- 즉 "여기부터 슬라이스 안쪽"은 vISA의 영역. TCL로는 볼 수도 없다.

### ④ 함정/주의
- TCL 공개 API에 `Slice`/`Lane`/`Packet`/`TRF`/`VRF`/`commit-trim`은 **0건**이다(`_GROUND_TRUTH.md:39`). "TCL로 레인을 제어한다" 같은 말은 틀림.
- 계측 도구도 갈린다: `furiosa-tcc`(TCL)는 덤프/프로파일 옵션이 **전무**하지만, `cargo furiosa-opt compile`은 `--dump-schedule/--dump-ir/--dump-visa/--dump-graph/--dump-summary`로 **NPU 점유 없이 사이클 단위 스케줄**을 뽑는다(`_GROUND_TRUTH.md:41-42`).
  - 플래그 5개 전부 `cargo furiosa-opt compile --help` 실측 확인(2026-07-24): `--dump-visa <FILE>`, `--dump-ir <FILE>`(LIR), `--dump-schedule <FILE>`(JSON), `--dump-graph <FILE>`(JSON), `--dump-summary <DIR>`. `[FILTER]`는 `#[device]` 이름에 대한 **부분문자열 매칭**이라 접두사가 겹치는 다른 커널까지 함께 선택된다 — 판정 자동화 시 오탐의 원인([12-예제-전수실행](./12-예제-전수실행.md) §9).
  - **"NPU 점유 없음"도 실증됐다**: 이 덤프로 커널 130개 스케줄을 뽑는 동안 실기 테스트를 동시에 돌렸다. 단 덤프값은 **AOT 컴파일러의 스케줄 모델 예측치**이며 실기 실행 결과가 아니다(사이클 특성 분석은 [13-NPU-실기-매트릭스](./13-NPU-실기-매트릭스.md) §4).

## 2. 설치와 백엔드 — 이 서버의 실제 상태

### ① 책이 뭐라 하는가
세 가지를 설치: (1) 핀된 Rust 툴체인(`nightly-2026-05-01`, rustc 드라이버라 ABI가 특정 nightly에 고정), (2) `cargo-furiosa-opt`(백엔드 `--cfg backend="..."` 주입 + NPU 커널 프리컴파일), (3) Furiosa SDK + 실물 NPU(`--backend npu`일 때만). **`emulation`/`typecheck`는 SDK 불필요, 순수 호스트 실행**. (`introduction.md:21-42`)

### ② 우리 코드/래퍼의 대응 — 실측
아래는 이 서버에서 직접 실행한 값이다.

```text
$ cargo furiosa-opt --version
cargo-furiosa-opt 0.3.0                      # ← 문자열은 0.3.0

$ cargo furiosa-opt --help    (발췌)
Options:
  --backend <BACKEND>
      Possible values:
      - typecheck: Validate kernel mapping and shapes without computing values
      - emulation: Run kernels on the host CPU over Npu's physical buffer storage
      - npu:       Run compiled kernels on the NPU
      [default: emulation]
```
(출처: 실서버 `cargo furiosa-opt --version` / `--help` 출력, 2026-07-23 실측)

## 3. 백엔드 3종의 의미

| 백엔드 | 무엇이 실행되나 | NPU 필요 | 언제 쓰나 | 근거 |
|--------|----------------|:---:|-----------|------|
| `typecheck` | 매핑·shape만 타입 수준 검증. 값 루프는 **phantom(빈) 텐서**로 단락(short-circuit) | ❌ | 매핑/shape 오류를 빠르게 잡을 때 | `introduction.md:130` / `--help` |
| `emulation`(기본) | 호스트 CPU가 **Npu의 물리 버퍼 위에서** 커널을 실제 해석 실행 → 수치 정확성 검증 | ❌ | 개발 기본값, 값 검증 | `introduction.md:131` / `--help` |
| `npu` | 컴파일된 EDF를 실기(또는 NVP 시뮬)에서 실행 | ✅ (+ SDK) | 하드웨어 경로 포함 종단 검증 | `introduction.md:132` |

초심자 요점:
- **`typecheck`는 값을 안 센다.** 그래서 `test`를 typecheck로 돌리면 `actual`이 빈 Vec → 비교 루프가 0회 반복 → **원소 단위 비교는 통과**한다(`introduction.md:106-108`). 벡터 전체를 한 번에 비교하는 단언은 `left: []`로 실패한다(아래 실측). "통과했다"고 안심하면 안 됨.
  - 실측 보정: 벤더 예제 크레이트를 `typecheck`로 돌리면 **97 passed / 7 failed / 10 ignored**다. 실패 7개는 전부 phantom 텐서 vacuity(`left: []`)라 **오류가 아니다** → typecheck에서는 통과/실패 수 자체가 신호가 아니고 **빌드가 되는지**만 신호다.
- `cargo check`는 **커널 함수 본문을 실행하지 않는다** → `Collect output packet must be exactly 32 bytes` 같은 매핑 assert에 도달 못 함. 그건 `--backend typecheck run`으로 잡아야 한다(`introduction.md:145`).
- `emulation`은 "물리 버퍼로 실행"이지 하드웨어가 아니다. NPU 카드 없이 정확도까지 본다.

### ⚠ `--backend npu`의 진짜 제약 (2026-07-24 실기 실측) — 처음 npu를 켤 때 가장 크게 걸리는 함정

> **`--backend npu`는 패키지 안의 *모든* `#[device]` 함수를 빌드 시점에 EDF로 낮춘다.** 테스트가 그 함수를 부르든 말든 상관없다. **하나라도 못 낮추면 크레이트 전체가 죽는다.**

- 벤더 예제 크레이트(`furiosa-opt-examples`)를 그대로 `--backend npu`로 돌리면 **63개 커널 에러로 빌드 실패, 테스트 0개 실행**. 같은 크레이트가 `emulation`에서는 **104 passed / 0 failed / 10 ignored**다.
- 즉 **`typecheck`/`emulation` 통과는 npu 로워링을 전혀 보장하지 않는다.** 한 단계 더 내려가도 마찬가지다 — **`compile` 성공도 실기 실행을 보장하지 않는다**(컴파일은 되지만 `furiosa_kernel_load`에서 프로세스가 abort하는 사례 3건: [13-NPU-실기-매트릭스](./13-NPU-실기-매트릭스.md) §2.1).
- 우회법 2가지가 실기로 검증됐다:
  1. **서브셋 패키지** — 되는 모듈만 골라 새 크레이트 (실기 테스트 21개) → [12-예제-전수실행](./12-예제-전수실행.md) §7
  2. **게이팅**(권장) — 실패 커널에만 `#[cfg(not(backend = "npu"))]`. 상류가 이미 쓰는 관용구다(`furiosa-opt-examples/tests/matmul_tests.rs:124` 실물 확인). 실기 테스트 **89개** → [12-예제-전수실행](./12-예제-전수실행.md) §10
- 게이팅 후 **실기 실행 결과**(스케줄 모델 예측이 아니라 실제 NPU 실행): **89개 중 PASS 80 / FAIL 5 / ABORT 3 / `#[ignore]` 1**. 결함 유형·값 검증은 [13-NPU-실기-매트릭스](./13-NPU-실기-매트릭스.md).
- **테스트마다 별도 프로세스로 격리해야 한다.** 한 프로세스에 몰아 돌리면 hang 커널 하나가 HAL `-110`(ETIMEDOUT)을 남겨 **이후 모든 커널 실행이 실패**한다 → 멀쩡한 커널이 대량 오집계(`vector_engine`: 격리 33 통과 vs 배치 10 통과).
- NPU 카드는 이 실행 내내 유휴였다: `furiosa-smi status`가 **`npu0~npu3` 전부 `alive`, `0.00/47.50 GiB`**(실행 전·후 동일, 자원 누수 0).

## 4. 우리 프로젝트 지형 — `/home/jun/yik`

### ① 구성
- 라이브러리 1개(`src/lib.rs` → `pub mod kernel;`) + 커널 5개(`src/kernel/*_kernel.rs`) + 호스트 바이너리 5개(`src/*.rs`).
- 5개 예제 bin: **constant_add, elementwise_mul, dot_product, gemv, gemm** (`Cargo.toml:15-33`, `_GROUND_TRUTH.md:18`).
- 커널 재노출: `src/kernel/mod.rs`가 5개 모듈 `pub mod` (`src/kernel/mod.rs:1-5`).

### ② 버전·마커 현실 (npu 불가 원인)
```toml
# yik/Cargo.toml:36
furiosa-opt-std = "0.3"
```
```text
# yik/src/  (ls 실측)
-rw-r--r-- ... 0  furiosa-opt.tag        # ← 0바이트 구형 마커
# Cargo.toml 에 [package.metadata.furiosa-opt] 섹션 없음
```
- yik는 **0.3을 핀**하고 **`src/furiosa-opt.tag`(0바이트)** 를 마커로 쓴다 → **현재 0.4 래퍼로는 `--backend npu` 불가**. 실측 시 `cargo furiosa-opt compile gemm_kernel` → **"no kernel packages found"** (`_GROUND_TRUTH.md:14-16`).
- npu를 쓰려면: (1) `Cargo.toml`에 `[package.metadata.furiosa-opt]` 추가, (2) 커널을 0.4 API로 포팅 — **둘 다** 필요(`_GROUND_TRUTH.md:16`).
- **하지만** `typecheck` / `emulation`은 잘 돈다(NPU 불필요, `_GROUND_TRUTH.md:17`). 즉 학습·검증은 지금 그대로 가능.

### ③ 실행 시 `--bin` 필수
`Cargo.toml`에 `default-run`이 없다 → `--bin <name>` 없이 `run` 하면 cargo가 "could not determine which binary to run"으로 죽는다(`_GROUND_TRUTH.md:19`).

```bash
# 반드시 --bin 지정 (기본 emulation, NPU 불필요)
cargo furiosa-opt run --release --bin gemm
cargo furiosa-opt test --release --bin gemm            # 값 비교까지
cargo furiosa-opt --backend typecheck run --release --bin gemm   # 매핑/shape만

# ⚠ yik 에서만 npu 백엔드가 실패한다. 이유는 위 §4-②(0.3 핀 + 구형 마커)이지,
#   NPU 카드가 막혀 있어서가 아니다 — 카드는 유휴이고 실기 실행은 예제 크레이트로 실증됐다(§3 ⚠).
# cargo furiosa-opt --backend npu run ...   ← "no kernel packages found"
```

### ④ 0.3 → 0.4 API 드리프트 (yik는 0.3 API로 작성됨)
| 항목 | 0.3 (yik가 쓰는 것) | 0.4 (설치된 크레이트) | 근거 |
|------|--------------------|----------------------|------|
| `contract_outer` 제네릭 수 | 4개 | **5개** (`::<Time,Packet,_,_,_>`) | `_GROUND_TRUTH.md:22` |
| DMA 주소 인자 | `to_dm(&mut ctx.tdma, 0)` 명시 | **주소 인자 제거** `to_dm(&mut ctx.tdma)` | `_GROUND_TRUTH.md:23` |
| 버퍼 접근자 | `to_buf()` | **`into_vec()`** | `_GROUND_TRUTH.md:24` |
| NPU 런타임 | `runtime::Npu` | **`backend::` 모듈** | `_GROUND_TRUTH.md:25` |

실물 확인: `yik/src/gemm.rs:34`가 `a.to_buf()`(0.3), `yik/src/kernel/gemm_kernel.rs:18`가 `to_dm(&mut ctx.tdma, 0)`(0.3 명시 주소)를 쓴다. → **문서 코드를 0.4 크레이트에 그대로 붙여넣으면 컴파일 안 됨**을 유념.

### ⑤ 사용자 커리큘럼과의 버전 드리프트

## 5. yik 코드에 박혀 있는 알려진 오류 (그대로 믿지 말 것)

`gemm_kernel.rs`의 주석 두 곳은 **틀렸다**. 이후 매핑 챕터에서 반복 인용되므로 여기서 못박아 둔다.

| 위치 | 잘못된 주석 | 실제 | 검산 |
|------|-------------|------|------|
| `gemm_kernel.rs:8` | "Each slice handles a **16 × 16** output tile" | `Slice = m![I/32, J/32]`는 **16×16 격자 = 256 슬라이스**, 각 슬라이스가 담당하는 타일은 `m![I%32, J%32]` = **32×32** | 256 × 1024(32×32) = 262,144 = I·J ✔ (256×256 ≠ I·J) |
| `gemm_kernel.rs:22-23` | "**Switch Engine** distributes B across 256 slices" | 실제로 `switch()`는 **호출되지 않는다.** 분배는 `to_dm`의 `Slice` 타입 파라미터가 한다 | 코드에 `.switch(` 없음 |

(근거: `_GROUND_TRUTH.md:31-35`) — "슬라이스 격자(16×16)"와 "슬라이스가 담당하는 타일(32×32)"을 **혼동하지 말 것**이 핵심 교훈.
