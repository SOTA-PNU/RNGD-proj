# 11 · vISA로 만든 모델 실행 결과 — MNIST를 RNGD에서 돌려본 판정

> "vISA로 만든 모델을 실제로 돌려보면 되나?"에 대한 결과 정리.
> 구조 해부는 [10-MNIST-실전해부](./10-MNIST-실전해부.md), 이 문서는 **돌려본 결과·판정**만 다룬다.
> 실행 결과 수치는 실기 task 로그에서, 사이클 수치는 컴파일러 스케줄 덤프(예측치)에서 그대로 옮겼다.

## 0. 한 줄 결론

**된다.** vISA로 만든 2층 MLP MNIST 분류기가 실제 RNGD NPU에서 **이미지 10장 전부 정답(10/10)** 분류했고,
forward 전체가 단일 68KB EDF 커널로 실기에서 0.12초 만에 돌았다. NPU 자원 누수도 없었다.

이 판정은 더 이상 단발 결과가 아니다. 이후 벤더 예제 크레이트 전체를 실기로 올려
**실기 테스트 89개 중 80개 PASS** 매트릭스를 뽑았고, MNIST는 그 안에서 `mnist 1/1`
(`hal=0 mismatch=0 load=0`) 행으로 **별도 크레이트에서 독립 재현**됐다
→ [13-NPU-실기-매트릭스](./13-NPU-실기-매트릭스.md) §1.

## 1. 무엇을 돌렸나

- **모델**: 2층 완전연결 MLP (fc1 800→256 + bias + ReLU → fc2 256→16 + bias)
- **가중치**: 실제 학습된 값 (`mnist.safetensors`, 859,220 B)
- **입력**: MNIST 숫자 이미지 10장 + 정답 라벨 10개
- **판정 방식**: 각 이미지의 argmax 예측이 실제 라벨과 **정확히 일치해야** 테스트 통과
  (`mnist_tests.rs`의 `assert_eq!(predicted, expected)`)
- **위치**: `/home/jun/.claude/jobs/46bc5c7e/tmp/visa_mnist/` (사용자 원본 `/home/jun/yik` 미변경)

## 2. 3단계 실행 결과 (실측)

| 단계 | 백엔드 | NPU | 결과 | 의미 |
|---|---|:--:|---|---|
| ① 매핑 검증 | typecheck | 불필요 | 매핑 ✅ / 값 N/A | 모든 커널이 하드웨어 제약 만족 |
| ② 호스트 수치 검증 | emulation | 불필요 | **`1 passed`** (1.48s) | **10/10 정답** (호스트 CPU 해석) |
| ③ 실기 | **npu** | **필요** | **`1 passed`** (0.12s) | **실제 RNGD에서 10/10 정답** |

### ①에 대한 주의 (정직하게)
typecheck 단계는 테스트 로그상 `test_mnist ... FAILED`로 나온다. **이건 정상이다.**
typecheck 백엔드는 phantom 텐서(축 메타데이터만, 값 없음)라 커널의 매핑·shape는 전부 검증하지만
**값을 계산하지 않는다.** 그래서 argmax할 logits가 비어 있어 테스트의 argmax 단계에서 멈춘다.
→ **매핑 검증은 통과했고, 값 검증은 ②·③이 담당한다.** (이 vacuity는 [00-개요와-환경](./00-개요와-환경.md)의 typecheck 설명과 동일.)

## 3. 실기(NPU) 실행이 진짜였다는 증거

| 확인 | 결과 |
|---|---|
| 실행 전 npu0 유휴 | `0.00/47.50 GiB` (`furiosa-smi status`) |
| 로드된 커널 | `forward.edf` 68,106 B (edf_hash `142c619969744e07…`) |

| 실행 후 누수 | 잔존 프로세스 0, npu0 메모리 0.00 GiB (재확인) |
| 라우터 영향 | 없음 (실행 시점 백엔드 미기동 상태였음) |

## 4. forward 커널이 한 일 (사이클 = 컴파일러 스케줄 모델 값)

`--dump-schedule` 기준, 총 **17,953 cycle** (@1GHz ≈ 18.0 µs), 인스트럭션 22개:

| 항목 | 값 |
|---|--:|
| computation_cycle | 8,472 |
| main context (DPE+Vector) | 7,682 (42.8%) |
| io (DMA) | 12,365 (68.9%, 겹침) |
| sub (TRF 적재) | 790 (4.4%) |
| DRAM io 총량 | 419,968 B |

엔진 전체 분해(위 표에 안 나온 항목까지): DmaEngine 12,365 · MainContext 7,682 · VectorEngine 1,162 ·
SubContext 790 · PeCore 600.
**서로 더하는 항목이 아니다** — `VectorEngine 1,162` 는 Main 인스트럭션 4개가 MainContext 와 VectorEngine
컨텍스트를 동시에 점유한 값이라 위 표의 `main context 7,682` 안에 이미 들어 있다
(인스트럭션별 근거는 [10-MNIST-실전해부](./10-MNIST-실전해부.md) §7).

> **이 표는 실기 계측이 아니라 컴파일러의 스케줄 모델 예측치다.**
> `--dump-schedule`은 AOT 산출물이라 NPU를 아예 점유하지 않는다. **실기 실행 증거는 §2·§3**
> (`1 passed`, 10/10, 0.12s). 두 계열을 섞어 읽지 말 것.
> 단, 이 값들은 나중에 커널 **130개**를 일괄 스캔한 스케줄 덤프에서 **그대로 재현**돼
> 그 분석기의 검증 기준점으로 쓰였다 ([13-NPU-실기-매트릭스](./13-NPU-실기-매트릭스.md) §4).

동원된 엔진: **Contraction(DPE)** 로 두 번의 행렬곱, **Vector Engine** 으로 bias-add와
**ReLU(`vector_clip(Max,0)`)**, **Switch/Transpose** 로 bias 재배치, **DMA** 로 HBM↔DM 이동.
(단계별 상세는 [10-MNIST-실전해부](./10-MNIST-실전해부.md) §7.)

## 5. 이 결과가 갖는 의미

이번 세션에서 vISA "**성능** 향상" 주제는 반복적으로 무너졌다 —
① "vISA만 정밀도 선택" → TCL의 `write.to(.../f32)` 한 줄로 반박,
② "f32 커밋이 3배 느림" → 스케줄 모델상 오히려 121 cycle 빠름(호스트 측정 오류),
③ "vISA만 출력 정렬 제어" → TCL의 `tcl.Dram` 로 반박.
공통 원인: vISA가 배타적으로 노출하는 슬라이스 내부 데이터패스의 Amdahl 상한이 좁다.

**이 상한은 이제 추론이 아니라 수치가 있다.** 스케줄 덤프를 뽑은 커널 **130개**의 스케줄을 합산하니
**DmaEngine 75,464,336 cycle = 총 사이클의 96.5%**, PeCore 2,586,167 (3.3%), VectorEngine 14,770 (0.0%).
인스트럭션 **수**는 PeCore가 1,557개로 최다인데 사이클은 3.3%다(DmaEngine은 470개로 96.5%).
합산의 착시도 아니다 — **130개 중 107개(82%)가 DMA 사이클 비중 50% 이상, 54개는 90% 이상, 중앙값 82.8%.**
→ 슬라이스 내부 연산을 0 사이클로 줄여도 상한은 **3.3%**.
(이 수치는 §4와 같은 계열, 즉 컴파일러 스케줄 모델 예측치다. 분해 상세: [13-NPU-실기-매트릭스](./13-NPU-실기-매트릭스.md) §4.1~4.2.)

**그런데 이번 MNIST는 "성능"이 아니라 "표현력·완결성"의 결과다.**

- 개별 커널(gemm 하나) 검증을 넘어, **실제 학습된 모델이 vISA만으로 end-to-end**
  (컴파일 → 매핑검증 → 호스트검증 → 실기실행 → 정답분류)까지 완주했다.
- matmul·ReLU·bias·transpose·switch·argmax(호스트)를 조합한 **다단 파이프라인**이 실기에서 정확히 돌았다.
- 이것은 앞선 주제 조사에서 유일하게 살아남은 방향 **B(커스텀 연산자/모델을 vISA로 얹기)의 실증 발판**이다.
  furiosa-llm이 거부하는 구조(예: DeltaNet 순환)를 vISA로 짜서 돌리는 다음 단계의 근거가 된다.
  - 단, **그 다음 규모는 아직 안 열렸다.** 저장소에서 end-to-end 학습 모델은 **MNIST 하나뿐**이고,
    유일한 다른 후보인 transformer(Qwen 2.5 0.5B, 24레이어)는 `embedding`·`attention`·`decoder`·`head`의
    `forward` **4개가 전부 `internal compiler error`(ICE)** 로 실기 컴파일 자체가 막힌다(가중치도 전부 `zero()`).
    → 발판은 MNIST 규모까지다 ([12-예제-전수실행](./12-예제-전수실행.md) §2.1·§6.3).

## 6. 정직한 한계

- **속도 비교는 안 했다.** 같은 MNIST를 furiosa-llm/TCL로 돌린 값과 대조하지 않았으므로
  "vISA가 빠르다/느리다"는 말할 수 없다. 이 결과는 **"돈다·정확하다"까지**다.
- **argmax는 호스트에서** 한다(벤더 예제 설계). NPU에서 도는 건 forward(fc1+relu+fc2)까지.
- **모델을 새로 짠 게 아니라** 벤더 예제(`furiosa-opt-examples/src/mnist`)를 0.4로 포팅해 돌렸다.
  기여는 "우리 서버(0.4 래퍼)에서 실기 실행이 된다는 실증"이지 "새 모델 설계"가 아니다.
- 배치=1, 단일 칩. 처리량/동시성은 측정 대상이 아니었다.
- **"MNIST가 됐다"는 스택 전반의 보증이 아니다.** 같은 스택의 실기 전수 실행에서 결함 **4유형**이
  잡혔다 — 진짜 결함은 ①~③의 **6건**이고, ④의 2건은 커널이 옳으므로 결함 집계에서 뺐다:
  ① 커널 로더 범위초과 → 프로세스 abort(3건), ② 에러 없이 조용한 데이터
  오배치(2건), ③ 커널 hang → HAL `-110`(ETIMEDOUT)(1건),
  ④ 커널은 옳은데 테스트 기준이 과한 것(2건, 버그 아님).
  **MNIST는 이 중 어디에도 걸리지 않았다**(매트릭스 행 `hal=0 mismatch=0 load=0`).
  유형별 원문·판별법은 [13-NPU-실기-매트릭스](./13-NPU-실기-매트릭스.md) §2.
- **`compile` 성공이 실기 실행을 보장하지 않는다.** ①의 3건은 컴파일도 에뮬레이션도 통과하는데
  `furiosa_kernel_load`에서 프로세스가 죽는다. MNIST의 통과는 MNIST에 대한 사실일 뿐이다.

## 7. 재현 (한 줄)
```bash
. "$HOME/.cargo/env"
cd /home/jun/.claude/jobs/46bc5c7e/tmp/visa_mnist
CARGO_TARGET_DIR=target_emu cargo furiosa-opt --backend emulation test --release   # 10/10 (NPU 불필요)
CARGO_TARGET_DIR=target_npu cargo furiosa-opt --backend npu test --release         # 실기 10/10 (npu0 유휴 확인 후)
```

> **함정 — 이게 되는 건 `visa_mnist`가 `mnist` 모듈만 담은 단독 패키지이기 때문이다.**
> `--backend npu`는 패키지 안의 **모든** `#[device]` 함수를 빌드 시점에 EDF로 낮춘다.
> 테스트가 부르지 않는 커널이라도 하나만 실패하면 크레이트 전체가 죽는다.
> 벤더 예제 크레이트(`furiosa-opt-examples`)를 그대로 `--backend npu`로 돌리면
> **63개 커널 에러로 빌드 실패, 테스트 0개 실행**이다. 전체를 실기로 올리려면
> 실패 커널만 `#[cfg(not(backend = "npu"))]`로 게이팅해야 한다
> ([13-NPU-실기-매트릭스](./13-NPU-실기-매트릭스.md) §6, [12-예제-전수실행](./12-예제-전수실행.md) §5).
