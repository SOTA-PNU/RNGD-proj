### 실기(real NPU)로 가려면 — 2026-07-24 실기 세션 실측

`--backend npu` 는 **패키지 안의 *모든* `#[device]` 함수를 빌드 시점에 EDF 로 낮춘다.** 테스트가 그 함수를 부르든 말든 상관없다 → **하나라도 못 낮추면 크레이트 전체가 죽는다.** 벤더 예제 크레이트(`furiosa-opt-examples`)를 그대로 `--backend npu` 로 돌린 결과: **63개 에러로 빌드 실패, 테스트 0개 실행**(NPU 백엔드 **빌드 시점** 실패 — 실기에서 돈 코드는 하나도 없다).

검증된 우회법은 **게이팅**: 실기 컴파일에 실패하는 커널·테스트에만 `#[cfg(not(backend = "npu"))]` 를 붙인다(상류가 이미 쓰는 관용구 — `tests/matmul_tests.rs:124`). 이렇게 해서 **실기 테스트 89개 중 80 PASS**(정상 동작으로 봐야 하는 수 83/89) 를 실제 NPU 카드에서 돌렸다. 단 **테스트마다 새 프로세스로 격리 실행**이 전제다 — 한 프로세스에 배치로 돌리면 hang 커널의 HAL `-110` 이 이후 커널까지 오염시켜 58 passed 로 떨어진다(격리 80 vs 배치 58).
 - 레시피·백엔드 3종 전수 결과: [12-예제-전수실행](./12-예제-전수실행.md)
 - 실기 전용 매트릭스·결함 유형·사이클 특성: [13-NPU-실기-매트릭스](./13-NPU-실기-매트릭스.md)

### 모든 예제가 공유하는 골격

책이 말하는 Tensor Unit 은 고정 파이프라인이다: **Fetch → Switch → Collect → Contraction → Vector → Cast → Transpose → Commit** (quick-start.md:57). 5개 예제는 이 파이프라인의 부분집합만 쓴다:

| 예제 | dtype | 쓰는 엔진 구간 | 새로 배우는 개념 |
|---|---|---|---|
| constant_add | i32 | Fetch→Collect→**Vector**→Commit | 파이프라인 뼈대, `vector_fxp` |
| elementwise_mul | i32 | 위 + `sub`→**VRF** | `sub` 컨텍스트, VRF operand |
| dot_product | bf16 | Fetch→Collect→**Contraction**→Cast→Commit | `contract_*` 4단, TRF |
| gemv | bf16 | 위 + 슬라이스 분산 | 출력축 `I` 를 슬라이스에 분산 |
| gemm | bf16 | 위 + 출력 2축 타일링 | `Slice = m![I/32, J/32]` |

호스트 흐름도 전부 동일하다(quick-start.md:94-106): `Context::acquire()` → `HostTensor::rand` → `to_hbm(&mut ctx.pdma, addr)`(호스트↔HBM, PCIe DMA) → `launch(kernel, (&mut ctx, &입력...))` → 결과 `to_host`. 커널 안에서는 `to_dm(&mut ctx.tdma, addr)`(HBM↔DM, Tensor DMA)로 온칩으로 내린다.

`m![]` 매핑 연산자 3개(quick-start.md:85-88): `/` = stride로 쪼개기(슬라이스 개수), `%` = 슬라이스 안 개수, `#` = 하드웨어 단위 수로 패딩.

## 1. Constant Add — 벡터에 상수 1 더하기 (난이도 1)

**① 책이 뭐라 하나**: i32 벡터의 각 원소에 상수 1을 더한다. 칩 1개, 클러스터 1개(2개 중), 그 클러스터의 256 슬라이스 전부를 쓰고 슬라이스당 8개씩 처리. 덧셈은 Vector Engine 의 `vector_fxp(FxpBinaryOp::AddFxp, 1)` (quick-start.md:110-114).

**② 우리 코드**: 호스트 `/home/jun/yik/src/constant_add.rs`, 커널 `/home/jun/yik/src/kernel/constant_add_kernel.rs`.

**③ 쉬운 설명 — 호스트 main 흐름** (`constant_add.rs:6-14`):
```rust
let mut ctx = Context::acquire();                                  // 컨텍스트 잡기
let input = HostTensor::<i32, m![A]>::rand(&mut rng);              // 난수 i32 벡터 (A=2048)
let in_hbm = input.to_hbm(&mut ctx.pdma, 0).await;                // 호스트→HBM (PCIe DMA)
let _out_hbm = launch(constant_add_kernel, (&mut ctx, &in_hbm)).await;  // 커널 실행
```
축 선언은 `axes![A = 2048]`, 매핑은 `Slice = m![A / 8 # 256]`(2048/8=256 슬라이스), 슬라이스당 `m![A % 8]`=8개(`constant_add_kernel.rs:3-7`).

**커널 본문 단계별** (`constant_add_kernel.rs:12-33`):
```rust
let dm = input.to_dm::<Cluster, Slice, m![A % 8]>(&mut ctx.tdma, 0);  // HBM→DM, 2048개를 256슬라이스에 8개씩
let result = ctx.main
    .begin(dm.view())                       // 파이프라인 시작
    .fetch::<m![1], m![A % 8]>()             // DM→스트림, Time=1·Packet=8
    .collect::<m![1], m![A % 8]>()           // 정확히 한 flit(32B = i32 8개)로 정규화
    .vector_init()                           // Vector Engine 진입
    .vector_intra_slice_tag(TagMode::Zero)   // intra-slice 체인 시작, Zero=매 사이클 무조건 실행
    .vector_fxp(FxpBinaryOp::AddFxp, 1)      // 8개 각각에 1 더함
    .vector_final()                          // VE 종료
    .commit_trim::<m![A % 8]>()              // 패킷을 commit 폭으로 트림
    .commit::<m![A % 8]>(1 << 12);           // DM 주소 4096 에 씀(입력은 0, 겹침 회피)
result.to_hbm(&mut ctx.tdma, 1 << 28)        // DM→HBM
```
`TagMode::Zero` = "모든 원소 조건 없이 매 사이클 실행"(quick-start.md:132). `flit` 은 이 하드웨어가 한 번에 다루는 32바이트 덩어리 — i32 8개가 정확히 32B라 `A%8`=8이 딱 한 flit. `commit_trim` 은 0.4 소스에도 존재(`furiosa-opt-std-0.4.0/src/engine/commit_adapter.rs:156`).

**④ 테스트가 뭘 assert 하나** (`constant_add.rs:20-40`): 참조값 `expected[i] = in[i].wrapping_add(1)` 을 만들고, 커널 결과 `actual` 과 원소별로 `assert_eq!` 한다.
 - ⚠️ **typecheck 백엔드에서는 `actual` 이 phantom(빈 벡터)이라 비교 루프가 0번 돌고 단언이 그냥 통과**한다(`constant_add.rs:34-36` 주석). 진짜 값 검증은 emulation 에서만 일어난다.

**실행**:
```bash
cargo furiosa-opt --backend emulation run  --release --bin constant_add   # 예상 출력: "Constant Add: kernel ran"
cargo furiosa-opt --backend emulation test --release --bin constant_add   # 참조(out=in+1) 대조
```

**함정**: (1) 입력 dm(주소 0)과 출력 commit(주소 `1<<12`)은 반드시 다른 DM 주소여야 한다 — main/sub 가 같은 평평한 SRAM 을 공유(quick-start.md:101-102). (2) Vector Engine 은 32비트(i32/f32)만 받는다 — 그래서 이 예제가 i32 인 것. (3) 한 VE 패스에서 같은 ALU 재사용 금지: `AddFxp`/`SubFxp` 는 둘 다 `FxpAdd` ALU 공유(`op/mod.rs:154`), 함께 넣으면 "FxpAdd is already in use" 패닉(→ 커리큘럼 `03_elementwise.md` 실험 03.3).

## 2. Elementwise Multiplication — 두 벡터 원소곱 (난이도 2)

**① 책이 뭐라 하나**: 같은 모양 두 벡터를 원소별로 곱한다. 한 피연산자는 파이프라인으로 흘리고, **다른 하나는 VRF(Vector Register File, 슬라이스별 레지스터)에 미리 싣는다**. Vector Engine 이 매 사이클 VRF 를 읽어 결합. 이 예제가 `sub` 컨텍스트를 도입한다(quick-start.md:146-179).

**② 우리 코드**: `/home/jun/yik/src/elementwise_mul.rs`, `/home/jun/yik/src/kernel/elementwise_mul_kernel.rs`.

**③ 쉬운 설명 — 핵심: 두 컨텍스트**. 모든 커널은 `ctx.main`(주 계산)과 `ctx.sub`(프리페치)를 **동시에** 굴린다(quick-start.md:96-99). main 이 아직 sub 가 채우는 중인 operand 를 필요로 하면 **자동으로 sub 를 기다린다**. 둘은 같은 SRAM 을 공유하므로 주소가 겹치면 안 된다.

**커널 본문** (`elementwise_mul_kernel.rs:16-42`):
```rust
let lhs_dm = lhs.to_dm::<Cluster, Slice, m![A % 8]>(&mut ctx.tdma, 0);        // 주소 0
let rhs_dm = rhs.to_dm::<Cluster, Slice, m![A % 8]>(&mut ctx.tdma, 1 << 12);  // 주소 4096 (겹침 회피)

// sub 컨텍스트: rhs 를 VRF 에 채운다 (main 과 동시 실행)
let rhs_vrf: VrfTensor<i32, Chip, Cluster, Slice, m![A % 8]> = ctx.sub
    .begin(rhs_dm.view())
    .fetch::<m![1], m![A % 8]>()
    .collect::<m![A % 8 / 8], m![A % 8 % 8]>()
    .to_vrf(0);                                  // ← main 과 달리 마지막이 to_vrf

// main 컨텍스트: lhs 를 흘리며 VRF 의 rhs 와 곱함
let result = ctx.main
    .begin(lhs_dm.view())
    .fetch::<m![1], m![A % 8]>()
    .collect::<m![1], m![A % 8]>()
    .vector_init()
    .vector_intra_slice_tag(TagMode::Zero)
    .vector_fxp(FxpBinaryOp::MulInt, &rhs_vrf)   // ← operand 자리에 상수 대신 &VRF
    .vector_final()
    .commit_trim::<m![A % 8]>()
    .commit::<m![A % 8]>(1 << 13);
result.to_hbm(&mut ctx.tdma, 1 << 28)
```
핵심은 두 곳이다: (a) `sub` 파이프라인이 `.to_vrf(0)` 로 끝나 rhs 를 VRF 에 적재. (b) main 의 `vector_fxp(FxpBinaryOp::MulInt, &rhs_vrf)` 가 operand 자리에 상수가 아니라 **VRF 텐서 참조**를 받는다 — `vector_fxp` 의 operand 는 상수/VRF 둘 다 받는다. `MulInt` 는 `FxpMul` ALU(`op/mod.rs:156`)라 `AddFxp` 와 충돌하지 않는다.

**④ 테스트** (`elementwise_mul.rs:22-44`): 참조 `expected[i] = lhs[i].wrapping_mul(rhs[i])` 와 원소별 `assert_eq!`.

**실행**:
```bash
cargo furiosa-opt --backend emulation run  --release --bin elementwise_mul  # "Elementwise Mul: kernel ran"
cargo furiosa-opt --backend emulation test --release --bin elementwise_mul
```

**함정**: `lhs_dm`(주소 0)과 `rhs_dm`(주소 `1<<12`)이 다른 DM 주소를 쓰는 것에 주목(`elementwise_mul_kernel.rs:16-17`) — 같으면 서로 덮어써 결과가 깨진다. → 커리큘럼 `03_elementwise.md` 4.2절, 실험 03.4.

## 3. Dot Product — 내적 `I,I→1` (난이도 3, 첫 축약)

**① 책이 뭐라 하나**: 내적은 두 피연산자를 같은 축을 따라 곱해 합친다(브로드캐스트 없음). 한 피연산자는 흘리고, 다른 하나는 **TRF(Tensor Register File)** 에 세워둔다. `contract_outer`(곱)→`contract_packet`(공간 합)→`contract_time`(시간 누적)→`contract_lane`(레인 접기) 4단으로 스칼라를 만들고, `cast` 로 f32 누산기를 bf16 으로 되돌린다(quick-start.md:193-206).

**② 우리 코드**: `/home/jun/yik/src/dot_product.rs`, `/home/jun/yik/src/kernel/dot_product_kernel.rs`.

**③ 쉬운 설명 — 여기서 dtype 이 bf16 으로 바뀐다.** 축약은 곱하면서 타입을 넓힌다(bf16→f32)라 Vector Engine 의 32비트 제약을 피한다. 매핑이 특이하다(`dot_product_kernel.rs:5-9`):
```rust
pub type Slice = m![1 # 256]; // 활성 슬라이스 1개(256으로 패딩). m![A/8 # 256]이면 256개 전부에 분산
pub type Time  = m![1];       // 시간 반복 없음(선언용)
pub type Lane  = m![1];       // 레인 병렬 없음
```
즉 A=2048 전체 내적을 **단 한 슬라이스** 안에서 처리한다.

**커널 본문 4단 축약** (`dot_product_kernel.rs:18-45`):
```rust
let lhs: DmTensor<..> = lhs.to_dm(&mut ctx.tdma, 0);
let rhs: DmTensor<..> = rhs.to_dm(&mut ctx.tdma, 1 << 12);

// sub: rhs 를 TRF 에 적재 (TrfAddress::Full = TRF 전체를 이 텐서에)
let rhs: TrfTensor<..> = ctx.sub
    .begin(rhs.view()).fetch::<Time, m![A]>()
    .collect::<m![{ Time }, A / 16], m![A % 16]>()
    .to_trf(TrfAddress::Full);

// main: lhs 를 흘려 A 를 따라 reduce
let result: DmTensor<bf16, Chip, Cluster, Slice, m![1 # 8]> = ctx.main
    .begin(lhs.view()).fetch::<Time, m![A]>()
    .collect::<m![A / 16], m![A % 16]>()
    .contract_outer::<m![A / 32], m![A % 32], _, _>(&rhs)  // 32B flit 2개를 64B 패킷으로 묶음(PackSize=2)
    .contract_packet::<m![1]>()                            // 패킷 안 32원소를 덧셈트리로 → 1
    .contract_time::<m![1]>()                              // 64 Time단계 누적 → 1
    .contract_lane::<m![1], m![1 # 8]>(LaneMode::Interleaved)
    .cast::<bf16, m![1 # 16]>()                            // f32→bf16, 16원소=32B(1 flit)
    .commit_trim::<m![1 # 8]>()
    .commit(1 << 13);
result.to_hbm(&mut ctx.tdma, 2 << 28)
```
**K 축(A=2048)이 어떻게 줄어드나** (제일 중요한 직관): `contract_outer::<m![A/32], m![A%32], _, _>` 는 A 를 **Packet 32(공간) × Time 64(시간)** 으로 쪼갠다. `A%32`=32원소=64바이트(bf16)를 한 패킷에 담고(PackSize=2로 64B 꽉 채움 → MAC 100%), `contract_packet` 이 32개를 덧셈 트리로 한 방에, `contract_time` 이 그 결과를 64사이클 누적. 검산: 32 × 64 = 2048 = A. → 커리큘럼 `04_contraction.md` 실험 04.1, Q1.
 - `contract_outer` 뒤 두 제네릭 `_, _`(Lane, TrfElement)은 TRF 텐서에서 추론(0.4 는 이 제네릭이 5개, `_GROUND_TRUTH.md:22`).
 - `contract_packet`/`contract_time` 의 제네릭에는 **살아남는 축**을 적는다(줄일 축이 아님). 전부 줄이면 `m![1]`.
 - `LaneMode::Interleaved` = Lane 을 `OutPacket` 안쪽으로 접음(`furiosa-opt-std-0.4.0/src/engine/contraction/lane.rs:19,48`).
 - `cast::<bf16, m![1 # 16]>()` 의 16은 필수: Cast 는 출력을 정확히 32바이트로 패딩, bf16 16개=32B. `m![1 # 8]`(16B)로 쓰면 "output packet must be exactly 32 bytes" 단언(→ 실험 04.3).

**④ 테스트** (`dot_product.rs:22-54`): 참조를 **f32 로 합산 후 bf16 반올림**한다. `expected = bf16::from_f32(Σ f32(lhs)·f32(rhs))`. 비교는 **허용오차** `tol = max(0.02 * |expected|, 0.5)` 로 `assert!(diff <= tol)` — bf16 반올림 오차 때문(`dot_product.rs:48`).

**실행**:
```bash
cargo furiosa-opt --backend emulation run  --release --bin dot_product  # "Dot Product: kernel ran"
cargo furiosa-opt --backend emulation test --release --bin dot_product
```

**함정**: 내적은 모든 슬라이스가 **같은 축**을 줄이므로 슬라이스 간 데이터 이동이 필요 없다 — dot_product 는 `.switch()` 를 안 쓴다(GEMV/GEMM 과의 결정적 차이).

## 4. GEMV — 행렬·벡터 곱 `IJ,J→I` (난이도 4)

**① 책이 뭐라 하나**: GEMV 는 출력 차원 `I` 를 슬라이스에 분산한다 — 각 슬라이스가 한 행 `y_i = Σ_j A_{ij} x_j` 를 계산. 내적과 달리 **각 슬라이스가 벡터 전체를 받아야** 하므로, 축약 전에 벡터를 슬라이스 간에 브로드캐스트해야 한다(quick-start.md:221-224).

**② 우리 코드**: `/home/jun/yik/src/gemv.rs`, `/home/jun/yik/src/kernel/gemv_kernel.rs`.

**③ 쉬운 설명 — 매핑** (`gemv_kernel.rs:3-10`): `axes![I = 256, J = 2048]`.
```rust
pub type Slice  = m![I];       // 출력축 I 를 256 슬라이스에 1행씩 분산
pub type Time   = m![J / 32];  // 축약축 J 를 시간으로: 64 사이클
pub type Packet = m![J % 32];  // 축약축 J 를 공간으로: 32원소=64B
```
dot_product 와 결정적 차이: `Slice = m![I]`. 출력 I 가 슬라이스에 흩어진다.

**커널 본문** (`gemv_kernel.rs:19-47`): 구조는 dot_product 와 동일(sub 가 vector 를 TRF 에 `Full` 로 적재 → main 이 matrix 를 흘려 `contract_outer::<Time, Packet, _, _>(&vector_trf)` → packet/time/lane → cast → commit). 차이는 `contract_time::<m![1]>()` 가 J 를 전부 누적해 슬라이스마다 스칼라 `y_i` 를 남기는데, **슬라이스마다 서로 다른 행**을 담당한다는 점.

**Switch 브로드캐스트 — 주의**: 책 본문은 `input.switch(SwitchConfig::Broadcast01 { slice1: 256, slice0: 1, time0: 1 })` 로 벡터를 256 슬라이스 전체에 복제하는 걸 **의사코드로** 보여준다(quick-start.md 개념 설명). 그러나 **yik `gemv_kernel.rs` 본문에는 명시적 `.switch()` 호출이 없다** — 분배는 `to_dm`/`to_trf` 의 매핑 타입 파라미터가 끌어낸다. 커리큘럼 `04_contraction.md`(라인 89-99)와 일치. 명시적 `.switch()` 손코딩 예는 더 복잡한 matmul 변종에서만 나온다.

**실기 실측 — 브로드캐스트는 경로에 따라 갈린다**(벤더 예제 크레이트, 실제 NPU 실행):
 - Switch 엔진 브로드캐스트 경로는 실기에서 **끝까지 돈다**(크래시·HAL 에러 0): `.switch(SwitchConfig::Broadcast01 {..})`/`Broadcast1 {..}` 를 명시적으로 호출하는 테스트 **5개**(`switch_assertions::broadcast01` 3 + `::broadcast1` 2) 전부 PASS — `switch_assertions` 바이너리 전체가 **18/18 PASS**. 단 이 5개는 출력값을 assert 하지 않는다(`tests/switch_assertions_tests.rs` 에 `assert` 0건, 파일 주석도 "This test never asserts on `output`") → **값이 맞는지는 확인되지 않았다.**
 - 반면 **view 기반 HBM→HBM 브로드캐스트 DMA 는 조용히 실패한다**: `tests/broadcast.rs::test_view_broadcast`(`hbm1.to_hbm::<{ Dma::Tensor }, m![A, B]>(&mut ctx.tdma)`)가 실기에서 **2048/2048 원소 전부 불일치** — 목적지에 아무것도 쓰이지 않고 그 HBM 영역의 **이전 f32 잔류물**이 읽힌다. 에러도 크래시도 없다. **에뮬레이션에서는 통과한다.**
 - 교훈: 브로드캐스트를 손으로 짜면 **반드시 값 검증을 붙일 것**. 상세: [13-NPU-실기-매트릭스](./13-NPU-실기-매트릭스.md)

**④ 테스트** (`gemv.rs:22-59`): 참조 `y[i] = bf16::from_f32(Σ_j f32(A[i,j])·f32(x[j]))`, 행별(`chunks(J::SIZE)`)로 계산. 허용오차 `max(0.02*|e|, 0.5)`, 원소별 `assert!`.

**실행**:
```bash
cargo furiosa-opt --backend emulation run  --release --bin gemv  # "GEMV: kernel ran"
cargo furiosa-opt --backend emulation test --release --bin gemv
```

**함정**: J(축약축)를 32의 배수로 유지해야 Packet=J%32=32(64B), Time=J/32 가 깔끔하게 떨어진다. → 실험 04.4 심화.

## 5. GEMM — 행렬곱 (난이도 5, 이후 모든 문서의 기준 예제)

> **가장 중요.** GEMM 은 출력이 두 축(`I`,`J`) 모두를 가지므로, 출력 두 축을 **함께** 슬라이스에 매핑하는 새 개념이 등장한다. 후속 문서(mapping/computing/moving)가 전부 이 예제를 기준으로 삼는다.

**① 책이 뭐라 하나**: GEMM `IK, JK → IJ` (`C_{ij} = Σ_k A_{ik} B_{jk}`). 각 행렬은 없는 출력 차원을 따라 브로드캐스트(A 는 J 방향, B 는 I 방향). 새 개념은 `type Slice = m![I / 32, J / 32]` — 두 출력축을 함께 슬라이스에 매핑(quick-start.md:238-247).

**② 우리 코드**: `/home/jun/yik/src/gemm.rs`, `/home/jun/yik/src/kernel/gemm_kernel.rs`.

> ⚠️ **주의: 우리 einsum 표기 확인.** 책 quick-start.md:39 표는 GEMM 을 `IK, KJ → IJ`(공유축 K 가 B 에서 두 번째)로 적지만, quick-start.md:240 본문과 **우리 yik 코드**는 `IK, JK → IJ`, `C_{ij} = Σ_k A_{ik} B_{jk}` 를 쓴다. 즉 **B 의 축 순서가 `m![J, K]`** (`gemm.rs:11`, `gemm_kernel.rs:15`)이고 참조 계산도 `a_row·b_row`(둘 다 K 로 chunk)로 대칭적이다(`gemm.rs:33-48`). 이 문서는 코드 기준 `IK, JK → IJ` 를 따른다.

**③ 쉬운 설명 — 매핑** (`gemm_kernel.rs:3-9`): `axes![I = 512, J = 512, K = 64]`.
```rust
pub type Slice = m![I / 32, J / 32]; // 주석 "Each slice handles a 16 × 16 output tile" ← 아래 정정
pub type Lane  = m![J % 8];          // J 의 안쪽 8개를 8레인에 얹음
```

### 🔴 `gemm_kernel.rs:8` 의 "16 × 16" 주석은 틀렸다 (GROUND_TRUTH 정정)

`_GROUND_TRUTH.md:31-34` 에 따라 바로잡는다. 주석은 **슬라이스 격자 크기**와 **슬라이스가 담당하는 타일 크기**를 혼동했다.

| 항목 | m![] 표현 | 값 | 의미 |
|---|---|---|---|
| 슬라이스 **격자** | `Slice = m![I/32, J/32]` | (512/32)×(512/32) = **16 × 16 = 256 슬라이스** | 출력행렬을 덮는 슬라이스 좌표 격자 |
| 슬라이스 **1개가 담당하는 타일** | 결과 `m![I%32, J%32]`(`gemm_kernel.rs:35`) | 32 × 32 = **1024 원소** | 각 슬라이스가 실제 계산하는 출력 조각 |

**검산**: 256 슬라이스 × 1024(32×32) = **262,144 = 512×512 = I·J** ✓. (주석대로 256×256 이면 65,536 ≠ I·J 로 안 맞는다.)

→ 정확한 문장: "슬라이스 **격자**가 16×16(=256 슬라이스)이고, **각 슬라이스는 32×32 출력 타일**을 담당한다." (책 본문 quick-start.md:243,267 도 "each slice computes a 16 × 16 tile" 라 적어 **같은 오류**를 반복하니 함께 정정.)

또한 `gemm_kernel.rs:22-24` 의 "Switch Engine distributes B across 256 slices" 주석도 오해 소지: 실제로 이 커널은 **`.switch()` 를 호출하지 않는다.** 분배는 `to_dm`/`to_trf` 의 Slice 타입 파라미터가 끌어낸다(`_GROUND_TRUTH.md:35`).

**커널 본문** (`gemm_kernel.rs:18-49`):
```rust
let a: DmTensor<bf16, Chip, Cluster, Slice, m![I % 32, K]> = a.to_dm(&mut ctx.tdma, 0);
let b: DmTensor<bf16, Chip, Cluster, Slice, m![J % 32, K]> = b.to_dm(&mut ctx.tdma, 1 << 12);

// sub: B 를 TRF 에 적재
let b_trf: TrfTensor<..., m![J / 8 % 4, K]> = ctx.sub
    .begin(b.view())
    .fetch::<m![J % 8, J / 8 % 4], m![K]>()
    .collect::<m![J % 8, J / 8 % 4, K / 16], m![K % 16]>()
    .to_trf(TrfAddress::Full);

// main: A 를 흘려 K 를 따라 reduce, I·J 는 출력에 보존
let result: DmTensor<bf16, Chip, Cluster, Slice, m![I % 32, J % 32]> = ctx.main
    .begin(a.view())
    .fetch::<m![I % 32, J / 8 % 4], m![K]>()
    .collect::<m![I % 32, J / 8 % 4, K / 16], m![K % 16]>()
    .contract_outer::<m![I % 32, J / 8 % 4, K / 32], m![K % 32], _, _>(&b_trf)  // K%32 를 Packet 에
    .contract_packet::<m![1]>()                              // K 를 공간 트리로 합
    .contract_time::<m![I % 32, J / 8 % 4]>()                // I·(J의 일부)는 살리고 K/32(=2)는 누적
    .contract_lane::<m![I % 32, J / 8 % 4], m![J % 8]>(LaneMode::Interleaved)  // Lane(J%8)을 출력 패킷에 접음
    .cast::<bf16, m![J % 8 # 16]>()
    .commit_trim::<m![J % 8]>()
    .commit(0);
result.to_hbm(&mut ctx.tdma, 2 << 28)
```
**K 축(=64)이 어떻게 줄어드나**: `contract_outer::<..., m![K % 32], _, _>` 가 K%32=32 를 Packet(공간), K/32=2 를 Time(시간)에 둔다 → K=64 = 32(공간) × 2(시간). `contract_time::<m![I % 32, J / 8 % 4]>()` 의 제네릭에 출력축(살아남는 I·J 조각)을 적어 두면 K/32 만 누적되어 사라진다. `contract_lane` 이 8레인(J%8)을 출력 패킷 안쪽으로 접어 `I`·`J` 를 모두 출력에 보존(quick-start.md:246).

**④ 테스트** (`gemm.rs:22-58`): 참조 `C[i,j] = bf16::from_f32(Σ_k f32(A[i,k])·f32(B[j,k]))` — A 는 `chunks(K::SIZE)` 로 행, 각 A 행마다 B 를 `chunks(K::SIZE)` 로 돌며 내적. 허용오차가 dot/gemv 보다 **큼**: `tol = max(0.05 * |e|, 1.0)`(`gemm.rs:55`) — K 누적이 많아 bf16 오차가 더 쌓이기 때문.

**실행**:
```bash
cargo furiosa-opt --backend emulation run  --release --bin gemm  # "GEMM: kernel ran"
cargo furiosa-opt --backend emulation test --release --bin gemm
```

**함정**: (1) 위 "16×16" 주석 오류. (2) 명시적 switch 없음. (3) `cast::<bf16, m![J % 8 # 16]>()` 의 16(=32B) 필수. (4) K 를 Time 에만 두면(K-in-Time) bf16 곱셈기 32개 중 1개만 일해 MAC 활용률 1/32 로 퇴화 — K 는 Packet 에 둬 트리로 줄이는 게 정석(→ `04_contraction.md` Q4).

## 7. 함정 총정리

- **`--version` 은 0.3, 실체는 0.4.** 세대를 문자열로 판단 금지(`_GROUND_TRUTH.md:3-6`).
- **yik 에서 `--backend npu` 불가.** `[package.metadata.furiosa-opt]` 미비 + 0.3 tag → "no kernel packages found"(`_GROUND_TRUTH.md:14-16`). typecheck/emulation 만 사용. 실기는 게이팅한 벤더 예제 크레이트로 → [13-NPU-실기-매트릭스](./13-NPU-실기-매트릭스.md).
- **`--backend npu` 는 크레이트 전체를 낮춘다** — 부르지 않는 `#[device]` 함수까지. 하나라도 실패하면 빌드 0개 테스트(벤더 예제 그대로 돌리면 **63개 에러**). 게이팅(`#[cfg(not(backend = "npu"))]`)이 정석.
- **`--backend simulation` 은 거부됨**(0.3 시절 이름). `emulation` 을 쓸 것. `--backend` 는 서브커맨드 앞에.
- **`--bin <name>` 필수** — default-run 없음.
- **DM 주소 겹침 금지** — main/sub 공유 SRAM. 예제들이 0, `1<<12`, `1<<13` 등으로 분리.
- **Vector Engine 은 32비트만** — 원소연산은 i32, 축약은 곱하며 bf16→f32 로 넓어지므로 OK.
- **같은 ALU 한 패스 두 번 금지** — AddFxp/SubFxp 는 FxpAdd 공유 → 패닉(`op/mod.rs:154`).
- **`cast` 출력은 정확히 32B** — bf16 은 `m![1 # 16]`(16원소). 틀리면 매핑 단언, 그리고 `cargo check` 로는 안 잡히고 `--backend typecheck run` 이라야 잡힌다.
- **`gemm_kernel.rs:8` "16×16" 주석 오류** — 격자가 16×16(256슬라이스), 각 슬라이스 타일은 **32×32**(5절 정정표).
- **typecheck 는 phantom** — 값 비교 루프 0회, 단언 통과. 수치 검증은 emulation.
- **typecheck/emulation 통과 ≠ 실기로 낮출 수 있음**(실측). 벤더 예제 소스의 `#[device]` 커널 **200개 중 137 OK / 63 FAIL**(68.5%) — typecheck·emulation 백엔드에서는 같은 크레이트가 그대로 빌드되고 emulation 은 **104 passed / 0 failed** 인데, `--backend npu` 에서만 막힌다. 반복되는 벽 3가지: DMA 8바이트 정렬(`not aligned by 8`, `tail_size % min_align`), 다중 칩/클러스터 경로, 분기(`Branch conversion is not yet implemented`). 분류·에러 원문: [12-예제-전수실행](./12-예제-전수실행.md).
- **`compile` 성공 ≠ 실기 실행 성공**(실측). 컴파일된 EDF 가 **커널 로드**(`furiosa_kernel_load`)에서 범위초과로 **프로세스 abort** 하는 사례 3건(reshape 2건은 요구 50,560 vs 실제 33,792, `chip_shuffle` 은 56,576 vs 37,888 — **세 건 모두** 요구가 실제의 약 1.5배). 세 건 다 **에뮬레이션에서는 통과**한다. → [13-NPU-실기-매트릭스](./13-NPU-실기-매트릭스.md).

## 8. 미확인 항목

- 각 예제의 실제 emulation 실행 출력/통과 여부: **yik 5개 예제는 여전히 미실행**(target 오염·시간 회피). "예상 출력"은 소스의 `println!`(constant_add.rs:13 등)에서 옮긴 것.
  - 다만 **래퍼의 emulation 백엔드 자체는 실측 검증됐다**: 벤더 예제 크레이트에서 **104 passed / 0 failed / 10 ignored**(→ [12-예제-전수실행](./12-예제-전수실행.md)). 즉 백엔드가 도는지는 더 이상 의문이 아니고, yik 5개 예제의 출력 문자열만 미확인이다.
- 책 표(quick-start.md:39)의 GEMM einsum `IK, KJ→IJ` 와 본문/코드의 `IK, JK→IJ` **표기 불일치**: 문서 원문의 오탈자 가능성이나, 원저자 의도(전치 여부)는 미확인. 우리 코드는 `m![J, K]`(B 를 K 로 chunk, 대칭 내적)이므로 코드 기준 `IK, JK→IJ` 로 서술했다.
- gemv/gemm 의 슬라이스 간 브로드캐스트가 하드웨어에서 정확히 어느 엔진(Switch)으로 실현되는지: yik 커널 본문에 명시 호출이 없어 **매핑 타입에서 추론**된다고만 확인. 구체 Switch 토폴로지는 후속 문서(moving/computing)에서 다룸.
  - 이번 세션에 확인된 것: `SwitchConfig::Broadcast01`/`Broadcast1` 을 **명시적으로** 쓰는 벤더 예제 테스트 5개는 실기에서 전부 통과(`switch_assertions` 바이너리 18/18, **단 값 assert 가 없어 "크래시 없이 끝까지 돈다"까지만 참** — 4절)하고, view 기반 HBM→HBM 브로드캐스트 DMA 는 실기에서 실패한다(4절). yik gemv/gemm 이 낮춰지는 경로가 그중 어느 쪽인지는 여전히 미확인(yik 은 `--backend npu` 컴파일 자체가 불가).
