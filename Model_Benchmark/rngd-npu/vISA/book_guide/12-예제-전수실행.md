### 2.1 "모델"은 왜 MNIST 하나뿐인가

12개 그룹을 각각 독립 조사한 뒤 **적대적 재검증**까지 거친 결과, `is_model = true`는 mnist 하나였다.
근거는 소스에 그대로 있다.

**transformer (Qwen 2.5 0.5B)** — 차원은 진짜다:

```rust
// src/transformer/axes.rs
axes![
    D = 64,           // head_dim
    H = 896,          // hidden_size = 14 * 64
    M = 4864,         // mlp_intermediate_size
    W_vocab = 151936, // vocab_size
    S_prefill = 1024, T = 1024, C_kvcache = 1124, P = 32768,
];
```

그런데 테스트가 넣는 가중치가 전부 0이다:

```rust
// tests/transformer_tests.rs:22-28
// TODO: Fill with actual weight values (mirror PyTorch weight loading)
let embedding_table = HostTensor::<bf16, m![W, H]>::zero().to_hbm(&mut ctx.pdma).await;
let q_weight       = HostTensor::<bf16, m![Q, H]>::zero().to_hbm(&mut ctx.pdma).await;
```

→ **데이터플로우 검증용이지 추론 모델이 아니다.**

**attention (Llama 3.1)** — 함수가 중간에 끊겨 있다:

```rust
// src/attention.rs:101  (파일 끝)
        // TODO: Complete the function definition.
    }
}
```

임베딩까지만 하고 끝난다.

> **정정 사항**: 이 테스트의 `#[ignore]` 사유는 `"incomplete kernel with todo!()"` 라고 적혀 있지만,
> 크레이트 전체에 `todo!()` **매크로는 한 개도 없다**(`grep -rn "todo!\|unimplemented!" src` → 0건).
> 실제로는 위처럼 **주석 TODO**로 남아 있다. 사유의 취지는 맞지만 문구는 부정확하다.

### 3.2 백엔드 3종의 실제 의미

이번 실행으로 세 백엔드의 차이가 **행동으로** 확인됐다.

| 백엔드 | 커널을 언제 컴파일하나 | 값을 계산하나 | NPU 필요 |

이 표의 마지막 줄이 5장의 핵심 사건을 만든다.


## 5. 핵심 발견 — NPU 백엔드는 "안 쓰는 커널"에도 발목이 잡힌다

### 5.1 63개 에러의 정체

모듈별로 분류하면:

| 모듈 | 에러 수 | 성격 |
|---|--:|---|
| `contract_outer_assertions` | 17 | **의도적으로 잘못된 매핑** |
| `switch_assertions` | 11 | **의도적으로 잘못된 매핑** |
| `matmul` | 7 | 실제 로워링 공백 |
| `transformer` | 4 | 실제 로워링 공백 |
| `view` | 3 | 실제 로워링 공백 |
| `vector_engine` | 3 | 실제 로워링 공백 |
| `memory_op` | 3 | 실제 로워링 공백 |
| `cluster_chip_shuffle_slice` | 3 | 실제 로워링 공백 |
| 기타 11개 모듈 | 13 | 실제 로워링 공백 |

> ⚠️ **이 표의 해석은 뒤에 정정됐다.** 아래에서 나는 `*_assertions`의 28개를 "의도적 표본"으로
> 묶었지만, 전수 분류해 보니 **의도적인 건 23개뿐**이고 나머지는 진짜 로워링 공백이거나
> 컴파일러 ICE다. 이름이 `valid_*`인데 실패하는 것도 있다.
> 정확한 분류는 [13-NPU-실기-매트릭스 §7](./13-NPU-실기-매트릭스.md) 참조.

앞의 두 줄(**28개**)이 문제의 절반 가까이다. 이름을 보자:

```
contract_outer_assertions::lane_size::invalid_size_16
contract_outer_assertions::trf_mapping::invalid_lane_not_divisible_by_time
switch_assertions::packet::packet_mismatch
switch_assertions::broadcast1::invalid_out_time
switch_assertions::inter_transpose::invalid_time2_mismatch
```

전부 `invalid_*` 아니면 `*_mismatch`다.

### 5.2 증거 — 이 커널들은 아무도 호출하지 않는다

```bash
grep -rn "invalid_\|_mismatch" furiosa-opt-examples/tests/
# → 0건
```

**어떤 테스트도 이 커널들을 호출하지 않는다.** 이들은 "이렇게 매핑하면 안 된다"를
소스로 보여주는 **표본**일 뿐이다.

### 5.3 그래서 무슨 일이 일어났나

- `typecheck`·`emulation`: 커널을 **호출될 때** 처리한다 → 아무도 안 부르는 `invalid_*`는 그냥 지나간다 → 빌드 성공
- `npu`: 패키지 안의 **모든** `#[device]` 함수를 **빌드 시점에** 실기 바이너리(EDF)로 낮춘다 → `invalid_*`가 컴파일 에러를 내고 → **크레이트 전체가 죽는다**

> ### 실무 규칙
> **`--backend npu`로 돌리려면, 패키지 안에 실기로 낮출 수 없는 `#[device]` 함수가
> 단 하나도 없어야 한다.** 그 함수를 테스트가 부르든 말든 상관없다.
>
> 이것이 지난번 MNIST를 돌릴 때 `visa_mnist`라는 **별도 패키지**를 만들어야 했던 진짜 이유다.
> 그때는 경험적으로 그렇게 했지만, 이번에 원인이 확정됐다.

## 6. 2차 시도 — `#[ignore]` 10개를 직접 돌려봤다

전체 실행에서 10개가 `ignored`로 건너뛰어졌다. 상류가 붙여 놓은 사유가 **지금도 유효한지**
직접 확인했다. 각 테스트를 개별 실행:

```bash
cargo furiosa-opt --backend emulation test -p furiosa-opt-examples --release \
  --test <파일> -- --ignored --exact <테스트명> --nocapture
```

### 6.1 결과 — 10개 중 3개는 그냥 통과한다

| 테스트 | 상류가 적어둔 사유 | **실측 결과** | 판정 |
|---|---|---|---|
| `matmul::test_matmul_4096` | `Failing on cpu` | **통과** (2s) | 🔴 **낡음** |
| `matmul::test_matmul_with_chip_reduce` | `Failing on cpu` | **통과** (4s) | 🔴 **낡음** |
| `vector_engine::normal::test_ve_elementwise_vrf` | `Failing on cpu` | **통과** (0.13s) | 🔴 **낡음** |
| `matmul::test_matmul_16384` | `takes too much time to run` | 실패 — **4초 만에** `commit.rs:57` | 🟠 사유 부정확 |
| `attention::test_compile_llama3_1_...` | `incomplete kernel with todo!()` | 실패 — `collect.rs:125` | 🟠 사유 부정확 (`todo!()` 없음) |
| `transformer::run_qwen` | `DmaCommandScatter lowering not yet implemented` | 실패 — **128초** 뒤 `collect.rs:125` | 🟠 사유와 다른 지점 |

| `vector_engine::normal::test_vrf_add` | `Failing on cpu` | 실패 — `memory.rs:57` | ✅ 유효 |

### 6.2 이게 왜 의미가 있나

- **에뮬레이션 실질 통과 수는 104가 아니라 107이다.** 3개가 `#[ignore]`에 가려져 있었다.
- `test_matmul_16384`는 "너무 오래 걸려서" 무시된 게 아니라 **4초 만에 실패**한다.
  사유가 실제 동작과 다르다.
- 이런 낡은 주석은 상류에 보고할 만한 실제 관찰이다.

> **주의(방법론)**: `--exact` 필터는 **모듈 경로까지 포함한 전체 이름**을 요구한다.
> 처음에 `normal::test_vrf_add`로 걸었더니 `0 passed; 39 filtered out`이 나왔다 —
> 통과처럼 보이지만 **테스트가 아예 안 돈 것**이다. 정확한 이름은
> `vector_engine::normal::test_vrf_add`. 이름은 `-- --list`로 확인해야 한다.

### 6.3 Qwen은 왜 실패하나 — 독립 확증

`run_qwen`은 128초를 돌다 죽는다. 같은 커널을 **다른 경로**로도 때려봤다.
저장소에는 `kernel_sim`이라는 별도 벤치 진입점이 있고, Qwen의 attention/decoder를
테스트와 무관하게 직접 실행한다:

```bash
cargo furiosa-opt --backend emulation build -p furiosa-opt-examples --bench kernel_sim --release
./target_emu/release/deps/kernel_sim-<hash> attention 2
```

## 8. 실기 실패 2건 정밀 분석

실패를 "실패"로만 적으면 쓸모가 없다. 두 건은 성격이 완전히 다르다.

### 8.1 `test_ve_group_pair_ternary_selective` — 1 ULP 문제 (커널은 옳다)

로그의 `left`(NPU)와 `right`(호스트 기준값) 512개 원소를 그대로 뽑아 비교했다:

| 지표 | 값 |
|---|--:|
| 원소 수 | 512 |
| **비트 단위로 일치** | **489 (95.5%)** |
| 불일치 | 23 (4.5%) |
| 최대 절대오차 | 2.000e-06 |
| **최대 상대오차** | **1.742e-07** |
| **최대 ULP 차이** | **1** |
| ULP 분포 | `{0: 489, 1: 23}` |

가장 나쁜 원소조차 `npu=4.0194473` vs `host=4.019448` — **f32의 마지막 한 자리**다.

이 테스트는 `tests/common.rs`의 `assert_f32_vec_eq`를 쓰는데, 이 함수는 NaN만 특별 취급할 뿐
**나머지는 완전 일치를 요구**한다:

```rust
// tests/common.rs
impl PartialEq for F32 {
    fn eq(&self, other: &Self) -> bool {
        self.0 == other.0 || (self.0.is_nan() && other.0.is_nan())
    }
}
```

→ **커널 오류가 아니다.** 실기 부동소수 연산의 반올림 순서가 호스트 해석기와 마지막 자리에서
갈리는 것이고, 테스트가 비트 일치를 요구해서 난 실패다.
(같은 테스트가 에뮬레이션에서는 통과한다 — 그 경우 양쪽이 같은 호스트 산술을 쓰므로.)

> 참고로 이 1 ULP 규모는 지난 세션의 DeltaNet 감사에서 `1.907e-6 = 2^-19`를
> "오류가 아니라 리덕션 순서 차이"로 판정했던 것과 **같은 종류의 현상**이다.
> 그때의 교훈이 여기서 재사용됐다.

## 10. 4차 시도 — 크레이트 전체를 실기로 (게이팅 접근)

7장의 서브셋은 **모듈 단위**로 잘랐다. 9장의 매트릭스를 보면 그건 과하게 버린 것이다 —
`switch_assertions`는 46개 중 34개, `vector_engine`은 50개 중 47개가 실기로 간다.
**커널 단위로 실패분만 도려내면** 훨씬 넓게 가져갈 수 있다.

### 10.1 방법 — 실패 커널만 `#[cfg(not(backend = "npu"))]`로 게이트

이 관용구는 저장소가 **이미 쓰고 있다**:

```rust
// tests/matmul_tests.rs:124  (상류 원본)
#[cfg(not(backend = "npu"))]
#[tokio::test]
async fn test_matmul_with_split_reduce2() { ... }
```

즉 "이 함수는 npu 백엔드에서는 존재하지 않는 것으로 친다". 9장 매트릭스의 FAIL 64개에
이 게이트를 붙이면, npu 빌드는 그 커널들을 **아예 컴파일 대상에서 뺀다.**
emulation·typecheck는 게이트가 없으므로 영향을 받지 않는다.

`perkernel_matrix.txt`의 FAIL 목록을 그대로 스크립트에 먹여 자동 삽입했다
(`tmp/gate_kernels.py` — 인라인 모듈 경로까지 추적해 동명 함수를 구분).

### 10.2 게이트 규모

| 대상 | 게이트 수 | 내용 |

`use` 게이트는 통째로 지우지 않고 **게이트된 심볼만** 별도 `use`로 분리했다.
예: `memory_op_tests`는 9개 import 중 3개만 게이트하고 6개는 그대로 뒀다 — 커버리지 손실 최소화.


`-110`은 리눅스 **`ETIMEDOUT`** 이다. 즉 커널 실행이 **하드웨어에서 시간 안에 안 끝난다.**

**단서 3 — 진짜 범인 vs 무고한 피해자 (단독 실행으로 확정):**

| 커널 | 단독 실행 결과 | 판정 |
|---|---|---|
| `normal::test_ve_stash_fp_fp` | **60초 타임아웃 후 실패** | 🔴 **진짜 hang 버그** |
| `reduce::test_ve_intra_slice_reduce_add_f32` | **0.13초 통과** | 🟢 연쇄 피해자 |

`test_ve_stash_fp_fp`는 **단독으로 돌려도** NPU에서 영영 안 끝난다(진짜 결함).
문제는 이 커널이 한 번 걸리면 **같은 프로세스의 뒤 커널 실행이 전부 `-110`으로 연쇄 타임아웃**된다는 것.
그래서 `reduce`의 정상 커널들까지 25개가 무더기로 실패한 것처럼 보였다.

> **NPU는 손상되지 않았다.** 연쇄 실패 직후 `furiosa-smi status`에서 npu0~npu3 모두
> `alive / 0.00 GiB`. 프로세스가 끝나면 상태가 회복된다. 즉 **프로세스 수명 내의 오염**이지 영구 손상이 아니다.

**단서 4 — 각 테스트를 별도 프로세스로 돌리면 (결정적 증거):**

vector_engine 36개를 **한 개씩 새 프로세스로** 실행했다(`ve_names.txt` 루프, 각각 `--exact`).
프로세스가 끝나면 NPU 상태가 회복되므로 연쇄 오염이 원천 차단된다.

| 실행 방식 | 통과 | 실패 |
|---|--:|--:|
| 한 프로세스에 전부 (원래) | 10 | 25 |
| **개별 프로세스 격리** | **33** | **3** |

**격리하면 25개 실패가 3개로 줄어든다.** 22개는 연쇄 피해자였다는 게 확정됐다.

살아남은 진짜 실패 3개의 성격:

| 커널 | HAL 오류 | ULP | 성격 |
|---|:--:|:--:|---|
| `normal::test_ve_stash_fp_fp` | ✅ | — | 🔴 **진짜 hang** (단독 60초 타임아웃) |
| `reduce::test_ve_intra_slice_reduce_split_time_packet` | — | 1 | 🟡 1 ULP (8.1과 동종, 커널은 옳음) |
| `zip::test_ve_group_pair_ternary_selective` | — | 1 | 🟡 1 ULP (8.1에서 이미 분석) |

→ **실기에서 실제로 깨지는 vector_engine 커널은 단 하나**(`test_ve_stash_fp_fp`)다.
나머지 2개는 마지막 비트 반올림 차이라 커널 결함이 아니다.

> **정직한 총합**: 게이팅 크레이트를 한꺼번에 돌리면 58 통과지만, 그중 vector_engine이 10만
> 기여했다(연쇄 때문). **격리 실행 기준으로는 vector_engine이 33 통과**하므로, 실기에서
> **실제로 도는 테스트는 약 81개**(= 58 − 10 + 33)다. "58"은 연쇄 오염이 깎아낸 하한이고,
> "81"이 실제 능력에 가깝다.

### 10.6 서브셋 vs 게이팅 — 어느 쪽을 쓰나

| 기준 | 7장 서브셋 (`visa_ex_npu`) | 10장 게이팅 (`visa_ex_gated`) |
|---|---|---|
| 자르는 단위 | 모듈 | **커널** |
| 실기 실행 테스트 | 21개 | **58개+** |
| 원본과의 관계 | 파일을 추려 새 크레이트 | **원본에 게이트만 삽입** (diff 최소) |
| 상류 반영 가능성 | 낮음 (구조가 다름) | **높음** (상류가 쓰는 관용구 그대로) |
| 만들기 | 수작업 선별 | **매트릭스 → 스크립트 자동** |
| 언제 | 소수 커널만 빠르게 실기 확인 | **크레이트를 최대한 실기로 돌릴 때** |

게이팅이 서브셋의 상위호환이다. 서브셋은 "빠른 최소 재현", 게이팅은 "최대 커버리지"에 쓴다.

## 11. 종합 판정 — "MNIST처럼 실행 가능한 것"의 실제 범위

세 겹으로 나뉜다.

| 층 | 무엇 | 규모 | 어디까지 되나 |
|---|---|--:|---|
| **A. 모델** | MNIST | 1개 | **실기 완주** — 학습 가중치로 10/10 정답 |
| **B. 커널/원시연산** | 게이팅 크레이트 전체 | 58개 테스트 | **실기 통과** (한꺼번에 58, 격리하면 vector_engine까지 더) |
| **C. 실기 불가** | 게이트된 커널 64개 | — | 컴파일 실패(로워링 공백 + 의도적 `invalid_*`) |

- 질문 "MNIST처럼 **모델**이 또 있나"의 답은 **없다**.
- 질문 "MNIST처럼 **실기에서 돌릴 수 있는 것**이 또 있나"의 답은 **있다 — 57개 더**.
- Qwen·Llama 예제는 **미완성 골격**이라 지금은 어느 백엔드에서도 안 돈다.
- 실기 실패는 딱 셋으로 압축된다: `test_ve_stash_fp_fp`(진짜 hang), `reshape`(로더 결함),
  그리고 소수의 **1 ULP** 불일치(커널은 옳고 테스트가 비트일치를 요구). 나머지 "실패"는 전부 연쇄 오염이었다.

### 11.1 이 결과의 위치

지난 세션에서 vISA **"성능 향상"** 주제는 세 번 무너졌다(정밀도·타이밍·정렬 모두 TCL로도 가능하거나 측정 오류).
이번 결과도 성능 주장이 **아니다**. 대신 두 가지를 확정한다.

1. **실행 가능성의 경계가 어디인지** — 무엇이 실기까지 가고 무엇이 못 가는지, 그리고 **왜**인지
2. **실기로 가는 재현 가능한 절차** — 서브셋(7장)과 게이팅(10장), 두 레시피는 앞으로 어떤 커널을 새로 짜든 그대로 쓴다

특히 5장의 규칙(패키지 안에 낮출 수 없는 커널이 하나라도 있으면 실기 빌드 전체가 죽는다)과
그 우회법(10장 게이팅)은 **새 연산자를 vISA로 얹으려는 모든 후속 작업의 전제 조건**이다.
게이팅은 상류가 쓰는 관용구 그대로라, 새 커널을 원본 예제 크레이트에 얹어 실기로 돌리는
가장 마찰 적은 경로다.

## 12. 정직한 한계

- **성능 비교를 하지 않았다.** 실기 통과 여부와 테스트 프레임워크 소요시간만 기록했다.
  TCL/furiosa-llm 대비 속도는 이 문서의 주장 범위 밖이다.
- **서브셋 선정은 컴파일 성공 여부로만 했다.** 배제한 모듈 중 일부는 소스를 고치면 실기로 갈 수도 있다.
  고치는 시도는 하지 않았다.
- **`cargo furiosa-opt compile`의 성공 = 실기 실행 성공이 아니다.** `reshape`가 그 반례다
  (컴파일은 됐지만 로드에서 죽었다).
- **`run_qwen`을 실기에서 시도하지 않았다.** 에뮬레이션에서 이미 죽고, 커널 4개가 실기 컴파일도
  안 되므로 실기 시도는 의미가 없다.
- 배치=1, 단일 칩. 다중 칩·처리량은 측정 대상이 아니었다.
- **게이팅한 커널의 실기 동작은 확인하지 않았다.** 64개는 컴파일 실패라 실기로 못 가는 게 맞지만,
  그중 소스를 고치면 살아나는 게 몇 개인지는 조사하지 않았다.
- **`test_ve_stash_fp_fp`의 hang 원인을 소스 수준에서 규명하지 않았다.** "단독으로도 60초 타임아웃"
  까지만 확인했다. 커널의 어느 매핑이 하드웨어를 멈추는지는 후속 과제다.
- 상류 저장소에 이슈를 제기하지 않았다. **보고할 가치가 있는 실측 3건**: (1) 낡은 `#[ignore]` 3건,
  (2) 8.2의 `reshape` 로더 범위초과, (3) 10.5의 `test_ve_stash_fp_fp` 실기 hang(+한 프로세스 내 연쇄 오염).

## 13. 전체 재현 절차

```bash
. "$HOME/.cargo/env"
BASE=/home/jun/.claude/jobs/46bc5c7e/tmp

# --- 0) 작업 사본 ---
cp -a $BASE/foptsrc/furiosa-opt-main $BASE/visa_ex
cd $BASE/visa_ex

# --- 1) 크레이트 전체, 3개 백엔드 ---
CARGO_TARGET_DIR=target_tc  cargo furiosa-opt --backend typecheck  test -p furiosa-opt-examples --release --no-fail-fast
CARGO_TARGET_DIR=target_emu cargo furiosa-opt --backend emulation  test -p furiosa-opt-examples --release --no-fail-fast
CARGO_TARGET_DIR=target_npu cargo furiosa-opt --backend npu        test -p furiosa-opt-examples --release --no-fail-fast  # 빌드 실패가 정상

# --- 2) ignored 테스트 실검증 (이름은 -- --list 로 먼저 확인) ---
CARGO_TARGET_DIR=target_emu cargo furiosa-opt --backend emulation test -p furiosa-opt-examples --release \
  --test matmul_tests -- --ignored --exact test_matmul_4096 --nocapture

# --- 3) Qwen 커널 직접 실행 ---
CARGO_TARGET_DIR=target_emu cargo furiosa-opt --backend emulation build -p furiosa-opt-examples --bench kernel_sim --release
./target_emu/release/deps/kernel_sim-<hash> attention 2

# --- 4) 실기용 서브셋 만들고 돌리기 (빠른 최소 재현) ---
$BASE/mk_npu_subset.sh
cd $BASE/visa_ex_npu
CARGO_TARGET_DIR=target_emu cargo furiosa-opt --backend emulation test --release --no-fail-fast   # 23/23
furiosa-smi status                                                                                # npu 유휴 확인
CARGO_TARGET_DIR=target_npu cargo furiosa-opt --backend npu       test --release --no-fail-fast   # 실기 20/21
furiosa-smi status                                                                                # 누수 확인

# --- 5) 게이팅으로 크레이트 전체 실기 실행 (최대 커버리지) ---
cp -a $BASE/visa_ex $BASE/visa_ex_gated                     # 커널 매트릭스가 있어야 함 (9장)
python3 $BASE/gate_kernels.py                               # FAIL 커널 64개 게이트
#  ↳ 그다음 build → gate_tests.py 를 에러 0까지 반복 (본문 10.1)
cd $BASE/visa_ex_gated
CARGO_TARGET_DIR=target_npu cargo furiosa-opt --backend npu test -p furiosa-opt-examples --release --no-fail-fast  # 58 passed

# --- 6) vector_engine 연쇄 실패를 개별 격리로 판별 ---
while read t; do
  CARGO_TARGET_DIR=target_npu cargo furiosa-opt --backend npu test -p furiosa-opt-examples --release \
    --test vector_engine_tests -- --exact "$t"    # 각 테스트를 별도 프로세스로 → 연쇄 오염 제거
done < ve_names.txt
```
